1. VipAndroid：VIP App 主工程与组件装配

定位 / 技术栈 / 模块。 yyyyy-cdoe/VipAndroid 是 com.zhihu.vip.android 主壳，源码业务量不大，核心价值是把约 80 个组件组装成多渠道 App。只有 :app 模块；Java/Kotlin、AGP 4.2、Gradle 6.7.1、Kotlin 1.7.20、RxJava2、ZRouter、Robust、Walle、AspectJ、Tinker/VirtualAPK、RN/Hermes 等由 app/build.gradle、version.gradle 和仓库 AGENTS.md 共同印证。

关键链路。

  1. 组件装配：app/build.gradle 的 allComponents → 循环声明组件依赖 → META-INF/modules.json 提供组件注册信息 → App 运行时按组件服务协作。
  2. VIP 裁剪：VIP_APP_REMOVED_COMPONENTS 移除主 App 不需要的组件；dependencyReplace 把 comment/account/passport_ui 等替换为 VIP 变体。这是产品裁剪和依赖治理，不是普通页面代码。
  3. 本地联调：settings.gradle 应用 gradle/sourcecode.gradle → 读取 sourcecode.properties → 把 Maven 坐标替换为相邻源码工程，并自动处理 -api/实现模块依赖。
  4. 发布防线：app/gradle/check_deps.gradle 做三方依赖白名单与临时版本检查；handleSo() 检查 32/64 位 so 对齐；componentInsight 输出依赖图；business_aop.gradle 按 flavor 做编译期织入。

亮点、难点与风险。 亮点是多渠道、组件裁剪、版本锁定、源码联调和产物完整性形成一套交付闭环。难点是 Gradle 脚本约束很多，组件升级可能触发重复类、版本倒退、so 不对齐或渠道差异。风险是 README.md 明显沿用旧主 App，真实规则应以 Gradle 为准；当前可见业务测试只有 yyyyy-cdoe/VipAndroid/app/third/test-bypass/java/com/zhihu/android/app/report/HiddenCompatTest.kt，主壳更依赖构建验证和集成回归。

3. km_home_base：VIP 知识首页与书架容器

定位 / 技术栈 / 模块。 yyyyy-cdoe/km_home_base 有 km_home_base、km_home_base-api 和示例 app，负责知识首页子 Tab、书架 Provider、音频页和 Hybrid 容器。核心新链路使用 DevKit/Mavericks 轻量 MVI、Paging3、协程，同时保留 RxJava 事件。

关键链路。

  1. 首页瀑布流：discovery/HomePinTabFragment.kt → HomePinTabViewModel.refresh() → DevKit Pager.invalidate() → 匿名 ResponsePagingSource 调接口并实现 resolveNextKey/resolvePreKey/resolveValue → pager.flow 写入 PinTabState.data → Fragment invalidate()/adapter 渲染。
  2. 局部互动：Fragment 触发 deleteItem()/likeEvent() → PagerMediator.remove/update → 对当前 PagingData 做过滤或映射，避免每次互动都重新拉整页。
  3. 状态与加载分工：PinTabState 保存 PagingData；刷新、追加等 CombinedLoadStates 仍由 adapter 监听。它是轻量 MVI，不是统一 Intent/Reducer 的严格 MVI。
  4. 书架/音频容器：yyyyy-cdoe/km_home_base/km_home_base-api/src/main/java/com/zhihu/android/feature/km_home_base/BookShelfFragmentProvider.kt 暴露入口；AudioPageContainerFragment.kt/CommonAudioPageFragment.kt 与 CommonAudioPageViewModel.kt 组织音频子页；BookShelfRnFragment.kt 支持 RN 形态。

亮点、难点与风险。 亮点是 Paging3 与异构卡片结合，并用 PagerMediator 做点赞/删除的本地即时反馈；还包含 WebView 预热、首屏 banner 过滤和最后阅读位置上报。难点是 Paging generation、adapter load state、协程和 Rx 生命周期同时存在。两个测试文件都是 ExampleUnitTest，分页 key、刷新竞态和 mediator 变换缺少真实单测。

候选人可负责的业务集成点。 新卡片 ViewHolder/Diff、PagingSource 接口映射、点赞删除、下拉刷新和错误态、WebView 预热、RN/原生切换。应说“使用并扩展 DevKit 的调用点”，不说“实现了 DevKit Pager”。

条件式 STAR 模板（仅限真实经历）。 如果 HomePinTab 的业务接入确实由你负责，可以按真实经历替换后说：“首页是异构瀑布流，我使用现有 DevKit Pager 将接口分页映射为 PagingData，Fragment 负责卡片注册与渲染；点赞、删除通过 PagerMediator 局部变换。排障时我区分 state 数据、adapter LoadState 与 PagingSource generation，并针对旧请求回写或 loading 状态异常做验证。”R：需本人补充真实指标或可核验的验证结果。

追问与回答。

  • 问：它和 MVVM 有什么差别？答：页面状态集中在不可变 PinTabState 并单向渲染，但业务方法仍由 Fragment 直接调用，没有统一 Intent/Reducer，所以是轻量 MVI。
  • 问：为什么 loading 不放进 State？答：Paging3 的 refresh/append/prepend 已由 CombinedLoadStates 表达，重复搬运容易出现两个状态源。

  1. 首页与内容消费闭环： HomePinTabFragment → MVI/Paging3 → 卡片路由 → AudioDetailFragment/VipManuscriptFragment → 阅读/播放 → 进度/书架。

24.3 可观测性与性能的统一回答

  • 请求层：记录接口、错误码、业务 id、刷新/翻页类型，严禁记录 Token 和隐私字段。
  • 页面层：首屏、首卡/首章/首帧、WebView ready、播放器 prepare、支付结果各有独立耗时。
  • 列表层：Paging generation、缓存/预加载命中、delegate/ViewHolder 渲染耗时、掉帧和内存。
  • 稳定性：启动用 LaunchTaskMonitor/SafeBoot，Feed 有 FeedMonitor/OnlineLog，评论有 APM/Grafana，业务埋点用 ZA；不要只说“打了埋点”，要说明指标如何定位问题。

24.4 当前最值得主动指出的风险

  1. 测试与复杂度不匹配：支付、详情 Hybrid、播放器、阅读进度和双向分页缺少真实业务测试。
  2. 多代架构并存：MVP、旧 MVVM、LiveData/Rx、协程、MVI/Paging3、RN/Hybrid 同时存在，容易出现多个状态源和生命周期泄漏。

  4. 模块映射不直观：VipKmAudio、LiteKnowledgeMarket 用无扩展名文件把发布名映射到物理目录，CI、IDE 与人工排查都可能误判。
