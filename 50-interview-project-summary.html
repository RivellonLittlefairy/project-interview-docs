三年 Android 候选人：项目主线与面试总述

本文是源码证据化的表达骨架，不是候选人履历。所有带 “需本人确认” 的句子，必须在本人确实做过并能说明需求、动作和验证时才可使用。真实结果和指标不得由源码推测或杜撰。

1. 推荐主讲策略

三年经验不需要把 60 多个仓库都讲成“我的项目”。更可信的结构是：

  • 选 1 条核心业务线 深讲状态、接口、生命周期和排障；
  • 选 1 条工程或跨端线 证明协作和交付能力；
  • 其余作为追问储备，回答“我在业务侧如何使用公共能力”；
  • 框架源码用来解释为什么这样接入，不用来认领框架作者身份。

推荐的五条项目主线如下，实际面试只保留本人参与的 2—3 条：

  1. 知识首页与内容发现：KnowledgeMarket + km_home_base + DevKit
  2. 阅读消费：VipManuscript + VipReader
  3. 知识音频：Kmaudio + Media/Audio/Zhplayer/mediax
  4. App 宿主交付：VipAndroid + VipHome
  5. Native/RN 协作：pikachu

3. 可直接口述的三个时长版本

30 秒版本

如果相关调用点确实属于我的工作范围（需本人确认），我会把它概括为组件化内容 App 的 Android 业务接入：主要工作不是发明底层框架，而是在既有组件、路由和状态体系中把业务链路接完整。最适合展开的是知识首页：业务由 KnowledgeMarket 和 km_home_base 承接，页面使用 DevKit 的 Mavericks 轻量 MVI 与 Paging3；刷新创建新的分页代际，点赞和删除用 mediator 做局部更新。阅读/音频、主工程交付或 RN 页面协作也只保留本人实际负责并能核验的调用点。

2 分钟版本

这个工作区体现的是一个组件化内容 App。VipAndroid 负责版本、组件替换、多渠道和构建检查，VipHome 负责 Application、Launcher 和主导航；业务能力拆成知识首页、手稿、EPUB 阅读、音频、评论、账号等独立 API/实现模块。

如果首页调用点确实属于我的职责（需本人确认），我会重点讲 HomePinTab：Fragment 触发 HomePinTabViewModel.refresh()，ViewModel 让 DevKit Pager 失效并创建新的 PagingSource generation，接口结果进入 PagingData 和 PinTabState，Fragment 再交给异构卡片 adapter。刷新、追加和前插的加载态仍由 adapter 的 CombinedLoadStates 管理；点赞、删除用 PagerMediator 对当前 PagingData 做 map/filter。它有不可变 State 和单向渲染，但没有统一 Intent/Reducer，所以我会称它为 Mavericks-based 轻量 MVI。

内容消费侧要区分两条线：VipManuscript 解决从任意章节进入后的双向目录分页和互动，VipReader 解决 EPUB 准备、相邻预解析和端云进度合并。音频侧也要区分 Kmaudio 的业务数据源、播放列表和权益，与 Media/Audio/mediax 的播放基础能力。如果我讲跨端，会用 pikachu 的 AI 生图说明 taskId、轮询、Deep Link、Bridge 和 Jotai 的合同边界。

我不会把 DevKit、路由或播放内核说成自己设计的。个人动作、故障和结果都需要本人确认；没有真实指标时，我只讲代码机制、验证方法和风险。

5 分钟版本

我对这个项目的理解可以分成宿主、业务和基础能力三层。宿主层里，VipAndroid 是构建装配仓，它通过组件列表、VIP 替换表、版本锁和源码替换把业务组装成 App，并检查三方依赖和 so 完整性；VipHome 才是运行时启动与导航模块，负责 Application delegate、Launcher、MainActivity、启动阶段监控和异常恢复。这两个仓库能放在一条交付链里讲，但职责不能混。

业务上我最推荐讲知识首页与内容消费。如果 HomePinTab 确实是我参与的调用点（需本人确认），页面使用 km_home_base 接入 DevKit。用户下拉刷新后，Fragment 调 refresh()，ViewModel 调 pager.invalidate()，Paging3 创建新的 ResponsePagingSource；分页值通过 Flow 写入 PinTabState.data，Fragment 订阅后交给 adapter。加载态不重复塞进 State，而由 adapter 的 CombinedLoadStates 表达 refresh/append/prepend。点赞和删除则通过 PagerMediator 对当前 PagingData 做局部 map/filter，减少整页重拉。这里的取舍是迁移成本低、Paging3 接入自然，但事件入口和副作用没有严格统一；另外 ResponsePagingSource 捕获 Throwable、默认 refresh key 为 null 都是需要继续验证的风险。

进入消费页后，阅读不能笼统说成一个模块。VipManuscript 的核心是以目标章节为 initial key，同时计算 prepend 和 append，处理去重、首尾 null 和目标定位；互动、书架与一次性事件又有各自状态边界。VipReader 则面向 EPUB：后台准备和解析章节、预解析相邻窗口，并用章节 id、页索引或偏移处理本地与服务端进度。前者难在双向分页代际，后者难在 IO、内存窗口和进度不能倒退。

音频链也分层：Kmaudio 把不同 SKU 差异收敛到业务 DataSource，管理资源、目录、播放列表、试听和 ownership；Audio 用 Service 承担跨页面后台播放会话，Media 提供事件化 UI/插件能力，mediax 隔离 TTVideoEngine 一类厂商实现，Zhplayer 提供统一 facade 和预播放器。业务接入者应该讲自己如何映射数据、处理新 Intent、切集、权益刷新、错误和生命周期，而不是声称实现了解码或整个播放器框架。

工程交付方面，如果我确实参与过相应接入（需本人确认），我会说明怎样用 sourcecode.properties 把 Maven 制品替换成本地源码，怎样排版本冲突、重复类、多 flavor 和 so 对齐问题；启动需求则放在 VipHome 的既有任务/Delegate 边界里，不把所有 SDK 堆进 Application.onCreate()。

如果岗位关心跨端，我会补充 pikachu。它不是独立 RN App，而是嵌入 Native 的多页面 Bundle。AI 生图先创建 taskId，再跳结果页每两秒轮询、最多等待六十秒；成功后按来源写 Jotai、调用 Native Bridge 或继续走 Deep Link。这个链路适合说明跨端合同和生命周期：当前 cleanup 只停止后续轮询，没有取消在途 HTTP；图库分页缺并发门禁；app 生命周期 atom 的清理也有缺口。当前 checkout 还缺 prn/* 与 .yarn/，所以不能把不能 Bundle 直接归因于业务代码。

最后，我会主动划边界：以上是源码能证明的项目结构。哪些需求是我负责的、哪次故障由我定位、结果是多少，都必须由本人确认并给出提交、需求记录、日志或指标口径。对三年经验候选人来说，能把一个真实业务调用点讲透，比认领整套框架更可信。

4. 五条主讲线

4.1 知识首页与内容发现

模块关系

  • KnowledgeMarket：知识市场聚合业务，覆盖首页、书架、草稿、已购等场景。
  • km_home_base：知识首页/书架容器，是 HomePinTab 的真实业务调用点。
  • DevKit：提供 Mavericks 状态封装、Paging3 Pager、ResponsePagingSource、PagerMediator 和 adapter 辅助能力。

关键链路

text
HomePinTabFragment
  → HomePinTabViewModel.refresh()
  → Pager.invalidate()
  → 新 ResponsePagingSource generation
  → onRefresh/onLoadMore
  → PagingData Flow
  → PinTabState.data
  → Fragment collectFrom
  → SuperAdapter / RecyclerView

点赞或删除走 PagerMediator.update/remove，对当前 PagingData 做 map/filter；refresh/append/prepend 的加载态由 adapter CombinedLoadStates 管理。

技术亮点

  • 不可变 State 与单向渲染；
  • Paging3 代际、异构卡片和局部互动更新结合；
  • 业务状态与 adapter 加载态分源，避免重复状态源。

取舍与风险

  • 它是轻量 MVI，不是严格 Intent/Reducer MVI；优点是迁移成本低，代价是事件和副作用不完全统一。
  • ResponsePagingSource.load() 捕获 Throwable 可能影响协程取消语义。
  • 默认 getRefreshKey() == null 不保留锚点。
  • 业务测试不足，分页 key、刷新竞态和 mediator 变换需补测。

个人贡献条件

【需本人确认】只有本人确实接入过页面状态、PagingSource、卡片、刷新/点赞/删除或排查过分页问题，才能使用“我负责”。安全说法是“我在业务侧使用 DevKit，负责某个调用点；DevKit 框架由团队提供”。

4.2 阅读消费：手稿与 EPUB

模块关系

  • VipManuscript：盐言手稿阅读、双向目录、点赞/书架、评论和礼物。
  • VipReader：EPUB 文件准备/解析、分页、预解析、阅读设置和进度同步。
  • 两者都服务阅读场景，但一个突出服务端章节与双向 Paging，一个突出本地文档解析与进度恢复。

关键链路

  • 手稿：NativeManuscriptAuthorFragment → ManuscriptBillboardViewModel → Pager/ResponsePagingSource → prepend/append → BillboardState.data。
  • EPUB：VipReaderFragment → EpubViewModel/BaseEpubViewModel → prepare/parseChapter → preParseAround → save/syncProgress。

技术亮点

  • 从任意目标章节进入并向前、向后加载；
  • 章节稳定 id 去重和目标位置展示；
  • EPUB 按需解析与相邻窗口预解析；
  • 进度用章节、页索引或偏移表达，而不是只存易漂移的百分比。

取舍与风险

  • 双向分页需要同时处理 initial key、首尾 null、重复数据和两个方向的排序。
  • 预解析能降低翻页等待，但必须限制窗口、取消离屏任务和控制内存。
  • 端云进度合并要避免网络旧值让本地进度倒退。
  • 两仓可见业务测试不足，不能声称已自动化覆盖所有阅读边界。

个人贡献条件

【需本人确认】应明确本人做的是目录分页、阅读页状态、进度同步、互动接入还是解析能力调用；公共 EPUB/分页内核不是本人所写时，不认领内核实现。

可被追问的源码证据

4.3 知识音频播放

模块关系

  • Kmaudio：知识音频业务入口、DataSource、资源、目录、播放列表、权益和下载。
  • VipKmAudio：VIP 产品变体，在音频能力上叠加购买、广告、弹幕等业务。
  • Audio：播放器会话、后台 Service、通知和音频焦点相关能力。
  • Media：Tornado 事件协议、插件化播放 UI、播放器池、预加载和会话监控。
  • Zhplayer：统一播放 facade、工厂和预播放器；mediax：厂商引擎薄适配。

关键链路

text
KMPlayerInterface.play()
  → KMPlayer.play(type, id, trackId)
  → 对应业务 DataSource / PlayRequest
  → 资源与目录接口
  → ZhPlayEngine / Audio
  → mediax 等底层 engine
  → Service 持有会话，页面订阅状态

技术亮点

  • 多 SKU 差异收敛在 DataSource，播放内核保持稳定；
  • Resource Service 与 Business Service 分离；
  • Service 成为后台播放会话 owner，UI 不拥有播放器生命周期；
  • facade/adapter 隔离厂商 option、错误码和实现替换。

取舍与风险

  • 全局播放器方便跨页面，但 DataSource、列表、engine 三份状态容易不一致。
  • 新 Intent 切歌要取消或隔离旧请求，回调前校验当前业务 id/generation。
  • 试听转付费后应以服务端 ownership 为真值，不能只凭客户端回调放权。
  • 音频焦点、耳机拔出、Service 重建和进度恢复测试证据不足。

个人贡献条件

【需本人确认】适合认领的是新 SKU 数据映射、播放 UI/状态绑定、权益刷新、错误处理、联调和监控；不把解码器、厂商 SDK 或整个播放框架说成个人实现。

4.4 App 宿主交付

模块关系

  • VipAndroid：VIP App 构建装配，负责组件版本、产品裁剪、VIP 变体替换、源码联调和构建检查。
  • VipHome：运行时启动和主导航，负责 Application delegate、Launcher、MainActivity、Tab、启动监控和异常恢复。

关键链路

  • 构建：allComponents/VIP_APP_REMOVED_COMPONENTS/dependencyReplace → 组件依赖 → sourcecode.properties 本地替换 → 依赖/so 检查。

技术亮点

  • Maven 制品与本地源码可切换；
  • 产品差异通过组件裁剪和实现替换表达；
  • 启动链区分隐私前、授权后和首屏后的任务；
  • 依赖白名单、组件图和 so 对齐形成交付防线。

取舍与风险

  • 复杂 Gradle 约束提高交付一致性，也增加升级、重复类、版本倒退和多 flavor 回归成本。
  • VipAndroid README 有过时内容，真实规则以 Gradle 和源码替换脚本为准。
  • 启动测试主要依赖阶段监控和集成回归，自动化证据弱。

4.5 Native/RN 协作

模块关系

  • pikachu 是多页面 RN Bundle 工作区，不是独立 RN App。
  • PRN runtime 提供注册和宿主能力，但当前 checkout 缺 prn/*。
  • 页面通过 pageName/initProps、Deep Link、Bridge 和 Jotai 与 Native 宿主协作。

关键链路

text
GenerateAIImage
  → 创建 taskId
  → Deep Link 打开 GenerateAIImageResult
  → 每 2 秒轮询，最多 60 秒
  → FINISHED / FAILED / ILLEGAL / TIMEOUT
  → 评论写 Jotai，发布器走 Bridge，默认编辑器走 Deep Link

技术亮点

  • 输入页与长任务等待页解耦；
  • 不同消费方使用不同跨端合同；
  • 页面表动态注册，Native 只依赖稳定页面名；
  • 能把 RN 的状态和生命周期问题映射回 Android 的 Intent、ViewModel、长任务和 Bridge。

取舍与风险

  • cleanup 只停止后续轮询，不取消在途 HTTP。
  • 图库 paging.next 缺少分页并发门禁和完整错误状态。
  • app 生命周期 atom 的清理调用被注释，可能留下场景数据。
  • 当前副本缺 prn/*、.yarn/，且 CI 跳过单测，不能声称 Bundle/测试已通过。
  • .sentryclirc 有疑似明文凭据风险；应轮换并迁移 Secret，面试中不复述任何值。

个人贡献条件

【需本人确认】只在本人做过 Native 入口、Bridge、页面接入、联调或故障排查时作为项目经验；否则只能作为源码阅读和跨端理解。不能认领 PRN 框架或整个 RN 工作区。

可被追问的源码证据

  • pikachu/pages/entry/src/getRNPageLoaders.ts
  • pikachu/pages/GenerateAIImage/src/Entry.tsx

5. 七个辅助技术点

  1. Feed 数据编排：FeedFragment → FeedViewModel → FeedRepository → remote/local/preload/downgrade DataSource。适合补充 generation、缓存与网络替换、异构 delegate 和首卡监控；【需本人确认】具体接入或优化。
  2. Comment/VipComment 变体治理：两者都有根/子/锚点列表和互动，标准版另有 RN、segment、AI 预制评论和草稿。它们是同类组件的产品变体，不是两个独立个人项目；【需本人确认】本人维护的协议或迁移点。
  3. VipPassport/Account 身份边界：VipPassport 负责登录注册、验证码、社交绑定和 Token，Account 负责登录后的账号真值、认证、安全和退出清理。可讲“注册成功但绑定失败”“多请求同时 401”等一致性问题；【需本人确认】本人职责。
  4. Net/Netdns/ZRouter 调用侧排障：业务 Service 经过 Net/OkHttp 与 DNS，页面跳转经过 ZRouter mapper/interceptor/fallback。适合证明能从业务追到底层，但不要认领网络或路由框架作者身份。
  5. Mercury Hybrid 安全：业务 Web 容器依赖 mercury-core 的 H5Page、JsBridge、资源策略和 WebView LRU。可讲 origin 白名单、callback 生命周期和复用 reset；风险不能说成已发生事故。
  6. Picasa/Picture/Share 内容链：Picasa 是媒体选择、拍摄、处理和上传门面，Picture 更接近图片浏览/大图，Share/ShareCore 负责渠道分发。不要沿用“Picasa 是图片加载库”的旧分类。
  7. 个人样例补充：meter 可讲 widget、通知、缓存和隐私复盘；Purrfolio 可讲可测试领域算法；mcp-financial-calculator 可讲 schema 和数值稳定性。即使本地形态像个人项目，作者身份和个人贡献仍需提交、演示或历史记录确认。
