01 · 高频基础：拆分、依赖和组件通信

组件化的基本概念、模块之间怎么调用，以及调试和依赖配置。

01 · 组件化、模块化、插件化分别是什么？P0

我理解模块化就是按职责把工程拆开，比如首页、书架、网络库各有自己的 module。这样除了代码放的位置不同，Gradle 还能限制模块可以引用哪些类。单纯分几个包，约束就没有这么强。

组件化通常会在这个基础上继续处理复用和接入的问题。一块业务除了内部代码，还会有对外接口，其他业务通过这些接口使用它。比如知乎和盐言共用首页，列表、分页和状态处理放在公共组件里，两边各自接入。模块化和组件化这两个词在实际讨论中有重叠，没有特别统一的硬分界。

插件化还涉及运行时加载。普通组件化的 library 一般跟宿主一起打包，更新后仍需要宿主发版，也不会因为多了一个 module 就多出一个进程。每个模块是否需要单独运行，要看开发需求，不是组件化的必要条件。

核对资料：Android 官方：模块化指南 · Android 官方：创建 Android Library

02 · 为什么要组件化？收益和代价是什么？P0

主要是为了减少重复维护，也减少业务之间互相影响。比如两个 App 都有首页，如果分别复制一份，共同功能就要开发两遍，同一个问题也可能修两遍。共用组件后，这些修改可以落在同一份核心代码里，两个 App 再处理各自不同的地方。

对团队来说，模块拆开以后，谁负责哪块、哪些接口允许其他业务使用，也比较清楚。功能可以有自己的调试入口和测试，开发时不一定每次都跑完整 App。依赖控制得合适，部分增量构建也有机会更快。

代价是要维护公开接口、版本兼容和宿主接入。公共代码一改，多个 App 可能都需要回归。所以我会看是否确实有复用、协作或隔离需求，小项目没必要为了形式拆很多模块。编译有没有提速、开发效率提高多少，也需要实际测量。

核对资料：Android 官方：模块化指南

03 · 按什么拆模块？粒度怎么确定？P0

我一般先按业务职责拆。首页、书架、支付处理的问题不同，通常有比较清楚的分界。网络、存储、设计系统这些多处会用的能力，再按复用需要单独放。不会默认一个页面一个 module，也不会把每个工具类都拆出去。

粒度是否合适，我会看改动方式。如果两个 module 经常一起改，而且 A 总得知道 B 内部的细节，可能说明拆分位置不合适。反过来，一个 module 里几块代码几乎没有关系，负责人和变化原因也不同，就可以考虑继续拆。

分层也要看规模。比如业务 Repository 是否要独立成模块，要看它有没有单独复用和验证的价值。如果数据层很小，先放在一个模块里也可以；如果所有业务 Repository 都堆进同一个 data 模块，后面又可能变成另一个大工程。

核对资料：Android 官方：模块拆分模式 · Android 官方示例：Now in Android 模块划分

04 · 组件之间的依赖关系应该长什么样？P0

这里我主要关注编译依赖。一般是 App 壳引入需要的业务模块，业务实现依赖自己的 API 和基础库，基础库不反过来引用首页、广告这些具体业务。最后的依赖图应该没有环，否则模块之间会越拆越难分开。

业务之间确实需要调用时，可以依赖对方公开的 API，尽量不直接引用实现类。比如首页要用音频能力，可以引用音频接口，而不需要知道播放器内部怎么做。路由虽然能省掉对页面类的引用，但调用方仍依赖路径和参数的约定。

遇到 A 需要 B、B 又需要 A，我会先看是不是只需要返回结果。如果是，回调就能解决；如果两边需要的是共同能力，可以提取接口；如果两边总要相互了解内部状态，就要重新考虑模块划分。把代码全搬到 common 里，并没有真正处理职责问题。

核对资料：Android 官方：模块拆分模式 · Android 官方示例：Now in Android 模块划分

05 · API 模块和实现模块为什么要分开？P0

API 模块主要放外部使用这项能力必须知道的内容，比如接口、参数和结果类型。实现模块再放网络请求、缓存、页面和具体业务逻辑。这样调用方只引用 API，宿主最终把对应实现引入进来。

好处是调用方不用跟着了解所有内部细节。内部实现可以继续调整，只要对外约定保持兼容，其他模块就不需要一起改。测试时也更容易替换成假实现。不过，API 如果又暴露了内部数据库实体、具体 Activity 或大量第三方类型，这些依赖还是会传出去。

是否拆成两个 Gradle 模块也要看复杂度。很小、没有替换或跨模块调用需求的功能，不一定值得再拆一次。另外，xxx-api 是模块名称，api(...) 是 Gradle 的依赖配置，不能因为模块叫 API，就把它的所有依赖都写成 api。

核对资料：Android 官方：模块拆分模式 · Gradle 官方：API 与实现依赖

06 · 依赖倒置、接口和依赖注入怎么串起来？P0

依赖倒置可以用首页跳转来理解。公共首页需要打开故事详情，但不应该直接引用知乎或盐言的具体跳转实现。所以可以先定义一个接口，由两个 App 分别实现，首页只调用接口。这样首页编译时依赖的是接口，运行时执行的仍然是宿主提供的代码。

依赖注入解决的是这个实现对象怎么交给首页。可以手动传，也可以通过框架提供，不一定非要用 Dagger、Hilt 之类的框架。如果只定义了接口，但首页内部仍直接 new 某个 App 的实现，换宿主时还是得改首页，依赖没有真正隔开。

创建和提供实现的工作一般放在宿主。放到 Fragment 里还要考虑系统重建：不能只在第一次创建时通过自定义构造参数传进去，后面恢复 Fragment 时也要能重新拿到正确的依赖。

Kotlin · 教学示例
// 教学示例：用来解释边界，不是项目原有类名。
// home-api：契约由公共模块与宿主共同依赖。
interface HomeHost {
    val sourcePage: String
    fun openStory(storyId: String)
    fun trackClick(storyId: String, sourcePage: String)
}

// home-impl：不直接依赖某个 App 的实现类。
class HomeActions(private val host: HomeHost) {
    fun onStoryClick(storyId: String) {
        host.trackClick(storyId, host.sourcePage)
        host.openStory(storyId)
    }
}

// App 壳负责创建自身的 HomeHost 实现，再装配 HomeActions。
// Fragment 的创建与进程重建，另需通过宿主/Factory/DI 正确恢复依赖。

核对资料：Android 官方：模块拆分模式

07 · 组件通信有哪些方式？怎样选择？P0

我会根据通信目的选方式。打开页面，用路由或导航接口；调用音频、奖励这些业务能力，用接口或服务；一次操作结束后返回结果，用回调；多个页面关心同一份数据，就由 Repository 等模块保存状态，再让页面观察。

接口除了方法名，还需要说清楚成功和失败怎么返回、回调在哪个线程、页面退出后能不能取消。事件通知则要考虑订阅和退订、事件顺序、是否重放，以及重复消费。EventBus 能降低一些直接引用，但也容易把调用链藏起来，所以不适合承担所有通信。

同一个进程里的普通模块通信，通常不用 AIDL。AIDL 主要解决跨进程接口调用。如果确实跨了进程，再处理序列化、连接和远端失败这些额外问题；分了 module 本身不会带来跨进程需求。

核对资料：Android 官方：模块拆分模式 · Android 官方：多模块导航

08 · 没有直接依赖目标页面，路由为什么还能跳转？P0

调用方只需要知道路径和参数，不必直接引用目标页面类。目标模块提供路径到页面的映射，最终宿主把目标模块和路由表一起打进包。运行时由框架找到目标 Class，再创建或打开页面，所以目标模块和注册信息仍然必须存在。

以 ARouter 为例，编译时处理 Route 注解，生成 Root、Group 等映射；启动时注册分组索引，navigation 时补全 Postcard，必要时先加载对应分组。Activity 最终用 Intent 启动，Fragment 则创建实例、设置 arguments 后返回，显示它的容器仍由应用处理。

项目里的 ZRouter 封装的是知乎的 com.zhihu.router，还处理 URL 改写、拦截、Fragment 宿主选择、ZHIntent 转换和兜底。它不能直接当成 ARouter 的包装层。

阅读全文：ARouter 与 ZRouter 路由原理详解

09 · 组件如何独立调试？一定要切换 application/library 插件吗？P0

我比较容易理解的一种方式，是业务模块保持 library，再给它配一个很小的调试 App。这个 App 提供 Application、启动页和必要的宿主服务，只把要调试的功能接进来，这样开发时不用每次跑整个大 App。

调试壳还要准备组件依赖的环境，比如登录态、网络配置、路由初始化。有些服务可以提供假实现。另一种做法是通过开关切换 application 和 library 插件，同时切换 Manifest、入口和调试代码，这两种都能满足独立调试的需求。

当前 km_home_base 的 app 模块就引用了 km_home_base 和 km_home_base-api，是独立壳的结构。不过壳里正常，不代表接进知乎和盐言都正常，真实宿主的主题、依赖版本和 Manifest 组合还需要单独验证；这次也没有验证这份旧工程当前能否成功构建运行。

核对资料：Android 官方：创建 Android Library · Android 官方：构建变体

10 · api 和 implementation 有什么区别？P0

两种配置都能让当前模块使用依赖，主要区别在是否继续提供给下游编译使用。比如 App 依赖首页，首页用 api 引入网络库，App 就能通过这条依赖看到网络库；如果首页用 implementation，App 不能仅靠这条关系直接使用网络库的类型。

implementation 只是没有把这条依赖放到下游的编译类路径里，不表示网络库不会进入最终 APK，也不提供运行时隔离或代码加密。通常优先用 implementation，可以减少其他模块对内部实现的依赖，也有利于控制需要重新编译的范围。

如果公开方法的参数、返回值或者继承关系里用了某个依赖的类型，就要检查是否应当用 api 暴露，或者改成自己的类型。编译影响还要看改的是公开 API 还是内部方法体，不能简单理解为只要改了一个库，所有下游就一定重编。
