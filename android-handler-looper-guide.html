Handler / Looper：从消息循环到项目中的延迟、切线程与清理

先回答“这段代码在哪个线程、何时执行、何时取消”，再把答案落实到框架调用链。本篇用当前项目的原码串起来，最后准备 26 道面试题。

01 · P1：Handler 到底解决什么问题？

Handler 用来把消息或任务放入指定 Looper 的队列，由那个 Looper 所在线程取出执行。它同时解决“在哪个线程执行”和“何时具备执行条件”这两类问题。Handler 本身不是线程，也不会因为 post 了任务就创建线程。

比如后台拿到了结果，需要回主线程修改界面；或者广告加载超过某段时间，需要触发兜底。这两种场景都能用 Handler，但排到主线程的工作依然必须轻量。

角色负责什么和其他对象的关系
Thread真正执行代码的线程线程可以没有 Looper；准备后通常有一个 Looper
Looper在所属线程中循环取出、分发消息一个 Looper 对应一条 MessageQueue，多个 Handler 可以绑定它
MessageQueue保存待处理消息，选择下一条可处理消息，必要时等待普通消息按执行时间安排；不是简单先进先出队列
Handler提供发送、取消、分发接口绑定一个 Looper；消息的 target 指向接收它的 Handler
Message消息载体含 what、arg1、arg2、obj、when、target 和 callback 等
Runnable一段待执行的动作post 会把它放到 Message.callback，最终调用 run()
执行关系
发送线程：handler.post(task)
            ↓ 把 task 包装成 Message
目标线程的 MessageQueue：保存消息、按条件选择下一条
            ↓ Looper 在自己的线程里取出消息
message.target.dispatchMessage(message)
            ↓
task.run() 或 Handler 的消息处理逻辑

阅读范围：P1 是业务使用和常见面试基础；P2 是同步屏障、IdleHandler 等追问。项目证据来自 2026-09-21 当前工作区；框架实现以 android-13.0.0_r1 为明确基线，特别是队列内部结构和 Native 细节，不推断所有未来版本都完全相同。

02 · P1：回调在哪个线程执行，由谁决定？

看 Handler 绑定的 Looper，不是看 Handler 对象在哪里创建，也不是看谁调用 post。默认构造 Handler() 隐式使用当前线程的 Looper，容易产生歧义；无 Looper 时会抛异常。新代码明确传 Looper.getMainLooper() 或工作线程的 Looper。

教学示例 · thread-binding
fun demonstrateThreadBinding() {
    Thread({
        val main = android.os.Handler(android.os.Looper.getMainLooper())
        android.util.Log.d("HandlerDemo", "sender=${Thread.currentThread().name}")
        main.post {
            android.util.Log.d("HandlerDemo", "receiver=${Thread.currentThread().name}")
        }
    }, "demo-sender").start()
}

在正常 Android App 中调用这个函数，sender 来自 demo-sender，receiver 来自主线程。Handler 即使是在子线程创建，显式绑定主 Looper 后仍向主线程派发任务。子线程只发送，不需要自己先调用 Looper.prepare。

主线程已经有 Looper，普通 Thread 默认没有

AOSP Android 13 的 ActivityThread.main() 先调用 Looper.prepareMainLooper()（第 7871 行），完成启动相关初始化后进入 Looper.loop()（第 7898 行）。Activity 生命周期、输入和界面调度围绕这条主线程事件循环协作，不是让 onCreate 后面的代码另开一个“UI 循环”。

AOSP Android 13 原码：Looper.java，第 112—117 行。

Looper.java · android-13.0.0_r1
    private static void prepare(boolean quitAllowed) {
        if (sThreadLocal.get() != null) {
            throw new RuntimeException("Only one Looper may be created per thread");
        }
        sThreadLocal.set(new Looper(quitAllowed));
    }

ThreadLocal 给每个线程保存自己的 Looper；同一线程重复 prepare 会报错。它不是“复制一个共享 Looper”，也不负责创建线程。Looper.myLooper() 获取当前线程的 Looper，可能为 null；getMainLooper() 获取当前进程的主 Looper。不要在 Activity 里自行调用 prepare 或 loop。

03 · P1：从 post 到执行，完整走一遍

  1. 发送方调用 handler.post(runnable)。这一步通常在调用者线程立即执行。
  2. Handler 用 Message.obtain() 取一个可复用消息，把 Runnable 放进 message.callback。
  3. 计算 when = SystemClock.uptimeMillis() + delay，设置 message.target = handler。
  4. 进入目标 MessageQueue 的 enqueueMessage，加锁插入队列，必要时唤醒等待中的目标线程。
  5. 目标线程的 Looper 调用 MessageQueue.next()。有可分发消息就取出，没有则按条件等待。
  6. Looper 在自己的线程中执行 msg.target.dispatchMessage(msg)，完成后按框架流程回收消息。

AOSP Android 13 原码：Handler.java，第 927—931 行。

Handler.java · android-13.0.0_r1
    private static Message getPostMessage(Runnable r) {
        Message m = Message.obtain();
        m.callback = r;
        return m;
    }

AOSP Android 13 原码：Handler.java，第 770—779 行。

Handler.java · android-13.0.0_r1
    private boolean enqueueMessage(@NonNull MessageQueue queue, @NonNull Message msg,
            long uptimeMillis) {
        msg.target = this;
        msg.workSourceUid = ThreadLocalWorkSource.getUid();

        if (mAsynchronous) {
            msg.setAsynchronous(true);
        }
        return queue.enqueueMessage(msg, uptimeMillis);
    }

Android 13 的 MessageQueue 内部用 Message.next 串起单链表，普通消息依 when 插入；相同 when 的普通消息按实际入队先后排列。多线程同时发送时，不应假设调用者看到的先后就是最终入队顺序。队头插入、同步屏障和异步消息会改变简单的排序直觉。

入队和取队列元素时会使用同一个队列锁；用户回调在取出消息、离开队列锁之后执行。因此回调很慢会占用目标线程，但不能简单说它一直拿着 MessageQueue 的锁让其他线程无法发送。队列同步也不保证你发出后继续修改 message.obj 所指向的对象是安全的。

源码定位：Handler.post / sendMessageDelayed / enqueueMessage → MessageQueue.enqueueMessage / next → Looper.loop / loopOnce → Handler.dispatchMessage。先掌握这条链，再看细节。

04 · P1：post 和 sendMessage 最后走哪里？

AOSP Android 13 原码：Handler.java，第 97—108 行。

Handler.java · android-13.0.0_r1
    public void dispatchMessage(@NonNull Message msg) {
        if (msg.callback != null) {
            handleCallback(msg);
        } else {
            if (mCallback != null) {
                if (mCallback.handleMessage(msg)) {
                    return;
                }
            }
            handleMessage(msg);
        }
    }
  1. 优先看 msg.callback：有 Runnable 就执行它，正常分发路径不再走下面两个消息处理分支。
  2. 没有 Runnable 时，若构造 Handler 时传了 Handler.Callback，先调用它。返回 true 表示消费完，直接结束。
  3. Callback 不存在或返回 false，最后调用 Handler 子类重写的 handleMessage()。
教学示例 · dispatch-order
fun demonstrateDispatch() {
    val handler = object : android.os.Handler(
        android.os.Looper.getMainLooper(),
        android.os.Handler.Callback { msg ->
            android.util.Log.d("HandlerDemo", "Callback: ${msg.what}")
            msg.what == 1
        }
    ) {
        override fun handleMessage(msg: android.os.Message) {
            android.util.Log.d("HandlerDemo", "handleMessage: ${msg.what}")
        }
    }
    handler.post { android.util.Log.d("HandlerDemo", "Runnable") }
    handler.sendEmptyMessage(1)
    handler.obtainMessage(2, "payload").sendToTarget()
}

在正常执行、无队列退出等干扰时，自己的这三条普通消息依次产生：Runnable；Callback: 1；Callback: 2 后接 handleMessage: 2。what=1 被 Callback 消费，what=2 继续交给 handleMessage。

如果直接调用 handler.handleMessage(msg) 或 runnable.run()，只是当前线程上的普通方法调用，不会自动切线程，也不会入队。正常业务应使用 post / sendMessage。

05 · P1：postDelayed 为什么不一定准时？

postDelayed(task, 2000) 表示按 uptime 时钟计算，至少到指定时间之后才具备被选中执行的条件；不是精确的两秒计时器，也不是让发送线程睡两秒。

场景结果
t=0 发送两秒后执行；主线程 t=1 开始一个持续四秒的任务延迟任务最早要等主线程 t=5 左右空出来；还可能有其他等待
调用时设备随后进入深度睡眠uptimeMillis 不计深睡，实际墙钟等待会更长
到期了，但前面有同步屏障且这是一条普通同步消息可能继续等待屏障移除
已经成功入队，但之后被 remove、Looper 退出或进程死亡任务可能完全不执行
每次执行结束后再 postDelayed(this, 1000)下次执行包含上次任务耗时与排队影响，会产生周期漂移

System.currentTimeMillis() 是墙钟，会受校时影响；uptimeMillis() 不计深睡，Handler 定时用它；elapsedRealtime() 包含深睡，更适合衡量跨休眠的经过时间。需要倒计时 UI 时，可保存合理时钟的截止时间，每次更新重新算剩余时间，而不是简单减一。跨重启、后台持久任务还需要独立设计，Handler 不负责。

没有消息时会不会一直空转？

不会一直 Java 空循环抢 CPU。Android 13 的 MessageQueue.next() 通过 nativePollOnce 进入 Native Looper；底层使用 epoll_wait 等待事件或超时，并用 eventfd 等唤醒机制。等待时线程可让出 CPU；新消息是否需要唤醒会根据它是否改变待处理条件等判断，不是每次 post 都无条件唤醒。

这也解释了“主线程 Looper 为什么不会天然 ANR”：主线程本来就应在事件循环里，有工作时处理、没工作时等待。ANR 涉及某类系统关注的工作未在期限内完成；如果回调耗时、等待锁、同步 Binder 阻塞等导致无法及时处理，才需要排查。不能把循环存在等同于卡死。

06 · 项目实例一：Toast 切主线程与按 token 取消

VipThemeToast 在奖励中心的 RewardCenterToastHelper、VideoRewardCenterToastHelper 中存在调用。它同时展示了“当前就在主线程则直接执行”和“后台来调用则入队”的区别。

项目原码节选：yyyyy-cdoe/VipCommon/vip_common/src/main/java/com/zhihu/android/vip_common/widget/toast/VipThemeToast.kt，第 38—51 行。

VipThemeToast.kt · 原码
    private val mainHandler = Handler(Looper.getMainLooper())

    fun show(
        activity: Activity,
        text: CharSequence,
        longDuration: Boolean = false,
        style: Style = Style.AUTO_BY_THEME,
        onClick: (() -> Unit)? = null,
    ) {
        if (Looper.myLooper() == Looper.getMainLooper()) {
            showInternal(activity, text, longDuration, style, onClick)
        } else {
            mainHandler.post { showInternal(activity, text, longDuration, style, onClick) }
        }

如果从主线程进入 show，showInternal 当场执行；从其他线程进入，就把动作放到主线程队列。普通 Handler.post 即使在主线程调用，也仍然入队，不会采用上述“同线程直接执行”的分支。Activity.runOnUiThread 则也有同线程直接执行的语义，需要留意执行先后和重入。

项目原码节选：yyyyy-cdoe/VipCommon/vip_common/src/main/java/com/zhihu/android/vip_common/widget/toast/VipThemeToast.kt，第 110—124 行。

VipThemeToast.kt · 原码
        val duration = if (longDuration) LONG_DURATION_MS else SHORT_DURATION_MS
        val dismissRunnable = Runnable {
            (toastView.parent as? ViewGroup)?.removeView(toastView)
        }
        mainHandler.postAtTime(
            dismissRunnable,
            toastView,
            SystemClock.uptimeMillis() + duration
        )
    }

    private fun clearExistingToast(parent: ViewGroup) {
        val existingToastView = parent.findViewWithTag<TextView>(TOAST_VIEW_TAG) ?: return
        mainHandler.removeCallbacksAndMessages(existingToastView)
        (existingToastView.parent as? ViewGroup)?.removeView(existingToastView)

这里把 toastView 当 token：postAtTime 的 token 存入 Message.obj，清理旧 Toast 时，用同一个 view 对象取消它的待执行任务。这样可让共用 mainHandler 的不同 Toast 分组清理，不必清掉这个 Handler 的所有业务。token 在该 AOSP 移除路径按对象引用匹配，不是按字符串内容匹配。

执行链：奖励中心 helper → VipThemeToast.show → 主线程 showInternal → 将隐藏任务排到 uptimeMillis + duration → clearExistingToast 用同一个 token 取消旧任务。showInternal 还检查 Activity 的 finishing / destroyed，但排队任务仍可能临时持有 View / Activity；这种检查不能代替所有生命周期清理。

07 · 项目实例二：阅读进度延迟合并上传

SkuProgressManager.saveProgress 启动数据库保存订阅后，在第 126 行调用 pendingUploadToServer(*toSave)。所以延迟上传安排并不等于“等待数据库保存成功之后再安排”；读源码时要看语句顺序和异步边界。

项目原码节选：yyyyy-cdoe/KmBase/sku-progress/src/main/java/com/zhihu/android/app/sku/progress/SkuProgressManager.kt，第 41—51 行。

SkuProgressManager.kt · 原码
    private val pendingUploadProgress = ConcurrentHashMap<String, SkuProgress>()
    private const val MSG_BATCH_UPLOAD_PROGRESS = 123

    @SuppressLint("HandlerLeak")
    private val lazyUploadHandler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            if (pendingUploadProgress.isNotEmpty() && msg.what == MSG_BATCH_UPLOAD_PROGRESS) {
                uploadPendingProgress()
            }
        }
    }

项目原码节选：yyyyy-cdoe/KmBase/sku-progress/src/main/java/com/zhihu/android/app/sku/progress/SkuProgressManager.kt，第 158—172 行。

SkuProgressManager.kt · 原码
    fun pendingUploadToServer(vararg toUpload: SkuProgress) {
        var uploadImmediately = false
        toUpload.forEach {
            pendingUploadProgress[it.key] = it
            //如果包含一个已完成的进度，需要立即上传
            uploadImmediately = it.isFinished || uploadImmediately
        }

        lazyUploadHandler.removeMessages(MSG_BATCH_UPLOAD_PROGRESS)

        if (!uploadImmediately) {
            lazyUploadHandler.sendEmptyMessageDelayed(MSG_BATCH_UPLOAD_PROGRESS, 2000)
        } else {
            lazyUploadHandler.sendEmptyMessage(MSG_BATCH_UPLOAD_PROGRESS)
        }
  1. 先把进度按 key 放进 pendingUploadProgress，同一内容的后续进度可覆盖之前值。
  2. 移除当前 Handler 中 what 等于 MSG_BATCH_UPLOAD_PROGRESS 的待处理消息。
  3. 没有完成状态时，重新安排两秒后的消息；若包含完成进度，安排立即可执行消息。
  4. 目标主线程处理该 what 后进入 uploadPendingProgress，再构造并订阅网络上传。
更新到达时间新安排的普通上传时间发生了什么
0 秒约 2 秒以后第一次安排
0.5 秒约 2.5 秒以后移除 2 秒的旧消息，重新计时
1 秒约 3 秒以后再次合并；若之后安静两秒，才具备处理条件

这是“持续更新时往后推”的防抖 / 延迟合并方式，不是严格每两秒上传一次的节流。若普通进度一直频繁更新，触发可能持续后移；是否需要最大等待时间、退出页面兜底等，要按业务要求补充。已完成进度走立即消息，不等于同步完成网络上传。

项目原码节选：yyyyy-cdoe/KmBase/sku-progress/src/main/java/com/zhihu/android/app/sku/progress/SkuProgressManager.kt，第 179—191 行。

SkuProgressManager.kt · 原码
    private fun uploadPendingProgress() {
        val toUpload: Array<SkuProgress> = pendingUploadProgress.values.toTypedArray()

        pendingUploadProgress.clear()

        uploadToServer(*toUpload)
            .retry(1)
            .subscribeOn(Schedulers.io())
            .subscribe({
                toUpload.forEach { p -> logger.debug("上传进度成功: $p") }
            }, {
                toUpload.forEach { p -> logger.error("上传进度失败: $p", it) }
            })

Handler 的 handleMessage 在主线程，但这里网络链路有 subscribeOn(Schedulers.io())。因此要分开“主线程做上传调度 / 构造参数”和“订阅后的 IO 请求”，不能把它描述成主线程直接同步请求网络。

可追问的边界：ConcurrentHashMap 不让“取 values 快照 → clear”自动变成原子事务；多个线程也可能在 remove 与 send 两步之间交错。源码说明存在这种实现，不能据此断言已经实现严格串行、完全无竞态的防抖。这里列的是需结合调用线程进一步验证的风险，不是确认发生过的线上问题。

08 · 项目实例三：开屏广告超时与只结束一次

调用入口在 LauncherAdActivity：onCreate 创建 SplashAdController，加载时调用 loadAndShowSplashAd，onDestroy 调用 controller.destroy。控制器为广告安排兜底任务，并在成功、失败或关闭等路径清理。

项目原码节选：yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/splash/SplashAdController.kt，第 195—218 行。

SplashAdController.kt · 原码
    private fun scheduleLoadDeadline(timeoutMs: Long, callback: SplashCallback) {
        cancelLoadDeadline()
        val runnable = Runnable {
            loadDeadlineRunnable = null
            HomeLogger.info(TAG, "host load deadline ${timeoutMs}ms, skip splash -> onJumpToMain")
            finishOnce { callback.onJumpToMain() }
        }
        loadDeadlineRunnable = runnable
        handler.postDelayed(runnable, timeoutMs)
    }

    private fun cancelLoadDeadline() {
        loadDeadlineRunnable?.let { handler.removeCallbacks(it) }
        loadDeadlineRunnable = null
    }

    private fun elapsed(): Long = SystemClock.elapsedRealtime() - loadStartTime

    /** 保证终态（进首页 / 降级）只触发一次 */
    private fun finishOnce(action: () -> Unit) {
        if (ended) return
        ended = true
        cancelLoadDeadline()
        action()

这段代码有三个关键点：先移除旧任务；把新 Runnable 保存到字段，之后按同一实例移除；finishOnce 用 ended 避免终态反复触发。网络失败、广告关闭等回调通过 context.runOnUiThread 进入终态逻辑。

项目原码节选：yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/splash/SplashAdController.kt，第 247—253 行。

SplashAdController.kt · 原码
    fun destroy() {
        try {
            HomeLogger.info(TAG, "destroy")
            cancelLoadDeadline()
            ended = true
            splashAdImpl = null
            splashAdContainer = null

为什么移除之后还要 ended？移除只能处理队列中尚未执行的任务，阻止不了另一路 SDK 回调晚到。状态判断负责业务“只结束一次”，remove 负责队列清理，两者处理不同问题。ended 无锁读写成立的前提是这些访问都约束在主线程；文件注释有这个约定，但入口也必须遵守，不能只凭变量存在就认定任意线程调用都安全。

另外，超时并不会抢占正在卡住的主线程。如果主线程被长任务占住，兜底 Runnable 一样会迟到。这段源码用 elapsedRealtime 统计耗时，延迟调度却由 Handler 的 uptime 时钟驱动；它们在深睡期间的表现不同。

09 · P1：取消、内存泄漏与生命周期

API会移除什么不会做到什么
removeCallbacks(r)这个 Handler 中 callback 是同一个 Runnable 实例的待处理消息不会根据代码内容识别两个新建 lambda；不打断正在运行的回调
removeMessages(what)这个 Handler 中匹配 what 的待处理消息不会区分你对 what 的业务命名；普通 post 包装的消息默认 what=0
removeCallbacksAndMessages(token)这个 Handler 下与 token 引用匹配的消息 / 回调不自动取消网络请求，也不保证生产者以后不再投递
removeCallbacksAndMessages(null)这个 Handler 的所有待处理消息 / 回调不是清空整条 Looper 队列，不影响其他 Handler 的消息

同一个 Looper 可以对应多个 Handler。移除时框架比较 message.target == handler，因此临时 Handler(mainLooper).removeCallbacksAndMessages(null) 并不能清掉另一个 Handler 之前发出的任务。移除和 hasMessages 在这个链表实现里可能需要扫描 O(n)，不要当作高频零成本状态查询。

常见引用链
主线程 Looper / MessageQueue
  → 尚未处理的 Message
  → callback Runnable 或 target Handler
  → 被捕获的 Activity / Fragment / View / 控制器

页面已经退出，但消息还没执行 / 清掉，就可能延长这些对象的存活。

非静态内部 Handler 可能持有外部对象，Runnable lambda 也可能捕获它。静态 Handler 或 WeakReference 只能处理特定引用边，不能自动解决队列里的其他回调、监听和对象缓存。先明确任务与谁同寿命：Fragment 的 View 任务通常在 onDestroyView 清理；Activity 任务在适当的停止或销毁时清理；是否在不可见时停止由产品语义决定。

教学写法：同一 Runnable、明确线程、可关闭的防抖动作

教学示例 · debounced-action
class DebouncedAction(private val action: () -> Unit) {
    private val handler = android.os.Handler(android.os.Looper.getMainLooper())
    private var closed = false
    private val pending = Runnable {
        if (!closed) action()
    }

    // submit 和 close 都由主线程调用。
    fun submit() {
        check(android.os.Looper.myLooper() == handler.looper)
        if (closed) return
        handler.removeCallbacks(pending)
        handler.postDelayed(pending, 500L)
    }

    fun close() {
        check(android.os.Looper.myLooper() == handler.looper)
        closed = true
        handler.removeCallbacks(pending)
    }
}

页面持有一个 DebouncedAction 实例，事件到来时 submit，生命周期结束时 close。action 应是轻量动作；真正请求的取消、结果过期处理仍由请求层负责。close 会移除排队任务并拒绝后续 submit；若其他长期对象仍持有 DebouncedAction，里面的 action 引用也仍存在，应同时释放拥有者引用。示例不是项目现有实现。

10 · P1：HandlerThread——带消息循环的后台串行线程

HandlerThread 是 Thread 子类，会在自己的 run 中准备 Looper 并进入 loop。常用于需要固定线程、顺序处理、延迟调度的工作。它不是线程池，同一线程一次只执行一个回调，回调里启动的外部异步请求是否串行完成则另说。

AOSP Android 13 原码：HandlerThread.java，第 58—69 行。

HandlerThread.java · android-13.0.0_r1
    public void run() {
        mTid = Process.myTid();
        Looper.prepare();
        synchronized (this) {
            mLooper = Looper.myLooper();
            notifyAll();
        }
        Process.setThreadPriority(mPriority);
        onLooperPrepared();
        Looper.loop();
        mTid = -1;
    }

典型顺序是 start() → Handler(thread.looper)。getLooper 在已启动但 Looper 尚未建立时会等待初始化；线程没启动或已不存活时可返回 null。不要直接调用 thread.run，也不要在主线程等待工作完成而制造卡顿。

教学示例 · worker-thread
fun demonstrateWorkerThread() {
    val worker = android.os.HandlerThread("demo-worker")
    worker.start()
    val handler = android.os.Handler(worker.looper)
    handler.post {
        android.util.Log.d("HandlerDemo", "first: ${Thread.currentThread().name}")
    }
    handler.post {
        android.util.Log.d("HandlerDemo", "second: ${Thread.currentThread().name}")
        worker.quitSafely() // API 18+，本演示不再提交新任务
    }
}

两条任务在 demo-worker 中按正常入队顺序执行。生产代码应由明确的拥有者管理这个线程，退出后不能再次 start 同一个 Thread，必要时创建新的 HandlerThread。普通一次性 IO 更适合协程或执行器，不必每个请求都建立独立 HandlerThread。

11 · P2：同步屏障和“异步消息”是什么意思？

这里的“异步消息”是 Message 的一种标记，不是新线程，也不代表这个回调和主线程其他回调并行。它指遇到同步屏障时，这类消息可以被越过屏障选中。

  1. Android 13 的同步屏障用 target 为 null 的特殊队列条目表示。它不是普通发给 Handler 的业务 Message。
  2. next 遇到队头屏障时，跳过其后的普通同步消息，寻找异步消息；找到后仍要检查 when 是否到期。
  3. 选中的异步消息依然由同一个 Looper 线程执行，不会抢占当前正在执行的任务。
  4. 屏障移除后，受阻的同步消息才恢复正常处理。框架使用屏障协调界面遍历与相关调度。

Handler.createAsync(looper)（API 28+）会把它发出的消息标记为异步；兼容版本可根据 AndroidX 依赖使用 HandlerCompat。它不是“加急万能开关”，会改变与其他 Handler 消息的相对顺序，不能拿它修复主线程重计算。业务不要依赖隐藏 API 手动插入屏障。

两个不同概念：调用 post 后调用者不用等回调完成，属于通常意义的异步调度；post 包装出的 Message 默认仍可能是同步消息。面试先区分这两种“异步”，再回答。

12 · P2：IdleHandler 能不能放耗时任务？

IdleHandler 也是在所属 Looper 线程执行。Android 13 的 next 在队列为空，或首条消息尚未到期等条件下，会调用注册的空闲处理器；并不要求队列一定完全没有消息。返回 false 表示执行后移除，true 表示保留供后续空闲阶段调用。

教学示例 · idle-handler
fun registerSmallIdleTask() {
    check(android.os.Looper.myLooper() == android.os.Looper.getMainLooper())
    android.os.Looper.myQueue().addIdleHandler {
        android.util.Log.d("HandlerDemo", "small idle task on main")
        false // 执行一次后移除
    }
}

适合轻量、可延后的工作；若这里执行长 IO、重计算，依然阻塞主线程。它没有“首帧之后一定执行”“每帧执行一次”“某个时间前一定执行”的保证。持续繁忙时可能长期等不到机会，需要按业务设计兜底，不能把关键初始化完全押在 idle 上。

16 · 常见面试题与参考答案

先尝试自己回答，再展开核对。P1 建议能结合本篇项目例子说清；P2 知道作用、限制和执行线程即可，按岗位要求再深入。

P1 · 1. 一句话讲清 Handler、Looper、MessageQueue 的关系。

Handler 向绑定 Looper 的 MessageQueue 投递消息；Looper 在所属线程循环取消息并分发给对应 Handler；Message 保存数据或 Runnable。线程真正执行代码，Handler 本身不是线程。

P1 · 2. Handler 创建在哪个线程，就在哪个线程回调吗？

不是。执行线程由绑定的 Looper 决定。可以在工作线程创建 Handler(Looper.getMainLooper())，其回调仍在主线程。无参构造隐式使用创建时当前线程的 Looper，所以容易让人误以为永远由创建线程决定。

结合项目：VipThemeToast 显式持有主线程 Handler。

P1 · 3. 一个线程有几个 Looper、MessageQueue 和 Handler？

标准使用中一个线程最多 prepare 一个 Looper，该 Looper 对应一个 MessageQueue；可以有多个 Handler 绑定它。没有准备 Looper 的普通线程，也可能一个都没有。不要把“有多个 Handler”理解为“有多个消息线程”。

P1 · 4. 子线程用 Handler 一定要调用 Looper.prepare 吗？

要区分发送和接收。子线程只是用主线程 Handler 发送消息，不需要自己 prepare。若希望在这个子线程处理消息，就需要为它准备并运行 Looper；常用 HandlerThread 代劳。

P1 · 5. 主线程为什么不用手动 prepare？ThreadLocal 的作用是什么？

Android 启动主线程时已准备主 Looper 并进入 loop。ThreadLocal 将 Looper 与所属线程关联，myLooper 获取当前线程的那份；它不创建线程，也不让所有线程共享一份可随意使用的 Looper。

P1 · 6. post 和 sendMessage 有什么区别？

post 的 Runnable 被包装进 Message.callback；sendMessage 通常承载 what 和数据。两者都走消息队列。正常 dispatch 优先执行 Runnable，否则先尝试构造参数中的 Handler.Callback，再视返回值决定是否调用子类 handleMessage。

P1 · 7. Handler.Callback 返回 true 和 false 有什么区别？

true 表示已经消费，不再交给 Handler.handleMessage；false 表示还要继续。这个返回值不会阻止已经优先命中的 Message.callback Runnable，因为它们是不同分支。

P1 · 8. 主线程里 post 会立即执行吗？和 runOnUiThread 一样吗？

普通 Handler.post 仍然入队，通常要等当前主线程调用栈返回并轮到该消息；Activity.runOnUiThread 在当前已是 UI 线程时会直接执行，否则再投递。直接调用 runnable.run 也只是当前线程执行，不会入队。

结合项目：VipThemeToast.show 显式写了“主线程直接执行，否则 post”的分支。

P1 · 9. postDelayed 两秒后一定执行吗？会创建一个计时线程吗？

不会为每条延迟消息创建计时线程。它按 uptimeMillis 设置 when，通过消息队列等待和调度；主线程忙、屏障、深度睡眠等会使执行晚于预期，被移除、退出或进程终止还可能不执行。

P1 · 10. Looper 是死循环，为什么不会一直耗 CPU 或导致 ANR？

消息循环是线程的正常工作模型。没有可处理事件时底层等待会让出 CPU，而不是持续忙等。ANR 关注的是特定工作超时；长回调、锁等待等阻止事件及时处理才是重点排查方向。

P1 · 11. MessageQueue 是严格 FIFO 吗？

不应笼统回答是。本文 Android 13 实现中，普通消息按 when 排列；相同 when 按入队顺序。队头插入、同步屏障与异步消息会影响处理顺序；多个发送线程的业务先后还需额外协调。

P1 · 12. 多个线程同时给同一个 Handler 发消息安全吗？

队列入队等内部操作有同步机制，允许跨线程投递；但这不保证你的复合业务步骤或消息引用的数据对象线程安全。发出后继续修改 payload、先 remove 再 send 被其他线程插入，都需要自己的并发约束。

结合项目：SkuProgressManager 用 ConcurrentHashMap，但 values 快照与 clear 仍是两步。

P1 · 13. removeCallbacks 怎样才取消得掉？

必须对原 Handler 使用同一个 Runnable 实例，移除队列中尚未处理的匹配消息。新建一个内容相同的 lambda 不是同一个任务对象；移除也不会中断已经开始执行的回调。

结合项目：SplashAdController 把 loadDeadlineRunnable 保存到字段后再移除。

P1 · 14. removeCallbacksAndMessages(null) 会清空主线程所有消息吗？

不会，只清理当前 Handler 对应的待处理消息和回调。其他 Handler 即使绑定同一个主 Looper，也不受影响。共享 Handler 的业务要慎用全清理，可以用保留的 Runnable 或 token 分组取消。

结合项目：VipThemeToast 用 toastView 作为 token，清理同一条 Toast 的任务。

P1 · 15. 为什么不建议随便 removeMessages(0)？

post 产生的普通 Message 默认 what=0，removeMessages(0) 可能把这个 Handler 下多个 Runnable 一起移除。需要取消指定工作时使用独立 what、同一 Runnable 或 token，不要把默认 0 当成业务专属编码。

P1 · 16. Handler 为什么可能造成内存泄漏？静态内部类够不够？

延迟消息通过 callback 或 target 持有 Runnable / Handler，再可能持有已退出页面。静态 Handler 只切断某条外部类引用；Runnable 捕获、业务字段或缓存仍可能持有页面。关键是明确任务所有权，在生命周期结束清理并阻止过期任务再投递。

P1 · 17. Message.obtain 有什么意义？发送后能重复用同一个 Message 吗？

obtain 可从消息池复用对象，减少分配。消息入队后会被标记为使用中，不能重复投递同一个在用 Message；发送后应把它视为交给框架，不继续修改或自行回收。下一次发送重新 obtain；obj 引用的可变内容也要避免并发修改。

P1 · 18. post 返回 true，是否证明任务完成了？

不是，只说明入队阶段成功。任务可能还在等待，也可能随后被移除、遇到队列退出或进程结束。需要业务完成结果应通过回调、Future、协程结果等显式表达。

P1 · 19. HandlerThread 与普通 Thread、线程池怎么选？

普通 Thread 不自动提供消息循环；HandlerThread 提供固定线程和串行消息处理，适合有线程绑定要求的持续工作；线程池复用多个工作线程，适合并发任务。普通请求也可用协程加合适 Dispatcher，重点看并发、生命周期和固定线程要求。

P1 · 20. quit 与 quitSafely 有什么区别？

quit 丢弃剩余待处理消息并请求退出；quitSafely 清除未来消息，允许已经到期且可分发的工作正常处理后退出。都不强行打断正在执行的回调；主 Looper 不允许业务退出；退出后的 Thread 不能原地重新 start。同步屏障等情况也使“safe 就全部执行完”不成立。

P2 · 21. 什么是同步屏障？异步 Handler 会开新线程吗？

屏障使其后的同步消息暂缓，异步标记的消息可以被选中，但仍检查到期时间，仍在同一个 Looper 线程执行。createAsync 不是新线程或线程池，不会抢占正在运行的回调，也不能解决耗时任务阻塞。

P2 · 22. IdleHandler 什么时候执行？可以做初始化 IO 吗？

在满足队列空闲条件时执行，不要求队列必须完全为空；执行线程仍是队列所属线程。返回 false 移除、true 保留。主线程 IdleHandler 只适合短小工作，重 IO 会阻塞后续事件，而且空闲机会没有固定期限保证。

P2 · 23. postAtFrontOfQueue 能保证任务立即执行吗？

不能抢占当前回调，只影响后续取消息的位置。频繁向队头插入可能饿死其他消息、破坏业务顺序；它是特殊工具，不适合作为普遍的性能优化。

P1 · 24. 如何用 Handler 做防抖？这和节流有什么不同？

保留同一任务，事件到来时先移除旧任务再延迟投递；持续事件会不断推迟执行，这是等待安静窗口的防抖。节流限制固定周期内的执行频率，不应被每次事件无限后推。多个线程参与时，remove 与 post 不是自动原子事务。

结合项目：SkuProgressManager 普通进度重新计时两秒，完成进度则立即安排。

P1 · 25. 主线程卡住，超时 Handler 能及时救场吗？

不能。绑定主 Looper 的超时任务也要等主线程腾出执行机会。需要监测主线程是否不响应，观察者应有独立的执行机会；但监测任务被调度延迟也会影响判断，不能直接把检测结果等同系统 ANR。

结合项目：BlockTracer 采用 UI 心跳与观察 Handler；接入点选择 500ms，受配置开关控制。

P1 · 26. 结合项目讲一个 Handler 的完整使用案例。

可以讲开屏广告：Activity 创建控制器；控制器保存超时 Runnable 并 postDelayed；广告失败或关闭等路径回主线程，通过 ended 避免重复终态，同时 removeCallbacks；Activity 销毁时再清理。最后补充边界：超时不精确、不能抢占主线程，状态安全依赖主线程约束。只把自己实际参与的部分表述为个人工作。
