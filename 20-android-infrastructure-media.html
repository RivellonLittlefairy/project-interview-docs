Android 基础设施、Hybrid 与媒体仓库：源码证据化面试手册

检查范围：yyyyy-cdoe 下 33 个指定仓库，时间为 2026-07-24。本文只陈述当前检出的源码；README 仅作线索，结论以 settings.gradle、构建脚本、主源码和真实业务调用为准。源码数量只用于衡量测试密度，不代表代码质量。文中不记录任何凭据值。

[!IMPORTANT] 源码事实不等于个人经历。 本文的类、函数、架构、测试数量和风险均是仓库事实，不能直接改写成“我负责、我设计、我实现、我推动”。只有本人确实参与过相应需求、接入、排障或治理时，才可使用文中的条件式话术；框架并非本人所写时，应明确说“我在业务侧使用/接入/排查过，并阅读源码确认其机制”。任何性能收益、成功率、故障下降、工期或业务结果都必须由本人补充可核验的真实数据、时间范围和统计口径；没有数据就只讲机制、验证方法与风险，禁止杜撰。

个人归因与指标填写规则

  • 可以直接讲的仓库事实：模块边界、调用链、类和函数行为、当前检出的测试文件、可从代码推出的风险。
  • 只有确实参与时才讲的个人动作：在我实际参与的某需求中，我负责/完成了______，使用了______，遇到______，通过______验证。
  • 结果必须本人补充：结果：______（指标）、______（统计口径）、______（时间范围）、______（数据来源）。四项缺一时，不写百分比或绝对收益。
  • 没有参与框架开发时的安全表达：该能力由基础库提供；我负责的是业务调用侧的状态建模、接入、异常处理或问题定位。

0. 先建立全局心智模型

这组仓库实际可以拼成五条链：

  1. 应用与基础设施：Futureve 应用壳 → FutureveGlobal 全局初始化 → Net/Netdns 网络 → ZRouter 页面路由 → Dependencies 构建期依赖治理。
  2. 轻量状态与分页：业务 Fragment → DevKit.MvxViewModel → Mavericks state → Paging3 Pager/ResponsePagingSource → SuperAdapter。
  3. Hybrid：Mercury/VipMercury 业务页面 → mercury-core.H5Page → JsBridge/插件 → WebViewClient 资源拦截与离线资源。
  4. 视频/音频：VideoEntity/Kmaudio 业务 → Media/Audio 播放协议与 UI → mediax/Zhplayer 引擎、预加载、清晰度切换。
  5. 内容生产与消费：Camera/Picasa 采集上传 → ZhEditor 编辑 → Picture 浏览 → Share/ShareCore 渠道分发；VipPrerender、VipCommon 做会员内容预取和复用。

面试时不要声称“这些框架都是我写的”。更稳妥的表达是：我在业务调用点完成接入、状态建模、异常处理和性能治理，并能从源码追到底层边界。

1. DevKit

  • 定位 / 技术栈 / 模块：settings.gradle 只有 app、devkit；主体是 Kotlin、Coroutines、RxJava2、Airbnb Mavericks、Paging3。入口 devkit/src/main/java/com/zhihu/android/devkit/DevKit.kt，初始化任务是 T_DevKitInit.kt；状态层在 mvx/，分页层在 paging/。
  • 关键机制与真实调用：MvxViewModel.collectState() 把 Flow/Rx 值通过 setState 收敛到不可变 state，execute() 把 Rx 过程包装成 Mavericks Loading/Success/Fail；Pager.flow 用 cachedIn(coroutineScope) 共享分页代际，invalidate() 让当前 PagingSource 失效；ResponsePagingSource.load() 把 Refresh/Append/Prepend 分派到 onRefresh/onLoadMore/onLoadBefore，再由 resolveValue/resolvePreKey/resolveNextKey 组装 LoadResult.Page；PagerMediator 用 PagingData 的 filter/map 做就地删除和替换。
    • 真实链路：yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabFragment.kt 的 collectFrom(viewModel, PinTabState::data) → 同目录 HomePinTabViewModel.kt 的 Pager(...){ DiscoverTabListDataSource() } 和 setOnEach { copy(data = it) } → 网络分页；刷新由 Fragment 直接调用 viewModel.refresh() → pager.invalidate()；删除由 viewModel.deleteItem() → pagerMediator.remove()；加载态仍由 Fragment 的 adapter.addLoadStateListener 管理。
  • 必须讲清的架构边界：这是 Mavericks-based 轻量 MVI，不是严格 Redux/MVI。证据是有单一 PinTabState、不可变 copy 和 state-driven render，但没有统一 Intent/Action/Reducer 层，Fragment 直接调用 refresh()、deleteItem()；CombinedLoadStates 也没有全部进入 state。优势是迁移成本低、Paging3 适配顺滑；代价是事件入口和副作用没有完全统一。
  • 线程、稳定性、测试与风险：MultiCoroutineScope.kt 用 ConcurrentHashMap 管 Job，SafeCoroutine.kt/ViewScope.kt 提供生命周期安全封装；当前有 SuperAdapterTest、SafeCoroutineTest、InstanceContainerTest 3 个单测。风险一：ResponsePagingSource.load() 捕获 Throwable，可能把 CancellationException 当普通错误；风险二：默认 getRefreshKey() 始终 null，不保留锚点；风险三：PagerMediator.cachedDataList.add() 不在同步块内，需关注并发访问假设。
  • 面试问答：
    • 问：为什么不是严格 MVI？答：状态更新是单向的，但用户动作没有统一 action/reducer，Fragment 仍调用具体 ViewModel 方法，adapter 的 load state 也留在 View 层，因此从源码边界看，应称为“以 Mavericks 为状态容器的轻量 MVI”。若本人参与过 HomePinTab，可再补充自己实际负责的业务调用侧工作。
    • 问：刷新为什么不是重新 new Pager？答：Pager 持有当前 PagingSource，invalidate() 结束旧代际，Paging3 通过 factory 创建新 source，原 flow 仍可被 UI 收集。

2. Dependencies

  • 定位 / 技术栈 / 模块：这不是 Android Runtime 库，而是纯配置治理仓库；无 Gradle 模块、无 Java/Kotlin 源码。核心文件为 dependencies.json、dependenciesV2.json、substitute.json、permissions.json、thirdSdk.json、rules_breaker.json。
  • 关键机制与业务关系：substitute.json 描述新旧 artifact 替换，解决“新库已包含旧库但业务仍显式依赖旧库”的重复类问题；permissions.json 和 thirdSdk.json 为权限、三方 SDK 治理提供清单。主应用 VipAndroid/app/gradle/check_deps.gradle 会在构建期拉取/校验白名单，因此它属于 供应链控制面，不是网络或媒体数据面。
  • 亮点 / 风险 / 工程化：规则外置使治理不必散落在几十个业务 build.gradle；风险是远端规则可用性、变更审计与版本可重复性，如果构建总取“最新规则”，就会出现同一 commit 不同时间结果不同。仓库无自动化测试，至少应给 JSON Schema、冲突样例和规则回归测试。
  • 面试问答：
    • 问：依赖治理为什么不能只靠 Gradle resolutionStrategy？答：resolutionStrategy 解决版本选择，substitute.json 还表达“功能替代/包含关系”；权限和三方 SDK 清单又是合规问题，所以需要更高层的策略仓库。

3. Net

  • 定位 / 技术栈 / 模块：net-api 暴露稳定门面，net 提供 Retrofit/OkHttp 实现；Java/Kotlin、Retrofit、OkHttp、RxJava，另有 SSE、QUIC、Cookie、监控和缓存。门面见 yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/api/net/Net.java、同目录 OkHttpFamily.java，实现见 yyyyy-cdoe/Net/net/src/main/java/com/zhihu/android/net/common/NetProviderImpl.java、同目录 OkHttpFamilyProviderImpl.java。
  • 关键机制与调用关系：业务通过 Net.createService(Service.class) 门面拿 Retrofit service；NetProviderImpl 用 ConcurrentHashMap<Class<?>, Object> SERVICE_MAP 缓存 service，并在 initialize(...) 内创建 Retrofit.Builder、组装 converter/call adapter 后构建 Retrofit；OkHttpFamilyProviderImpl.inflateBuilder() 按 ClientType 组合 cookie、DNS、应用 interceptor、网络 interceptor、metrics、QUIC 配置。CookieStoreImpl.kt 用内存 ConcurrentHashMap 配合持久化，NetSseProviderImpl 为 SSE 建独立 Retrofit。
  • 并发、性能与稳定性：NetThreadPool.kt 是 OkHttp dispatcher 的受控线程池；AsyncResponseCallManager.newCachedThreadPool() 给 Retrofit callback 单独执行器；DispatcherMonitor 记录 execute/enqueue/urgent 数；SseCallImpl 用单线程 ScheduledExecutorService 管重连。优点是把网络调度、监控和多 client 族集中治理；风险是 interceptor 顺序高度敏感、全局 service cache 隐含进程级生命周期、SSE 重试需防抖和退出时取消。
  • 测试 / 工程化：按复核时统一排除 sample app 样板项的口径，Net 有 33 个 test 文件；既有配置和缓存测试，也有部分测试辅助类。面试不要只说“封装 Retrofit”，应强调 client family、线程隔离、事件监听和协议扩展。
  • 面试问答：
    • 问：为什么要有 net-api？答：业务只依赖稳定抽象，具体 OkHttp、DNS、QUIC 和监控可在实现模块替换；同时减少组件间传递具体网络实现。
    • 问：请求慢怎么排查？答：先按 EventListener 拆 DNS/connect/TLS/request/response，再看 DispatcherMonitor 排队和 NetThreadPool 饱和，最后排 interceptor 与服务端耗时。

4. VipNet

  • 定位 / 技术栈 / 模块：app、net-api、net，是 Net 的 VIP 分支。接口形态仍是 OkHttpFamily/provider，主实现仍在 NetProviderImpl、OkHttpFamilyProviderImpl。
  • 关键机制与差异：调用链与 Net 相同，但当前源码不是简单软链接：例如 yyyyy-cdoe/VipNet/net/src/main/java/com/zhihu/android/net/common/OkHttpFamilyProviderImpl.java 的 builder 装配与 Net 分支存在差异，说明已产生产品分叉。两边都有 SignInterceptorTest、PolicyCacheFirstTest、PolicyNetFirstTest、PolicySaveOnlyTest 等同组缓存策略测试；按统一排除 sample app 样板项的口径，Net 为 33 个 test 文件、VipNet 为 32 个，不能据此声称 VipNet 的缓存测试更完整。
  • 亮点 / 风险：产品定制与主干隔离能降低 VIP 改动风险；最大工程风险是 双份网络栈漂移，安全补丁、超时策略、DNS/QUIC 能力可能只进一边。更合理的长期形态是共享 core + 产品 decorator，而不是复制实现。
  • 面试问答：
    • 问：如何控制双分支漂移？答：抽公共协议和 contract tests，对 public/VIP 跑同一套缓存、签名、取消、超时测试；差异通过 BuilderDecorator/配置注入。

5. Netdns

  • 定位 / 技术栈 / 模块：app + netdns；Kotlin/Java、OkHttp Dns、DoH/HTTPDNS、IPv4/IPv6、IP 优选与 QUIC 探测。核心入口有 dns/DnsFactory.java、dns/MainDns.java、dns/zhihu/ZhihuDns.java、preferred/IPPreferred.kt。
  • 关键机制与调用关系：DnsFactory 组装不同 DNS 实现；ZhihuDns 通过 ResolveExecutor 并发解析并用 reResolvingMap 合并重复任务；DnsCacheHelper 用内存 map + ReentrantReadWriteLock，IpsCache/DnsRecordCache 保存解析结果；IPPreferred 缓存 host 候选、上次地址和时间，SpeedCheck 分派 CheckQuic 或 CheckOkHttp 探测；ZHDnsResolver 用单线程 executor 串行处理系统 DNS 与 cancellation signal。
  • 性能与稳定性亮点：并行 DNS、重复请求合并、缓存、IPv6、备用 IP 和主动探速形成完整容灾链；18 个测试覆盖 ZhihuDns、hijack、IPv6、backup/preferred/loopback。风险是缓存 TTL/网络切换失效复杂，PreferredThreadPool 使用 DiscardPolicy 会静默丢任务，探测本身也可能放大弱网流量。
  • 面试问答：
    • 问：HTTPDNS 为什么还需要系统 DNS？答：它不是全替代；系统 DNS 是兜底与网络本地性来源，HTTPDNS/DoH 解决劫持和解析质量，最终应按 TTL、网络状态、失败回退融合。
    • 问：怎么防止一个 host 同时发几十次解析？答：用 resolving map 做 single-flight，多个调用复用同一解析结果，并给任务设置超时和网络切换取消。

6. ZRouter

  • 定位 / 技术栈 / 模块：app + zrouter；基于 com.zhihu.router 的注解路由，封装 Activity/Fragment 启动、拦截器、fallback、cookie、screen name 和 launch mode。核心入口 yyyyy-cdoe/ZRouter/zrouter/src/main/java/com/zhihu/android/app/router/ZRouter.java、同目录 RoutesResolver.java、RouterDispatcher.java。
  • 关键机制与业务调用：目标通过 @Router 生成 mapper；RoutesAccessor.addMappers() 在 mapper 写锁内注册并排序；MapperCreator.generateMappers() 解析 scheme/host/path/query、参数正则、priority、module 和 redirect；解析阶段经过 Configs.resolveInterceptors（CopyOnWriteArrayList），失败进入 fallback；FragmentLauncher 把路由结果转为 Fragment 栈操作，ZHIntent 承载动画和导航参数。
  • 亮点 / 风险 / 测试：编译期映射避免全量运行时扫描；动态拦截和 fallback 适合登录、灰度、兼容老链接；20 个测试覆盖 URL、cookie、screen name、fallback 和 dispatcher 非法实现。风险是 URL 作为外部输入必须校验域、目标和超长参数（已有 UrlTooLongException）；拦截器顺序、重定向环与跨模块注册冲突要有规则。
  • 面试问答：
    • 问：路由为什么同时要 annotation 和 interceptor？答：annotation 解决静态“URL 到目标”的映射，interceptor 解决运行时登录态、实验和合规，职责不同。

7. Bootstrap

  • 定位 / 技术栈 / 模块：app + bootstrap，是 UI 基础控件集合，不是应用启动框架。包含 BottomSheetLayout、连续滚动、VerticalPager、弹簧动画、引导队列、模糊工具和轻量内存缓存。
  • 关键机制与调用关系：consecutive/ConsecutiveScrollerLayout.java 协调多个可滚动 child；BottomSheetLayout.java 处理拖拽与状态；guide/GuideQueue.kt/GuideTask.kt 把引导按队列串行展示；MemoryCache.kt 用 ConcurrentHashMap<String, Any> 做进程缓存。业务 View 直接组合这些控件，不经过 service API 层。
  • 亮点 / 风险 / 测试：交互组件沉淀能统一手势和视觉；风险是嵌套滚动、触摸冲突和 Activity 泄漏，MemoryCache 存 Any 也容易没有淘汰策略。约 62 个主源码但未检出测试，手势状态机至少需要 Robolectric/仪器测试和截图回归。
  • 面试问答：
    • 问：连续滚动最难的是什么？答：不是把两个 RecyclerView 放一起，而是统一消费 dy、边界判断、fling 传递和 nested-scrolling contract，避免父子同时滚或速度丢失。

8. Futureve

  • 定位 / 技术栈 / 模块：单 app 的主应用壳，不是普通 library；yyyyy-cdoe/Futureve/app/src/main/java/com/zhihu/android/app/ZhihuApplication.java 是应用入口，同目录 ConfigCreator.java 注入构建配置。仓库还包含 features/ 动态能力和 app/third/ 下的定制三方源码/桩。
  • 关键机制与调用关系：ZhihuApplication.onCreate() 建立进程级环境，再由模块任务系统初始化各组件；flavor source set 提供 alpha/beta/mr/release/huawei 等差异；features/VideoXFeature、ScannerFeature、LeLinkFeature 显示部分能力按 feature 交付。它是 Net、Router、Mercury、Media 等组件最终汇合点。
  • 亮点 / 风险 / 工程化：亮点是多 flavor、feature、定制 SDK 和初始化任务的超级应用工程能力；风险是 app 壳依赖面极大、启动路径易膨胀，app/third fork 会带来升级和安全补丁负担。当前检出的主源码少，是因为大量能力以外部组件和预编译/third source 接入，不能误判为小项目。
  • 面试问答：
    • 问：超大 App 怎么控制启动？答：Application 只建最小底座，其余按任务依赖、进程、隐私同意和首屏关键性分级；用 trace 校验而不是只靠“异步化”。

9. FutureveGlobal

  • 定位 / 技术栈 / 模块：app + global，承载可被主应用复用的全局初始化、构建配置、网络 decorator、埋点和路由入口。核心任务为 T_NetInit.java、T_PostNetInit.java、T_ZAInit.java、T_ZhiTrackInit.java。
  • 关键机制与业务调用：AppBuildConfig.Builder 把产品 host、渠道和额外配置集中注入；GlobalRequestDecorator.decorate() 给 OkHttp builder 追加全局请求能力，LaunchRequestCountDecorator 统计启动请求；T_PostNetInit.initDns() 在网络底座后初始化 DNS；外链先进入 RouterPortalActivity，再经过 RouterPortalInterceptor/legacy interceptor 分发。
  • 亮点 / 风险 / 测试：把 app 壳与全局实现拆开，有利于不同产品复用；风险是静态全局状态、初始化顺序和隐私边界。约 28 个主源码、5 个测试，任务依赖和 portal 安全仍应有集成测试。
  • 面试问答：
    • 问：为什么 Net 初始化和 PostNet 初始化分开？答：先建立 client/公共拦截器，再加载依赖网络或运行时配置的 DNS、监控等后置能力，可减少依赖环并明确首屏关键路径。

10. Mercury

  • 定位 / 技术栈 / 模块：mercury-api（模型/外部插件契约）、mercury（业务 Web 容器）、app（demo）；底层依赖 mercury-core。包含 WebView 页面、插件、支付模型、DNS/离线资源、Hybrid 卡片和监控。
  • 关键机制与调用关系：典型业务入口是 yyyyy-cdoe/Mercury/mercury/src/main/java/com/zhihu/android/app/ui/fragment/webview/WebViewFragment2.java，创建 H5Page、绑定 InnerWebClient，由 core 的 H5PageImpl 装 JSBridge 和 WebViewClient；业务插件在 yyyyy-cdoe/Mercury/mercury/src/main/java/com/zhihu/android/app/mercury/plugin/，API 契约放 yyyyy-cdoe/Mercury/mercury-api/src/main/java/com/zhihu/android/app/mercury/plugin/H5ExternalPlugin.java 等。DnsWebViewClient.shouldInterceptRequest() 可把 Web 资源请求切入 ResourceProvider。
  • 亮点 / 风险 / 测试：页面容器、bridge、资源加载和业务插件分层，支持渐进迁移；约 262 个主源码、37 个测试。最大风险是 WebView/bridge 攻击面：必须做 origin、事件白名单、参数校验、页面销毁后的 callback 清理，并避免把敏感数据写入 URL/日志。
  • 面试问答：
    • 问：Hybrid 插件如何避免变成上帝接口？答：按事件拆插件契约，页面只持 H5Page/plugin manager；插件声明可调用域和权限，统一参数 schema、超时、一次性 callback 与审计。

11. VipMercury

  • 定位 / 技术栈 / 模块：与 Mercury 同样的 mercury-api/mercury/app，是 VIP 产品分支；额外暴露 WebViewEmptyViewInterface 等产品能力。

12. mercury-core

  • 定位 / 技术栈 / 模块：app + mercury-core，是真正的 Hybrid 内核：抽象系统/X5 WebView、H5Page/H5Session、JSBridge、插件、资源加载、WebView/Page LRU、APM。
  • 关键机制与调用关系：H5PageImpl 创建 IZhihuWebView，addJavascriptInterface(mJsBridge, IJsBridge.JS_BRIDGE_NAME)，再绑定 H5WebViewClient；JsBridge 用 ConcurrentHashMap<String,H5Event> 关联请求与回调，并通过 evaluateJavascript() 回传；ResourceLoader/ResourceProvider + RequestPolicy 接管离线/网络资源；WebViewLruCache、H5PageLruCache 和 WebViewQueue 支持复用。
  • 线程、性能与稳定性：AndroidWebView2.evaluateJavascript() 检查 destroyed 状态并切主线程；页面 onDestroy 清 client、bridge 和 WebView；缓存减少冷启动但必须 reset cookie、history、JS interface、listener 和页面状态，不能只把 WebView 放 LRU。17 个测试覆盖 JsBridgeTest、PluginManagerTest、H5PageStatusTest、WebViewHelperTest、静态工具等。
  • 亮点 / 风险：抽象系统/X5 内核、资源策略和页面生命周期是核心亮点；风险是 addJavascriptInterface 的权限模型、LRU 复用污染、回调 map 泄漏、同步资源拦截阻塞 WebView IO 线程。
  • 面试问答：
    • 问：WebView 预热为什么容易出 bug？答：复用的不只是 View，还有 WebSettings、client、bridge、cookie/history、页面 callback；必须定义可验证的 reset contract，并限制缓存上限和进程内存。

  • 亮点 / 风险 / 测试：小而独立，易嵌入播放器；风险是主线程布局抖动、文本测量/富文本图片开销、轨道碰撞和 seek 后时间同步。4 个测试相对体量尚可，但必须包含高密度和 seek 场景。
  • 面试问答：
    • 问：弹幕性能怎么优化？答：对象池、预计算文本宽度、限制同屏量/轨道、按时间窗口取数据，View 层只做必要布局；卡顿时优先降密度而不是阻塞播放。

27. BlurView

  • 定位 / 技术栈 / 模块：library + app，是第三方 BlurView 源码仓。BlurAlgorithm 抽象算法，RenderNodeBlurController、RenderScriptBlur 适配平台，PreDrawBlurController 在 root 预绘制阶段采样并模糊。
  • 关键机制与调用关系：业务 BlurView.setupWith(root) 一类入口配置 overlay/半径；controller 计算缩放尺寸，抓取 root 背景到内部 bitmap/canvas，算法处理后由 BlurView 绘制；新平台可走 RenderNode，旧平台走 RenderScript/no-op。
  • 亮点 / 风险 / 测试：下采样和多后端兼容兼顾效果与性能；风险是每帧抓屏、递归绘制、尺寸变化重分配、RenderScript 废弃和低端机 GPU/CPU 峰值。19 个主源码仅 1 个测试，需性能基准与截图测试。
  • 面试问答：
    • 问：实时模糊为什么先下采样？答：模糊复杂度与像素数/半径相关，先缩小再模糊、放大能大幅降成本，视觉差异通常可接受。

28. bottomnav

  • 关键机制与调用关系：业务通过 API model/event（NavBadge、NumberBadge、BadgeEvent 等）而非直接操作具体 View；BottomNavInstaller 安装菜单，BottomNavConfigUtils/BottomNavFileUtils 读取云端或本地 JSON，BottomNavResManager 管亮/暗主题和动画资源，BottomDynamicMenu 应用变化。
  • 亮点 / 风险 / 测试：配置化让 Tab、红点和主题不发版更新；风险是远端 schema 兼容、坏配置回退、下载资源校验、启动时 IO 和动态菜单状态恢复。11 个测试对基础组件尚可，应重点覆盖旧 schema 和离线 fallback。
  • 面试问答：
    • 问：云控底栏如何保证不会把 App 配坏？答：版本化 schema、严格校验、原子写入、上次成功配置/内置默认三级回退，配置生效前做资源完整性检查。

29. ZhEditor

  • 定位 / 技术栈 / 模块：zh_editor-api、zh_editor、app，约 51 个主源码，是富文本编辑容器。入口 ZhihuEditorService.java、EditorHostActivity.kt、AbsEditorFragment.kt；能力以 AbsZVideoAbility、AbsMentionAbility 等拆分，UI 以 PictureUIComponent、VideoUIComponent、UndoUIComponent 等组合。
  • 关键机制与调用关系：外部通过 service/API 进入 host activity/fragment，BaseEditorViewModel 管草稿和页面状态，各 Ability 对接媒体、@、附件等业务，各 UIComponent 只处理工具栏交互；VideoPreviewDownloader 下载预览资源，EditorConsoleMessageReceiver 和组合 logger 处理 Hybrid/编辑器日志。
  • 亮点 / 风险 / 测试：Ability + UI component 比巨型编辑 Fragment 更可扩展；风险是编辑状态、Web/native bridge、撤销栈、草稿持久化和大媒体 Uri 权限。约 5 个测试，撤销/重做、进程死亡、复杂富文本 round-trip 应是核心。
  • 面试问答：
    • 问：编辑器为什么要区分 Ability 和 UIComponent？答：Ability 表达“能做什么”和业务依赖，UIComponent 表达“怎么触发/展示”；同一能力可在不同工具栏复用，也便于无 UI 测试。

30. ZIM

  • 定位 / 技术栈 / 模块：zim-api、zim、app，约 222 个主源码，提供 IM 输入面板、消息列表适配、表情/贴纸、富文本 span 与权限工具；API 入口 IZimInterface.kt，实现 ZimImp.kt。
  • 关键机制与调用关系：T_EmoticonInit.java 注册表情服务，EmoticonService/ImageCacheInterface 隔离贴纸资源；ImInputPanel、IMInputBox 管输入，IMRecyclerViewHelper、FetchLoadAdapterBuilder、ImListOperation 处理拉取和列表增量；RichSpanUtils、TagHandlerGroup 解析富文本。
  • 亮点 / 风险 / 测试：把 IM UI kit 和消息后端解耦、列表操作显式化；风险是消息顺序/去重、分页与实时消息竞态、输入法/权限、富文本不可信输入和贴纸缓存。仅 2 个测试，明显不足。
  • 面试问答：
    • 问：历史分页和实时消息同时到达怎么处理？答：以 messageId 去重、server sequence 排序，所有列表 mutation 串行进入 reducer/operation 层，不能让 adapter 在多个线程直接改。

31. VipPrerender

  • 定位 / 技术栈 / 模块：vip_prerender-api、vip_prerender、app；约 41 个主源码，面向会员内容 Web/原生预渲染。入口 PrerenderPlugin.kt，模型 PreloadBean.java，缓存 DataCache.kt/DataSource.kt。
  • 关键机制与调用关系：上层发送 LoadAction，LoadActionReceiver 接收；NativePreload 或 Web 预渲染提前取数据并写 DataCache，真正页面消费后更新状态；ReporterCore/Reporter 记录命中、耗时与失败。它与 Mercury 的 H5 预热、VipCommon 的业务预加载互补：前者偏页面/数据预渲染，后者偏通用资源与业务入口。
  • 亮点 / 风险 / 测试：把“预测—加载—缓存—消费—上报”闭环独立出来；风险是过期数据、用户身份/会员态变化、内存预算、重复请求和命中统计口径。5 个测试对小模块尚可，但需时间与身份变更测试。
  • 面试问答：
    • 问：怎么证明预渲染有效？答：不能只看任务成功率，要看消费命中率、首屏收益、额外流量/内存、错误率；未被消费的成功预载仍是浪费。

32. ReaderSDK-CMake

  • 定位 / 技术栈 / 模块：跨 Android/iOS 的 C/C++ 阅读排版内核，约 2063 个 C/C++ 主源码；Android 由 Android/CMakeLists.txt 编译 wrapper 并链接 kernel、log、zlib/DRM 相关库。格式内核在 kernel/epub，Android JNI 在 Android/src/。
  • 关键机制与调用关系：Java com.zhihu.android.app.nextebook.jni.* → APPJni.h/DRWrap.h 的 JNI_FN → DRWrap.cpp/EpubWrap.cpp/TxtWrap.cpp → CEpubInterface/CTxtInterface 单例 → 解析 EPUB/TXT、分页布局、drawPage、文字选区、搜索和图片索引；StructureConvert.cpp 在 JNI/内核结构间转换。
  • 线程、缓存、性能与风险：APPJni.cpp 用全局 pthread_mutex_t 保护部分调用，内核有 book/page cache API。原生排版避免 Java 层高频对象和跨平台重复实现，但 JNI local/global ref、字符串编码、Bitmap 所有权、异常边界和全局单例并发都高风险；全局锁也可能把耗时排版串行化。当前只做 Android wrapper/构建/接口层审查，未逐算法验证 2000+ 文件。
  • 测试 / 工程化：检出约 15 个测试相关文件，相对内核规模不足；应有同书同参数 golden page、乱码/损坏 EPUB fuzz、ABI/ASan、分页确定性和跨平台一致性测试。
  • 面试问答：
    • 问：JNI 阅读内核最常见崩溃点？答：生命周期/所有权和线程：Java 对象已释放但 native 持引用、local ref 爆表、跨线程复用 JNIEnv、Bitmap buffer 越界、异常未清理。

33. VipCommon

  • 定位 / 技术栈 / 模块：vip_common + app，约 190 个主源码，是会员业务共享层：资源中心、预加载、奖励任务、弹窗/Fragment 队列、未读消息、装扮、公共 View 和 service。
  • 关键机制与调用关系：
    • 资源：ResourceCenter.initialize()/preloadResource() → ResourceLoader.loadResource(scope,url,callback)，ConcurrentHashMap 保存资源项并做定时清理。
    • 预载：Preloader 按 manuscript/mini-series/webview/pin-detail 分流；WebViewPreloadHelper 以 URL key 缓存 preloader；PinDetailPreloadHelper 预取接口、MMKV 与首图。
    • 任务：TaskCenter.startTask()/VideoTaskCenter.startTask() 用 ConcurrentHashMap 保存任务和 Job，协程 timer 累积时长、自动暂停、完成后请求服务端。
    • 展示串行化：FragmentQueueImpl/DialogStackManager 避免多个浮层竞争。
  • 亮点 / 风险 / 测试：把高复用、强协调的会员能力集中沉淀；风险是 Common 继续膨胀成业务垃圾桶，全局 map/job 的生命周期、预载缓存身份隔离、计时任务后台准确性、MQTT 与接口未读数一致性。约 3 个测试，和 190 个主源码、多个并发中心不匹配。
  • 面试问答：
    • 问：奖励计时为什么不能只用每秒 Handler +1？答：进后台、掉帧、进程重建都会漂移；应以 monotonic clock 的时间差结算，显式处理 pause/resume，并让服务端做最终校验。
