项目面试资料导航

适用对象：约三年 Android 经验的候选人。
证据快照：2026-07-24，基于 C:\Users\msf\Desktop\code 当前检出内容。
核心原则：先讲自己真实做过的业务接入，再用源码解释机制；不要把公司框架、团队仓库或上游项目包装成个人作品。

1. 这套资料覆盖什么

  • 仓库全量盘点 记录了 67 个 .git 标记，其中 66 个是有效 Git 仓库；另有 pikachu、xxxxx-html 等非 Git 源码或资料目录。
  • Android 业务仓库 深入或标准分析 23 个业务/主工程仓库。
  • Android 基础设施与媒体 分析 33 个基础设施、Hybrid、媒体及相关仓库。
  • 10 与 20 合计 56 个章节、55 个唯一仓库；Kmaudio 是同一仓库的业务视角和媒体视角，不能重复计算成两个项目。
  • 跨端 RN/Web 分析 pikachu 与 html-anything。pikachu 当前副本缺少 prn/* 和 .yarn/，不能据此形成可信 Bundle 结论。
  • 工具、样例与资产 区分个人/实验型项目、公司团队资产、上游开源工程和离线文档。
  • Android 证据复核 对 10、20 抽查了 102 条关键文件、类型和函数证据，并确认条件式个人贡献口径已经收口。
  • 全工作区覆盖复核 已完成 66 个有效 Git 仓库的并集、大小写和交叉证据检查：覆盖、源码证据、个人归因措辞和敏感信息门禁均已通过。通过表示文档口径合格，不表示源码已经证明候选人的具体经历；使用综合材料时仍须逐条确认“需本人确认”项。

这不是“所有仓库都是候选人的项目”的清单，也不是完整 Git 历史归属审计。它能证明当前源码中有什么、调用链如何工作、有哪些工程风险；不能单独证明候选人负责过什么。

2. 三层证据边界

层级 可以怎样说 不可以怎样说
代码事实 “HomePinTabViewModel.refresh() 会触发 pager.invalidate()。” 把当前源码行为自动改写成“这是我实现的”。
工程判断 “捕获 Throwable 可能破坏协程取消语义，这是一个风险点。” 把风险写成已经发生的线上事故或已经完成的治理。
个人经历 “在我实际负责的某需求中，我接入了……并通过……验证。” 没有提交、需求、同事或数据佐证时声称“我主导/设计/从零搭建”。

凡涉及个人职责、方案决策、故障处理、测试贡献或结果，统一标记 “需本人确认”。结果必须说明指标、统计口径、时间范围和数据来源；缺任一项时，不写百分比、绝对收益或线上结论。

安全表达模板：

该框架/基础库由团队提供；如果这个调用点确实属于我的工作范围（需本人确认），我负责的是业务状态建模、接口接入、异常处理、联调或问题定位。结果只补充我能核验的真实数据。

3. 先建立正确的模块关系

关系 各自职责 面试边界
VipAndroid 与 VipHome 前者是 VIP App 的构建装配壳；后者负责 Application、Launcher、主导航和启动生命周期。 可作为一条“交付链”讲，但不能把两个仓库混成同一模块。
KnowledgeMarket、km_home_base 与 DevKit KnowledgeMarket 是知识市场聚合业务；km_home_base 是知识首页/书架容器及真实 Paging3 调用点；DevKit 提供 Mavericks 轻量 MVI 与分页封装。 优先讲“在业务侧使用/接入 DevKit”，除非本人确实参与框架开发。
VipManuscript 与 VipReader 前者是盐言手稿阅读、双向目录和互动；后者是 EPUB 解析、预解析与进度同步。 都属于阅读消费，但数据模型、分页/解析问题不同，不要说成同一个阅读器。
Kmaudio 与 Media 等基础库 Kmaudio 负责知识音频业务、数据源、播放列表和权益；Media/Audio/Zhplayer/mediax 提供协议、UI、Service、门面或引擎适配。 讲清业务层和播放基础设施层，不把播放内核作者身份归给业务接入者。
Feed、Comment 与 VipPassport Feed 是内容分发，Comment/VipComment 是互动，VipPassport 是登录注册和 Token；Account 承接登录后的账号态与安全。 它们能组成用户旅程，但源码不足以证明候选人全链路负责。
pikachu 与 Native 宿主 pikachu 是嵌入原生 App 的多页面 RN Bundle 工作区，通过 pageName、Deep Link、Bridge 和 Jotai 协作。 适合讲 Android/RN 边界协作；不声称编写了 PRN 底层或整个 RN 工作区。

4. 推荐阅读顺序

30 分钟：先形成可说的项目故事

  1. 读 项目主线总结 的 30 秒、2 分钟和五条主线。
  2. 用 简历与 STAR 模板 只选择本人真实参与的 1—2 条主线，补齐“需本人确认”和“结果待补”。
  3. 从 面试题库 选择对应主讲题，练习 40—90 秒的“边界—链路—取舍—验证”回答。
  4. 回到对应专题文档，记住入口、关键状态、一个取舍、一个风险和两个源码锚点。

2 小时：准备源码追问

  1. 读 Android 业务仓库 的第 0、24、25 节，再读所选业务章节。
  2. 读 Android 基础设施与媒体 的第 0、34—36 节，再读相关基础库章节。
  3. 若要讲 RN 协作，读 跨端 RN/Web 的第 0—11、23—25 节。
  4. 用 Android 证据复核 检查 API 名、去重口径和风险措辞。
  5. 用 全工作区覆盖复核 核对 66 仓覆盖和个人归因门禁，再用 面试题库 做源码追问、压力追问与模拟面试。
  6. 最后在 简历与 STAR 模板 中补本人动作、验证证据和真实结果；未确认的模板不进入简历。

全量审计：理解工作区边界

  1. 从 仓库全量盘点 核对仓库性质和当前 checkout。
  2. 顺序阅读 10、20、30、31。
  3. 读 Android 证据复核，区分“已验证事实”“仍是风险推断”“无法从源码判断”。
  4. 以 全工作区覆盖复核 收口全仓覆盖：当前结论是“最终通过，可进入综合面试材料”，但候选人仍须确认每项真实职责、动作和结果。
  5. 再按 项目主线总结 → 面试题库 → 简历与 STAR 模板 的顺序完成口述、追问和简历准备。

6. 面试前最后检查

  • 只保留本人确实做过的需求和调用点。
  • 能说清“公司已有能力”和“我的业务动作”的分界。
  • 每条主线至少能指出两个真实文件或类。
  • 指标包含口径、时间范围和来源；没有指标就讲验证范围。
  • 不把 Kmaudio 的两种分析视角算成两个项目。
  • 不把 VipAndroid 与 VipHome、VipManuscript 与 VipReader 混为一个模块。
  • 不把 Moonlight、CUDA、Obsidian Skills、html-anything 等自动归为个人项目。
  • 不复述 Token、密钥、内网地址或其他敏感配置。
