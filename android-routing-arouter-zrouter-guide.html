Android 路由原理：ARouter 与 ZRouter 的实现

调用方没有直接依赖目标页面，指的是它的源码里不需要 import 目标页面，也不需要写 StoryDetailFragment.class。目标页面本身仍然要进入最终安装包，路由表里也必须能找到它。业务代码只给出路径和参数，由路由框架找到目标，再完成创建或打开。

这件事可以拆成两个过程：编译时把“路径对应哪个页面”记录下来；运行时根据这份记录找到页面。真正拿着目标 Class 的，是目标模块生成的代码和运行时路由信息，不是每一个调用它的业务模块。

这里有个需要分清的关系：当前仓库的 ZRouter 依赖的是 com.zhihu.android:router，调用的是 com.zhihu.router.Routers。它不是这份代码中可见的 ARouter 包装层。下面先用 ARouter 说明通用路由怎么实现，再看 ZRouter 怎样在知乎 Router 上处理具体 App 的页面行为。

ARouter 核对版本：官方标签 1.5.2，提交 452297cef567838238571c181189d17d92847aa4。ZRouter 为当前工作区源码。核对日期：2026-10-25。本次读取源码与现有测试，没有执行 Android 构建或真机跳转。

调用方不引用页面类，目标页面为什么仍然能被找到

假设首页在 feature-home，详情页在 feature-story。直接跳转时，首页要写详情页的类名，就得让首页编译时能看到详情模块。换一种写法，首页只写“打开 /story/detail”，目标模块自己声明这个路径，首页便只需要知道路由 API 和参数约定。

模块关系 · 结构示意
feature-home 依赖路由 API
feature-story 依赖路由 API，并接入注解处理器
app 引入 feature-home、feature-story 和路由运行库

首页调用：路径 /story/detail，参数 storyId
详情模块生成的路由表：/story/detail 对应 StoryDetailFragment.class

最终 app 仍然要把目标模块带上。否则即使调用代码编译通过，运行时也找不到对应路径。这里减少的是首页对详情实现的直接编译依赖，路径、参数和版本约定仍然需要维护。

生成的表能够引用 StoryDetailFragment.class，是因为它就在详情模块的编译过程中生成，编译时能看到详情页。这个表和目标类一起进入最终包，框架运行时再读取它，不需要首页反过来认识详情页的实现类。

ARouter 在编译时生成了哪些东西

页面上声明 @Route 之后，注解处理器 RouteProcessor 会收集这些声明，判断目标是 Activity、Fragment 还是 Provider，再把路径、分组、目标类型、目标 Class 和参数信息组织成路由元数据。

声明与调用 · 简化示例，省略 import 和页面内容
@Route(path = "/story/detail")
public class StoryDetailFragment extends Fragment {
    // 页面实现省略。
}

ARouter.getInstance()
    .build("/story/detail")
    .withLong("storyId", 123L)
    .navigation();

这个例子中的类名和路径只是用来说明过程，不是项目里已经注册的详情路由。ARouter 1.5.2 源码使用的 Fragment 类型包含 android.app.Fragment 和旧的 android.support.v4.app.Fragment；具体 AndroidX 工程是否经过依赖迁移、最终引用哪个版本，需要按实际依赖确认。

生成代码里比较重要的是两层表。Root 记录某个分组由哪个 Group 类负责；Group 再记录完整路径对应哪个目标。默认情况下，/story/detail 的分组是 story，也可以显式指定分组。

生成结果与运行时表的对应关系 · 示意，省略完整生成类
// Root 的作用：登记一个分组的加载类。
groupsIndex.put("story", ARouter$$Group$$story.class);

// Group 的作用：登记这个组内的具体路由。
routes.put("/story/detail", RouteMeta.build(
    RouteType.FRAGMENT,
    StoryDetailFragment.class,
    "/story/detail", "story", null, -1, Integer.MIN_VALUE
));

真实生成类会实现 IRouteRoot、IRouteGroup 等接口，在 loadInto(...) 方法里填入映射。Root 类名还带模块名，用来区分不同模块生成的入口。Provider 和拦截器也有各自的元信息表。

@Route 在这个版本使用 RetentionPolicy.CLASS。因此，运行时找的是编译期生成的表，不是每次跳转再遍历全部页面、读取每个页面的 Route 注解。生成表的代码与运行时注册，是两个不同步骤。

源码：RouteProcessor.parseRoutes:124；Group 生成位置:315；Root 生成位置:358；@Route 保留策略:16。

启动时，生成的路由表怎样进入内存

ARouter.init(application) 会进入 _ARouter.init，再调用 LogisticsCenter.init。编译生成的文件只是包里的类，到这一步才会被加载，并把信息写进 Warehouse 中的运行时表。

运行时表里面放什么用于什么
groupsIndex分组名对应 Group 的 Class需要某一组时，找到它的加载入口。
routes完整路径对应 RouteMeta取得目标 Class、类型和参数信息。
providersIndex服务接口名对应路由信息根据接口查找 Provider。
providersProvider Class 对应已创建实例避免反复创建同一个服务。
interceptorsIndex、interceptors拦截器的类型、优先级与实例初始化并执行拦截流程。

1.5.2 里优先尝试插件注册。注册插件会向 LogisticsCenter.loadRouterMap() 加入注册逻辑，框架便能直接找到生成入口。如果没有通过插件完成注册，就走扫描或缓存路径：Debug 模式或新版本需要重新查找生成类，之后可以复用保存的类名集合。

这里扫描的是约定包名下的生成类，用来找到 Root、Provider 和拦截器入口，不是每次点击都扫描 Dex。插件注册减少了发现这些入口的扫描工作，也不能据此说整个 ARouter 完全没有反射；这个版本的注册与实例创建代码仍有反射调用。

初始化主要准备分组索引等信息，并不要求一次性把每个业务组的全部路由都展开。这样可以把一部分工作留到第一次使用该组时再做。

源码：ARouter.init:39；_ARouter.init:61；LogisticsCenter.init:141；Warehouse:23。

build 和 navigation 分别做了什么

build("/story/detail") 先创建一份路由请求 Postcard。它可以保存路径、分组、Bundle、Context、动画和 flags。此时仅有请求信息，目标 Class 还没有补齐，也还没有开始显示页面。

withLong("storyId", 123L) 这类调用把值写进 Postcard 的 Bundle。navigation() 才会把请求交给框架继续处理。路径替换服务如果存在，可以在构造请求时调整路径。

ARouter 的主要过程 · 调用链概括
ARouter.getInstance().build(path)
    _ARouter.build(path)
    创建 Postcard，保存 path、group、extras

Postcard.navigation(...)
    ARouter.navigation(...)
    _ARouter.navigation(...)
    可选的 PretreatmentService
    LogisticsCenter.completion(postcard)
    可选的 IInterceptor 链
    _ARouter._navigation(...)
    按目标类型打开 Activity、返回 Fragment 或返回 Provider

LogisticsCenter.completion() 先用完整路径查 Warehouse.routes。如果没有对应记录，再看 groupsIndex 里有没有这个分组。有的话，就创建 Group 加载器，调用 loadInto(Warehouse.routes)，把这一组的路由放进去，再查一次。加载完成的组会从待加载索引里移除，已经展开的路由继续缓存在 routes 里。

因此，第一次查到某个组时可能多一次加载，之后可以直接从完整路由表取目标。这是路由元信息的按需加载，不是业务代码按需下载，目标类仍然来自已经打进包里的模块。

查到 RouteMeta 后，框架把 destination、type、priority 等补到 Postcard。查不到会抛出 NoRouteFoundException，外层再根据是否提供回调，执行 onLost 或全局 DegradeService，而不是假定目标总会存在。

源码：_ARouter.build:180；Postcard.navigation:129；completion:221；Group 加载:358；navigation 与丢失处理:284。

找到目标后，Activity 和 Fragment 的处理为什么不同

如果目标是 Activity，ARouter 根据目标 Class 创建显式 Intent，把 Bundle、flags 等填进去，最后通过系统启动 Activity。非 Activity Context 需要补 FLAG_ACTIVITY_NEW_TASK；真正执行启动的部分会切到主线程。

如果目标是 Fragment，ARouter 1.5.2 的分支是反射创建 Fragment，设置 arguments，然后把实例返回。它不会在这一分支替应用选择容器、执行 FragmentTransaction 或维护应用自己的返回栈。拿到 Fragment 之后怎样显示，仍属于宿主页面框架的工作。

这也是 Fragment 和 Activity 的差别：Activity 可以交给系统启动，Fragment 必须放进一个 Activity 的界面中。通用路由知道目标类，不代表它知道当前业务应当在哪个容器显示、要不要隐藏上一个页面。

拦截也要看实际分支。这个版本在 completion() 中会给 Provider、Fragment 设置 green channel，跳过普通 IInterceptor 链；外层的 PretreatmentService 则在补全路由信息前执行。不能把“每个 Fragment 都会先经过同一组登录拦截器”当成这个版本的固定行为。

普通拦截链由 InterceptorServiceImpl 执行，通过 onContinue、onInterrupt 推进或终止，并处理超时。它在有拦截器时会使用执行器，但 Fragment 实例创建等其他分支不能因此统一理解为都会自动切到主线程。

源码：按目标类型分发:361；Activity 启动线程:428；Fragment 的 green channel:297；拦截链执行:33。

路由参数进入 Bundle，和字段自动赋值是两件事

手动调用 withLong、withString，值会直接放入 Postcard 的 extras。目标是 Activity 时，它们进入 Intent；目标是 Fragment 时，它们进入 arguments。页面可以自己按类型读取这些值。

如果是 build(Uri)，ARouter 会在补全过程读取 URI query，再根据路由表中已声明的参数类型做转换。这个版本保存的参数类型与 @Autowired 收集有关，不能认为任意一个 query 字符串都会自动变成对应业务字段。

字段注入还有另一条链路。AutowiredProcessor 会生成实现 ISyringe 的辅助类；调用 ARouter.getInstance().inject(this) 后，AutowiredServiceImpl 再找到辅助类执行注入。辅助代码从 Activity 的 Intent 或 Fragment 的 arguments 取值，写进对应字段。它和找到目标页面不是同一个步骤。

Provider 也有单独的处理：框架根据服务接口找到路由信息，创建对应实现、调用 init，并缓存实例，再把服务对象返回给调用方。Provider 的这个 init 与应用启动时注册路由表也要分开理解。

源码：手动写入参数:298；生成字段读取代码:157；执行注入:44；Provider 初始化与缓存:278。

ZRouter 封装的是哪一层，调用方看到了什么

ZRouter 仓库的“路由入门”明确写到：Router 是通用库，ZRouter 是针对知乎 App 的封装。当前 build.gradle 依赖的是 com.zhihu.android:router；实际解析最后进入 com.zhihu.router.Routers，没有在这条入口链路中调用 ARouter。

所以两套实现的关系是：ARouter 可以用来说明通用路由表和目标分发的原理；ZRouter 则需要沿它自己的接口和源码继续看。比较“ZRouter 多处理了什么”时，指的是它在知乎通用 Router 上面承接了哪些 App 行为，不表示这些扩展能力是 ARouter 完全没有的。

当前 ZRouter 的主要打开过程

    build() 调用 transformUrl() 处理特殊链接
    ZRouter.open(context, routerUrl)
        外部浏览器分支，或者 openRouter(...)
        RoutesResolver 的解析拦截链
        Routers.getDefault().resolve(uri)
        MatchResult：目标、参数、模块等信息
        合并额外 Bundle
        可选的 RouterDispatcher / RouterConsumer
        Activity：构造 Intent 并启动
        Fragment：构造 ZHIntent，处理打开选项和转换器

基础 Router 根据模板找到目标，ZRouter 继续决定这个目标在 App 里怎么打开，以及找不到时怎么处理。通用查表和具体页面行为在这里分成了不同层。

知乎 Router 怎样把 URL 变成目标和参数

当前仓库带有 @Router 的使用说明、动态 Mapper 创建代码和解析调用，但通用 Routers、编译期处理器的完整实现来自外部依赖，这次没有把它们的全部内部源码读到。生成入口的说明来自仓库文档，动态注册和解析入口则能直接对照当前 Java 代码。

仓库文档描述的是：每个模块通过自己的处理器生成 MapperInitializer_模块名，记录 URL 模板和目标；模块名用于区分生成入口。文档还说明，应用工程需要汇总子模块信息。当前真实构建如何汇总、所用处理器版本有没有调整，仍以构建插件和依赖解析为准，不能仅凭这份旧文档把细节当成全部确认。

从本仓库的 destination.MapperCreator 可以直接看到，映射不仅包含路径字符串，还包含 scheme、host、路径分段、query、参数类型、正则条件、优先级和模块。模板还能声明重定向，创建器会解析并检查重定向前后参数是否匹配。

知乎 Router 的声明格式 · 教学示例，不是现有业务路由
@Router({
    "zhihu://story/{story_id:long}",
    "https://www.zhihu.com/story/{story_id:long}"
})
public class StoryPage extends Fragment {
    // 注册完成后，匹配结果中会带目标类与解析出的参数。
}

这种模板可以表达“这一段是一个 long 类型的参数”，还可以在 query 中区分 URL 参数名、Bundle key、默认值和可选值。它和 ARouter 例子里的固定 path 加 query 元信息不是同一种模板语法，不能直接互换。

当前 ZRouter.addDestination(...) 也允许创建 Mapper 后加入路由表；RoutesAccessor 在写锁保护下调用 addMappers，再重新排序。这说明当前并不只有编译生成这一条登记入口。排序的完整实现和底层匹配算法属于外部 Router，本节不把它们臆断成哈希查找、Trie 或某种确定的扫描复杂度。

为什么先把 URL 包成 RouterUrl，还要改写链接

RouterUrl 把 Uri、额外 Bundle、requestCode、resultFragment、是否保持 Activity、是否新开 Activity 等放进一份请求。调用方不用把这些选项拼成一长串参数，也能用 buildUpon 在原请求上继续处理。

它的 build() 会调用 transformUrl()，因此部分链接在真正匹配前已经被改写。对调用者来说仍然只调用一次 open，特殊格式的处理则集中在这一处。

输入或选项当前源码中的处理处理后解决什么问题
zhihu://launch?url=...取出内部 URL，继续构造请求。兼容包了一层的启动链接。
http(s) 链接带 forceWebView=1改成 zhihu://open_url，原地址放进 url。这次请求指定按 WebView 路径处理。
http(s) 链接带 zh_forcehybrid=1改成 zhihu://hybrid，原地址放进 zh_url。交给 Hybrid 页面承载。
openinapp_instruction 与 app-argument取出 app-argument 里的地址继续处理。兼容这一类外部唤起格式。
https://oia.zhihu.com/...、https://soia.zhihu.com/...前缀转换成 zhihu://...。复用对应的 scheme 路由；soia 分支注释说明用于会员独立 App。

这些具体改写可以直接从代码确认。把处理集中起来的作用，是避免每个页面调用方都复制链接兼容逻辑。不是所有改写都会完整保留旧请求：大多数分支使用 buildUpon，oia、soia 分支则重新 newBuilder，不能无条件假设所有 Bundle 和打开选项在所有转换中都保持不变。

当前 keepQueries() 也只保留指定的 query，例如 extra_account_transformer_ignore，并非复制全部旧 query。这些差别在排查“改写后参数为什么丢了”时有实际影响。

源码：yyyyy-cdoe/ZRouter/zrouter/src/main/java/com/zhihu/android/app/router/RouterUrl.java:607；yyyyy-cdoe/ZRouter/zrouter/src/main/java/com/zhihu/android/app/router/RouterUrl.java:658；yyyyy-cdoe/ZRouter/zrouter/src/main/java/com/zhihu/android/app/router/RouterUrl.java:597；yyyyy-cdoe/ZRouter/zrouter/src/test/java/com/zhihu/android/app/router/RouterUrlTest.java。

解析前的拦截、匹配规则和参数合并

RoutesResolver 先把当前解析拦截器复制成数组，作为这次请求的处理链。拦截器收到请求和继续执行的方法，可以处理后继续往下传，也可以直接返回自己的结果。链路走完后，才调用底层 Routers.getDefault().resolve(uri)。

RoutesResolver 的链式处理 · 原码节选
    private static MatchResult resolve(RouterUrl routerUrl, ResolveInterceptor[] interceptors, int index) {
        if (index >= interceptors.length) {
            return Routers.getDefault().resolve(routerUrl.uri());
        }
        ResolveInterceptor interceptor = interceptors[index];
        return interceptor.intercept(routerUrl, url -> resolve(url, interceptors, index + 1));
    }

全局基础匹配配置则在 Configs.init() 中设置。当前配置允许 http 和 https 互相等价，也把 www.zhihu.com、zhihu.com、m.zhihu.com 视为一组等价 host。非公开构建还会处理开发环境域名。这样同一个业务页面不必为这些等价入口重复写完全相同的规则。

Configs 还会通过 InstanceProvider.getAll(Filter.class) 获取 Filter，交给底层 Router。它与外层 ResolveInterceptor 是不同入口，不能在没有继续查看实现时，直接把所有过滤、登录检查都归为同一条链。

拿到 MatchResult 后，ZRouter 会合并请求额外传入的 Bundle：

额外参数合并 · 原码节选
        result.bundle.putAll(routerUrl.bundle());

这意味着相同 key 下，后面这份额外 Bundle 会覆盖已经解析出的值。URL query、路径参数和调用时 putLong/putString 的参数并不总是各管各的；判断最终值时要看合并顺序。

为什么匹配结果还可能经过 Dispatcher 或 Consumer

有些 URL 可以确定属于哪个业务，却不能在注册时固定到唯一页面。当前 ZRouter 遇到 RouterDispatcher 目标时，会调用 dispatch，把原 MatchResult 换成另一份结果，再继续打开。例如仓库接口注释就举了把目标换成另一个 AnswerFragment 的例子。根据用户状态或实验结果换页面，是这种入口可以承载的用法，但具体线上条件还需要检查业务实现。

RouterConsumer 则表示请求由一段业务逻辑消费。匹配到它后调用 consume(context, result)，不会继续按普通页面分支打开。路由因此可以统一接收某类 URL，再把它交给行为处理，而不要求每条 URL 都对应一个能显示的页面。

GHOST 在这些分支中表示“后续默认打开不再处理”。它表达的是当前处理者接管了请求，不能据此认为某个页面已经完成显示。这里按源码分支解释语义，没有对所有 GHOST 路径做运行验证。

Dispatcher 返回 null 时，当前打开流程返回未处理；经由最外层 open 调用时，还可能继续走外层 fallback。直接调用 openRouter 与调用 open 的后续行为不能完全混为一谈。

ZRouter 对 Fragment 多做了什么

匹配到普通页面后，ZRouter 会把目标、Bundle 和 screenName 包装成 ZHIntent。这是 App 自己的页面请求对象，虽然实现了 Parcelable，但它不是系统的 Intent。除了目标和参数，它还可以带页面标识、隐藏前页、popSelf、keepActivity、新开 Activity 等选项。

如果目标是 Fragment，ZRouter 先把这些打开选项写入 ZHIntent，再交给 openFragment()。这段处理弥补了“找到了 Fragment 类”和“把 Fragment 显示到 App 里”之间的那一步。

Fragment 打开分支 · 原码节选

                                     int requestCode, boolean record) {
        Activity activity = ClassUtil.getActivityFromContext(context);
        if (activity instanceof FragmentLauncher) {
            ((FragmentLauncher) activity).startFragmentForResult(zhIntent, resultFragment, requestCode,
                    null, record);
        } else {
            Intent intent = geIntentFromZHIntent(context, zhIntent, uri);
            startActivityForResult(context, intent, requestCode, resultFragment);
        }

如果当前 Context 能找到实现了 FragmentLauncher 的 Activity，就直接调用它的 startFragmentForResult。现有页面容器接手后，才能按自身规则处理 Fragment 的显示与栈行为；ZRouter 这一步并没有自己直接执行 FragmentTransaction。

如果当前 Activity 不提供这项能力，ZRouter 就选择一个宿主 Activity，把 ZHIntent 放进系统 Intent 的 extras，再启动宿主。getComponentActivity() 会先看目标的 @AttachedActivity，再看 @BelongsTo 或底层 Router 返回的模块名，通过 ModuleActivityMapper 找该模块的 Activity，最后才使用默认 Host。

默认 Host 可以在初始化时设置，也可以从 zrouter.defaultActivity 配置读取。这样公共页面不必自己写死某个 App 的外层 Activity，各模块或宿主可以提供承载选择。App-specific 的容器关系集中在这一层，更适合多模块、多入口工程。

keepActivity、newActivity 等选项在这一层被传给页面框架，具体怎样影响栈，还要继续看 FragmentLauncher 的实现。不能只看到一个 flag 就断言 ZRouter 本身已经在这里完成了所有栈操作。

目标是 Activity 时，则走系统 Intent 启动流程，并处理 requestCode、resultFragment 和非 Activity Context 的 NEW_TASK。当前 ZRouter 打开入口没有 ARouter Activity 分支那种统一的主线程 Handler 派发，不能把两者的线程承诺直接套用。

解析之后，为什么还允许修改或替换 ZHIntent

参数解析结束不一定就能直接打开目标。当前 ZRouter 先执行这次请求自己的 intentProcessor，再执行全局的 ZHIntentTransformer。前者适合只对这次请求补充选项；后者可以集中调整某类页面的目标、参数或页面标识。

全局 Transformer 按注册顺序处理。返回同一个对象或 null，代码都会继续往后走；返回一个新 ZHIntent，才会停止后面的转换器并采用新结果。因此，“return null”在这个接口里不是取消跳转的意思。

Transformer 的实际继续条件 · 原码节选
    private static ZHIntent transformIntent(ZHIntent intent, Context context, RouterUrl routerUrl) {
        for (ZHIntentTransformer transformer : Configs.transformers) {
            ZHIntent zhIntent = transformer.transform(context, intent, routerUrl);
            if (zhIntent == intent || zhIntent == null) {
                //返回原来的或者 null，认为这个 Transformer 没有处理，接着交给下面的 Transformer
                continue;
            }
            // 否则就返回这个了，Router 会打开这个 Intent
            return zhIntent;
        }
        return intent;
    }

替换成新 ZHIntent 后，打开流程还会清空原 resultFragment，并加入 EXTRA_TRANSFORMED 标记。清空和标记可以直接从代码确认；从这个处理看，它在区分原请求和被换过的页面，避免直接沿用原来的返回接收关系。

仓库文档提到了登录和 AB 等扩展场景，但这些能力是否在某个 App、某次启动中生效，还取决于实际注册了什么实现。当前这层入口、调用顺序和现有测试能确认；线上全部注册项并不是本次已核对的内容。

找不到页面时，为什么还有多层 fallback

App 接到的链接可能来自旧版本、外部分享或不同业务，不一定都能匹配当前原生页面。ZRouter 把找不到目标后的选择也放在统一入口里，调用方不必每次重新实现浏览器、WebView 和业务回退。

最外层 open 先检查强制外部浏览器的 http(s) 请求，即 zh_external=true。其他请求尝试 openRouter。解析没有结果时，会尝试请求中的 fallback_url，以及注册的 RouterFallback；处理成功就结束。

如果 openRouter 仍没有处理，最外层 open 再进入一般 fallback。当前代码对 zhihu:// 不继续按普通网页兜底；站内网页，或者明确允许 fallbackWithBrowser 的请求，可以继续转到内部页面。其他未允许的外部地址会记录错误并返回未处理。

场景当前源码的去向
显式 forceWebView=1预处理时改成 open_url，参数名是 url。
显式 zh_forcehybrid=1预处理时改成 hybrid，参数名是 zh_url。
一般网页 fallback当前 getInternalWebViewUrl 改成 hybrid，并携带 zh_url。
强制外部浏览器，但设备没有可用处理 Activity捕获 ActivityNotFoundException 后，再尝试内部 open_url。

因此，不能把所有失败都概括成“最后打开 open_url”。不同入口、不同 query 和当前版本有不同分支。RouterUrl.Builder.openRouter() 也没有最外层 open 的全部兜底步骤，但它调用的内部流程在匹配失败时仍可能处理 fallback_url，不是完全没有回退。

链接改写、fallback_url、WebView 加载都仍需要和权限、地址校验一起考虑。找到一个能承载 URL 的页面，不等于输入已经安全，也不等于敏感业务已经获得授权。

页面标识、日志和只解析 API 分别有什么用

ZRouter 创建 ZHIntent 时会调用 ScreenNameResolver。它可以读取目标上的 @ScreenName，用 Bundle 参数填充页面标识；没有可用标识时，会生成带无效前缀的备用值，并通过 isValidScreenName 决定传给页面启动器的相关记录标记。页面因此不仅有目标 Class，也有用于后续统计的身份信息。

recordResolveRouter() 记录解析是否得到结果、目标类型、host 和解析耗时。这里计时包住的是路由解析，既不是页面首帧，也不是用户实际可交互时间；“有匹配结果”和“页面成功显示”也不是同一个指标。

API主要行为需要分清的地方
ZRouter.open发起处理、打开或交给消费者，并按入口处理回退。返回 true 表示相应分支已经接手，不是页面绘制完成的回调。
ZRouter.resolve解析并组织 ZHIntent，不执行最终启动。它仍会经过解析、Dispatcher 和适用的 Transformer，不是完全无处理的简单查询；也不等同于 open 的所有分支。
ZRouter.resolveToIntent把目标组织成系统 Intent。Fragment 目标会对应 HostActivity 的 Intent，不会因此绕过容器。
ZRouter.test检查解析是否有结果。不是网页兜底、后续授权或最终 UI 显示一定成功的保证。

完整参考回答

调用方不直接依赖目标页面，通常是说它不需要 import 页面类，只需要知道一个路径和参数约定。目标模块会把路径到页面的映射提供出来，最终宿主把目标模块和路由表一起打进包。运行时由框架查到目标 Class，再按页面类型处理，所以目标类并没有凭空消失，只是引用它的位置从各个调用方转到了路由表和框架里。

以 ARouter 为例，它在编译期处理 Route 注解，生成 Root 和 Group 等映射。启动时把分组索引等信息注册到 Warehouse。调用 build 会创建 Postcard，navigation 时再由 LogisticsCenter 补全目标，必要时先加载对应分组。之后按当前目标类型和是否跳过拦截，进入真正的分发：Activity 最终用 Intent 启动，Fragment 分支则创建实例、填 arguments 并返回。

项目里的 ZRouter 是另一条具体实现链，它封装的是知乎的 com.zhihu.router，并不能直接说成在 ARouter 上包装了一层。底层 Router 负责匹配目标，ZRouter 再处理 App 的具体规则，例如特殊 URL 改写、解析拦截、Dispatcher 和 Consumer、参数合并、ZHIntent 转换，以及 Fragment 的 HostActivity 选择。

对首页来说，这样只要提交 jumpUrl 和参数，不必知道目标 Fragment 应当由哪个 Activity 承载，也不必各自实现旧链接兼容和 WebView 兜底。它减少了调用方对目标页面的直接引用，但目标模块仍要打包、映射仍要注册，路径和参数仍要保持兼容。至于页面是否真正显示完成，还需要页面或性能指标来判断，不能仅看 open 返回 true。
