一、组件化与构建

Q01【基础｜主讲】这个项目的组件化是怎样落地的？

标准可说答案：“它不是单仓巨石，而是主壳加业务组件。业务仓通常拆成实现模块、-api 契约和 demo，发布为 Maven 制品；VipAndroid 再通过 allComponents、版本表和组件元信息完成装配。业务侧只依赖稳定 API，本地联调时可把制品替换为相邻源码。我若讲个人贡献，只会讲自己真实接入、升级或排障过的组件。”

证据路径：yyyyy-cdoe/VipAndroid/app/build.gradle；yyyyy-cdoe/VipAndroid/settings.gradle；yyyyy-cdoe/VipAndroid/gradle/sourcecode.gradle

**常见踩坑：**把“使用组件体系”说成“设计了整套组件框架”；只讲模块拆分，不讲发布、装配和运行时服务契约。

Q02【源码追问｜主讲】VIP 版本如何复用主 App，又保持产品差异？

标准可说答案：“构建脚本用 VIP_APP_REMOVED_COMPONENTS 裁掉不需要的组件，再通过 dependencyReplace 把评论、账号等标准实现替换为 VIP 变体。它解决的是产品裁剪和实现替换，而不只是 Gradle 版本冲突。变更后要验证依赖图、关键路由、多 flavor 和 so 完整性。”

证据路径：yyyyy-cdoe/VipAndroid/app/build.gradle；yyyyy-cdoe/VipAndroid/app/gradle/check_deps.gradle

**常见踩坑：**只验证能编译，不检查替换后是否同时打入两份实现；把产品变体复制成永久分叉而没有契约测试。

Q03【源码追问｜主讲】sourcecode.properties 源码替换解决什么问题？

标准可说答案：“主工程默认消费 Maven 制品，联调时 sourcecode.gradle 读取 sourcecode.properties，把指定坐标替换为相邻源码工程，并处理 API/实现模块关系。这样业务仓可以独立发布，也能在主壳里断点调试。它要求源码版本与主工程版本表一致，否则容易出现接口和实现错配。”

证据路径：yyyyy-cdoe/VipAndroid/gradle/sourcecode.gradle；yyyyy-cdoe/VipAndroid/sourcecode.properties

**常见踩坑：**同时保留 Maven 实现和源码实现导致重复类；只替换实现模块却漏掉 -api；联调完成后把本机路径提交进仓库。

Q04【基础】为什么实现模块与 -api 模块要分开？

标准可说答案：“API 模块放稳定契约，调用方无需感知具体实现和大量传递依赖，能降低编译耦合并允许产品变体替换。代价是接口演进要更谨慎，需要兼容策略、默认实现或版本化，不能为了分层制造大量没有边界价值的接口。”

证据路径：yyyyy-cdoe/Kmaudio/kmaudio-api/src/main/java/com/zhihu/android/kmarket/KMPlayerInterface.java；yyyyy-cdoe/Kmaudio/kmaudio/src/main/java/com/zhihu/android/kmaudio/player/KMPlayerInterfaceImpl.kt

**常见踩坑：**API 模块反向依赖实现；把业务模型全部暴露出去；只说“解耦”却说不出替换和编译隔离的实际收益。

Q05【压力追问】升级 AGP 或核心组件时，你如何控制风险？

标准可说答案：“我会先固定可构建基线，盘点自定义插件、Transform、R8、Jetifier、Kotlin 和 JDK 约束；再拆成 Gradle/JDK、AGP、Kotlin和业务插件几个阶段。每阶段跑关键 flavor、依赖白名单、重复类、资源压缩、so/ABI 和核心路由 smoke test，不把所有变量一次升级。真实收益需由本人补充。”

证据路径：yyyyy-cdoe/ZhihuLite/build.gradle；yyyyy-cdoe/ZhihuLite/app/build.gradle；yyyyy-cdoe/ZhihuLite/features.json

**常见踩坑：**一次跨多个大版本后无法归因；只验证 debug；关闭 lint/R8 问题来“通过升级”。

二、启动

Q06【基础｜主讲】请讲一下冷启动主链路。

标准可说答案：“ZhihuApplication 先在 attachBaseContext 建最小底座和安全恢复能力，再由 delegate 在 onCreate 分层初始化。入口 Activity 处理隐私、新用户和开屏策略，随后 startMain() 进入主页面。启动任务按首屏必要性、进程、线程和隐私时序拆分，并用阶段监控定位，而不是把所有 SDK 堆到 Application。”

证据路径：yyyyy-cdoe/VipHome/app/src/main/java/com/zhihu/android/app/ZhihuApplication.java；yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/ZhihuApplicationDelegate.java；yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/ui/activity/LauncherActivity.java

**常见踩坑：**把“全部异步”当优化；忽略隐私授权前后边界；不区分冷启动、热启动和深链启动。

Q07【源码追问｜主讲】启动 DAG 比在 Application 里并行初始化好在哪里？

标准可说答案：“DAG 能显式表达 dependsOn、finalizedBy、线程、延迟和调度器，既保留并行度，又避免依赖乱序。它还能把首屏关键任务与首屏后任务分开，并对节点做阶段耗时。异步本身不能解决错误顺序，只有明确依赖和完成条件才行。”

证据路径：yyyyy-cdoe/ZhihuLite/app/launch_config/TaskManager.json；yyyyy-cdoe/VipAndroid/app/launch_config/TaskManager.json

**常见踩坑：**任务声明异步但主线程等待 Future；依赖环；任务结束信号早于真实初始化完成；子进程重复执行主进程任务。

Q08【源码追问｜主讲】Launcher 到 MainActivity 为什么容易出现竞态？

标准可说答案：“Launcher 同时处理广告、动画、新用户、隐私和外部深链，不同回调都可能触发导航。如果没有一次性门禁和明确状态机，可能重复进入 Main，或 Main 覆盖本应打开的目标页。我会统一导航出口，让启动状态和目标 Intent 都带任务身份，并覆盖旋转、回后台和重复回调。”

证据路径：yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/ui/activity/LauncherActivity.java

**常见踩坑：**在多个动画/网络回调直接 startActivity；用固定延迟掩盖竞态；没有保存消费过的深链。

Q09【基础】为什么不能把所有 SDK 都放在 Application.onCreate()？

标准可说答案：“它们会争抢主线程、IO、锁和线程池，拖慢首帧；部分 SDK 还必须等隐私同意。应按首屏必需、授权后、空闲期和业务触发分层，并按进程去重。延后初始化也要评估首次使用抖动，不能只是把成本搬到用户点击时。”

证据路径：yyyyy-cdoe/VipHome/app/src/main/java/com/zhihu/android/app/ZhihuApplication.java；yyyyy-cdoe/FutureveGlobal/global/src/main/java/com/zhihu/android/app/util/netplugable/GlobalRequestDecorator.java

常见踩坑：“都放子线程”但仍发生锁竞争；隐私前读取设备标识；延迟任务没有取消和幂等。

Q10【压力追问】线上启动变慢 20%，你第一小时怎么排查？

标准可说答案：“先确认指标口径、版本、机型和冷/热启动分布，再按阶段监控定位 Launcher、Application、任务 DAG 或首屏渲染。之后用 trace 区分主线程 CPU、IO、锁等待、Binder 和 GC，结合版本 diff 与开关做单变量验证。这里的‘20%’若来自本人案例，必须补数据源；没有数据就只讲流程。”

证据路径：yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/ui/activity/LauncherActivity.java；yyyyy-cdoe/ZhihuLite/app/launch_config/TaskManager.json

**常见踩坑：**一上来删除初始化；只看平均值；拿开发机热启动结论替代线上冷启动分位数。

三、MVI 与 MVVM

Q11【基础｜主讲】这个项目的 MVI 和你以前使用的 MVVM 有什么差别？

标准可说答案：“这里用 Mavericks 的不可变 State 和 setState 做单向渲染，页面状态比传统多个 LiveData 更集中；但 Fragment 仍直接调用 refresh()、deleteItem()，没有统一 Intent/Reducer，Paging 的 LoadState 也留在 View 层，所以我会准确称为轻量 MVI。MVVM 同样能做单向数据流，关键差别是状态组织和写入口是否统一，而不是类名。”

证据路径：yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabViewModel.kt；yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabFragment.kt

**常见踩坑：**说 MVI 天然无副作用；说 MVVM 一定是多个 LiveData；把框架作者能力归到业务调用者。

Q12【源码追问｜主讲】HomePinTab 的状态如何从网络流到 UI？

标准可说答案：“ViewModel 用 Pager 创建 ResponsePagingSource，收集 pager.flow，经 mediator 后用 setOnEach { copy(data = it) } 写入 PinTabState；Fragment 通过 collectFrom 把 PagingData 提交给 SuperAdapter。刷新由 Fragment 调 ViewModel，真正通过 pager.invalidate() 切换分页代际。”

证据路径：yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabViewModel.kt；yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/ResponsePagingSource.kt

**常见踩坑：**把 PagingData 当普通 List 拷贝；反复 new Pager；在 Fragment 同时维护另一份业务列表。

Q13【源码追问｜主讲】一次性事件为什么不建议放进持久 State？

标准可说答案：“State 适合可重放的页面真值；Toast、导航、礼物动画这类事件被重放可能在旋转或重建后重复执行。它们应使用带消费语义的 event/channel，并让真正的业务结果仍回到 State。需要注意 Channel 也可能丢事件，所以要按‘状态还是通知’选择，而不是一律套模板。”

证据路径：yyyyy-cdoe/VipManuscript/vip_manuscript/src/main/java/com/zhihu/android/vip/manuscript/manuscript/catalog/ManuscriptBillboardViewModel.kt

**常见踩坑：**Event 包装器既不支持多订阅又难测试；把支付成功这种业务真值只做成 Toast 事件。

Q14【基础｜主讲】Fragment 和 ViewModel 的职责边界怎么划？

标准可说答案：“Fragment 负责 View、adapter、生命周期绑定和把用户操作转成命令；ViewModel 负责业务状态、请求编排和跨重建保存。Paging 的 adapter LoadState 属于控件加载语义，可以留在 View；业务是否有下一页、权限或空态应在业务状态中表达。边界看状态所有权，不是简单规定‘Fragment 不能写逻辑’。”

证据路径：yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabFragment.kt；yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabViewModel.kt

**常见踩坑：**ViewModel 持有 Activity/View；Fragment 自己发请求并维护状态；把所有 UI 控件状态强行塞进业务 State。

Q15【压力追问】页面同时有 StateFlow、LiveData、Rx 和 adapter LoadState，怎么治理？

标准可说答案：“先为每类状态指定唯一 owner 和写入口，再在边界做一次转换，不让同一事实跨四套容器双向同步。新链路优先协程/State，旧 Rx 用生命周期明确的 adapter 收口；LoadState 只表达 Paging 加载。迁移要按页面或用例渐进进行，并用状态图和测试保护，不能一次重写全仓。”

证据路径：yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/mvx/MvxViewModel.kt；yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabFragment.kt

**常见踩坑：**双向桥接形成循环；重复订阅；把取消当错误；为“统一”而大范围重构无关业务。

四、Paging3

Q16【基础｜主讲】Paging3 的刷新链路是什么？

标准可说答案：“页面调用 viewModel.refresh()，ViewModel 执行 pager.invalidate()，当前 PagingSource 失效，factory 创建新 source，原有 Flow 继续产出新 generation。它不是清空 adapter 后手动再请求第一页。UI 还要区分 refresh、append、prepend 的 LoadState，才能正确展示全屏错误和尾部重试。”

证据路径：yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabViewModel.kt；yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/Pager.kt

**常见踩坑：**刷新时创建多个并行 Pager；旧请求结果回写新页面；把 append 失败展示成全屏空态。

Q17【源码追问｜主讲】ResponsePagingSource 是怎样适配业务接口的？

标准可说答案：“它根据 Refresh、Append、Prepend 分发到 onRefresh、onLoadMore、onLoadBefore，业务实现再用 resolveValue、resolveNextKey、resolvePreKey 组装 Page。业务接入者重点负责接口字段到 key/items 的映射、空页和首尾判断，不需要声称自己实现了 Paging3。”

证据路径：yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/ResponsePagingSource.kt；yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabViewModel.kt

**常见踩坑：**空列表仍返回同一个 nextKey 导致死循环；吞掉 CancellationException；next/pre key 与方向写反。

Q18【源码追问｜主讲】点赞和删除为什么用 PagerMediator，不直接刷新整页？

标准可说答案：“mediator 在当前 PagingData 上用 filter/map 做删除或替换，能立即反馈并保留滚动位置；服务端请求失败时再按业务语义回滚或刷新。它适合局部、可定位的变更，不适合结构大改或跨页排序重算。”

证据路径：yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/PagerMediator.kt；yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabViewModel.kt

**常见踩坑：**用 adapter position 代替稳定业务 id；新 generation 仍应用旧回调；只乐观更新不做失败策略。

Q19【源码追问｜主讲】从任意章节进入的双向分页最难在哪里？

标准可说答案：“需要围绕 initial key 同时计算 prepend 和 append，正确处理首尾 null、两个方向返回重复章节以及结果排序；目标章节还要稳定定位到可见位置。去重应基于稳定 section id，刷新要生成新代际，不能沿用旧方向的 key。”

证据路径：yyyyy-cdoe/VipManuscript/vip_manuscript/src/main/java/com/zhihu/android/vip/manuscript/manuscript/catalog/ManuscriptBillboardViewModel.kt；yyyyy-cdoe/VipManuscript/vip_manuscript/src/main/java/com/zhihu/android/vip/manuscript/manuscript/catalog/native_catalog/recommend/actor/NativeManuscriptAuthorFragment.kt

**常见踩坑：**只测从第一页进入；prepend 后顺序反转；目标章节重复；并发两向返回导致列表抖动。

Q20【压力追问】刷新后偶现旧数据覆盖新数据，你怎么定位？

标准可说答案：“先给 generation、query、PagingSource 实例和 requestId 打关联日志，确认旧 source 是否真正失效；再检查业务请求是否可取消、回调是否校验 generation，以及 mediator 是否缓存旧数据。测试用可控延迟让旧请求后返回，验证结果被丢弃。不能只在 UI 层加时间戳排序掩盖问题。”

证据路径：yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/ResponsePagingSource.kt；yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/PagerMediator.kt

**常见踩坑：**捕获所有 Throwable 后把取消上报成失败；日志不带 generation；用全局变量标记页面存活。

五、网络与 DNS

Q21【基础｜主讲】项目网络层为什么不让业务直接 new Retrofit？

标准可说答案：“业务通过 Net.createService() 依赖稳定门面，NetProviderImpl 统一创建并缓存 service；OkHttpFamily 再按 ClientType 组合 cookie、签名、DNS、拦截器、metrics 和 dispatcher。这样安全、监控和协议能力可集中治理，业务只维护 Service 契约。”

证据路径：yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/api/net/Net.java；yyyyy-cdoe/Net/net/src/main/java/com/zhihu/android/net/common/NetProviderImpl.java；yyyyy-cdoe/Net/net/src/main/java/com/zhihu/android/net/common/OkHttpFamilyProviderImpl.java

**常见踩坑：**只回答“封装 Retrofit”；在业务模块私加不同超时和证书策略；service cache 隐含持有不该是进程级的对象。

Q22【源码追问】一个请求慢，你如何拆分定位？

标准可说答案：“先用 OkHttp EventListener 拆 DNS、connect、TLS、request body、TTFB 和 response body；再看 dispatcher 排队、线程池饱和和重试；最后对照 interceptor 耗时与服务端 requestId。只有先分段，才知道该查 DNS、客户端排队、网络传输还是服务端。”
