KmReporter：成功率报表与告警闭环

定位标签：团队监控工具 / Bun + TypeScript

定位与归属边界

  • Bun/TypeScript 服务：查询成功/失败时序数据，按场景和平台计算成功率，与上周对比，渲染截图并发送企业消息；同时接收告警、静默 ACK 和关联任务。
  • 这是团队监控资产，个人实现或运维范围需本人确认，且要用 commit、部署记录与指标证明。
  • 源码含企业内网端点和 webhook 形态信息；本文不展示任何具体值。

检出与构建信息

  • 库存记录：分支 node，提交 5c7a6f2（2025-10-28），TypeScript 微型仓。
  • 构建/运行：README 要求 Bun；bun install，bun run ./src/server.ts。也有 Dockerfile、compose 与 Puppeteer。
  • package scripts 只有 dev/start，未检出 test/lint/typecheck/CI；本轮未启动服务，避免网络、告警和任务创建副作用。

结构与核心入口

  • src/server.ts：Bun HTTP 路由、Cron、告警静默、任务关联。
  • src/main.ts / fetch.ts：按日与上周同期拉取、解析并聚合 Android/iOS 场景数据。
  • src/inflater.ts：阈值着色、环比、异常项收集；render.ts 用 Puppeteer 截图。
  • src/task.ts / wework.ts：任务持久化、HMAC 鉴权与企业消息。

关键工作流

  1. 每日 Cron → 查询昨天与上周同期数据 → 按 scene/platform 合并 success/failure → 计算 rate。
  2. 按配置阈值标红异常，生成 HTML → Puppeteer 1200px、2x 截图 → 条件开启时发送企业消息。
  3. /warning 解析告警项与级别 → critical 建任务 → ACK map 限时静默 → 推送负责人并查询补充结果。
  4. 每周汇总未关闭任务；周期检查任务状态并清理关闭超过一个月的记录。

亮点与取舍

  • 从指标到截图、告警、静默和任务形成闭环；配置化阈值支持多场景。
  • Bun + Puppeteer 简化服务与图片产出，但 Chromium 成本高，Docker 使用 no-sandbox 增加安全要求。
  • 当前本地 JSON 持久化简单，却有并发覆盖、损坏和多实例不一致风险。

风险、测试与排查

  • P0：源码存在 webhook/内网信息形态；需轮换迁 secret、清历史和日志，服务端加鉴权与网络访问控制。
  • P1：fetchData() 无限重试且无请求 timeout；上游故障会永久占用任务。应限定次数、指数退避、熔断和 stale 标记。
  • P1：HTTP 路由可触发报告、告警、ACK 和任务操作，当前未见通用认证；日志还会输出告警正文/任务 JSON，需脱敏。
  • 排查：Cron/时区 → 查询区间与 target → tag 解析 → total/rate 分母 → 阈值配置 → Puppeteer → 消息开关/响应 → ACK/任务持久化。

指标异常案例与回归测试

fetch.ts 的 parseItem() 从点号分隔 tag 中推断 platform、scene 与 true/false，再把 iPhone/iPad 汇总成 iOS。这个规则应使用表驱动测试覆盖 AndroidPhone、Android、iPhone、iPad、未知平台、缺成功标记、同 scene 多序列和多 datapoint 求和。解析失败项当前被改写为 ignore；线上应同时增加丢弃计数和样例化错误日志，否则 tag 规范变化会让报表悄悄少数据。rate 的测试还要覆盖 success=0、failure=0、total=0 与跨序列合并，明确 total=0 显示 N/A 而非 0% 失败率。

Infalater 按 scene/platform 阈值决定标红，并将异常标题加入待建任务列表。可准备固定 config 与今天/上周两组 Map，断言配置顺序、未知 scene 追加、平台独立阈值、环比百分比和异常列表去重。环比计算遇到上周 total=0 时不能除零；当成功率提升但样本骤降时，报表应同时展示数量变化，避免只看百分比。生成 HTML 后不必每次启动真实 Chromium：先 snapshot 模板数据，少量集成测试再用 Puppeteer 验证截图存在、尺寸和关键文本。

告警闭环测试要使用 fake clock。第一次 warning 建立半小时静默，同一项目重复告警应被抑制；warning 升级 critical 应突破静默并尝试建任务；ACK 修改截止时间后，在到期前抑制、到期后重新发送。当前任务 Map 写入单个 JSON 文件，多请求并发会出现读改写丢失；至少应串行化写入并采用临时文件原子替换，更稳妥是迁 SQLite/数据库并对告警指纹加唯一约束。HTTP 路由测试还要覆盖未认证请求、畸形 JSON、超大正文和上游慢响应。

面试讲法

30 秒版本

KmReporter 把成功率监控做成查询、阈值、同比、截图、告警静默和任务闭环。核心是按 scene/platform 聚合成功失败量并渲染报表。当前主要风险是敏感配置、无限重试、HTTP 鉴权和 JSON 并发持久化；个人贡献范围需本人确认。

2 分钟版本

服务每天查询昨天与上周同期时序数据，parseItem 从 tag 识别平台、场景和成功标记，聚合后按配置阈值标红，再用 Puppeteer 生成 2x 图片。告警接口会解析 check item，critical 时关联任务，ACK map 控制静默，周任务再汇总未关闭项。闭环完整，但 fetch 无限重试没有 timeout，Bun 路由缺少清晰认证，敏感配置和日志需要治理，本地 JSON 也不适合多实例。重做会拆 query/domain/render/notify，加入有界重试、持久化事务、鉴权、幂等和测试。个人负责内容必须有 commit 与运行指标。

追问与回答

问题1：成功率怎么计算？

同一 scene/platform 的 true 与 false 计数求和，rate=success/(success+failure)；total 为 0 时显示 N/A。

问题2：为什么要对比上周同期？

能减少星期分布差异，但仍不是因果基线；节假日、流量结构和版本变化要单独标注。

问题3：无限重试有什么问题？

上游故障会永久占用执行并掩盖失败；需要 timeout、有界退避、熔断和可观测错误状态。

问题4：ACK 静默如何避免丢告警？

静默应按告警指纹和级别，升级可打破静默，并持久化过期时间；恢复通知也要单独处理。

问题5：Puppeteer no-sandbox 可以接受吗？

只在强隔离容器、最小权限和可信 HTML 下勉强使用；更好是启用浏览器 sandbox 或独立渲染服务。
