KmDetailPage：知识商品详情、原生 Header/Bottom 与 Hybrid 正文组件

1. 仓库定位与面试边界

yyyyy-cdoe/KmDetailPage 的当前定位是知识商品详情、原生 Header/Bottom 与 Hybrid 正文组件。主要技术形态为 Kotlin/Java、ViewModel、LiveData/Rx、WebView Bridge、播放器与购买服务。

面试应聚焦业务入口、状态编排、生命周期、异常兜底和组件集成。可以讲“我如何使用既有能力完成业务调用与排障”，但“本人实现/主导”的范围一律需本人确认，且应有 MR、commit、需求、评审或上线记录佐证。

5. 关键调用链与边界

源码直接链路：音频详情桥接

  1. AudioDetailFragment 直接创建 SkuAudioHeaderViewModel
  2. AudioDetailFragment 直接创建 SkuAudioHybridViewModel
  3. Fragment 观察 Hybrid ViewModel 的音频状态
  4. WebView ready 后 Fragment 调 postAudioChangeEventToWeb

边界说明：Header ViewModel 与 Hybrid ViewModel 是 Fragment 并列持有的状态源，不应画成互相调用。

6. 技术亮点与取舍

亮点

原生承接稳定的首屏、播放器和购买交互，Hybrid 承接正文与快速业务迭代。

取舍

兼顾性能与迭代，但两端协议、WebView ready 时序和页面销毁后的回调清理更复杂。

面试时不要把“使用了某框架”本身当亮点。更有价值的是说清楚为什么这样划分状态与生命周期、失败如何降级、版本/协议如何兼容，以及出现竞态时如何用真实调用链定位。

7. 仓库专属风险与排查顺序

下面的顺序按本仓真实状态 owner、服务与生命周期组织；前一步没有证据时，不跳到渲染层猜测。

  1. 第 1 步。先核对 AudioDetailFragment 的 businessId/businessType 和两个 ViewModel 是否拿到同一内容身份。
  2. 第 2 步。原生 Header 错误只看 SkuAudioHeaderViewModel 的详情状态；Web 音频状态只看 SkuAudioHybridViewModel。
  3. 第 3 步。状态已更新但 H5 未变化时检查 WebView ready 标记与 postAudioChangeEventToWeb 的调用时机。
  4. 第 4 步。页面重建后事件丢失时验证最新快照是否在 Web ready 后重放，而不是只依赖一次性增量事件。

8. 可直接复述的讲法

30 秒版本

KmDetailPage 的关键是原生与 Hybrid 双状态桥接。AudioDetailFragment 并列创建 SkuAudioHeaderViewModel 和 SkuAudioHybridViewModel；Fragment 观察音频状态，在 WebView ready 后调用 postAudioChangeEventToWeb。两个 ViewModel 不是上下游关系。 个人参与范围需本人确认。

2 分钟版本

AudioDetailFragment 同时负责原生 Header 和 Hybrid 正文。它直接创建 SkuAudioHeaderViewModel 管原生详情，也创建 SkuAudioHybridViewModel 管播放器相关状态；Fragment 观察后，等 WebView ready 再把音频变化通过 postAudioChangeEventToWeb 发给 H5。这样能复用 Web 内容又保留原生播放体验，但要处理 ready 之前的状态缓存、重建后的快照重放和双状态源内容身份一致。 若要把其中某个调用点写成个人成果，仍需本人确认并提供可核验记录。

9. 仓库专属追问与回答

1. 问：两个 ViewModel 谁调用谁？

答：源码显示它们都由 AudioDetailFragment 直接创建，没有证据证明二者互相调用。

2. 问：音频状态到了但 H5 没更新先看什么？

答：看 WebView 是否 ready，以及 Fragment 是否真正执行 postAudioChangeEventToWeb。

3. 问：为什么需要 ready 后重放快照？

答：事件可能早于 JS 环境建立；只发一次增量会永久丢失当前播放态。

4. 问：怎样测试 Native-Hybrid 桥？

答：先给 Hybrid ViewModel 发状态，再分别模拟 ready 前后，验证只在可消费时发送且能重放最新快照。

5. 问：面试中怎样说明自己在这个仓库里的贡献边界？

答：只陈述自己能用需求单、MR、commit 或评审记录证明的 kmdetailpage 调用点；公共框架、团队装配体系和历史代码不据为己有。无法核验的个人动作、结果和指标统一标为“需本人确认”。
