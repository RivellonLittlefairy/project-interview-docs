html-anything：本地 Agent 驱动的 HTML 编辑器

定位与归属边界

  • 本地优先的 agentic HTML 编辑器：浏览器提交内容，Next.js 服务端调用本机已登录的 coding-agent CLI，再流式返回 HTML。
  • 仓库 README 指向公开社区与多个上游项目；不能仅凭本地 checkout 把全仓成果归为个人。个人实现、评审或维护范围均需本人确认并由 commit/PR 支撑。
  • 安全边界是“单机可信用户 + loopback API”，不是可直接无认证暴露公网的 SaaS。

检出与构建信息

  • 库存记录：分支 main，提交 aea7498（2026-07-05），TypeScript/TSX，中型规模。
  • pnpm workspace 实际包含 next、e2e、cli；根包不代理子包命令。
  • 入口：pnpm install，再运行 pnpm -F @html-anything/next dev；CI 使用 Node 24。已记录 guard、Next/e2e typecheck 和 Playwright 用例发现通过；Node 20 下 Vitest 启动兼容错误，不等于业务测试失败。

结构与核心入口

  • next/src/app/api/convert/route.ts：加载 skill、组装 prompt、把 Agent 事件包装为 SSE。
  • next/src/lib/agents/{detect,argv,invoke}.ts：CLI 检测、参数/协议适配、子进程调用。
  • next/src/lib/use-convert.ts 与 store.ts：按 task 管理并发、取消和增量 HTML。
  • next/src/components/preview-pane.tsx：约 320ms 防抖刷新 iframe；middleware.ts 保护全部 API Host。

关键工作流

  1. 用户发起转换 → useConvert.run(taskId) 创建 AbortController → POST /api/convert。
  2. 服务端加载模板，invokeAgent() spawn 本机 CLI；不同 stdout 协议被归一为 delta/html/meta/error/done。
  3. SSE 增量进入 Zustand 的 task 状态，预览约 320ms 一次更新 srcDoc；结束时立即提交最终值。
  4. 取消从 fetch signal 传播到服务端，再到 child SIGTERM；同一 task 重跑先取消旧请求，不同 task 可并发。

亮点与取舍

  • 亮点：薄 adapter 隔离 CLI 差异；SSE 适合当前单向流；task 级 controller 形成端到端取消。
  • 亮点：Host allowlist 对准 DNS rebinding 与本地高权限 API；skill 安装包含 tar 预检、大小限制、拒绝链接、原子替换与回滚。
  • 取舍：预览防抖降低 iframe 重载成本，但 320ms 是经验值，仍需性能数据；外部 CLI 协议升级会让 adapter 漂移。

风险、测试与排查

  • P0：主预览同时启用 allow-scripts allow-same-origin，不能宣称对不可信 HTML 强隔离；优先独立 origin 或移除 same-origin。
  • P0：API 能指定 cwd/bin 并启动本机 CLI，不可无认证暴露公网；远程化需认证、租户隔离、沙箱执行器、队列、配额和审计。
  • P1：error 或非零 exit 仍可能最终显示 done；应把退出码、错误事件和 HTML 完整性纳入状态机。
  • 排查顺序：Host/middleware → Agent 检测与实际协议支持 → argv/stdout parser → SSE 网络流 → task 日志/退出码 → iframe 控制台。

面试讲法

30 秒版本

这是一个本地 Agent 驱动的 HTML 编辑器：Next API 调用本机 CLI，把多种 stdout 归一成 SSE，前端按 task 增量写入并防抖预览。最值得讲的是 adapter、端到端取消和 Host 防 DNS rebinding；最大风险是 iframe 同时开放 scripts 与 same-origin。个人贡献范围需本人确认。

2 分钟版本

我会先把边界讲清：它不是前端直接调用云模型，而是复用本机 CLI 登录态。检测层扫描 PATH，argv/parser adapter 收敛不同协议，convert route 负责 skill 与 SSE，前端用 taskId 隔离状态和 AbortController。取消链从浏览器一直传到子进程 SIGTERM。安全上，middleware 保护全部本地 API，skill 安装也按供应链输入预检；但 iframe 隔离声明过强、错误退出仍可能落成 done、cli package 的门禁弱于 next/e2e。若说“我负责”，只说能由本人 commit/PR 证明的 adapter、状态或安全范围。

追问与回答

问题1：为什么用 SSE 而不是 WebSocket？

当前核心是服务端向浏览器单向输出，普通 POST 与 AbortSignal 已覆盖输入和取消；需要双向工具确认或多路会话时再考虑 WebSocket。

问题2：如何保证多个任务互不干扰？

controller 和 Zustand 写操作都按 taskId 管理；同一 task 重跑取消旧 run，finally 还校验 controller 身份，避免旧请求清掉新请求。

问题3：检测到 CLI 就算支持吗？

不算。还必须有 prompt 传输、stdout parser、取消和退出语义；源码里存在 detection-only 协议。

问题4：Host allowlist 能解决所有安全问题吗？

不能。它防 DNS rebinding，不替代身份认证、Agent 文件/网络沙箱，也不解决生成 HTML 的 iframe 权限。

问题5：退出码怎样映射 UI？

至少区分 cancelled、failed、done、done-with-warning；非零退出或 error 进入 failed，只有成功且 HTML 最小校验通过才更新 baseline。
