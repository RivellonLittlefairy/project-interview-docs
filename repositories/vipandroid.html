盐言 Android 组件化原理：从 VipAndroid 壳工程看懂“组件怎样变成一个 App”

适合谁：已经写过几年 Android，平时会加依赖、调路由、调用组件 API，也处理过冲突，但对“Maven、Maven 仓库与 Gradle 是什么关系，壳工程为什么只剩一个 app 模块，AAR 怎么进 APK，API/实现为什么能分开，源码替换到底替换了什么”还没有形成完整模型。

这篇不从“怎样新建一个组件”讲起，而是从最终 APK 是怎么被组装出来的反推。盐言壳工程的关键价值不是承载大量页面代码，而是确定：这次构建选哪些组件、用哪个版本、替换成哪个 VIP 实现、哪些渠道差异生效、启动时按什么顺序初始化，以及不合规的依赖能不能进入产物。

1. 先给结论：盐言组件化到底是什么

开发阶段

业务被拆进独立仓库或独立 Gradle 模块，各自可以有实现模块、API 模块和 demo app。团队可以并行开发、独立发布。

集成阶段

组件通常发布成 Maven 制品（Android 组件多为 AAR）。VipAndroid 根据坐标和版本把它们放进同一张 Gradle 依赖图。

构建阶段

壳工程裁剪普通知乎组件，替换成盐言版本，合并 Manifest、资源、字节码和 SO，针对不同 flavor 生成 APK。

运行阶段

打进 APK 后不存在几十个独立 App。组件通过路由、接口服务、事件或任务系统协作，共用同一个 Android 进程和 Application 生命周期（特殊多进程除外）。

所以，盐言组件化不是“运行时下载几十个业务模块”，也不是简单地“把代码分文件夹”。它主要是一套编译期模块边界 + 制品化交付 + 壳工程统一装配 + 运行时解耦通信的工程体系。

2. 为什么要组件化：它解决的是组织和依赖问题

一个小 App 把所有代码放在 :app 里也能运行。项目变大后，真正难的不是 Activity 数量，而是：

  • 任何模块都能直接 import 任何实现类，修改一处会牵动很多地方；
  • 所有人同时改一个仓库，构建、评审、发布互相阻塞；
  • 普通知乎 App 与盐言 App 需要复用基础能力，但产品功能集合不同；
  • 一个组件升级后可能传递引入另一版组件或三方库，产生重复类、资源冲突或运行时崩溃；
  • 本地调试需要改组件源码，但正式构建又必须回到可追踪的 Maven 版本。

组件化的本质是控制变化传播。理想边界是：组件内部高内聚，对外只暴露稳定契约；调用方依赖契约，不依赖某个具体 Fragment、Repository 或数据库实现。

3. 先把几个容易混的词说清楚

名词在本工程中的含义容易产生的误解
壳工程VipAndroid。它是最终 Android application，负责产品配置、组件装配、渠道和产物治理。壳不是“空项目”，它仍有 Application、启动任务和少量盐言专属适配代码。
业务组件例如 vip_comment、vip_growth、vip_manuscript。通常发布成 AAR 并进入依赖图。组件不一定等于一个 Git 仓库；一个仓库里可以有实现、API、widget 和 demo 多个模块。
API 模块放接口、跨组件模型或少量契约类型。例如 comment-api 中的 ICommentLikeViewProvider。API 模块不是 HTTP API 的同义词，它更接近“给其他组件看的编译契约”。
实现模块真正的页面、网络、存储和接口实现。例如 comment 中的 CommentLikeViewProviderImpl。调用方不应该为了一个能力直接依赖实现模块里的内部类。
基础库/新分层library、foundation、service、feature、sharedui 等坐标体系。不是所有能力都沿用老的 com.zhihu.android.component 分组，工程里存在新旧架构并行。
源码依赖把某个 Maven 坐标临时替换成本地 Gradle project，用于联调。不是运行时热更新，也不是复制源码到壳工程。

4. Maven 是包管理工具吗：先分清工具、仓库和制品

先回答：把 Maven 简称为“包管理工具”方便交流，但不够准确。Apache Maven 是 Java 生态的构建与依赖管理工具；Maven 仓库是存放和分发 JAR、AAR、POM 等制品的仓库约定。VipAndroid 真正执行构建的是 Gradle，它只是按 Maven 仓库规则去解析和下载组件。

4.1 四个角色不要混为一谈

角色它负责什么在 VipAndroid 中怎样理解
Apache MavenJava 生态的一套构建与依赖管理工具，普及了 POM、GAV 坐标和标准仓库布局。这里不是用 Maven 命令构建 App；“Maven 依赖”通常是在说依赖来自 Maven 格式仓库。
Maven 仓库按坐标保存制品及元数据的目录或服务，可以是公共仓库、公司私服、本地目录或 mavenLocal()。repositories 配置告诉 Gradle 去哪里寻找盐言组件。
Gradle读取构建脚本、建立任务图、解析依赖图并执行构建。读取 app/build.gradle 中的组件坐标，选择版本和变体，命中缓存或从仓库下载。
Android Gradle Plugin给 Gradle 增加 Android 专用的 variant、Manifest、资源、DEX、签名和 APK/AAB 打包能力。把解析到的 AAR/JAR 和 :app 源码加工成最终 Android 产物。

可以把关系记成一句话：Gradle 是施工队，Android Gradle Plugin 提供 Android 施工工艺，Maven 仓库是材料仓库，AAR/JAR 是材料，POM 或 Gradle Module Metadata 是材料清单和依赖说明。

4.2 GAV 坐标：Gradle 怎样准确找到一个组件

盐言评论组件在当前版本表中可以组成下面这个真实坐标：

com.zhihu.android.component:vip_comment:9.12.0.15
└────────── groupId ──────────┘ └artifactId┘ └version┘
  • groupId：组织或命名空间，这里是 com.zhihu.android.component；
  • artifactId：具体发布模块，这里是 vip_comment；
  • version：不可省略的版本标识，这里由 version.gradle 集中维护。

仓库通常会把 group 中的点转换成目录层级，因此这个坐标大致映射到 com/zhihu/android/component/vip_comment/9.12.0.15/。目录下可能同时有 vip_comment-9.12.0.15.aar、.pom、.module 和校验文件。坐标不是文件本身，它是定位某个模块版本的地址信息。

4.3 repositories 决定“去哪里找”，dependencies 决定“需要什么”

repositories {
    maven { url = uri("公司 Maven 私服") }
    mavenLocal()
}

dependencies {
    implementation("com.zhihu.android.component:vip_comment:9.12.0.15")
}

repositories 只是声明候选查找位置，不等于马上下载；dependencies 给当前 configuration 的依赖图增加需求，也不直接指定文件从哪个 URL 下载。Gradle 会结合仓库顺序、缓存、元数据、variant 属性和版本规则统一解析。

VipAndroid 的 settings.gradle 应用了 gradle/auto_maven_repo.gradle；该脚本定义了按本地配置加入指定 Maven 目录或 mavenLocal() 的能力。当前根 build.gradle 只在 buildscript.repositories 中调用这个本地仓库闭包，而普通工程依赖的 allprojects.repositories 配置公司 Maven 私服；app/build.gradle 再把 allComponents 转换成具体组件坐标。不能把“存在本地仓库脚本”直接理解成“所有 App 依赖都会优先从本地取”。

4.4 POM 是说明书，不是 Android 代码包

POM 是 Project Object Model 的缩写，常见形式是 XML。一个组件的 POM 可以声明自己的名称、打包类型、直接依赖、版本、scope 和 exclusions；Gradle 读取它以后，才知道这个 AAR 还需要哪些其他库。POM 里没有评论页面的 class 和资源，真正的 Android 内容在 AAR 中。

Gradle Module Metadata 通常是 .module JSON 文件，能比传统 POM 更完整地描述 variant、属性、能力以及 API/运行时依赖差异，这是 Gradle 的通用能力。但当前 VipAndroid 公司仓库块明确只配置了 mavenPom() 与 artifact()，没有启用 gradleMetadata()：它会读取 POM；若 POM 缺失，仍可直接发现 AAR/JAR 制品，但这时没有 POM 提供的传递依赖信息；该仓库配置不会消费 .module。所以不能把 Gradle 的全部能力等同于当前工程实际启用的元数据源。

4.5 Gradle 从一行坐标到可编译输入，经历了什么

  1. 读取当前 variant 对应 configuration 中的直接依赖坐标；
  2. 按仓库声明顺序和内容过滤规则查找模块元数据；
  3. 读取仓库允许的元数据并选择实际文件；对当前公司仓库就是读取 POM，或在缺少 POM 时以 artifact() 发现制品；
  4. 展开元数据中声明的依赖，形成包含直接依赖和传递依赖的图；
  5. 同一模块出现多个版本时执行冲突解决，并应用 force、约束、平台/BOM 或替换规则；
  6. 从 Gradle 缓存复用已有文件，或下载 AAR/JAR 和元数据并写入缓存；
  7. 把最终选中的文件交给 Java/Kotlin 编译器及 Android Gradle Plugin 后续处理。

“Gradle 默认总选数字最大的版本”也是过度简化。它会按自己的版本比较和冲突规则选择候选版本，但 version constraint、strictly、平台、resolution strategy、dependency substitution 等都可以改变结果。最终以目标 configuration 的 dependencies/dependencyInsight 输出为准。

4.6 Gradle 缓存了什么：为什么仓库有新包，本地却没变化

Gradle 不只是缓存一个 AAR 文件。理解缓存最好拆成三层：

  • 元数据缓存：某个坐标有哪些版本、POM 声明了哪些传递依赖、某次查询没有找到模块等解析结果；
  • 制品缓存：实际下载的 AAR、JAR、POM 以及按内容校验的文件；
  • 转换缓存：AAR 解压、Jetifier 或其他 transform 的中间结果，输入和参数未变时可以复用。
版本类型含义缓存时最容易误解的点
固定版本例如 9.12.0.15，坐标明确指向一个发布版本。仓库应把它当作不可变制品；覆盖发布同一 GAV 会破坏可复现性，不能指望每次构建自动发现内容被偷换。
动态版本例如 1.+ 或 latest.release，需要先解析“当前匹配哪个版本”。“动态选择结果”会缓存，在缓存期内仓库出现新版本也可能仍使用旧的解析结果。
Changing module同一个版本坐标被明确允许内容变化，Maven SNAPSHOT 是典型场景。是否 changing 取决于依赖/仓库语义与配置；版本名里出现 TEMP 不会自动让它成为 changing module。

当前 VipAndroid 在 configurations.all 中只对 CI 环境设置 cacheChangingModulesFor 30 minutes，含义是 CI 对已经被识别为 changing 的模块每 30 分钟重新检查一次，并不是所有组件每 30 分钟强制下载，也不改变固定版本应不可变的原则。

排查“版本没更新”时，先用 dependencyInsight 确认最终选中的坐标和选择原因；确认确实是缓存问题后，再使用 --refresh-dependencies 让 Gradle 重新校验依赖状态。不要一上来删除整个 Gradle 缓存，因为那会丢失定位证据并显著放大构建成本。

.\gradlew :app:dependencyInsight --dependency vip_comment --configuration devDebugRuntimeClasspath
.\gradlew --refresh-dependencies :app:assembleDevDebug

4.7 本地仓库、公司私服和公共仓库有什么区别

位置典型用途要注意什么
mavenLocal()从本机 Maven 本地仓库读取临时发布物，适合快速验证。只对本机生效，最容易出现“我这里能编，CI 找不到”或旧版本污染。
本地目录 Maven 仓库开发脚本把指定文件夹当成 Maven 布局仓库。仍依赖正确的目录结构、坐标和元数据，不等于直接把 AAR 拖进 libs。
公司 Maven 私服保存内部组件、代理公共制品、统一权限和版本发布。正式构建更可复现，但发布权限、版本不可变策略和凭据都需要治理。
公共仓库提供公开三方库，例如 Android/Java 生态常用组件。需要考虑可用性、供应链安全、许可证以及公司镜像策略。

5. 最重要的基础模型：分清三个阶段

阶段一：配置与解析Gradle 读取版本、组件清单、排除和替换规则，求出依赖图。
→
阶段二：编译与打包组件 AAR/源码的 Manifest、资源、class、assets、SO 被处理并合进产物。
→
阶段三：App 运行Application 启动，任务图初始化能力，页面通过路由或接口服务通信。

很多面试回答混乱，都是因为把三个阶段揉在一起。例如：

  • dependencyReplace 是构建期规则，不会在用户点击页面时再替换类；
  • sourcecode.properties 改的是编译输入，不会让线上 APK 动态读取你的本地目录；
  • ZRouter.open() 和 InstanceProvider.get() 是运行时通信，它们的目标代码必须先在构建期进入 APK 并完成注册；
  • TaskManager.json 描述运行时初始化依赖，但任务类来自已经装配进 APK 的壳或组件。

6. 为什么 settings.gradle 看起来只有一个 app 模块

VipAndroid 的 settings.gradle 明确 include ':app'，随后应用 gradle/sourcecode.gradle。这不代表整个盐言只有一个业务模块，而是代表默认集成形态以远程 Maven 制品为主。

壳源码 project默认只有 :app，负责生成最终 APK。
远程组件制品app/build.gradle 通过 group:artifact:version 依赖大量 AAR/JAR，它们不必出现在 settings 的 include 列表里。
临时本地 project启用源码替换时，sourcecode.gradle 才会动态 include 相邻仓库里的模块。

这是理解壳工程的第一个关键点：Gradle project 数量不等于最终 APK 里业务能力的数量。Maven AAR 也是编译输入，只是它已经由别的仓库构建并发布好了。

7. AAR 是什么：它怎样从组件产物变成 APK 的一部分

先纠正拼写：是 AAR，不是 arr。AAR 全称 Android Archive，是 Android Library 的发布归档。它通常是一个 ZIP 格式的构建输入，不能直接安装；APK 才是可安装的应用产物。

组件源码Android Library project 包含 Kotlin/Java、Manifest、资源和构建脚本。
→
发布制品构建得到 AAR，并发布 POM/.module 等依赖元数据。
→
Maven 仓库按 GAV 坐标保存 AAR 与元数据。
→
Gradle 解析选择版本和变体，下载 AAR/JAR 及传递依赖。
→
AGP 打包分别处理 Manifest、资源、class、SO，生成 APK/AAB。

7.1 AAR 里面通常有什么

AAR 可以用 ZIP 工具打开，但下面是典型内容，不是每个 AAR 都必须包含的固定清单：

路径/文件内容进入 App 后怎样处理
AndroidManifest.xml库声明的组件、权限、uses-feature 或元数据。参与 Manifest Merger，不是简单覆盖 app Manifest。
classes.jarJava/Kotlin 编译后的 JVM class。和 App、其他库的 class 一起交给 D8/R8，最后生成 DEX。
res/layout、drawable、string、style 等 Android 资源。由 AAPT2 编译/链接并进入最终资源表。
assets/需要按原始文件方式读取的资产。合入应用 assets，运行时通过 AssetManager 访问。
jni/<abi>/*.so按 ABI 分类的原生动态库。结合 abiFilters、split 和打包规则进入对应 ABI 产物。
R.txt/public.txt资源符号或公开资源信息，是否存在取决于 AGP/发布方式。供构建工具处理；R.txt 不是运行时直接加载的 R 类。
consumer-rules.pro/proguard.txt库提供给最终消费者的 R8/ProGuard 保留规则。在 App 开启压缩时并入最终程序的 shrink/optimize/obfuscate 配置。
libs/、lint、Prefab 等可选的嵌入 JAR、lint 规则或 Native 发布信息。由对应工具链继续消费，并非所有 AAR 都有。

普通 AAR 默认也不是“胖包”：它通常不会把自己依赖的所有 AAR/JAR 全部塞进归档，传递依赖主要由 POM 或 .module 描述，再由消费方 Gradle 继续解析。fat AAR 是额外的打包策略，容易带来重复类和版本不可见问题，不能把它当成普通 AAR 的默认行为。

7.2 JAR、AAR、APK 和本地 Gradle Project 的区别

形态主要内容支持 Android res/Manifest/JNI能否直接安装典型用途
JARJVM class 和普通资源/元数据。不能作为 Android Library 那样承载并合并 res/、Manifest 和 JNI 目录语义。不能纯 Java/Kotlin 工具库。
AARclass、Android 资源、Manifest、可选 SO 和消费者规则。支持不能发布 Android Library。
APKDEX、最终资源、合并 Manifest、签名和所需 SO 等完整应用内容。已经是处理后的最终结果可以安装、测试和分发应用。
本地 Gradle Project源码、构建脚本、任务、source set 和 variant。由该模块在本次构建中产生通常不能；application project 最终可生成 APK多模块源码协作和本地联调。

project(':vip_comment') 不是“没有压缩的 AAR”。本地 project 会以源码、任务和 variant 参与当前构建；AAR 是该 Library 某个发布变体已经生成好的归档。两种输入最终可以提供相近能力，但构建参数和依赖暴露可能不同。

7.3 AAR 进入 APK 时到底发生了什么

  1. 解析与展开：Gradle 先选定目标 variant 的 AAR、JAR、本地模块输出及其传递依赖，并缓存/展开归档。
  2. Manifest 合并：Manifest Merger 合并 app、直接库和传递库的 Manifest；优先级与 tools: 指令共同决定结果。
  3. 资源编译与链接：AAPT2 处理各库资源和 app 资源，生成最终资源表；同名资源要结合 overlay 优先级判断，不是所有重名都必然报错。
  4. 字节码转 DEX：D8 把 app 与依赖 class 转成 DEX；若启用代码压缩，R8 会基于整个最终程序图做 shrink、optimize 和 obfuscate。
  5. 消费者规则生效：AAR 发布的 consumer ProGuard 规则传给最终 App，保护反射、序列化、路由或 JNI 需要的类成员。
  6. Native 库处理：各 AAR 的 SO 按 ABI、过滤、split 与冲突规则进入最终 APK/AAB 对应产物。
  7. 打包与签名：构建工具把处理后的 DEX、资源、Manifest、assets 和 SO 组装、对齐并签名。最终 APK 通常不会原样嵌套那些 .aar 文件。

因此组件化不会给 Android 系统凭空增加新的隔离边界。除非显式使用独立进程、动态特性或插件技术，普通 AAR 组件最后仍进入同一应用运行环境。这正是为什么重复类、Manifest、资源、版本和 SO 问题通常由壳工程统一暴露。

7.4 引入 AAR 后常见故障，分别是哪一层出了问题

现象根因模型优先检查
Duplicate class两条输入路径提供了同一个全限定类名，常见于本地 module 与远程 AAR 同时存在、两个坐标重复封装，或 fat AAR 内嵌依赖。最终依赖图、dependencyInsight、AAR 内的 classes.jar 和 libs/。
资源覆盖/冲突相同资源键出现在多个输入，或 overlay、生成资源和资源可见性不符合预期。资源命名、依赖版本、source set 优先级和 merged resources；不要看到同名就直接下结论。
Manifest merge failed同一节点或属性无法按默认合并规则确定结果。merged manifest/report、provider authority、exported、权限和 application 属性；理解后再用 tools:replace。
NoSuchMethodError编译时看到的方法与运行时最终装入的 class 版本不一致，是二进制兼容问题，不是普通的“方法没写”。目标 variant 的 runtimeClasspath、版本冲突结果、force/替换规则和重复打包。
UnsatisfiedLinkError/dlopen failed设备所需 ABI 的 SO 没进入产物、同名 SO 选错，或 SO 自己依赖的库无法加载。设备 ABI、AAR 的 jni/、abiFilters、splits、APK 内 SO 清单及其依赖。
接口能编译但功能不可用API AAR 在 classpath 中，但实现 AAR 被裁剪、未发布配套版本或运行时注册缺失。实现坐标、依赖替换、最终 APK 内容、AutoService/路由生成物与初始化时机。

排错时不要只问“这个 AAR 在不在”。要连续回答四个问题：最终选中了哪个版本和 variant？它带来了哪些传递依赖？Manifest、资源、class、JNI 分别怎样进入应用？错误发生在解析、编译、打包还是运行时？

8. 盐言构建期组装：从候选组件到最终依赖图

version.gradle集中记录组件和基础库版本。
→
allComponents声明候选业务组件并循环添加 api 依赖。
→
全局 exclude用 VIP_APP_REMOVED_COMPONENTS 裁掉盐言不需要的普通知乎组件。
→
dependencyReplace把共用实现/接口换成 VIP 版本或渠道 no-op 版本。
→
版本锁与门禁收敛依赖图，检查未登记三方库、TEMP 版本和 SO 完整性。

8.1 version.gradle：统一回答“用哪个版本”

version.gradle 中同时存在老组件表 versions.component，以及 foundation、feature、service、sharedui 等新分层版本表。例如当前可见 vip_comment、vip_growth、vip_manuscript、vip_kmaudio、vip_km_home 等版本。

集中版本表的价值不是少写几个字符串，而是让壳工程对最终产品版本负责。组件 A 传递依赖某版本、组件 B 传递依赖另一版本时，壳可以统一收敛；代价是升级不能只看单个组件编译通过，还要验证整个产品依赖图兼容。

8.2 allComponents：声明“候选组件集合”

app/build.gradle 当前静态列出 75 个 allComponents 候选项，并在 dependencies 中循环执行：

allComponents.forEach { name ->
    api "${ZHIHU_COMPONENT_GROUP}:${name}:${versions.component[name]}"
}

该工程的构建插件允许在 application 中使用 api。由于 :app 已经是最终应用，通常没有需要消费它的上游模块，所以 API 暴露不是这里的主要设计收益；关键结果是这些坐标进入对应 configuration 的依赖解析。这里批量声明的是“候选集合”，不是最终一定保留的功能清单。

8.3 VIP_APP_REMOVED_COMPONENTS：做产品减法

盐言继承自更大的知乎主工程体系，但产品不需要完整社区能力。配置通过 configurations.all 对 com.zhihu.android.component 分组做全局 exclude，移除 feed、search、community、profile、kmarket、premium、kmaudio 等普通实现。

当前列表有 51 行组件名，其中 avg 重复，按唯一名字是 50 个；与 75 个候选集合静态相交 42 个，做集合差后剩 33 个候选项。这个 33 只是帮助理解“减法”的静态口径，不是最终 APK 的全部依赖数：壳还显式依赖 feature/service/foundation，组件也会带入传递依赖，替换规则还会改变节点。

8.4 dependencyReplace：不是只删除，还要换成盐言实现

仅排除普通组件会让调用方缺实现。因此壳工程对若干稳定契约做成对替换：

普通能力盐言能力为什么接口也常要换
growthvip_growthVIP 版本可能扩展或调整契约，壳同时替换 growth-api。
commentvip_comment实现、API 和评论编辑 widget 都有对应替换。
passport_uivip_passport_ui登录页面和 passport API 要保持配套版本。
accountvip_account账号实现和 account-api 同步切换。
pushvip_push从老 component 坐标换到新的 feature 坐标。

这体现了组件化里一个很重要的设计：调用侧尽量面向接口，产品壳决定装哪个实现。它类似依赖倒置，但这里的“注入”有两层：构建期先选择哪套 AAR，运行时再由服务注册表找到接口实现。

8.5 渠道替换：同一能力可以装真实实现或 no-op

dependencyReplace 还会根据 flavor 替换实现，例如预装渠道把某些 SDK 换成 no-op，Play 渠道对不兼容能力使用空实现。原理仍是构建期改变依赖图：调用代码可以依赖同一组接口，但不同产物包含不同实现。

9. 本地源码替换：为什么改了组件源码，壳可以直接编译

正常情况下，vip_manuscript 是一个 Maven 坐标，对应已发布 AAR。联调时在 sourcecode.properties 配置：

com.zhihu.android.component:vip_manuscript=/path/to/VipManuscript/vip_manuscript

gradle/sourcecode.gradle 做的不是“优先读本地文件”这么简单，而是一套 Gradle 模型变换：

  1. 解析坐标、源码路径和本地 project 名；
  2. 检查目标 build.gradle 中的 group/name 是否与坐标一致，防止替错模块；
  3. 如果旁边存在符合约定的 {name}-api，把 API 模块一起加入；
  4. 解析组件里声明的 usingProject，补上联调需要的相邻源码模块；
  5. 在 settings 阶段动态 include 本地 project；
  6. 在依赖配置阶段，把匹配的 Maven module 替换为 project(':name')；
  7. 通过 dependencySubstitution 继续覆盖传递依赖中的同一坐标。

所以源码联调失败时，不要只看 Android Studio 是否打开了那个目录。要确认三件事：坐标是否一致、project 是否被 settings include、目标 configuration 里 Maven 节点是否真正被 project 节点替换。

10. API 与实现分离：编译依赖为什么能降低耦合

以当前 VipComment 仓库为例，它包含 comment-api、comment、comment-widget-editor 和用于独立调试的 app。其中：

  • comment-api 发布为 com.zhihu.android.api:comment-api，包含 ICommentLikeViewProvider 等契约；
  • comment 发布为 com.zhihu.android.component:comment，包含真正的评论 UI 与数据实现；
  • CommentLikeViewProviderImpl 实现接口，并用 @AutoService(ICommentLikeViewProvider.class) 注册；
  • 其他组件只要依赖 API，就能按接口获取能力，不需要 import LikeView 这个内部实现。
调用组件只认识 API 接口。
→
InstanceProvider按接口类型查找已注册实现。
→
@AutoService 实现由真正业务组件提供对象或行为。

原理上，这把“编译时知道具体类”改成了“编译时只知道接口，运行时再绑定实现”。收益是实现可替换、调用方重新编译范围更小；代价是缺少实现时可能返回空值或启动后才暴露问题，所以代码里既有 get，也有更安全的 optional 用法。

11. 盐言组件层级怎么设计：新旧体系并存，依赖方向比名字重要

先给结论：盐言不是把所有模块硬塞进一条绝对层级链，而是按职责把代码分成产品装配、业务功能、可复用服务/共享 UI、基础设施几类，再用 API 契约控制跨边界调用。当前源码能确认这些坐标分类和壳的直接依赖，但不能证明工程已经强制执行一张严格的 feature → service → foundation 依赖 DAG。

11.1 先看全局职责模型

产品装配层：VipAndroid application 壳决定本次产品选择哪些组件、使用哪些版本、排除或替换哪些实现、启用哪个 flavor，并对最终 APK 的依赖和产物负责。
业务功能层：feature 与旧 business component承载用户可感知的完整业务能力，例如内容生产、评论、阅读、会员业务或 RN 业务入口。新旧坐标体系会同时存在。
跨业务复用层：service 与 shareduiservice 偏可复用能力或 SDK 封装，sharedui 偏跨业务共用界面。两者更像并列职责，不要机械理解成 service 一定高于或低于 sharedui。
基础设施层：foundation、library 与三方库提供任务调度、线程、存储、网络、日志、RN 基建等通用能力，原则上不应该反向依赖具体产品业务。

API 契约不是简单的“第五层”。*-api 更像穿过层级边界的插座：上层依赖接口，真正实现由业务组件或服务组件提供。它可以位于业务边界、服务边界或基础能力边界，关键是调用方只看到稳定契约，不直接 import 对方内部实现。

11.2 旧组件体系和新组件体系为什么同时存在

体系当前可见分类应该怎样理解
旧体系com.zhihu.android.component:*、com.zhihu.android.api:*、少量 component.api，以及 com.zhihu.android.library:*大量历史业务仍按 component + API + library 的方式发布，VipAndroid 的 allComponents 主要装配这一体系。
新体系feature、service、sharedui、foundationversion.gradle 明确把它们称为“新架构组件层级”，坐标和 modules.json 的 layer 元数据用于版本登记与解析。
预留分类limited、coreui当前版本文件只看到空 Map 声明，没有对应成员，最多说明分类被预留，不能当作已经落地的实际层。

这不是“旧体系在下面、新体系在上面”两套纵向层级，而是迁移期间并行存在的两套分类方式。例如构建规则可以把旧 component/API 坐标替换为新的 feature 坐标；同时，仍有大量旧 component 与 API 被壳直接依赖。判断一个模块承担什么职责，应看坐标、构建依赖和源码内容，而不是只看它属于新还是旧。

11.3 推荐依赖方向：上层使用下层能力，跨业务只看契约

VipAndroid 壳选择并装配各层制品。
→
Feature / Component组织业务流程与页面。
→
Service / Shared UI提供复用能力与界面。
→
Foundation / Library提供通用基础设施。
  • 壳工程可以直接装配业务、服务、共享 UI 和基础设施，因为它对最终产品负责；
  • 业务功能可以依赖基础能力，也可以依赖其他业务公开的 API，但原则上不直接依赖其他业务的实现模块；
  • Service 应提供可复用能力或稳定契约，不应悄悄承载只服务于某个页面的完整业务流程；
  • Shared UI 应复用视觉和交互能力，不应因为“多个页面都用”就把业务状态机、网络流程全部搬进去；
  • Foundation/Library 应保持业务无关，若它反向依赖某个 Feature，就会形成倒置依赖和潜在环；
  • common、base、common-dep 只是名字，聚合很多依赖并不会自动让模块成为合理的底层。

11.4 当前源码证明了什么，没有证明什么

可以确认不能直接断言
version.gradle 显式声明新架构的 foundation、feature、service、sharedui 等版本容器。每一个容器都已有实际模块；当前 limited/coreui 仍只是空分类。
app/build.gradle 同时直接依赖 feature、service、sharedui、foundation、library 和旧 component/API。这些类型之间一定存在统一且强制的单向依赖顺序。
lock_versions.gradle 能根据模块 layer/alias 找集中版本，并在缺少 layer 时回退旧版本表。版本锁脚本就是架构依赖检查器，或者能禁止基础层引用业务层。
旧 push、zcode 等坐标存在替换到新 feature 坐标的迁移规则。所有旧 component 都已经迁移完成，或旧 API 体系已经废弃。

因此，这套层级首先是一套职责与依赖方向设计，其次才是坐标命名。坐标能帮助版本管理和识别模块角色，但真正判断是否分层合理，仍要查看目标 variant 的依赖图和模块源码。

11.5 设计或评审一个组件时，问这六个问题

  1. 谁拥有这段完整业务流程，它应该进入 Feature/Component 还是可复用 Service？
  2. 调用方依赖的是稳定 API，还是直接 import 了另一个业务的实现类？
  3. Foundation/Library 是否反向引用了具体业务，形成方向倒置或循环依赖？
  4. Shared UI 里放的是可复用界面能力，还是被包装成公共代码的业务流程？
  5. common/base 是否变成无边界的依赖垃圾桶，向所有上层泄漏传递依赖？
  6. 产品壳能否在不修改调用方业务代码的情况下，裁剪、替换或降级某个实现？

12. 组件打进 APK 后，运行时怎样通信

12.1 接口服务：适合“我要一个能力”

AutoService + InstanceProvider 适合返回对象、构建页面参数或执行明确能力。KnowledgeMarket 中 KmarketFragmentInterfaceImpl 实现 KmarketFragmentInterface；KmBase 的路由工具使用 InstanceProvider.optional(KmarketFragmentInterface.class) 获取它。调用方不需要知道具体 Fragment 位于哪个实现仓。

12.2 路由：适合“我要打开一个目标”

组件用路由注解注册 URL 与页面/分发器的关系，调用方用 ZRouter 打开 URL。VipAndroid Manifest 中的 VipRouterPortalActivity 对外接收 zhvip:// scheme，注释明确它用于外部打开和组件间跳转。

路由把“目标类名”换成“协议 URL”。这能避免跨组件直接 import 页面类，但并不等于完全无契约：URL、参数名、返回结果和登录拦截规则本身就是协议，仍需要版本兼容和测试。

12.3 启动任务：适合“能力要按依赖顺序初始化”

ZhihuApplication.onCreate() 经过隐私进程、SafeBoot 和进程判断后，把真正初始化交给 ZhihuApplicationDelegate.onCreate(this)。壳中的 TaskManager.json 再描述大量任务的 scheduler、dependsOn、finalizedBy 和 delay。

例如 T_VipNetInit 依赖 crash 与广告预初始化，网络完成后再触发 MQTT、PostNet 和首页预请求；账号初始化依赖网络，登录初始化又依赖账号、网络、埋点等。这本质上是一张有向依赖图，任务调度器按边约束执行顺序，而不是在 Application 里顺序写几十行 init。

12.4 生命周期聚合：适合“多个组件都关心全局事件”

CrossLifecycleManager.json 列出账号、网络、评论、推送、RN、资源等生命周期实现。壳把全局 Activity/Application 事件汇总后分发给多个能力，避免每个组件各自侵入 Application。代价是回调数量多、顺序隐含时，排障要回到注册清单和真实调度顺序。

13. 版本冲突为什么总在壳工程爆出来

假设 A 依赖 common:1，B 依赖 common:2。Gradle 必须在同一 configuration 中选一个版本。若二进制不兼容，编译可能通过，运行时却出现 NoSuchMethodError；若两个不同坐标含同名 class，则可能直接 duplicate class。

VipAndroid 有多层治理：

  • lock_versions.gradle 读取 META-INF/modules.json，把坐标 alias 映射到集中版本；
  • lock_third_versions.gradle 锁定三方库版本；
  • lock_versions_for_vip.gradle 对盐言暂未适配的新版本单独 force；
  • componentInsight 生成 app/build/componentInsight.json，用来查看组件之间的依赖关系；
  • check_deps.gradle 检查三方库登记、允许渠道以及生产构建中的 TEMP 版本。

需要注意，force 不是免费的“修复冲突”。它只是替依赖图做选择；被强制升级/降级的调用方是否二进制兼容，仍需要编译、启动和关键链路验证。

14. 组件化与多渠道：为什么同一份代码能产出很多包

VipAndroid 的 productFlavors 包含 dev、alpha、mr、beta、market、minor，以及华为、小米、OPPO、VIVO、预装等渠道。最终 variant 是 flavor 与 buildType 的组合，例如 devDebug 或 huaweiRelease。

渠道差异可以来自四个层面：

  1. 依赖差异：xxxApi 只给某个 flavor 加组件，或 dependencyReplace 换 no-op；
  2. 源码差异：src/dev、src/beta、src/huawei 覆盖同名类或添加渠道类；
  3. Manifest/资源差异：各 source set 的 Manifest 与资源参与合并；
  4. BuildConfig 差异：例如 INSTALLER_ID 和内部调试开关。

因此“dev 能跑、release 崩”不能只归结为混淆。两者可能从依赖图、源码集、Manifest、SDK 初始化和 ProGuard 任一层开始不同。

15. 壳工程为什么要做最后一道产物门禁

单个组件仓只能证明“我自己能编译”，不能证明“所有能力组装后仍然正确”。VipAndroid 在接近最终产物的位置做统一检查：

  • 三方依赖白名单：未登记或不允许进入当前 flavor 的库会触发异常；
  • TEMP 版本检查：防止临时组件版本进入正式包；
  • SO 对齐：handleSo() 比较 arm64-v8a 与 armeabi-v7a 的 SO 名称，白名单外缺失会直接中断构建；
  • 资源与包体治理：资源压缩、Resource Guard、包大小分析按构建条件接入；
  • CI 与渠道打包：Athena 配置覆盖版本发车、打包、部署和热修复流程。

这说明壳工程的职责不是“把依赖都写进去就结束”，而是对最终交付物负责：能否解析、是否合规、架构是否齐全、各渠道是否能安装运行。

16. 用一条完整链把原理串起来

  1. 评论团队在独立仓库开发 comment-api 与 comment，发布版本化制品；
  2. VipAndroid 在 version.gradle 记录 vip_comment 版本；
  3. allComponents 把 VIP 评论实现加入候选依赖；
  4. 全局配置排除普通 comment/comment-api；
  5. dependencyReplace 确保传递依赖里出现普通评论坐标时也切换到 VIP 版本；
  6. Gradle 解析唯一依赖图，Android Gradle Plugin 合并评论组件的 Manifest、资源和 class；
  7. 注解处理/注册机制让 @AutoService 实现和路由表在运行时可发现；
  8. Application 启动任务完成网络、账号等前置能力；
  9. 其他组件通过 API 服务或路由调用评论能力，而不是直接 new 评论内部 Fragment；
  10. 若本地联调评论源码，sourcecode 脚本把 Maven 节点替换为本地 project，其余装配流程基本不变。

这就是“独立开发、制品交付、壳统一装配、运行时解耦”的闭环。

17. 这种组件化的收益与代价

收益对应代价
多团队可以独立开发、发布组件版本协同和跨仓变更成本上升，接口变更要考虑兼容窗口。
知乎主工程能力可被盐言复用盐言需要维护排除、替换和特有版本锁，跟随上游升级并不自动。
调用方面向 API，减少实现耦合运行时服务发现可能把缺实现问题延迟到启动或页面调用。
组件可用 Maven 版本稳定集成，也可切源码联调本地 project 与线上 AAR 的构建参数、传递依赖可能漂移。
多 flavor 复用主体代码variant 数量膨胀，问题可能只在特定渠道/构建类型出现。
壳工程统一做依赖和产物门禁Gradle 脚本复杂，构建系统本身成为需要维护的核心代码。

18. 实战排障：从现象回到正确阶段

场景 A：明明加了组件，运行时却找不到类

  1. 先运行 :app:dependencies 或 dependencyInsight，确认目标坐标是否在该 variant 的 runtimeClasspath；
  2. 检查是否被 VIP_APP_REMOVED_COMPONENTS 或其他全局 exclude 裁掉；
  3. 检查 dependencyReplace 是否换成另一个坐标；
  4. 若类理论上存在，再看混淆、条件源码集和动态反射保留规则。

场景 B：本地改了组件代码，壳 APK 没变化

  1. 确认 sourcecode.properties 路径存在且未被注释；
  2. 确认配置坐标与组件 build.gradle 的 group/artifactId 一致；
  3. 用 gradle projects 看本地模块是否已 include；
  4. 用 dependencyInsight 确认 Maven module 已替换为 project；
  5. 检查当前构建 variant 是否走了另一个同名实现或渠道替换。

场景 C：接口能编译，InstanceProvider 却拿不到实现

  1. API 在 classpath 只说明契约存在，不说明实现 AAR 一定被装进 APK；
  2. 检查实现组件是否被裁剪或替换；
  3. 检查实现类是否有正确 @AutoService，注解处理产物是否生成并被混淆保留；
  4. 检查调用时机是否早于服务注册/组件初始化；
  5. 非强依赖能力优先使用 optional 并设计降级。

场景 D：只在某个渠道崩溃

  1. 比较两个 variant 的依赖图，而不是只比较 Java 代码；
  2. 比较 flavor Manifest、source set 和 BuildConfig；
  3. 检查真实 SDK 是否被替换成 no-op，或反过来；
  4. 若是 Native 崩溃，核对该渠道 APK 的 ABI 与 SO 清单。

常用证据命令

./gradlew :app:dependencies
./gradlew :app:dependencyInsight --dependency vip_comment --configuration devDebugRuntimeClasspath
./gradlew :app:componentInsight
./gradlew :app:assembleDevDebug
./gradlew :app:processDevDebugMainManifest

命令名和 configuration 会随 Gradle/AGP 版本变化，但排障思想不变：先证明依赖图，再证明合并产物，最后才看运行时调用。

19. 常见误区纠正

  • 误区：组件化就是多 Module。 多 Module 只是源码组织形式；盐言正式集成大量使用远程制品，默认 settings 仍只有 :app。
  • 误区：依赖 API 就等于有实现。 API 只能保证编译契约，最终还要装入实现组件并完成运行时注册。
  • 误区：Gradle 选了最高版本就一定兼容。 版本选择只解决图上的唯一性，不保证二进制/行为兼容。
  • 误区：exclude 只是减小包体。 它也用于产品裁剪、避免重复类和强制走 VIP 实现；排错时必须把它当功能逻辑。
  • 误区：路由没有依赖。 路由降低类依赖，但 URL 与参数成为新的协议依赖。
  • 误区：源码依赖和发布 AAR 完全一样。 理想上行为一致，实际上 build variant、依赖暴露、资源和编译参数可能不同，需要回切制品再验证。
  • 误区：壳工程没有业务代码。 壳应尽量薄，但仍包含产品级 Application 适配、启动任务、网络装饰器、渠道配置和最终门禁。

20. 面试时怎样把原理讲清楚

30 秒版本

盐言采用的是制品化组件集成。各业务仓把实现和 API 发布成 AAR，VipAndroid 作为 application 壳，通过集中版本表和组件清单形成 Gradle 依赖图，再用全局 exclude 裁掉知乎主 App 不需要的组件，用 dependencyReplace 换成 VIP 实现。构建时 Manifest、资源、字节码和 SO 合进同一 APK；运行时组件再通过路由、AutoService/InstanceProvider 和启动任务图通信。源码联调只是把 Maven 节点替换成本地 project，不是运行时动态加载。

2 分钟版本

我理解盐言组件化要分构建期和运行期。构建期里，VipAndroid 默认只有 app project，大量业务来自 Maven AAR。version.gradle 决定版本，allComponents 声明候选组件，VIP_APP_REMOVED_COMPONENTS 在 configuration 上做产品裁剪，dependencyReplace 把 account、comment、growth、passport 等普通实现及 API 换成盐言版本。之后版本锁、三方库白名单、TEMP 检查和 SO 对齐负责让最终依赖图可控。需要联调时，sourcecode.gradle 动态 include 本地模块，用 dependencySubstitution 把相同 Maven 坐标替换成 project。运行期里，AAR 已经合进一个 APK，跨组件调用主要靠路由和接口服务，初始化由 TaskManager 的依赖图调度。这样做的收益是团队并行、产品复用和实现可替换；代价是版本、渠道和 Gradle 规则更复杂，所以排障必须先确认 variant 的依赖图，再看运行时。

面试官可能追问

1. 问：为什么要拆 API 模块，直接依赖实现不行吗？

能运行，但调用方会编译依赖具体实现，内部类调整会扩大影响面，也很难按产品替换实现。API 模块提供稳定契约，让调用方和实现分别演进；代价是接口兼容和运行时实现缺失需要治理。

2. 问：api 与 implementation 的区别是什么？

在 Android Library 中，api 会把依赖类型暴露给上游编译，implementation 尽量只在当前模块内部可见，有助于缩小编译影响。VipAndroid 是最终 application，批量使用 api 更多是历史装配策略；在普通业务 library 中应根据对外签名是否需要该类型选择。

3. 问：dependencyReplace 与 InstanceProvider 的区别是什么？

前者在 Gradle 构建期决定 APK 里放哪个制品；后者在 App 运行时按接口找到已经打进 APK 并注册好的实现。没有构建期装配，运行时服务表也不会凭空出现实现。

4. 问：为什么单组件能编译，集成到壳却冲突？

单组件只看到自己的局部依赖图；壳把所有组件的传递依赖、资源、Manifest 和 SO 合并，才会暴露跨组件版本不一致、重复类和 ABI 不齐。壳工程必须做最终集成门禁。

5. 问：组件化最大的技术风险是什么？

不是“模块太多”本身，而是边界和依赖图变得隐式：接口版本漂移、传递依赖带入旧实现、渠道规则只在特定 variant 生效、运行时注册缺失。解决手段是契约治理、依赖可视化、版本锁、产物检查和关键链路测试。

补充快问：Maven 在盐言组件化里到底是什么角色？

严谨地说，Apache Maven 是构建和依赖管理工具，Maven 仓库是制品存储与分发约定。盐言 App 不是用 Maven CLI 构建，而是由 Gradle 根据 GAV 坐标从 Maven 私服解析 AAR/JAR 和 POM，再由 Android Gradle Plugin 把这些输入加工进 APK。日常说“发 Maven”通常是省略说法，实际指把组件制品和元数据发布到 Maven 仓库。

补充快问：AAR 和 APK 最本质的区别是什么？

AAR 是 Android Library 的不可安装构建输入，可能带 class、资源、Manifest、SO 和消费者混淆规则；APK 是 App 经过依赖解析、Manifest/资源处理、DEX、打包和签名后的可安装输出。AAR 通常不会原样嵌套进 APK，而是被拆成不同类型的输入分别加工。

延伸思考：如果让你改进这套体系，你会先做什么？

先让依赖图和产品组件清单可观测：为每个正式 variant 生成并保存组件/BOM 快照，对普通实现被重新带入、VIP 接口实现缺失、TEMP 版本和 SO 差异做 CI 门禁。之后再逐步减少全局 api 和散落 force，推动组件声明明确依赖边界。

22. 证据边界

本文基于当前本地检出解释实际可见机制。可以确认的是 Gradle 清单、新旧组件坐标分类、排除/替换规则、源码替换脚本、任务配置、路由入口和代表性 API/实现。不能仅凭这些文件断言所有线上版本都使用完全相同的配置，也不能把职责分层理解成已由 Gradle 强制执行的完整依赖 DAG；本次文档任务同样没有执行依赖内网制品的完整 APK 构建。

工程内 README 仍带有旧知乎主 App 描述，因此产品身份以仓库 AGENTS.md、applicationId、VIP 组件配置和实际源码为准。个人负责范围、上线收益和性能指标需本人确认，并用需求、MR、commit 或监控数据佐证。
