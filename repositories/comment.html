1. 仓库定位与面试边界

yyyyy-cdoe/Comment 的当前定位是标准评论列表、编辑器、草稿与 Native/RN 多场景组件。主要技术形态为 Kotlin/Java、ViewModel、Repository、Retrofit、RecyclerView 多类型卡片与 RN 容器。

面试应聚焦业务入口、状态编排、生命周期、异常兜底和组件集成。可以讲“我如何使用既有能力完成业务调用与排障”，但“本人实现/主导”的范围一律需本人确认，且应有 MR、commit、需求、评审或上线记录佐证。

5. 关键调用链与边界

源码直接链路：根评论列表

  1. CommentListFragment 创建 CommentViewModel 并调用 getRootCommentList
  2. CommentViewModel 构造 RootCommentListRepository
  3. RootCommentListRepository 调用 NetUtil.commentService.getRootCommentList
  4. comment_for_v7/api/CommentService.kt 定义真实接口

边界说明：点赞、折叠、子评论和下一页各有独立 Repository，是并行操作链，不等于根评论首刷的每一步。

6. 技术亮点与取舍

亮点

列表、编辑器、草稿、分段与 RN 容器并存，标准实现承担评论协议演进。

取舍

按动作拆 Repository 便于隔离错误，但类数量较多；与 VIP 分支并行演进又带来协议漂移。

面试时不要把“使用了某框架”本身当亮点。更有价值的是说清楚为什么这样划分状态与生命周期、失败如何降级、版本/协议如何兼容，以及出现竞态时如何用真实调用链定位。

7. 仓库专属风险与排查顺序

下面的顺序按本仓真实状态 owner、服务与生命周期组织；前一步没有证据时，不跳到渲染层猜测。

  1. 第 1 步。从 CommentListFragment 的 resource id、resource type、排序和锚点参数开始，先排除场景入参错误。
  2. 第 2 步。确认 getRootCommentList 对应的 CommentViewModel 实例仍属于当前 Fragment，避免旧资源回调污染新页面。
  3. 第 3 步。在 RootCommentListRepository 检查请求参数和 RepositoryCallback，再进入 NetUtil.commentService。
  4. 第 4 步。接口成功但列表不对时按 commentId 检查合并、局部操作与 adapter 更新，不要把投票版 CommentService 当成列表接口。

8. 可直接复述的讲法

30 秒版本

Comment 的根列表是一条可以逐行落断点的链：CommentListFragment 调 CommentViewModel，ViewModel 创建 RootCommentListRepository，Repository 再调用 NetUtil.commentService，对应接口定义在 comment_for_v7/api/CommentService.kt。点赞和折叠是旁支 Repository，不能混成首刷链。 个人参与范围需本人确认。

2 分钟版本

我会用根评论首刷说明 Comment 的分层。Fragment 负责资源参数和列表生命周期，CommentViewModel 选择根列表意图，RootCommentListRepository 处理仓储回调，最后由 NetUtil.commentService 调 comment_for_v7 的 CommentService。这样定位无数据时能逐层判断是参数、ViewModel 实例、Repository 回调还是接口问题。该设计让操作按 Repository 隔离，但局部更新多，必须用稳定 commentId 和当前资源身份防止旧回调改错列表。 若要把其中某个调用点写成个人成果，仍需本人确认并提供可核验记录。

9. 仓库专属追问与回答

1. 问：根评论接口的真实 CommentService 在哪里？

答：在 comment_for_v7/api/CommentService.kt，不是 com.zhihu.android.comment.api.service 下的投票相关同名接口。

2. 问：为什么要按操作拆多个 Repository？

答：根列表、下一页、点赞和折叠的参数及失败恢复不同，拆开能限制职责；代价是列表一致性需要统一协调。

3. 问：切换资源后旧评论回来了怎么查？

答：核对 Fragment 的资源身份和 ViewModel 回调归属，旧 resource id 的结果不能再写入当前列表。

4. 问：Comment 最小补测覆盖什么？

答：用 fake CommentService 验证根列表参数、失败回调、下一页合并和同 commentId 的局部更新。

5. 问：面试中怎样说明自己在这个仓库里的贡献边界？

答：只陈述自己能用需求单、MR、commit 或评审记录证明的 comment 调用点；公共框架、团队装配体系和历史代码不据为己有。无法核验的个人动作、结果和指标统一标为“需本人确认”。
