DataSource → ZhPlayer.setDataSource() → ZhPreplayerManager.getPreplayer() 或 playerFactory → prepare/start → switchQuality/seek → release

复述时建议按“业务入口 → 稳定抽象 → 实现/策略 → 系统或三方边界 → 状态回传”展开，这样能明确自己在调用侧做了什么，也能说明故障应在哪一层定位。

6. 核心机制、亮点与取舍

  • 工厂注入隐藏具体播放内核
  • ZhPreplayerManager 按 DataSource identity 复用已 prepare 的播放器
  • 预播放首帧快于单纯网络预加载，但占用更多 engine、内存和生命周期资源

取舍结论：统一封装提高复用、可替换性和观测一致性，但会把配置、生命周期、并发或兼容性问题集中到公共层。因此接入不能只验证 happy path。

7. 风险、兼容性与调试路径

主要风险

  • 预播放器的 DataSource、Surface 和 listener 可能污染下一会话
  • 切清晰度要保持 position/playing 状态并处理失败回退
  • 3 个检出测试均需核对是否只是模板，不能据数量推断质量

建议调试顺序

  1. 记录 DataSource identity 与是否命中 preplayer
  2. 对比切源前后 position、Surface、listener 和播放状态
  3. release 后检查 HandlerTimer 与迟到 callback

涉及 Android 版本、OEM、系统组件或三方 SDK 的路径，应补真机矩阵；涉及缓存、并发和生命周期的路径，应同时保留会话 id、时间线和线程信息。
