1. 仓库定位与面试边界

yyyyy-cdoe/LiteKnowledgeMarket 的当前定位是轻量产品的知识市场复用与模块别名发布仓。主要技术形态为 Kotlin/Java、多模块 Gradle、发布坐标别名、原生/Hybrid 与 ViewModel/DataSource。

面试应聚焦业务入口、状态编排、生命周期、异常兜底和组件集成。可以讲“我如何使用既有能力完成业务调用与排障”，但“本人实现/主导”的范围一律需本人确认，且应有 MR、commit、需求、评审或上线记录佐证。

5. 关键调用链与边界

构建期直接链：模块别名

  1. settings.gradle include :lite_kmarket 与 :lite_kmarket-api
  2. Gradle 脚本把发布项目名映射到 kmarket/kmarket-api 物理源码
  3. 调用方最终依赖轻量产品坐标

边界说明：这是构建期映射，不会在页面 refresh 后执行。

运行时直接链：原生首页

  1. ContentMarketHomeFragment 创建 NativeTabViewModel
  2. Fragment 调 refreshInfo
  3. NativeTabViewModel 直接创建 NewMarketService
  4. tabListInfoData/pagedListInfo 驱动首页

边界说明：BookCityViewModel 与 DiscoverPinDataSource 分别属于书城和 Pin Tab，不是本链中间层。

运行时独立链：书城

  1. BookCityContentFragment 创建 BookCityViewModel
  2. BookCityViewModel 直接使用 NewMarketService
  3. listing 暴露首刷与加载更多状态

边界说明：轻量裁剪改变依赖与入口集合，不等于改写这条运行时调用关系。

6. 技术亮点与取舍

亮点

通过发布名、Gradle 项目名与物理目录映射复用核心源码，不复制两套业务实现。

取舍

复用降低维护成本，但三种命名层级增加依赖排查难度，轻量包还需额外验证资源与 SDK 裁剪。

面试时不要把“使用了某框架”本身当亮点。更有价值的是说清楚为什么这样划分状态与生命周期、失败如何降级、版本/协议如何兼容，以及出现竞态时如何用真实调用链定位。

7. 仓库专属风险与排查顺序

下面的顺序按本仓真实状态 owner、服务与生命周期组织；前一步没有证据时，不跳到渲染层猜测。

  1. 第 1 步。类或资源缺失先查 settings.gradle 的项目名、物理目录和最终依赖，不进入运行时 ViewModel。
  2. 第 2 步。首页无数据沿 ContentMarketHomeFragment.refreshInfo → NativeTabViewModel → NewMarketService 查。
  3. 第 3 步。书城分页异常只看 BookCityViewModel.listing 的 initial/after 状态。
  4. 第 4 步。标准版正常而轻量版异常时对比依赖坐标、资源裁剪和 SDK 能力，不把产品差异伪装成接口失败。

8. 可直接复述的讲法

30 秒版本

LiteKnowledgeMarket 要分构建和运行两层。构建期用 lite_kmarket、lite_kmarket-api 项目名映射到物理源码；运行时原生首页仍是 ContentMarketHomeFragment → NativeTabViewModel → NewMarketService，书城则单独走 BookCityViewModel.listing。模块别名不是页面调用链。 个人参与范围需本人确认。

2 分钟版本

这个仓库的特色是复用同一套知识市场源码生成轻量产品坐标。settings.gradle 负责项目名和物理目录映射，这是构建期；APK 运行后，ContentMarketHomeFragment 仍创建 NativeTabViewModel 并 refreshInfo，书城仍由 BookCityContentFragment 持有 BookCityViewModel。区分两个时间轴后，类找不到查 Gradle，页面无数据查 ViewModel/Service。复用降低双份维护，但三层命名和资源裁剪增加了依赖诊断成本。 若要把其中某个调用点写成个人成果，仍需本人确认并提供可核验记录。

9. 仓库专属追问与回答

1. 问：lite_kmarket-api 和 kmarket-api 是两套实现吗？

答：当前工程通过项目名映射复用物理源码，不能仅凭发布名不同就认为有两份逻辑。

2. 问：模块别名会参与 refreshInfo 吗？

答：不会，它在构建期决定依赖；refreshInfo 属于 APK 内的运行时调用。

3. 问：轻量版首页的状态 owner 是谁？

答：原生首页仍由 NativeTabViewModel 持有 tabListInfoData/pagedListInfo。

4. 问：怎样验证别名发布没有串错？

答：检查 Gradle projects、依赖图、产物坐标和一个真实类断点，四处必须指向同一物理实现。

5. 问：面试中怎样说明自己在这个仓库里的贡献边界？

答：只陈述自己能用需求单、MR、commit 或评审记录证明的 liteknowledgemarket 调用点；公共框架、团队装配体系和历史代码不据为己有。无法核验的个人动作、结果和指标统一标为“需本人确认”。
