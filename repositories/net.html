3. 模块、分层与核心抽象

模块：net-api（稳定门面）、net（实现）。

  • net-api 隔离具体 Retrofit/OkHttp 实现，SERVICE_MAP 复用 service proxy
  • OkHttpFamilyProviderImpl 按 ClientType 组合 cookie、DNS、业务/网络 interceptor 和 metrics
  • DispatcherMonitor、NetThreadPool 与 SSE 独立执行器便于观测和隔离

分层判断来自 settings.gradle、模块构建脚本以及下列源码入口的交叉核对；README 只作线索。

4. 初始化与真实业务接入入口

业务调用 Net.createService(Service.class)；NetProviderImpl 在初始化后构建并缓存 Retrofit service。

接入责任边界：业务侧需要负责参数映射、页面/会话生命周期、错误态与降级、埋点和真实场景验证；基础库内部机制能解释问题，但不能据此宣称自己是框架作者。

5. 关键调用链

业务 Service.class → Net.createService() → NetProviderImpl.SERVICE_MAP → Retrofit proxy → OkHttpFamilyProviderImpl.inflateBuilder() → interceptor/DNS/dispatcher → 网络

复述时建议按“业务入口 → 稳定抽象 → 实现/策略 → 系统或三方边界 → 状态回传”展开，这样能明确自己在调用侧做了什么，也能说明故障应在哪一层定位。

6. 核心机制、亮点与取舍

  • net-api 隔离具体 Retrofit/OkHttp 实现，SERVICE_MAP 复用 service proxy
  • OkHttpFamilyProviderImpl 按 ClientType 组合 cookie、DNS、业务/网络 interceptor 和 metrics
  • DispatcherMonitor、NetThreadPool 与 SSE 独立执行器便于观测和隔离

取舍结论：统一封装提高复用、可替换性和观测一致性，但会把配置、生命周期、并发或兼容性问题集中到公共层。因此接入不能只验证 happy path。

7. 风险、兼容性与调试路径

主要风险

  • interceptor 顺序会改变签名、缓存、重试与监控语义
  • 进程级 service/client 缓存隐藏生命周期和配置刷新成本
  • SSE 重连、请求取消与线程池饱和需要显式治理

建议调试顺序

  1. 先用 EventListener 拆 DNS/connect/TLS/request/response
  2. 再看 DispatcherMonitor 排队和 NetThreadPool 饱和
  3. 最后检查 ClientType、interceptor 顺序、缓存策略与服务端耗时

涉及 Android 版本、OEM、系统组件或三方 SDK 的路径，应补真机矩阵；涉及缓存、并发和生命周期的路径，应同时保留会话 id、时间线和线程信息。

  1. 问：这个仓库和相邻能力怎么划界？
