1. 仓库定位与面试边界

yyyyy-cdoe/Premium 的当前定位是会员套餐、支付方式、优惠券、权益与离开挽留业务组件。主要技术形态为 Kotlin/Java、MVVM/RxJava、Retrofit、Router、原生/RN 购买页。

面试应聚焦业务入口、状态编排、生命周期、异常兜底和组件集成。可以讲“我如何使用既有能力完成业务调用与排障”，但“本人实现/主导”的范围一律需本人确认，且应有 MR、commit、需求、评审或上线记录佐证。

5. 关键调用链与边界

源码直接链路：会员购买页

  1. VipPurchaseSuperFragment 创建 VipPurchaseViewModel
  2. VipPurchaseViewModel 直接调用 PremiumService
  3. ViewModel 将套餐、支付方式和购买状态回传 Fragment

边界说明：VipPurchaseHostActivity 只是可能的宿主入口；支付 SDK 与权益刷新是提交后的相邻链，不是套餐请求的固定中间层。

6. 技术亮点与取舍

亮点

把套餐、优惠、支付方式、余额和挽留组成完整交易状态，而非零散弹窗。

取舍

统一编排便于闭环，但 ViewModel 状态较重，支付幂等、重建恢复与倒计时都要单独治理。

面试时不要把“使用了某框架”本身当亮点。更有价值的是说清楚为什么这样划分状态与生命周期、失败如何降级、版本/协议如何兼容，以及出现竞态时如何用真实调用链定位。

7. 仓库专属风险与排查顺序

下面的顺序按本仓真实状态 owner、服务与生命周期组织；前一步没有证据时，不跳到渲染层猜测。

  1. 第 1 步。先核对 VipPurchaseSuperFragment 的会员类型、SKU、来源和实验参数。
  2. 第 2 步。检查 VipPurchaseViewModel 当前套餐状态与 PremiumService 的请求/响应。
  3. 第 3 步。能展示但不能支付时区分页面套餐链和支付 SDK 回调链，记录订单号与支付渠道。
  4. 第 4 步。支付成功仍未解锁时以服务端订单/权益真值刷新，不只相信本地成功回调。

8. 可直接复述的讲法

30 秒版本

Premium 的直接业务链是 VipPurchaseSuperFragment → VipPurchaseViewModel → PremiumService。套餐展示、支付提交和权益到账是不同阶段；排障时要用 SKU 与订单身份贯穿，并以服务端权益真值结束，不能把支付 SDK 成功当作最终完成。 个人参与范围需本人确认。

2 分钟版本

VipPurchaseSuperFragment 创建 VipPurchaseViewModel，ViewModel 直接向 PremiumService 请求会员套餐和页面状态。用户提交支付后才进入渠道 SDK 与订单回调，最终还要重新确认服务端权益。这样的分层支持多会员类型和促销组合，但一次购买跨套餐、订单、支付和权益四个状态域，任何一步只看本地布尔值都会误判。 若要把其中某个调用点写成个人成果，仍需本人确认并提供可核验记录。

9. 仓库专属追问与回答

1. 问：套餐列表是谁请求的？

答：VipPurchaseViewModel 直接调用 PremiumService，Fragment 负责参数和展示。

2. 问：支付 SDK 返回成功就能立刻解锁吗？

答：不能只依赖渠道回调，应查询或刷新服务端订单与权益真值。

3. 问：价格显示错误先看哪里？

答：核对 Fragment 的会员类型/SKU，再看 PremiumService 返回和 ViewModel 的促销选择。

4. 问：怎样测试购买状态机？

答：用 fake Service/支付回调覆盖下单失败、支付取消、支付成功但权益延迟和重复回调。

5. 问：面试中怎样说明自己在这个仓库里的贡献边界？

答：只陈述自己能用需求单、MR、commit 或评审记录证明的 premium 调用点；公共框架、团队装配体系和历史代码不据为己有。无法核验的个人动作、结果和指标统一标为“需本人确认”。
