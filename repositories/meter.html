meter：工资实时计量 Android 原型

定位与归属边界

  • 单 app 模块 Kotlin + XML/ViewBinding 原型，按月薪、作息与工作日计算当日/当月收益，并展示曲线、通知和桌面组件。
  • 包名仍为 com.example.meter，更像原型；个人所有权和具体实现范围需本人确认。
  • 工资与作息属于敏感数据，存储、日志、备份、通知和 widget 都在隐私边界内。

检出与构建信息

  • 库存记录：分支 main，提交 cde4305（2026-06-10），Kotlin 微型仓。
  • 构建入口：./gradlew assembleDebug / testDebugUnitTest，AGP 8.7.2、Kotlin 2.0、Java 17、minSdk 32。
  • 聚合分析记录离线运行仍尝试下载 Gradle 8.9 并超时，未进入测试；现有 unit/androidTest 只是 Android Studio 模板。

结构与核心入口

  • MainActivity.kt：表单、权限、动画、保存、通知、widget 刷新。
  • data/EarningsCalculator.kt：纯收益计算。
  • HolidayRepository.kt：节假日 API、24 小时缓存与工作日 fallback。
  • EarningsWidgetProvider.kt、EarningsNotificationHelper.kt、EarningsTrendView.kt：外围呈现。

关键工作流

  1. 用户录入月薪、上下班和午休 → EncryptedSharedPreferences 保存。
  2. HolidayRepository 先读缓存，未命中同步 fallback 周一至周五，并异步拉节假日数据。
  3. EarningsCalculator 按本月工作日和每日有效分钟计算累计收入。
  4. Activity、通知和 widget 各自读取配置并刷新；自绘 View 画日/月趋势。

亮点与取舍

  • 小项目串起加密偏好、网络缓存、通知、widget、自绘 View，产品闭环直观。
  • fallback 保证离线可用，却无法识别调休；Activity 集中编排快，但职责过重且多处重复计算。
  • 高频视觉反馈适合前台，后台/widget 不适合 10 秒 alarm。

风险、测试与排查

  • P0：工资/作息被写入 debug 日志；存储加密不能抵消日志泄露，需全链路脱敏并审计备份策略。
  • P1：widget 使用 GlobalScope；10 秒 inexact alarm 不可靠且耗电；receiver exported=true 的自定义 action 缺权限保护。
  • P1：时间字符串校验不足、节假日依赖中文字符串、重复依赖装配；应抽 repository/use case 并注入 clock。
  • 排查：输入与 LocalTime → 缓存 TTL/API/fallback → 工作日与分母 → Activity/notification/widget 一致性 → alarm/Doze → receiver 权限。

收益计算边界与后台刷新设计

EarningsCalculator 最适合先抽成完全确定的 use case：输入月薪、月份工作日数、上下班/午休区间、当前时间和当天是否工作日，输出当日已赚、当日进度与当月累计。测试表要覆盖上班前为 0、上午工作中线性增长、午休冻结、下午继续、下班后封顶、周末/节假日不增长、二月和跨月，以及午休越界、下班早于上班等非法配置。金额用明确精度和舍入策略，展示层再格式化；不能让 Activity、通知和 widget 各算一遍。

HolidayRepository 的 24 小时缓存要注入 clock 和 fake API，验证缓存命中、过期刷新、网络失败保留旧数据、首次离线 fallback，以及调休工作日。服务端返回中文状态字符串属于脆弱契约，解析应收敛为枚举并把未知值记录为降级。UI 必须标明“精确节假日数据”还是“周一至周五估算”，否则用户会把 fallback 当真实工资口径。

前台页面可以用 lifecycle-aware coroutine 或定时器做秒级动画，但 widget 与通知应按系统约束降低频率。Widget 更新可由系统周期、用户点击和配置变化触发；通知只在上班、午休结束、下班等节点更新。取消 GlobalScope，使用受控 CoroutineScope/WorkManager；自定义广播若无需外部调用就设为不导出，或加 signature permission。验收时同时检查 Doze、重启后恢复、通知权限拒绝和备份恢复，并用同一 use case 对比三种界面的金额一致性。

面试讲法

30 秒版本

这是工资实时计量 Android 原型：配置月薪和作息后，结合节假日缓存计算累计收入，并同步曲线、通知和 widget。亮点是小闭环，问题是 Activity 过重、敏感日志、GlobalScope 和不合理的 10 秒 AlarmManager；归属及个人模块需本人确认。

2 分钟版本

核心计算由 EarningsCalculator 承担，HolidayRepository 提供缓存/API/fallback，结果在 Activity、自绘趋势、通知和 widget 展示。方案的产品反馈很直观，但外围各自重复装配和计算，容易不一致；后台 10 秒 inexact alarm 不符合系统限制，widget GlobalScope 无生命周期，工资虽然加密存储却进入日志。重做会抽单一 use case、注入 clock 和 holiday source，改用合理刷新策略，保护 receiver，并补计算边界、缓存、widget 与通知测试。只有本人 commit 能证明的部分才说“我负责”。

追问与回答

问题1：为什么 10 秒 AlarmManager 不合理？

inexact alarm 不保证频率，Doze 和最小间隔会干预，高频唤醒还耗电。

问题2：加密存储为什么仍不安全？

明文日志、备份、通知与 widget 都可能泄露；安全要覆盖全数据生命周期。

问题3：fallback 有什么业务误差？

周一至周五无法识别法定调休和补班，只能作为降级估算并明确标记。

问题4：怎么测试时间计算？

注入固定 clock，覆盖上班前、午休、下班后、非工作日、跨月与非法时间。

问题5：如何减少三处重复计算？

抽 EarningsUseCase，统一配置、节假日与 clock 依赖，Activity/通知/widget 只消费同一结果模型。
