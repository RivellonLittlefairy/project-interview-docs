km-attention：书城分类、关注、搜索与多内容 Tab 业务组件

1. 仓库定位与面试边界

yyyyy-cdoe/km-attention 的当前定位是书城分类、关注、搜索与多内容 Tab 业务组件。主要技术形态为 Kotlin/Java、ViewModel、RxJava/Retrofit、Provider/Router 与 Native/Hybrid 页面。

面试应聚焦业务入口、状态编排、生命周期、异常兜底和组件集成。可以讲“我如何使用既有能力完成业务调用与排障”，但“本人实现/主导”的范围一律需本人确认，且应有 MR、commit、需求、评审或上线记录佐证。

5. 关键调用链与边界

源码直接链路：关注页 Tab

  1. AttentionContainerFragment 创建 AttentionContainerViewModel
  2. Fragment 观察 ViewModel.tabs
  3. AttentionContainerViewModel 直接创建并调用 AttentionService
  4. 服务端 Tab 数据返回后由容器更新页面

边界说明：Pin、长篇、广播剧等子 Fragment 是 tabs 渲染后的分支，不是 AttentionService 返回前的中间节点。

6. 技术亮点与取舍

亮点

一个容器按服务端模型适配多内容类型，搜索、分类和关注又通过独立入口复用。

取舍

扩展新 Tab 较快，但未知类型、Native/Hybrid 跳转和搜索联想竞态都需要显式降级。

面试时不要把“使用了某框架”本身当亮点。更有价值的是说清楚为什么这样划分状态与生命周期、失败如何降级、版本/协议如何兼容，以及出现竞态时如何用真实调用链定位。

7. 仓库专属风险与排查顺序

下面的顺序按本仓真实状态 owner、服务与生命周期组织；前一步没有证据时，不跳到渲染层猜测。

  1. 第 1 步。先检查 AttentionContainerFragment 的创建参数与 tabs observer 是否注册在 viewLifecycleOwner。
  2. 第 2 步。进入 AttentionContainerViewModel 核对 AttentionService 请求、响应和 tabs 写入。
  3. 第 3 步。tabs 有值但页面缺页签时检查服务端 type 与容器支持类型的映射。
  4. 第 4 步。只有具体子页无数据时才进入对应 Pin/长篇/广播剧 Fragment 的独立 ViewModel。

8. 可直接复述的讲法

30 秒版本

km-attention 的容器主线很短：AttentionContainerFragment 创建 ViewModel 并观察 tabs，ViewModel 直接调用 AttentionService，返回配置后容器装配页签。各业务子页是装配后的分支，不应该塞进容器首刷链。 个人参与范围需本人确认。

2 分钟版本

我会先定位关注页的容器职责。AttentionContainerFragment 只创建 AttentionContainerViewModel 并观察 tabs；ViewModel 直接持有 AttentionService，服务返回的 Tab 配置决定容器展示哪些子页。Pin、长篇或广播剧的分页是后续各子 Fragment 自己的链。服务端配置提升扩展性，但客户端必须维护类型白名单和降级，否则未知 type 会导致空页或错位。 若要把其中某个调用点写成个人成果，仍需本人确认并提供可核验记录。

9. 仓库专属追问与回答

1. 问：tabs 的状态 owner 是谁？

答：AttentionContainerViewModel，Fragment 只按生命周期观察并装配页面。

2. 问：某一个子页无数据为什么不能先查 AttentionService？

答：AttentionService 只负责容器 Tab 配置；子页内容通常由自己的 ViewModel 和 Service 获取。

3. 问：服务端下发未知 Tab 类型怎么办？

答：容器需要白名单、默认排序和可观测的忽略策略，不能直接反射创建未知页面。

4. 问：怎样测试动态 Tab？

答：用 fake AttentionService 覆盖空配置、未知类型、顺序变化和重复 type，再验证容器装配结果。

5. 问：面试中怎样说明自己在这个仓库里的贡献边界？

答：只陈述自己能用需求单、MR、commit 或评审记录证明的 km-attention 调用点；公共框架、团队装配体系和历史代码不据为己有。无法核验的个人动作、结果和指标统一标为“需本人确认”。
