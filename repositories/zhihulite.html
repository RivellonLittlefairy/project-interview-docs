1. 仓库定位与面试边界

yyyyy-cdoe/ZhihuLite 的当前定位是知乎盐选版 Android App 宿主、启动 DAG 与组件化交付工程。主要技术形态为 Java、Android/Gradle、源码替换、多 flavor、动态 feature、启动任务与路由兼容。

面试应聚焦业务入口、状态编排、生命周期、异常兜底和组件集成。可以讲“我如何使用既有能力完成业务调用与排障”，但“本人实现/主导”的范围一律需本人确认，且应有 MR、commit、需求、评审或上线记录佐证。

5. 关键调用链与边界

构建期直接链：轻量 feature 装配

  1. settings.gradle include :app
  2. settings.gradle 加载 sourcecode.gradle 与 settings_feature.gradle
  3. settings_feature.gradle 根据 features.json 装配 ScannerFeature、VideoXFeature、LeLinkFeature 等

边界说明：这是 Gradle 配置期，不会在 Application 启动时再次执行。

源码直接链路：应用启动

  1. ZhihuApplication.attachBaseContext 调 ZhihuApplicationDelegate.beforeAttachBaseContext
  2. 随后调用 ConfigCreator.create 与 ZhihuApplicationDelegate.attachBaseContext
  3. ZhihuApplication.onCreate 调 ZhihuApplicationDelegate.onCreate
  4. onCreate 后调用 LiteRouterConfig.init

边界说明：TaskManager.json 是 Delegate 消费的配置证据，不能把 JSON 文件本身写成运行时方法调用者。

源码直接链路：路由兼容

  1. LiteRouterConfig.init 触发 ZRouter 初始化
  2. Routers.getDefault().setChecker 安装轻量产品 EqualChecker

边界说明：它修改路由匹配规则，不负责把所有请求导航到某个固定外部业务组件。

6. 技术亮点与取舍

亮点

宿主源码少但控制大量制品、feature、渠道与启动任务，是大型 App 的装配和交付边界。

取舍

组件化与任务 DAG 支持产品裁剪，但旧 Gradle 栈、内网依赖和多渠道差异提高升级成本。

面试时不要把“使用了某框架”本身当亮点。更有价值的是说清楚为什么这样划分状态与生命周期、失败如何降级、版本/协议如何兼容，以及出现竞态时如何用真实调用链定位。

7. 仓库专属风险与排查顺序

下面的顺序按本仓真实状态 owner、服务与生命周期组织；前一步没有证据时，不跳到渲染层猜测。

  1. 第 1 步。feature 缺失先查 features.json 的 enable/flavors 和 settings_feature.gradle 装配结果。
  2. 第 2 步。attachBaseContext 崩溃按 beforeAttach、ConfigCreator、Delegate.attachBaseContext 记录阶段。
  3. 第 3 步。onCreate 能完成但组件未初始化时看 Delegate 与 TaskManager 配置的任务状态。
  4. 第 4 步。同一 URL 在轻量版匹配异常时检查 LiteRouterConfig 安装的 EqualChecker 规则。

8. 可直接复述的讲法

30 秒版本

ZhihuLite 也要分构建与运行。构建期 settings_feature.gradle 按 features.json 装配 feature；运行时 ZhihuApplication 调 ConfigCreator 和 ZhihuApplicationDelegate，之后 LiteRouterConfig.init 安装路由 EqualChecker。TaskManager.json 是配置，不是一个会主动调用 Java 的对象。 个人参与范围需本人确认。

2 分钟版本

轻量宿主在 Gradle 配置期读取 features.json，决定 Scanner、VideoX、LeLink 等是否进入对应 flavor。APK 启动后，ZhihuApplication 在 attachBaseContext 分别调用 Delegate.beforeAttach、ConfigCreator.create 和 Delegate.attachBaseContext，在 onCreate 再调用 Delegate.onCreate，随后 LiteRouterConfig.init 替换路由 EqualChecker。这样可以同时裁剪产物和保持启动能力，但构建 feature、启动任务和路由兼容是三个独立故障面。 若要把其中某个调用点写成个人成果，仍需本人确认并提供可核验记录。

9. 仓库专属追问与回答

1. 问：features.json 会在应用启动时动态加载 feature 吗？

答：当前证据表明它服务 Gradle 装配；是否进入 APK 在构建期已决定。

2. 问：TaskManager.json 能直接调用 ZhihuApplication 吗？

答：不能这样表述，它是启动任务配置，由 Delegate/任务框架消费。

3. 问：LiteRouterConfig 改了什么？

答：它触发 ZRouter 初始化并向 Routers 安装自定义 EqualChecker，调整轻量产品匹配规则。

4. 问：怎样验证某 flavor 的 feature 集合？

答：读取 features.json 的 enable/flavors，检查 Gradle projects/依赖图，并对最终 APK 类和路由做冒烟验证。

5. 问：面试中怎样说明自己在这个仓库里的贡献边界？

答：只陈述自己能用需求单、MR、commit 或评审记录证明的 zhihulite 调用点；公共框架、团队装配体系和历史代码不据为己有。无法核验的个人动作、结果和指标统一标为“需本人确认”。
