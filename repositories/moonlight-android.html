moonlight-android：低延迟游戏串流客户端

定位与归属边界

  • Moonlight 官方 Android 客户端，上游 README、许可证与 moonlight-common-c 子模块共同证明外部开源归属。
  • 不得作为个人项目。若本人做过 fork、patch 或设备实验，其范围、PR、环境和指标均需本人确认；否则只说源码学习。
  • 适合学习控制面、实时数据面、JNI、MediaCodec、音频和输入的系统边界。

检出与构建信息

  • 库存记录：分支 master，提交 f10085f5（2024-07-27），Java/C 中型仓。
  • 构建入口：Gradle + Android SDK + NDK/ndk-build + submodule；app/build.gradle 定义 root/nonRoot flavor。
  • 未执行构建：需要完整子模块、NDK 和较长 native 编译；仓内未检出传统自动化测试目录。

结构与核心入口

  • 发现/设备：DiscoveryService、ComputerManagerService、mDNS。
  • 控制面：NvHTTP、PairingManager、NvConnection。
  • JNI：MoonBridge 连接 Java listener 与 moonlight-common-c。
  • 数据面：MediaCodecDecoderRenderer、AndroidAudioRenderer、controller/touch/keyboard；UI 链 PcView → AppView → Game。

关键工作流

  1. 发现或手动添加主机 → NvHTTP 拉 server info/app list → 配对。
  2. Game 根据设备能力组装 StreamConfiguration → NvConnection 协商分辨率、HDR、codec 与连接类型。
  3. MoonBridge 启动 native 协议栈 → 回调 Java 视频解码/音频播放。
  4. 触控、键鼠、手柄事件经窄 JNI bridge 回传主机；停止时同步保护 native 非线程安全区。

亮点与取舍

  • 控制面与实时数据面分离，Java 负责 Android 设备能力，C 层复用核心协议。
  • 窄 JNI 边界利于跨平台复用，但线程、buffer 生命周期和错误传播变复杂。
  • MediaCodec 降低 CPU 成本，却引入 codec/厂商/系统版本矩阵。

风险、测试与排查

  • Game.java 体量大，UI、连接、输入与错误处理耦合；native + codec + 设备矩阵导致回归困难。
  • 没有本地自动化测试证据；质量不能只靠能编译，需要协议回放、弱网仿真与真实设备矩阵。
  • 排查：主机发现/DNS → 配对证书 → server info/app list → codec/HDR 能力 → native 连接日志 → decoder/audio → input 回传。
  • 延迟指标必须拆网络、解码、渲染与输入，并注明设备、网络、分辨率、帧率和采样方法。

黑屏、卡顿与输入延迟的分层定位

出现“能看到主机但无法开流”时，先把控制面和数据面分开。控制面检查 mDNS/手动地址是否解析、配对证书状态、NvHTTP 的 server info 与 app list 是否成功，以及 launch/resume 返回的 session 参数；只有这些都通过，才进入 NvConnection 与 native 协议栈。若连接建立后黑屏，记录协商到的 codec profile、分辨率、HDR、参考帧限制与设备 decoder 名称，再观察 MediaCodec configure/start、输入 buffer 和首个输出 frame，避免把 decoder 不兼容误判成网络断流。

“有画面但卡顿”需要同时采集 packet loss/jitter、native 接收队列、decoder input/output 队列、渲染掉帧和音频欠载。通过网络仿真分别注入固定延迟、随机丢包、突发丢包和带宽收缩，判断问题发生在拥塞/重传、解码吞吐还是渲染节奏。录制的码流可用于 decoder 回放，协议事件则用 fake callbacks 验证 Java 状态机；真实设备矩阵至少按厂商、Android 版本、H.264/HEVC/AV1 与 HDR 能力分层。只报平均帧率会掩盖长尾卡顿，应给帧时间分布和连续掉帧段。

输入延迟要从事件产生、Java 归一化、JNI 入栈、网络发送、主机处理到新画面呈现拆段。手柄热插拔、多个 controller ID、触摸手势、键鼠组合键和 Activity 生命周期切换都应回归。JNI 边界重点检查回调线程、DirectByteBuffer 生命周期和停止连接时的竞态；已有 semaphore 与 synchronized(MoonBridge.class) 说明 native 区域存在串行要求，新增并发不能绕开。没有本人设备实验日志时，这些只能作为阅读后的测试设计，不能声称实测延迟。

面试讲法

30 秒版本

Moonlight Android 是上游开源项目，不是本人项目。我主要把它当低延迟串流参考：NvHTTP/NvConnection 是控制与协商，MoonBridge 是 JNI 边界，MediaCodec/audio/input 是数据面。没有本人 PR 或设备实验记录时，只说源码学习。

2 分钟版本

典型链路从主机发现和配对开始，NvHTTP 拉设备与应用信息，Game 组 StreamConfiguration，NvConnection 协商 codec/HDR/分辨率，再由 MoonBridge 启动 native 协议栈。视频回到 MediaCodec，音频回到 Android renderer，输入反向穿过 bridge。亮点是控制面/数据面分离与窄 JNI，难点是 native 线程、buffer 生命周期、弱网和设备 codec 矩阵。若做过真实实验，才补充硬件、网络、采样和指标；否则明确无个人代码贡献。

追问与回答

问题1：低延迟串流为什么需要 JNI？

跨平台协议核心放 C 层复用，Android 层专注 codec、音频与输入；JNI 需保持窄接口。

问题2：最难测什么？

codec/厂商差异、弱网、HDR/分辨率协商、音画同步和输入延迟。

问题3：控制面和数据面为什么分开？

控制请求重可靠和状态，媒体/输入重时延与持续流，两者协议与故障策略不同。

问题4：怎么测端到端延迟？

用高速相机或时间戳链拆输入、网络、解码、渲染，固定设备/网络/帧率并给样本分布。

问题5：为什么不能把源码分析说成项目经验？

仓库明确属于上游；只有本人 fork/PR、实验记录与可复现结果能证明贡献。
