Media：统一视频/音频播放交互与 Tornado 插件编排平台

1. 仓库定位与面试边界

yyyyy-cdoe/Media 的当前定位是统一视频/音频播放交互与 Tornado 插件编排平台。主要技术形态为 Kotlin/Java、注解处理、事件化插件、播放器池、预加载与会话监控。

面试应聚焦业务入口、状态编排、生命周期、异常兜底和组件集成。可以讲“我如何使用既有能力完成业务调用与排障”，但“本人实现/主导”的范围一律需本人确认，且应有 MR、commit、需求、评审或上线记录佐证。

5. 关键调用链与边界

源码直接链路：Tornado 事件协议

  1. 调用方调用 TornadoGroup_player.play/pause 等默认方法
  2. 默认方法构造 TEvent2 并调用 sendTEvent2
  3. EventGroup.sendTEvent2 直接委托给 delegate

边界说明：后续由具体 delegate/插件处理；没有证据时不把某个 ZHPluginVideoView 方法硬接为所有事件的固定下一跳。

独立编译期机制：事件代码生成

  1. TornadoActionMethodProcessor 扫描 TornadoActionMethod2
  2. Processor 通过 Writer 生成 action/group map

边界说明：生成发生在编译期，不在每次 play 的运行时事件链中。

独立播放 View 路径

  1. ZHPluginVideoView.playVideo 校验 URL、投屏和窗口状态
  2. playVideoInternal 处理插件前置逻辑
  3. 再调用父类播放实现

边界说明：PlayerPool 按 DataSource 创建播放器是底层复用机制，与 APT 生成链不是同一条箭头。

6. 技术亮点与取舍

亮点

控制栏、弹幕、埋点和清晰度按协议组合，播放器不再依赖巨型继承树。

取舍

插件组合灵活且便于复用，但生成代码调试、事件顺序和复杂状态一致性更难。

面试时不要把“使用了某框架”本身当亮点。更有价值的是说清楚为什么这样划分状态与生命周期、失败如何降级、版本/协议如何兼容，以及出现竞态时如何用真实调用链定位。

7. 仓库专属风险与排查顺序

下面的顺序按本仓真实状态 owner、服务与生命周期组织；前一步没有证据时，不跳到渲染层猜测。

  1. 第 1 步。事件无响应先记录 TornadoGroup_player 生成的 event key 和参数，再看 delegate 是否收到。
  2. 第 2 步。action 找不到时对照 TornadoActionMethodProcessor 生成物和模块名，区分编译期缺图与运行时无订阅。
  3. 第 3 步。直接 View 播放失败从 ZHPluginVideoView.playVideo 的 URL、投屏、浮窗分支进入 playVideoInternal。
  4. 第 4 步。播放器实例异常时再检查 PlayerPool 的 DataSource 和工厂选择，不把 UI 插件顺序当成实例创建证据。

8. 可直接复述的讲法

30 秒版本

Media 有三个层次：TornadoGroup_player 在运行时把方法转成 TEvent2 并交给 delegate；TornadoActionMethodProcessor 在编译期生成 action map；ZHPluginVideoView 则有自己的 playVideo → playVideoInternal 路径。三者协作，但不能画成每次播放必经的一条直线。 个人参与范围需本人确认。

2 分钟版本

Tornado 协议让调用方以 play、pause 这样的类型化方法发事件，生成的默认方法实际构造 TEvent2，经 EventGroup.sendTEvent2 委托给 delegate。注解处理器只在编译期扫描 TornadoActionMethod2 并生成 action/group map。具体视频 View 又有 ZHPluginVideoView.playVideo 到 playVideoInternal 的直接路径，PlayerPool 负责底层实例选择。组合式插件扩展性强，但事件 key、生成物、插件顺序和播放器状态跨层，必须分层观测。 若要把其中某个调用点写成个人成果，仍需本人确认并提供可核验记录。

9. 仓库专属追问与回答

1. 问：APT Processor 会在用户点播放时运行吗？

答：不会，它在编译期生成映射；运行时消费生成结果。

2. 问：TornadoGroup_player.play 实际做了什么？

答：它构造 key 为 play 的 TEvent2，并通过 sendTEvent2 交给 delegate。

3. 问：为什么不能把 ZHPluginVideoView 写成所有 Tornado 事件的下一跳？

答：协议允许多个 delegate/插件处理，当前证据不足以证明所有事件固定进入这个 View。

4. 问：怎样定位事件存在但无人处理？

答：先看生成 map 是否含 key，再看 delegate/插件注册和生命周期，最后检查处理方法返回。

5. 问：面试中怎样说明自己在这个仓库里的贡献边界？

答：只陈述自己能用需求单、MR、commit 或评审记录证明的 media 调用点；公共框架、团队装配体系和历史代码不据为己有。无法核验的个人动作、结果和指标统一标为“需本人确认”。
