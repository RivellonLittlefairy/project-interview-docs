定位与归属边界

  • README 与许可证表明这是 NVIDIA CUDA Toolkit 官方样例集，覆盖入门、概念、特性、库、领域、性能与平台样例。
  • 不得包装为个人项目。若有本人实验或上游补丁，其环境、命令、结果和 PR 均需本人确认；否则只说源码学习。
  • 样例展示 API 与模式，不等于生产实现或严谨 benchmark。

检出与构建信息

  • 库存记录：分支 master，提交 8a9e2c83（2025-05-22），CUDA/C++ 大型仓。
  • 构建入口：根与 Samples/CMakeLists.txt，README 要求 CUDA Toolkit 12.9、CMake 3.20+、C/C++/CUDA 17 和匹配 GPU/driver。
  • 未执行全量构建：当前任务没有可确认的 GPU、driver、Toolkit 组合；run_tests.py 本身只是 sanity runner。

结构与核心入口

  • Samples/0_Introduction：最小 API 与 kernel 入门。
  • Samples/2_Concepts_and_Techniques、3_CUDA_Features：共享内存、stream、graph 等模式。
  • Samples/4_CUDA_Libraries、5_Domain_Specific、6_Performance：库、领域和性能示例。
  • run_tests.py + test_args.json：发现可执行文件、按 GPU 条件过滤、并行运行和汇总退出码。

关键工作流

  1. 以 vectorAdd 为例：host 初始化 → cudaMalloc → H2D → kernel launch → D2H → CPU 校验 → free。
  2. matrixMul 展示 shared-memory tiling 与计时，但输入、预热和硬件适配均是样例设定。
  3. CUDA Graph 样例把 memcpy、memset、kernel 和 host callback 固化为可重复 DAG，减少重复 launch 编排成本。
  4. 测试 runner 读取样例参数和最小 GPU 数，设置单例超时，汇总通过/跳过/失败。

亮点与取舍

  • 亮点是完整能力地图和大量可编译样例；代价是硬件、Toolkit、架构与可选库组合庞大。
  • Graph 适合重复稳定 DAG；图频繁变化或单 kernel 已很重时收益可能有限。
  • 样例优先可读性与特性展示，不应直接得出生产性能结论。

风险、测试与排查

  • 不能编造吞吐、延迟或加速比；性能结论必须写 GPU、driver、Toolkit、shape、精度、预热、计时边界与 Nsight/日志来源。
  • 官方 runner 是 sanity check，不覆盖数值边界、设备矩阵或生产回归。
  • 排查顺序：nvidia-smi/driver → nvcc/Toolkit → CMake 架构 → 可选库依赖 → 单样例构建 → CUDA error 与结果校验。

单样例实验设计与错误定位

学习 CUDA samples 时，建议从一个最小样例建立可复现实验单，而不是直接全量编译。以 vectorAdd 为例，先记录 GPU 型号、compute capability、driver、Toolkit、编译器和 CMake 生成参数；只构建目标可执行文件，运行前后检查每个 CUDA API 的返回值和 kernel launch error，再把 device 输出与 CPU reference 按容差逐项比较。随后把元素个数改成不能整除 block size 的值，确认边界判断有效；再分别测只含 kernel 的 event 时间和包含 H2D/D2H 的端到端时间，避免把两种指标混为一谈。

matrixMul 的共享内存版本适合观察 tile size、占用率和访存模式，但不能因为样例比朴素实现快就推导生产收益。更严谨的实验会固定矩阵 shape 与数据类型，完成预热，重复多轮并报告中位数和分位数，同时与 cuBLAS 对照；用 Nsight Compute 查看 achieved occupancy、global load efficiency、shared-memory bank conflict 和 warp stall 原因。如果结果错误，先缩小 shape 并开启同步错误检查，再验证 leading dimension、tile 边界和同步点，而不是先调 block size。

CUDA Graph 样例则要把“构图成本”和“重复执行成本”分开计时。手工 node 与 stream capture 两条路径应生成语义相同的 DAG，并验证 memcpy、kernel、host callback 的依赖顺序。只有当图被重复执行足够多次且拓扑稳定时，launch 开销摊薄才有意义；若每轮 shape、指针或节点关系变化，需要频繁重建/更新 graph，收益可能被抵消。实验结论必须附完整命令和原始日志，未实际运行时只描述源码机制。

面试讲法

30 秒版本

这是 NVIDIA 官方 CUDA 样例，不是本人项目。它按能力层次展示 host/device 内存、kernel、共享内存、stream、Graph 与 CUDA 库；run_tests 只做 sanity check。没有明确 GPU 环境和实验记录时，我只讲源码学习，不报性能数字。

2 分钟版本

我会用它建立 CUDA 能力地图：vectorAdd 讲最小数据搬运和 kernel 闭环，matrixMul 讲 shared-memory tiling 及 benchmark 边界，simpleCudaGraphs 讲把重复 DAG 固化来摊薄 CPU launch 成本。构建依赖匹配的 GPU、driver、Toolkit 与架构参数；官方 runner 能筛样例、设超时和汇总退出码，但不是严谨性能套件。若本人做过实验，才补充日期、硬件、命令、样本和 Nsight 数据，否则明确暂无个人贡献或可核验指标。

追问与回答

问题1：为什么 matrixMul 不能直接当 benchmark？

输入形状、预热、校验、计时范围和硬件适配都是样例设定，生产评估还要对照 cuBLAS 与端到端搬运。

问题2：CUDA Graph 解决什么？

减少重复多 kernel/memcpy DAG 的 CPU launch 编排开销。

问题3：shared memory 的主要代价？

容量有限、占用影响并发，访问模式不当会有 bank conflict，还需处理边界和同步。

问题4：怎样验证 kernel 正确？

固定输入与 CPU reference 对比，检查 CUDA API/launch error，并覆盖非整块尺寸和数值容差。

问题5：为什么没跑全量测试？

缺少已确认的匹配 GPU、driver 和 Toolkit；在这种条件下声称运行结果是不可靠的。
