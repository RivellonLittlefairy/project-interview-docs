8J52SRPW6X_Matchfile：Fastlane Match 签名配置

定位与归属边界

  • Ruby/Fastlane Match 配置仓，用于 development 与 appstore 签名材料的只读同步，不是 Android 业务代码。
  • 这是团队签名供应链资产；个人治理、迁移或维护贡献需本人确认，且只能用脱敏工单、MR 或审计记录举证。
  • 仓内存在凭据形态文件；本文不展示任何值、地址或证书内容。

检出与构建信息

  • 库存记录：分支 master，提交 462e8a3（2026-04-03），配置仓。
  • 构建/执行入口：Gemfile 固定 Fastlane 2.193.0，Matchfile 配置平台、App 标识、分支和凭据路径；README 给出 match ... --readonly 同步命令。
  • 有 CI 配置但未检出自动化测试或安全 dry-run；未执行真实签名同步，避免访问凭据和外部签名仓。

结构与核心入口

  • README.md：人工同步说明。
  • Gemfile / Gemfile.lock：Fastlane 依赖锁定。
  • Matchfile：Match 行为配置。
  • 凭据形态 JSON：仅确认存在，不读取、不复述内容。

关键工作流

  1. 受控 CI runner 注入短期凭据 → Fastlane Match 只读访问加密签名仓。
  2. 下载指定证书/profile → 仅写入 job 的临时 keychain → 构建消费 → job 结束销毁。
  3. development 与 appstore job 应使用不同权限边界，发布材料只对 protected ref、受信 runner 和审批环境开放。

亮点与取舍

  • --readonly 能防 Match 意外修改签名仓，不能防凭据泄露、runner 被利用或权限过宽。
  • 锁定版本提高复现性，但旧 Fastlane 需要在隔离分支验证 Ruby/Bundler 与 Apple API 兼容后升级。
  • 集中配置便于统一签名流程，同时把供应链权限和审计风险集中到少量文件与 CI。

风险、测试与排查

  • P0：先吊销/轮换仓内凭据并审计访问日志；删除当前文件之前也必须假设 Git 历史、缓存和 fork 已泄露。
  • P0：把凭据迁入受保护 CI secret/secret manager，使用最小权限 service account、临时 keychain 和 protected ref。
  • P1：补 secret scanning、证书到期预警、权限台账和不打印 secret 的 pipeline smoke test。
  • 排查签名失败：确认目标类型与 App ID → profile/证书有效期 → CI 变量注入范围 → 临时 keychain 解锁 → Match 分支/权限；全程不打印敏感值。

签名故障演练与验收口径

这类仓最容易出现的误判是把“Match 拉取失败”统一归因于证书过期。更可靠的分层定位是先区分 Ruby/Bundler 启动错误、Apple API 鉴权错误、签名仓访问错误和本机 keychain 导入错误。前两类通常在访问加密签名仓之前就失败；仓访问错误要核对只读 deploy key、目标 branch 和网络；导入阶段则核对证书与 provisioning profile 的 App ID、类型、有效期和私钥是否成对。诊断日志只保留阶段、错误码、证书指纹后几位和到期日，不能回显 API key、私钥内容、完整仓地址或解密口令。

安全整改的验收不能只看“流水线重新变绿”。至少要证明旧凭据已经撤销、受保护变量只在指定环境可见、普通 MR 与 fork pipeline 无法读取发布 secret、job 使用独立临时 keychain 且结束后删除、发布 job 只能由 protected ref 触发。还应准备一个不承载真实用户发布的测试 App：定期执行 development/appstore 两条只读同步，对证书到期、权限被撤销、签名仓不可达和错误 App ID 做负向演练。每次演练记录触发条件、期望错误分类、告警是否到达和恢复耗时，才能把“签名配置”提升为可审计的供应链能力。

若升级 Fastlane，不能直接改锁文件后覆盖生产 runner。应固定一套 Ruby 与 Bundler 版本，在隔离 runner 上使用测试 App 比较新旧版本解析的 Matchfile、下载材料集合与最终 codesign 校验；任何参数弃用、Apple API 响应变化和 keychain 行为差异都要进入迁移清单。回滚条件也要提前定义，例如新版本只读同步成功但产物签名验证失败时，立即恢复旧镜像，而不是临时修改发布环境。

面试讲法

30 秒版本

这是团队 Fastlane Match 签名配置，不是业务项目。它以只读方式同步开发和商店签名，但当前仓内有凭据形态文件，应按泄露治理：先轮换审计，再迁受保护 CI secret、临时 keychain、protected ref 和最小权限。任何个人整改范围需本人确认。

2 分钟版本

这类仓最重要的不是会跑 match，而是签名供应链治理。理想链路是受控 runner 注入短期凭据，Match 只读取加密材料，job 内临时 keychain 使用并销毁。当前风险是凭据形态文件进入版本库，readonly 只防误写，挡不住历史泄露或过权 runner。整改顺序必须是轮换与审计、清理历史、CI secret、环境隔离、到期与离职台账。没有脱敏 MR/工单证据时，我只描述团队配置结构，不声称个人成果。

追问与回答

问题1：为什么不能只删当前凭据文件？

Git 历史、fork、缓存与日志仍可能留存；必须先轮换，再清历史并审计使用记录。

问题2：readonly 为什么不等于安全？

它限制 Match 写签名仓，不限制凭据被读取、runner 被利用或 API 权限过宽。

问题3：如何隔离开发与发布证书？

发布 job 只允许 protected tag/branch、受信 runner 与审批环境，普通 MR 不注入发布 secret。

问题4：怎样做自动化验证？

使用受控测试 App 做 pipeline smoke test，验证证书/profile 有效且输出脱敏，并增加到期预警。

问题5：升级 Fastlane 怎么降风险？

隔离分支固定 Ruby/Bundler，先对测试 App 做只读同步与签名，再灰度切换 CI。
