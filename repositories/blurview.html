BlurView：实时模糊视图 UI 库

证据口径：本文直接核对当前工作区 Git 跟踪文件、构建脚本与主源码。未执行可能下载依赖或改写缓存的构建。仓库事实不等于个人经历；个人贡献、作者身份、效果数据统一标为需本人确认。

1. 仓库定位与业务边界

提供 Android View 背景采样、下采样和多后端模糊能力；它只解决视觉效果，不承担业务页面结构或图片加载。

  • 项目类型：实时模糊视图 UI 库
  • 技术栈：Java · Android/Gradle
  • 业务接入者视角：先理解稳定入口、输入输出和失败边界；除非有可核验经历，不把底层框架设计表述为个人贡献。

3. 模块、分层与核心抽象

模块：app（示例）、library（BlurView 实现）。

  • BlurAlgorithm 把算法后端抽象出来，RenderNode 与 RenderScript/软件回退可按平台切换
  • 先下采样再模糊，显著降低参与运算的像素数
  • 自动更新能获得实时效果，但每帧采样会增加 CPU/GPU、Bitmap 分配和递归绘制风险

分层判断来自 settings.gradle、模块构建脚本以及下列源码入口的交叉核对；README 只作线索。

4. 初始化与真实业务接入入口

业务在布局中放置 BlurView，并通过 setupWith(root/BlurTarget) 选择算法、缩放比例、噪点和模糊半径。

接入责任边界：业务侧需要负责参数映射、页面/会话生命周期、错误态与降级、埋点和真实场景验证；基础库内部机制能解释问题，但不能据此宣称自己是框架作者。

5. 关键调用链

BlurView.setupWith() → PreDrawBlurController/RenderNodeBlurController → 采样 BlurTarget → BlurAlgorithm.blur() → BlurView.draw()

复述时建议按“业务入口 → 稳定抽象 → 实现/策略 → 系统或三方边界 → 状态回传”展开，这样能明确自己在调用侧做了什么，也能说明故障应在哪一层定位。

6. 核心机制、亮点与取舍

  • BlurAlgorithm 把算法后端抽象出来，RenderNode 与 RenderScript/软件回退可按平台切换
  • 先下采样再模糊，显著降低参与运算的像素数
  • 自动更新能获得实时效果，但每帧采样会增加 CPU/GPU、Bitmap 分配和递归绘制风险

取舍结论：统一封装提高复用、可替换性和观测一致性，但会把配置、生命周期、并发或兼容性问题集中到公共层。因此接入不能只验证 happy path。

7. 风险、兼容性与调试路径

主要风险

  • RenderScript 已废弃，需要验证目标 Android 版本的回退路径
  • 尺寸变化和页面动画可能触发 Bitmap 重分配或抓取错误区域
  • 仅 1 个测试，视觉正确性和低端机性能不能从当前测试推断

建议调试顺序

  1. 先确认 BlurTarget 与 BlurView 是否形成递归绘制
  2. 记录缩放后 Bitmap 尺寸和每帧耗时
  3. 按 API 级别区分 RenderNode、RenderScript 和软件路径

涉及 Android 版本、OEM、系统组件或三方 SDK 的路径，应补真机矩阵；涉及缓存、并发和生命周期的路径，应同时保留会话 id、时间线和线程信息。

  1. 问：这个仓库和相邻能力怎么划界？
