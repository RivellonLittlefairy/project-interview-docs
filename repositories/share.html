Share：业务分享能力组件

证据口径：本文直接核对当前工作区 Git 跟踪文件、构建脚本与主源码。未执行可能下载依赖或改写缓存的构建。仓库事实不等于个人经历；个人贡献、作者身份、效果数据统一标为需本人确认。

1. 仓库定位与业务边界

把业务 ShareInfo/ShareUnifyInfo、短链、RN 参数和统一入口整理为分享请求；渠道 SDK、分享面板和系统 Intent 下沉到 ShareCore。

  • 项目类型：业务分享能力组件
  • 技术栈：Java/Kotlin · Android/Gradle · RxJava
  • 业务接入者视角：先理解稳定入口、输入输出和失败边界；除非有可核验经历，不把底层框架设计表述为个人贡献。

3. 模块、分层与核心抽象

模块：share-api（模型/跨组件接口）、share（业务实现）。

  • API/实现拆分避免业务直接依赖微信、QQ、微博 SDK
  • ShareInfo 与 ShareUnifyInfo 支持不同历史调用形态，RN 接口承担跨端参数转换
  • 分层利于复用，但多套模型长期并存会产生字段语义漂移

分层判断来自 settings.gradle、模块构建脚本以及下列源码入口的交叉核对；README 只作线索。

4. 初始化与真实业务接入入口

业务构造 ShareInfo/ShareUnifyInfo；RN 通过 IRNShareInterface 转为原生模型，ShareComponent 提供组件注册入口。

接入责任边界：业务侧需要负责参数映射、页面/会话生命周期、错误态与降级、埋点和真实场景验证；基础库内部机制能解释问题，但不能据此宣称自己是框架作者。

5. 关键调用链

业务/RN 模型 → ShareComponent/IRNShareInterface → ShareService/ShortUrlService 准备数据 → ShareCore 面板/渠道 → SDK callback

复述时建议按“业务入口 → 稳定抽象 → 实现/策略 → 系统或三方边界 → 状态回传”展开，这样能明确自己在调用侧做了什么，也能说明故障应在哪一层定位。

6. 核心机制、亮点与取舍

  • API/实现拆分避免业务直接依赖微信、QQ、微博 SDK
  • ShareInfo 与 ShareUnifyInfo 支持不同历史调用形态，RN 接口承担跨端参数转换
  • 分层利于复用，但多套模型长期并存会产生字段语义漂移

取舍结论：统一封装提高复用、可替换性和观测一致性，但会把配置、生命周期、并发或兼容性问题集中到公共层。因此接入不能只验证 happy path。

7. 风险、兼容性与调试路径

主要风险

  • 短链或图片准备失败需要有原链接/纯文本降级
  • Activity 离开前台后渠道 callback 可能丢失
  • 4 个测试中含样板项，不能视为完整渠道契约覆盖

建议调试顺序

  1. 按模型生成、短链/图片准备、渠道匹配、SDK 调用、回前台 callback 分段埋点
  2. 核对 RN 与 Native 字段默认值
  3. 复现前后台切换与进程重建

涉及 Android 版本、OEM、系统组件或三方 SDK 的路径，应补真机矩阵；涉及缓存、并发和生命周期的路径，应同时保留会话 id、时间线和线程信息。
