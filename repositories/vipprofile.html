5. 关键调用链与边界

源码直接链路：VIP 个人主页

  1. VipProfileFragment 调用 ProfileViewModel.checkRequestData
  2. ViewModel 调 ProfileRepository.getUserInfo
  3. ProfileRepository 调 ProfileService
  4. 结果转换为 ProfileUiState
  5. Fragment 观察 ProfileUiState 渲染

边界说明：编辑资料和附属卡片可以更新同一页面，但不是 getUserInfo 首刷的每个步骤。

6. 技术亮点与取舍

亮点

主资料与消息、助手、会员卡等附属状态可独立成功或失败，缓存先显后网络校正。

取舍

部分成功提升可用性，但多个并发请求、Rx 生命周期与编辑回写的一致性更复杂。

面试时不要把“使用了某框架”本身当亮点。更有价值的是说清楚为什么这样划分状态与生命周期、失败如何降级、版本/协议如何兼容，以及出现竞态时如何用真实调用链定位。

7. 仓库专属风险与排查顺序

下面的顺序按本仓真实状态 owner、服务与生命周期组织；前一步没有证据时，不跳到渲染层猜测。

  1. 第 1 步。先核对 VipProfileFragment 的 user id、是否本人主页和入口来源。
  2. 第 2 步。检查 checkRequestData 是否因已有状态、刷新条件或生命周期而跳过请求。
  3. 第 3 步。进入 ProfileRepository.getUserInfo 对比缓存与 ProfileService 网络结果。
  4. 第 4 步。接口正确但页面错误时查看 ProfileUiState 的合并和 Fragment observer，区分主资料与附属卡片。

8. 可直接复述的讲法

30 秒版本

VipProfile 的主资料链是 VipProfileFragment → ProfileViewModel.checkRequestData → ProfileRepository.getUserInfo → ProfileService → ProfileUiState。排障先看 user id 与是否本人，再分缓存、网络和 UiState 转换，不把编辑回写当成首刷中间层。 个人参与范围需本人确认。

2 分钟版本

Fragment 用 checkRequestData 让 ViewModel 决定是否加载，ViewModel 调 ProfileRepository.getUserInfo，Repository 再访问 ProfileService，最终把资料转成 ProfileUiState 供页面观察。仓储可做缓存和网络合并，提升首屏；代价是他人主页/本人主页、缓存身份和编辑后的临时状态容易互相覆盖，所以所有更新都要带稳定 user id。 若要把其中某个调用点写成个人成果，仍需本人确认并提供可核验记录。

9. 仓库专属追问与回答

1. 问：checkRequestData 为什么可能不发请求？

答：它会结合已有状态和刷新条件做判断，需要看当前 ViewModel 的 user id 与状态。

2. 问：缓存资料怎样避免串用户？

答：缓存 key、Repository 结果和 ProfileUiState 都必须绑定稳定 user id。

3. 问：编辑成功后必须全量刷新吗？

答：不一定，可局部回写明确字段，但服务端真值变化大时仍需触发 getUserInfo。

4. 问：怎样测试 ProfileUiState 合并？

答：覆盖缓存先到、网络后到、切换用户和编辑回写，确保旧 user id 结果被丢弃。
