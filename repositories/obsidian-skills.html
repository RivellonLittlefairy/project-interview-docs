定位与归属边界

  • README 明确这是 Obsidian Agent Skills 上游仓，兼容 Agent Skills specification，可供多种 coding agent 使用。
  • 不得当作本人项目；若本人做过验证或上游贡献，日期、版本、命令和 PR 均需本人确认。
  • 仓库主要是 Markdown 指令和 references，没有传统应用构建入口。

检出与构建信息

  • 库存记录：分支 main，提交 fa1e131（2026-04-02），文档/技能仓。
  • 使用方式是把 skill 安装到 Agent 的技能目录，再由触发描述按需加载；无传统 build/test/CI。
  • 本轮只核验 README、5 个 SKILL.md 与 references，未写入任何 Obsidian vault，也未全局安装 defuddle。

结构与核心入口

  • skills/obsidian-markdown：frontmatter、wikilink、embed、callout。
  • skills/obsidian-bases：.base YAML filter/formula/view/summary。
  • skills/json-canvas：.canvas node/edge schema 与引用完整性。
  • skills/obsidian-cli：读写/search/property/task 与插件调试；defuddle：网页抽取 Markdown。

关键工作流

  1. Agent 根据技能描述判断触发 → 读取主 SKILL 的高频流程。
  2. 遇到复杂语法才加载 references，降低上下文成本。
  3. 读操作先定位 vault 与目标文件；写操作应限定路径、备份并验证结果。
  4. CLI/插件调试通过 reload、error、screenshot、DOM 检查形成闭环。

亮点与取舍

  • 渐进披露把核心流程与低频语法分开，减少 token 和误用。
  • 文档技能易维护、跨 Agent 复用，但行为依赖模型遵循度和外部 CLI 版本。
  • defuddle 简化网页抽取，却引入全局 npm 安装、网络和内容信任边界。

风险、测试与排查

  • Obsidian CLI/Bases 语法会漂移；需要版本矩阵、示例 vault fixture 和 snapshot/contract 检查。
  • 所有写 vault 的技能应限定绝对目标、预览 diff、备份与恢复；外部网页内容视为不可信。
  • 排查：Agent 是否触发正确技能 → references 是否按需加载 → Obsidian/CLI 版本 → vault 路径/权限 → schema → 应用内实际渲染。
  • 没有真实实验记录时，不声称安装成功率、节省时间或个人代码贡献。

Fixture Vault 与技能验收设计

可建立一个不含个人笔记的小型 fixture vault：三篇带 frontmatter 的 Markdown、互相引用的 wikilink、图片与 PDF embed、一个 callout、一个 Base 和一个 Canvas。对 obsidian-markdown，验证属性类型、链接重命名后的引用、标题锚点、块引用和附件相对路径；对 json-canvas，检查 node id 唯一、edge 两端存在、坐标/尺寸为合法数值、文件节点引用真实文件。测试既比较文件结构，也要在指定版本 Obsidian 中打开并截图确认渲染，因为语法合法不代表产品行为正确。

obsidian-bases 应用固定数据验证 filter、formula、view 与 summary。边界包括缺属性、日期/数字/字符串混型、空集合、公式错误和排序稳定性。主 SKILL 只描述选择与验证流程，具体函数语法从 FUNCTIONS_REFERENCE.md 按需加载；这样测试可以发现 reference 更新而主流程未同步的漂移。每次升级 Obsidian/Bases 版本都跑同一 fixture，并记录生成文件 diff 与 UI 结果。

obsidian-cli 的写操作应先在 fixture vault dry-run，限定目标根并拒绝路径穿越；批量属性或任务修改前输出受影响文件列表，完成后重新 search/property 查询验证。插件调试链要记录 reload 是否成功、错误日志是否清零、截图/DOM 是否出现目标元素。defuddle 获取的网页 Markdown 是不可信输入：先保存到隔离草稿，清理脚本式链接和意外 frontmatter，再由用户确认是否写入 vault。测试安装命令时使用临时 npm prefix，不能污染全局环境。

面试讲法

30 秒版本

这是 Obsidian 社区上游技能仓，不是本人项目。它用 5 个 skill 覆盖 Markdown、Bases、Canvas、CLI 和网页抽取，设计亮点是主 SKILL 放高频流程、references 放复杂语法。没有本人实验或 PR 时，只说上游学习。

2 分钟版本

仓库把 Obsidian 的文件格式和 CLI 工作流编码成 Agent Skills。触发后先加载短的主流程，只有遇到 properties、embed、Base formula 或 Canvas schema 才读 references，这就是渐进披露。风险来自产品语法漂移、全局安装与网络，以及对 vault 的写入；应使用小型 fixture vault、版本矩阵、diff/备份和真实 Obsidian 渲染验证。若没有日期、版本和命令日志，不把阅读说成实践。

追问与回答

问题1：references 为什么不全塞进 SKILL？

高频流程先加载，少见语法按需读取，可降低上下文成本和误用概率。

问题2：怎么测试文档型 skill？

准备小型 vault fixture，断言触发、路径、输出 schema 和渲染结果，并对外部动作 mock。

问题3：写 vault 前为什么要备份？

技能可能批量修改链接、属性和 Canvas；路径误判或模型偏差会造成难恢复覆盖。

问题4：defuddle 的主要风险？

全局 npm 供应链、网络访问与不可信网页内容；需权限确认并限制后续写入范围。

问题5：如何处理 CLI 版本漂移？

在 metadata 写适用版本，维护最小命令 contract，并用多版本 CI/fixture 定期回归。
