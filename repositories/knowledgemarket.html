1. 仓库定位与面试边界

yyyyy-cdoe/KnowledgeMarket 的当前定位是知识市场发现、书架、已购与手稿阅读的聚合业务仓。主要技术形态为 Kotlin/Java、原生 Fragment、Hybrid、ViewModel/DataSource、Rx/LiveData 与多模块 Gradle。

面试应聚焦业务入口、状态编排、生命周期、异常兜底和组件集成。可以讲“我如何使用既有能力完成业务调用与排障”，但“本人实现/主导”的范围一律需本人确认，且应有 MR、commit、需求、评审或上线记录佐证。

5. 关键调用链与边界

源码直接链路一：原生首页

  1. ContentMarketHomeFragment 创建 NativeTabViewModel
  2. Fragment 调 refreshInfo
  3. NativeTabViewModel 直接创建 NewMarketService
  4. 结果写入 tabListInfoData/pagedListInfo 并由 Fragment 观察

边界说明：这条链不经过 BookCityViewModel 或 DiscoverPinDataSource。

源码直接链路二：Pin Tab

  1. VipPinChildFragment 用 Factory(selectedTab, …) 创建 VipPinViewModel
  2. ViewModel 按 tab 选择 DiscoverPinDataSource、LikePinDataSource 或 HistoryPinDataSource
  3. DataSource 基类使用 NewMarketService

边界说明：Pin 场景是独立入口，不是 ContentMarketHomeFragment 的下一跳。

源码直接链路三：书城

  1. BookCityContentFragment 创建 BookCityViewModel
  2. BookCityViewModel 直接创建 NewMarketService
  3. ViewModel 通过 listing 暴露分页状态

边界说明：书城和原生首页共用 Service 类型，但不是同一个 ViewModel 链。

6. 技术亮点与取舍

亮点

同一仓库覆盖发现—详情入口—阅读/收听—书架—已购的业务闭环，并以 API 模块对外暴露契约。

取舍

聚合便于端到端协作，但多代首页、原生/Hybrid 和 Rx/LiveData 并存提高维护成本。

面试时不要把“使用了某框架”本身当亮点。更有价值的是说清楚为什么这样划分状态与生命周期、失败如何降级、版本/协议如何兼容，以及出现竞态时如何用真实调用链定位。

7. 仓库专属风险与排查顺序

下面的顺序按本仓真实状态 owner、服务与生命周期组织；前一步没有证据时，不跳到渲染层猜测。

  1. 第 1 步。首页异常先确认当前页面是原生首页、Pin Tab 还是书城，三个入口不能共用同一断点结论。
  2. 第 2 步。原生首页沿 ContentMarketHomeFragment.refreshInfo → NativeTabViewModel → NewMarketService 查 tabListInfoData。
  3. 第 3 步。Pin Tab 检查 Factory 的 selectedTab 和实际选中的 DataSource，再看基类 Service 请求。
  4. 第 4 步。书城只看 BookCityContentFragment、BookCityViewModel.listing 和 NewMarketService 的分页状态。

8. 可直接复述的讲法

30 秒版本

KnowledgeMarket 不是一条首页大链，而是三个直接路径：原生首页走 ContentMarketHomeFragment → NativeTabViewModel；Pin Tab 走 VipPinChildFragment → VipPinViewModel → 对应 DataSource；书城走 BookCityContentFragment → BookCityViewModel。它们可以共用 NewMarketService，但不能互相串接。 个人参与范围需本人确认。

2 分钟版本

我会先按页面场景拆 KnowledgeMarket。ContentMarketHomeFragment 调 NativeTabViewModel.refreshInfo，ViewModel 直接用 NewMarketService 并暴露 tabListInfoData；VipPinChildFragment 通过 Factory 把 selectedTab 交给 VipPinViewModel，后者选择 Discover、Like 或 History DataSource；BookCityContentFragment 则单独持有 BookCityViewModel 和 listing。拆开后，无数据问题能直接落到正确 owner。多入口共享 Service 降低接口重复，但状态与分页模型不同，强行复用一条链反而会误导。 若要把其中某个调用点写成个人成果，仍需本人确认并提供可核验记录。

9. 仓库专属追问与回答

1. 问：ContentMarketHomeFragment 会创建 BookCityViewModel 吗？

答：已核对的原生首页链创建的是 NativeTabViewModel，书城 ViewModel 属于 BookCityContentFragment。

2. 问：Pin Tab 怎样选择 DataSource？

答：VipPinViewModel 根据 Factory 传入的 selectedTab 选择 Discover、Like 或 History DataSource。

3. 问：三个场景为什么可以共用 NewMarketService？

答：Service 是接口层复用，页面状态 owner 和分页策略仍可分别实现。

4. 问：怎样避免排查串场？

答：日志必须带页面类型、tab 类型和 ViewModel 身份，再沿对应的直接链定位。

5. 问：面试中怎样说明自己在这个仓库里的贡献边界？

答：只陈述自己能用需求单、MR、commit 或评审记录证明的 knowledgemarket 调用点；公共框架、团队装配体系和历史代码不据为己有。无法核验的个人动作、结果和指标统一标为“需本人确认”。
