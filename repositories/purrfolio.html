Purrfolio：本地资产追踪 WinUI 应用

定位与归属边界

  • WinUI 3 本地桌面 App，覆盖资产总览、永久组合偏离、固定收益 XIRR、派息日历、复利预测与截图 OCR 导入。
  • 可以作为个人项目候选，但所有权、本人模块与结果需本人确认并提供 commit/PR 或演示。
  • 当前仍是原型：不是专业投顾系统，真实行情、税费、付息规则与合规未完整覆盖。

检出与构建信息

  • 库存记录：分支 codex/minimax-ocr-import，提交 2d7d6aa（2026-04-03），C#/.NET 小型仓。
  • 构建入口：Purrfolio.sln，.NET 8、WinUI 3、CommunityToolkit.Mvvm、EF Core/SQLite、Win2D、xUnit。
  • 聚合分析记录 2026-07-24 dotnet test tests/Purrfolio.Core.Tests/Purrfolio.Core.Tests.csproj 为 9/9 通过；伴随 NuGet 漏洞数据源不可达警告。

结构与核心入口

  • src/Purrfolio.App：Views/ViewModels、DI、通知与 OCR。
  • src/Purrfolio.Core：领域模型、仓储接口、XIRR/组合偏离/派息/复利纯计算。
  • src/Purrfolio.Infrastructure：EF Core DbContext 与 SQLite repository。
  • tests/Purrfolio.Core.Tests：领域算法 xUnit 测试。

关键工作流

  1. 资产首页：异步流读 SQLite → 聚合市值 → 四类资产各 25% 目标偏离 → 复利预测 → observable UI。
  2. 固定收益：生成买入/票息/终值现金流 → XIRR Newton 求根，失败后二分 → 组合/单券/批次展示。
  3. 派息：按频率生成未来事件 → Windows notification 提醒。
  4. OCR：图片提交外部模型 → 兼容响应外壳并归一字段 → 生成可编辑草稿 → 人工复核与校验后入库。

亮点与取舍

  • App/Core/Infrastructure 分层让领域算法可脱离 UI/SQLite 测试。
  • XIRR 双算法提高数值稳定性；OCR 先草稿后人工确认，避免模型直接写库。
  • IAsyncEnumerable 便于流式读取/取消，但小数据量收益需性能数据证明。

风险、测试与排查

  • EnsureCreatedAsync() 不适合长期 schema 演进，应切 EF migrations。
  • OCR 上传投资截图，需要脱敏、显式同意、endpoint 白名单、大小/超时限制、安全凭据存储与可删除审计。
  • 派息规则与基准线是简化/示意，不得当真实市场数据；XIRR 多根歧义未检测。
  • 排查：输入/现金流符号与日期 → XIRR bracket/残差 → repository/DB migration → ViewModel 状态 → OCR 响应归一/人工校验。

固定收益案例与 OCR 导入验收

固定收益链路应从一笔可手算的债券批次开始：交易日的买入金额记为负现金流，历史票息和当前估值/到期本金为正现金流；核对票息频率、数量、面值、费用和日期后再调用 XIRR。测试不仅断言收益率，还把结果代回 XNPV 检查残差，并覆盖同日现金流、无正负号、到期日前估值、已到期资产和 Newton 失败后二分。组合、单券、批次三层聚合必须使用一致的现金流口径，不能平均各批次收益率代替组合 XIRR。

CouponCalendarGenerator 当前按频率递推，只能算原型规则。更真实的模型需要起息日、下一付息日、到期日、节假日调整、日计数约定和提前赎回信息。测试应覆盖月末、闰年、到期日与票息同日、查询窗口边界和多批次去重。Windows 通知只消费已确认事件，数据库更新后要可重新计算并撤销过期提醒，不能把一次生成结果永久缓存。

OCR 的 contract test 可用本地假服务返回纯 JSON、代码围栏 JSON、多层响应外壳、缺字段、错误类型和恶意超长文本，验证 ParseCandidates() 只产出草稿。ViewModel 对资产类型、日期、数量、价格、票息和到期日逐项报错，用户勾选后再以单事务写库；任一记录失败时应决定全回滚还是明确部分成功。图片发送前展示 endpoint、字段范围和隐私提示，API key 存系统凭据库，异常只保留 request id 与脱敏摘要。这样才能证明“AI 提取”没有绕开金融数据的人工确认边界。

面试讲法

30 秒版本

Purrfolio 是 WinUI 3 本地资产追踪原型，按 App/Core/Infrastructure 分层。Core 里 XIRR 用 Newton 加二分兜底，OCR 导入经过草稿、人工复核和字段校验。现有领域测试记录为 9/9；数据库迁移、真实金融规则和 OCR 隐私仍需完善，归属及个人范围需本人确认。

2 分钟版本

项目把 UI、纯领域计算和 SQLite 分层。资产首页流式读取记录，计算四类永久组合偏离和复利目标；固定收益把交易与票息转现金流，XIRR 先 Newton、失败后二分；OCR 不直接入库，而是外部模型抽取、草稿、人工复核、字段校验再持久化。这个结构利于测试和替换基础设施，但 EnsureCreated 不适合演进，OCR 涉及投资隐私，派息与基准仍是简化模型，多 IRR 也需提示。只有本人实际 commit 的模块才讲为个人贡献。

追问与回答

问题1：为什么 Newton 后还要二分？

Newton 快但依赖初值和导数；导数接近零或越界时失败，找到异号区间后二分更稳定。

问题2：仓储为什么返回 IAsyncEnumerable？

可边读边聚合和取消，并隐藏 EF 读取方式；小数据量下价值有限。

问题3：OCR 为什么不能直接入库？

模型会误识别且输入敏感，必须草稿、用户确认、字段校验和事务写入。

问题4：EnsureCreated 有什么问题？

无法像 migration 那样记录和演进 schema，长期版本升级风险高。

问题5：如何处理多 IRR？

扫描更宽利率区间识别多个符号变化，提示歧义并建议 MIRR 或业务约束。
