01 · HTML、CSS、DOM、React、RN，先分清角色

在浏览器里，HTML 描述页面结构，CSS 描述外观与布局，JS 处理逻辑和交互。浏览器把 HTML 解析成 DOM（Document Object Model，文档对象模型）：一棵可以被 JS 访问和修改的节点树。

// 浏览器中的写法：查找 DOM 节点，直接修改它
const title = document.getElementById('title');
if (title) title.textContent = '加载完成';

你可以把 DOM 树粗略类比为 Android View 层级，但 DOM 节点不是 Android View。浏览器会根据 DOM 和 CSS 做布局与绘制。

React 是组织 UI 的库：你描述“当前数据应该显示成什么”，由 React 和对应渲染器去更新界面。React 用在网页上时，通常由 React DOM 更新浏览器 DOM；用在 RN 中时，由 RN 渲染器连接 Android/iOS 的原生 UI。

环境常见 UI 写法最终界面
传统网页 JSdocument.querySelector(...) 后手动修改节点浏览器 DOM + CSS
React 网页<div>{title}</div>React DOM 更新浏览器节点
React Native<View><Text>{title}</Text></View>RN 渲染器更新原生界面

因此普通 RN 代码不能照搬 document.getElementById、<div> 和网页 CSS 选择器。网页与 RN 共用的是 JS、React 等部分概念，宿主 API 不同。类比 Android：都可以写 Kotlin，但 Android 工程和普通 JVM 工程能用的平台 API 不一样。

02 · let / const 与对象引用：const 不等于对象不可变

let 声明可以重新赋值的变量；const 声明不能重新赋值的变量绑定。它们有块级作用域。类比 Kotlin 的 var / val 有助于入门，但 JS 不会因此获得 Kotlin 的静态类型。

let count = 0;
count = 1;                       // 可以

const user = {name: '小林', age: 28};
user.age = 29;                   // 可以：修改对象内容
// user = {name: '小陈', age: 30}; // 不可以：给 const 重新赋值

const sameUser = user;
sameUser.age = 30;
console.log(user.age);           // 30：两个变量引用同一对象
console.log(user === sameUser);  // true

对象和数组使用引用。两个字段完全相同、分别创建的对象，=== 比较仍然是 false。原始值中的字符串、数字等则按值进行相应比较；=== 不像 == 那样先做隐式类型转换。

console.log({id: 1} === {id: 1}); // false：两个不同对象
console.log('1' === 1);          // false：类型不同
console.log('1' == 1);           // true：发生了类型转换

这会直接影响 React：普通对象作为 state 时，原地修改后又把同一个引用传给 setter，React 可能根据 Object.is 判断新旧值相同而跳过更新。后文的“不可变更新”和 memo 都与引用身份有关。

03 · 箭头函数和回调：传函数，还是立刻执行？

JS 函数可以保存在变量里，也可以作为参数、返回值。回调就是把函数交给别人，由对方在某个时机调用；这个时机可能立即发生，也可能稍后发生。不是所有回调都异步，例如 Array.map 会同步调用回调。

function add(a, b) { return a + b; }
const add2 = (a, b) => a + b;     // 表达式作为返回值
const add3 = (a, b) => {          // 使用代码块就要显式 return
  return a + b;
};
const makeUser = () => ({name: '小林'}); // 返回对象，用括号避免被当成代码块

const log = () => console.log('点击了');
const callback = log;            // 保存函数，没有执行
log();                          // 现在执行

放进 RN 事件属性时，区别尤其重要：

<Pressable onPress={save}>…</Pressable>
// 把 save 函数交给组件，点击时由它调用

<Pressable onPress={() => save(item.id)}>…</Pressable>
// 把一个包装函数交给组件，点击时再执行 save(item.id)

<Pressable onPress={save(item.id)}>…</Pressable>
// 通常是错误写法：渲染时就调用 save，把返回值当作 onPress

箭头函数还会沿用外围的 this，不创建自己的 this；它不是普通 function 的所有场景都可无差别替换。不过阅读现代 RN 函数组件时，优先掌握“函数是值”和“什么时候执行”即可。

04 · 解构、展开、可选链：读代码最常见的简写

const user = {name: '小林', age: 28};
const {name, age: userAge} = user;
// 相当于 const name = user.name;
//         const userAge = user.age;   冒号在这里表示重命名

const [first, second] = [10, 20];    // 数组解构，按位置取值
const nextUser = {...user, age: 29}; // 复制第一层字段，再覆盖 age
const nextList = [...[1, 2], 3];     // 新数组 [1, 2, 3]

const nickname = user.profile?.nickname; // profile 为 null/undefined 时不再往下取
const label = nickname ?? '匿名';        // 仅在 null/undefined 时用默认值
const display = '' || '默认标题';        // || 对空字符串、0、false 等也会使用右边

{...user} 和 [...items] 是浅复制。嵌套对象依然可能共用引用；修改深层数据时，要复制受影响路径上的对象。字段覆盖顺序也重要：{...user, age: 29} 与 {age: 29, ...user} 结果可能不同。

null 常被用于主动表示“没有”；undefined 常出现在属性不存在、可选参数未传等场景。TS 的可选属性常对应可能为 undefined 的值。?. 不负责检查数据业务上是否有效，例如空字符串、负数还要自行校验。

看到 const {vip_pin_id: pinId} = props 时，读作“从 props 取出 vip_pin_id，用本地变量 pinId 接住”。看到 ({title}) => … 时，读作“函数接受一个对象，并直接把其中的 title 解构出来”。

05 · import / export、npm、Node.js 与 package.json

大型 JS 项目通过模块拆分文件。export 声明文件向外提供什么，import 声明从哪里使用它。它有点像 Java/Kotlin import，但 JS 模块加载还涉及实际代码求值和依赖打包。

// math.ts
export const plus = (a: number, b: number) => a + b; // 命名导出
export default function square(n: number) { return n * n; } // 默认导出

// 在另一个文件中
import square, {plus} from './math';
import {plus as add} from './math';  // 导入时重命名
import {View, Text} from 'react-native';
import type {ViewProps} from 'react-native'; // 类型导入，构建时被移除

命名导入 {plus} 必须对应导出的名称，也可以用 as 重命名；默认导入的本地名称可以自己取。这里的花括号是模块语法，不等于普通对象解构，虽然外形类似。

名字作用Android 类比与边界
Node.js在电脑或服务器上执行 JS 的运行环境开发工具常由它运行；手机里的 RN JS 通常由 Hermes 执行，不是 Node.js
npm / Yarn / pnpm管理 JS 包和执行脚本的工具类似依赖管理工具的部分职责，不等于 JS 引擎
package.json包信息、依赖声明和 scripts 命令可类比构建配置的一部分，原生 Gradle 配置仍然存在
node_modules安装后的包及其可解析入口里面不全是源码仓库，也可能是链接或构建产物
锁文件记录具体依赖解析结果帮助复现版本；不能只看 package.json 的版本范围
Bundler分析依赖，转换并组织可以加载的代码和资源RN 常用 Metro；项目也可以定制，后文会核对

./math 是相对文件路径；react-native 是包名；@kfe/prn-utils 是带作用域的包名，不是 Java 注解。Monorepo 表示一个工作区里管理多个包；workspace:* 指向工作区中的包。它们的具体解析结果依赖工具配置。

版本写 0.72.10 是精确声明；^18.2.0 对这个主版本允许兼容的更高 18.x 版本，不等于实际安装必然是 18.2.0。想知道当前使用哪个版本，还要看锁文件和安装内容。

06 · TypeScript：给 JS 加类型，不是另一套手机运行时

TypeScript（TS）主要在开发、编译检查阶段帮助你发现参数、字段和返回值不匹配。运行时通常执行的是移除类型后的 JS；type 和 interface 不会自动生成 Android 对象，也不会替你验证服务器响应。

type User = {
  id: string;
  nickname?: string;          // 可以不存在
};
type Status = 'idle' | 'loading' | 'success' | 'error'; // 联合类型

function getName(user: User): string {
  return user.nickname ?? '匿名';
}

interface CardProps {
  user: User;
  onOpen: (id: string) => void; // 属性本身是一个函数
}

function first<T>(items: T[]): T | undefined {
  return items[0];
}
const n = first<number>([1, 2]); // T 是泛型参数，可类比 Kotlin 泛型
// 编译器通常也能从传入的数组推断 T

User[] 表示 User 数组；A | B 表示允许两种类型；Promise<User> 表示异步结果成功时是 User；void 表示接口不提供供调用者使用的返回值。函数返回 void 不能证明它触发的异步工作已经完成。

as User 是类型断言：告诉检查器“按 User 看”，不是把数据真的转换成 User。网络返回的字符串写 as number 并不会变成数字；JSON.parse(text) as User 也不会自动检查是否存在 id。

不知道外部值是什么时，unknown 要求先做检查再使用；any 会绕过许多检查。类型的意义是帮助写对代码，不能代替运行时校验。

扩展名可以这样读：.js 是 JS；.ts 是 TS；.jsx 通常包含 JSX；.tsx 是支持 JSX 的 TS 文件。useState<User | null>(null) 中的尖括号是泛型，不是标签，表示这个 state 可以存 User 或 null。

07 · JSX：标签只是描述，花括号切回 JS 表达式

JSX 是写在 JS/TS 中的一种语法扩展。它看起来像 HTML，但会被构建工具转换成创建 React Element 的 JS 调用。它不负责自己画出像素。

const title = '订单详情';
const screen = (
  <View style={{padding: 16}}>
    <Text>{title}</Text>
  </View>
);

// 可以近似理解成下面的对象描述构造；实际转换也可能使用 jsx/jsxs runtime
const screen2 = React.createElement(
  View,
  {style: {padding: 16}},
  React.createElement(Text, null, title)
);
  • {title}：在 JSX 中插入一个 JS 表达式的结果。
  • style={{padding: 16}}：外层花括号进入 JS，内层花括号创建对象。
  • <UserCard user={user} />：使用一个自定义组件，并传入属性。组件名通常首字母大写。
  • children：标签之间的嵌套内容，会成为传给组件的特殊属性之一。
  • <>…</>：Fragment 分组语法，不额外要求一个包裹的原生 View。

花括号里写的是表达式，不是任意语句；条件常用三元表达式。RN 的文本要放在 <Text> 中，不能直接把字符串当普通 View 的文本孩子。

<Text>{isLoading ? '加载中' : title}</Text>
{count > 0 ? <Text>共 {count} 条</Text> : null}

条件渲染不只是隐藏像素：当组件被移出 React 树，它会卸载，局部 state 可能随之丢弃，effect 清理会执行。这与 Android 把现有 View 设置为 GONE 不是同一件事。

08 · 闭包：函数可以继续访问创建它时的外围变量

闭包并不是什么特殊语法。函数被创建时，会保留访问外围词法作用域的能力；即使外层函数已经返回，内层函数仍然能访问相关变量。

function makeCounter() {
  let count = 0;
  return () => ++count;
}
const next = makeCounter();
console.log(next()); // 1
console.log(next()); // 2：仍能访问那次 makeCounter 调用中的 count

闭包不是一律把值复制冻结。如果修改的是同一个作用域里的变量，闭包可以读到它的变化。React 的旧闭包问题，是因为组件每次重新执行都会产生新一轮局部变量和函数。

// 用普通 JS 模拟“两次调用各有一份局部变量”
function makeHandler(count) {
  return () => count;
}
const oldHandler = makeHandler(0);
const newHandler = makeHandler(1);
console.log(oldHandler()); // 0
console.log(newHandler()); // 1

在 React 中，第一次渲染注册的定时器可能继续持有第一次的回调；后续渲染里的 count 虽然变了，旧回调并不会自动换成新函数。所以 effect 的依赖数组、函数式 state 更新和 ref 都是在处理不同需求下的状态访问问题，不能简单认为“用了闭包就是 bug”。

useCallback(fn, []) 会尝试保留同一个函数引用，但不会神奇地让这个函数读取每次渲染的最新局部变量。要根据真正使用的数据声明依赖，或使用适合该场景的状态访问方式。

09 · Promise、async / await：异步不等于另开一条 JS 线程

Promise 表示一个可能稍后完成的结果，状态从 pending 转为 fulfilled 或 rejected。你可以用 .then 处理成功、.catch 处理失败；async / await 是组织 Promise 控制流的语法。

async function loadTitle() {
  try {
    const response = await fetch('https://example.com/api/title');
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const data = await response.json();
    return data.title; // 示例：真实代码还应校验响应结构
  } catch (error) {
    console.log('读取失败', error);
    throw error;
  }
}
// 示例地址用于说明写法，不是本文提供的可用接口

声明为 async 的函数返回 Promise。它遇到 await 前会同步执行；await 挂起的是后续执行流程，不是阻塞整个 JS 线程。底层网络由宿主提供，但 async 本身不会把任意代码放到后台线程。

async function heavy() {
  // 这里如果进行很长的同步循环，仍然会占住当前 JS 执行线程。
  // async 关键字不会替你创建工作线程。
}

事件循环先掌握这个最小例子

一个常见 JS 执行上下文中，同步代码先沿调用栈运行。Promise 的后续处理通过微任务安排；定时器回调则等待宿主调度。下面这个简单例子，在常见浏览器和 Node 环境中输出 A → B → C → D：

console.log('A');
setTimeout(() => console.log('D'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('B');

setTimeout(..., 0) 不是“立即执行”，也不保证精确延时。RN 的定时器、微任务和原生事件还要经过版本及宿主实现，不能把浏览器 HTML 事件循环的所有阶段原样套到 RN；但当前同步 JS 长任务会推迟需要该线程的后续工作这一点仍是重要的排查起点。

还有一个细节：new Promise((resolve) => { … }) 里的执行器函数会立即同步运行，异步的是之后的结果通知方式。Promise 不是线程，也没有默认的通用取消功能；页面退出后的请求取消或忽略旧结果，要自己设计。

Android 类比：可以把“等待结果后接着写”联想到协程写法，但 async 不等于 withContext(Dispatchers.IO)。不要因为用了 await，就认定某段重计算已经离开 JS 线程。

10 · 组件、props、state：父级给输入，事件请求改变状态

组件可以先理解成“接收输入、返回 UI 描述的函数”。props 是父组件给的输入，state 是 React 为该组件保存的状态。普通局部变量不等于 state：重新调用组件函数时局部变量会重新建立，修改它也不会自动通知 React 更新。

type CounterButtonProps = {
  count: number;
  onIncrement: () => void;
};

function CounterButton({count, onIncrement}: CounterButtonProps) {
  return (
    <Pressable onPress={onIncrement}>
      <Text>点击次数：{count}</Text>
    </Pressable>
  );
}

function CounterPage() {
  const [count, setCount] = useState(0);
  return (
    <CounterButton
      count={count}
      onIncrement={() => setCount(previous => previous + 1)}
    />
  );
}

数据往下传：CounterPage → count → CounterButton。事件往上传：孩子调用父级传入的 onIncrement。父级更新 state 后，React 重新计算相关 UI，再把新 count 给孩子。这叫单向数据流。

子组件不应直接修改 props。多个兄弟组件需要共享同一份数据时，常把状态放到共同父级，再传给它们，称为“状态提升”。Context 用于向较深层后代提供数据；Redux、Jotai 等则是额外的状态管理方案，不是理解 RN 渲染前必须掌握的前置知识。

受控组件指 UI 的显示值由 React 状态控制。例如 <TextInput value={name} onChangeText={setName} />：用户输入通过事件改变 state，state 再决定输入框 value。如果只给 value 却不处理更新，输入框可能一直保持旧值。

11 · 从零理解 Hook：组件反复执行，状态为什么还在？

先不要背 API 表。你已经理解了 makeCounter() 返回的函数可以保留对 count 的访问，现在再往前一步：React 会反复调用组件函数；Hook 让这些调用能够使用 React 保存的状态、引用和同步逻辑。这些是 React 的能力，RN 使用同样的编程模型。这里的 Hook 不是 Android 插桩或拦截方法。

本节先用独立教学示例讲执行过程，再读你项目里的真实片段。第一次阅读建议依次看 1～6，弄懂 state、ref 和 effect 后，再看缓存、规则与项目源码；进阶部分可以稍后展开。

  4. useRef：跨渲染保存对象，为什么不刷新界面

1 · 先分清：调用函数、重新渲染、重新挂载

传统 Android View 写法里，你可能在 Activity 的字段中保存 count，再在监听器里修改字段和 TextView。React 函数组件则通常描述：“在当前数据下，界面应该是什么样。”数据变了，React 再调用组件函数，重新获得 UI 描述。

// 教学反例：普通局部变量不能承担 React 界面状态
function WrongCounter() {
  let count = 0;
  return (
    <Pressable onPress={() => { count += 1; }}>
      <Text>{count}</Text>
    </Pressable>
  );
}

这里有两个不同的问题。第一，点击闭包确实能修改那次调用中的 count，但 React 没收到状态更新通知，已经返回的 JSX 中的数字也不会跟着自动改变。第二，如果父级更新等原因让 WrongCounter 再次执行，新的调用又会创建一个初值为 0 的 count。

对照前面的 makeCounter：你调用的是它返回的 next，外层 makeCounter 没有再执行；这里 React 会再次执行外层组件函数。普通闭包能保留变量，但不会自动提供 React 的状态保存与更新调度。

术语具体发生什么Android 视角注意点
渲染 renderReact 调用组件，计算 UI 描述不是直接在 Canvas 上绘制，也不等于重建整页原生 View
提交 commit把这次计算确认的更新应用到界面树未提交的计算不代表用户看到了新界面
挂载 mount一个组件身份首次进入树并提交不是组件每被调用一次就挂载一次
卸载 unmount该组件身份从树中移除页面被遮挡或隐藏，不一定导致卸载

同一树位置和组件类型、key 等共同参与身份判断。身份保留时，重新渲染可以保留 Hook 状态；身份被替换或卸载后重新挂载，状态通常重新初始化。Hook 状态不是全局变量，也不像能独立于 View 生存的 ViewModel 那样自动跨组件卸载保留。

2 · useState：保存的是 React 的状态，count 是本次读取结果

import {useState} from 'react';
import {Button, Text, View} from 'react-native';

export function Counter() {
  const [count, setCount] = useState(0);

  function handlePress() {
    setCount(count + 1);
    console.log('这次回调中的 count:', count);
  }

  return (
    <View>
      <Text>点击次数：{count}</Text>
      <Button title="加 1" onPress={handlePress} />
    </View>
  );
}

先把第一行展开读：useState(0) 返回两个东西，数组解构把它们分别命名为 count 和 setCount。count 是本次渲染读取到的状态值；setCount 是向 React 请求更新该状态的函数。数字 0 是初始状态。

首次渲染
count = 0→点击回调
请求状态变为 1→再次渲染
新的 count = 1→提交更新
文本显示 1
时刻实际执行为什么
首次渲染useState 初始化为 0；创建 handlePress；返回 JSXonPress={handlePress} 只是传函数，没有调用它
第一次点击执行第一轮创建的 handlePress；setCount(0 + 1)该函数捕获的是第一轮的 count
紧接着打印输出 0setter 没有给当前闭包的 count 重新赋值
下一轮渲染React 再调用 Counter；useState 返回状态 1React 保留了该组件身份对应的状态

你前面提出的“每次都会新建 count”在这里是对的。每次调用都有自己的局部 const count，但 useState 给这个新变量的值可以分别是 0、1、2。跨渲染保存的是 React 管理的状态记录，不是某个一直被修改的局部 const。

这里的“状态快照”是指本次渲染读取到的值，并不意味着 React 会深复制或冻结所有对象。不要直接改 state 中的对象。setCount 在同一组件挂载期间具有稳定身份；更新可能被合并，也可能因值相同而跳过，不能按 setter 调用次数推算渲染次数。await setCount(1) 也不能等待界面提交，它不返回这样的 Promise。

3 · useState 的三个常见疑问

① 为什么连续加三次，有时只加了 1？假设这次回调读取到 count = 0：

// 片段 A：同一事件回调中连续执行
setCount(count + 1); // 请求设为 1
setCount(count + 1); // 仍然请求设为 1
setCount(count + 1); // 仍然请求设为 1

// 片段 B：另一种写法，单独使用，不与 A 混在一起
setCount(previous => previous + 1);
setCount(previous => previous + 1);
setCount(previous => previous + 1);

A 的三个表达式都读取同一个 count，三个请求都是“设成 1”。B 传的是更新函数，React 按队列把待处理的状态传进去：0 → 1 → 2 → 3。previous 不是 React 关键字，可以叫 n 或 prev；它是 React 调用更新函数时提供的参数。

当新值依赖旧值时，优先考虑这种函数式更新。更新函数必须保持纯粹：只计算并返回状态，不在里面发请求、埋点或操作原生服务，因为 React 可能重试计算，开发检查也可能重复调用它。

② useState(0) 每次都执行，为什么不会重置？React 在挂载阶段采用初值，在更新阶段读取保存的状态。但 JavaScript 的参数表达式依然会先执行：

// 假设 buildInitialItems 是一个纯计算函数
const [itemsA, setItemsA] = useState(buildInitialItems());
// 每次组件执行，JS 都会先调用 buildInitialItems()

const [itemsB, setItemsB] = useState(() => buildInitialItems());
// 把初始化函数交给 React，由 React 在初始化时调用

第二种叫惰性初始化，适合需要计算的初值；并不是后台执行，也不保证整个应用生命周期只调用一次。重新挂载会重新初始化，开发检查也可能额外调用，因此初始化函数要纯粹。useState(initialName) 不会在父级以后修改 initialName 时自动同步，是否重置要由业务明确决定。

③ 对象字段变了，为什么没更新？

// 错误示例：修改了原对象，还传回同一个引用
user.name = '小明';
setUser(user);

// 正确更新方式：创建新对象；其余字段保留
setUser(previous => ({...previous, name: '小明'}));

React 用 Object.is 判断状态值是否相同，同一个对象引用可能使更新被跳过，而且直接修改对象会破坏旧渲染的数据。展开语法只是浅拷贝；修改深层字段时，需要为变更路径上的对象逐层创建新对象。Hook 的对象 setter 是替换值，不会自动合并字段。

4 · useRef：一个跨渲染保留的可变盒子

import {useRef, useState} from 'react';
import {Button, Text, View} from 'react-native';

export function RefCounter() {
  const clicks = useRef(0);
  const [visibleCount, setVisibleCount] = useState(0);

  function recordClick() {
    clicks.current += 1;
    console.log(clicks.current);
  }

  return (
    <View>
      <Text>上次同步的次数：{visibleCount}</Text>
      <Button title="只记录，不刷新" onPress={recordClick} />
      <Button title="同步到界面"
        onPress={() => setVisibleCount(clicks.current)} />
    </View>
  );
}

useRef(0) 首次返回类似 {current: 0} 的对象。相同组件身份后续渲染时，React 返回同一个对象。局部变量 clicks 每次重新声明，但都指向这个盒子。第一次按钮点三次，控制台依次打印 1、2、3，文本仍显示 0；再点“同步到界面”，读取盒子里的 3 并更新 state，文本才显示 3。

可以把 ref 类比为随组件身份保留的可变字段，把 state 理解为参与 React 界面更新的数据。定时器句柄、订阅对象、原生组件引用常适合用 ref 保存；需要直接显示给用户的数据通常用 state。普通对象 const box = {current: 0} 每次都会重建，不具有 useRef 的保留机制。

ref 也能连接 RN 原生组件，例如 useRef<TextInput>(null) 配合 <TextInput ref={inputRef} />，在事件中调用 inputRef.current?.focus()。这和前面的数字盒子使用的是同一个 Hook，但用途不同。

与闭包的关系：旧回调如果捕获 clicks 这个稳定对象，并在执行时读取 clicks.current，可以读到后来写入的内容；若先写 const saved = clicks.current 再捕获 saved，拿到的仍可能是旧数字。ref 不会自动跟 state 同步，普通渲染过程也不应随意读写 ref 来驱动 UI；把必要读写放在事件或 effect 中。

5 · useEffect：在提交后建立外部同步，并交代怎么收尾

先回答“为什么需要它”：组件函数可能反复执行，渲染也可能被重试或放弃。如果直接在函数体里 setInterval、注册监听或连接服务，每次渲染都可能多建一份。Effect 用于把已经提交的组件数据与 React 之外的系统同步，例如定时器、事件源、网络或原生服务。

以下计时器是可单独阅读的完整教学组件：

import {useEffect, useState} from 'react';
import {Text} from 'react-native';

export function Ticker({intervalMs = 1000}: {intervalMs?: number}) {
  const [ticks, setTicks] = useState(0);

  useEffect(() => {                         // A：setup 建立函数
    const timer = setInterval(() => {      // B：定时回调
      setSeconds(previous => previous + 1);
    }, intervalMs);

    return () => {                          // C：cleanup 清理函数
      clearInterval(timer);
    };
  }, [intervalMs]);

  return <Text>触发次数：{ticks}</Text>;
}

ticks 每次回调加 1，表示触发次数；intervalMs 改变或 JS 忙碌时，不能把它当准确墙上时钟。现在逐个辨认函数：

  1. A 是 setup：组件渲染时把函数传给 useEffect。React 在相应提交后的 effect 阶段执行它，建立一个定时器。
  2. B 是定时回调：由定时器系统稍后调用，每次请求次数加 1；不是 React 每渲染一次就调用一次。
  3. C 是 cleanup：A 把这个函数返回给 React。此时没有执行 clearInterval；React 在需要清理时才调用 C。

return () => clearInterval(timer) 是“返回一个以后负责关定时器的函数”；return clearInterval(timer) 会立刻关掉定时器并返回 undefined，两者含义完全不同。

发生的事setup / cleanup 怎么执行
以 intervalMs=1000 挂载并提交setup A 执行，建立定时器 T1
T1 触发，state 变化并提交组件再次执行，依赖仍为 1000，不重建定时器
父级把 intervalMs 改为 500，新结果提交先调用旧 cleanup 关闭 T1，再运行新 setup 建立 T2
组件卸载调用 T2 对应的 cleanup

旧 cleanup 为什么能找到 T1？timer 是那次 setup 的局部变量，cleanup 通过闭包继续访问它。下一次 setup 创建另一个 timer 和另一个 cleanup，各自对应自己的资源。这里正是你前面学到的闭包在业务中的用途。

Effect 回调仍运行 JS，不是自动放到后台线程。请求 API 可以异步，但回调里的大计算依然会占用 JS 执行时间。useEffect 也不能作为“用户一定已看到屏幕”的严格时序保证。

不要直接套 Activity 生命周期：[] 的 effect 不是 onResume；RN 页面隐藏可能仍然挂载。需要进入可见状态就恢复播放、隐藏就暂停时，应接入宿主或导航提供的可见性事件。开发环境启用相应 Strict Mode 检查时，还可能额外经历 setup → cleanup → setup；RN 0.72 是否触发具体检查取决于根节点和渲染器配置，不能断言本项目一定“双调用”。资源建立和清理应当能够配对。

6 · 依赖数组不是“随便控制次数的开关”

useEffect(setup, [intervalMs]) 的意思是：这份同步逻辑依赖 intervalMs；它变化后，旧逻辑需要清理，新逻辑需要建立。React 不会扫描函数代码替你生成这个数组，你需要写出回调读取的响应式值，例如 props、state，以及组件体内声明并使用的变量和函数。

写法初次提交后续提交清理
省略第二个参数执行 setup该组件每次提交后重新执行重跑 setup 前清理旧 effect；卸载也清理
[]执行 setup不因普通依赖变化重跑卸载时清理；开发检查等另有边界
[intervalMs]执行 setup该值与上次不同时重新执行先清理上次，再建立本次；卸载也清理

React 逐项使用 Object.is 比较：相同数值或字符串通常相等；Object.is({}, {}) 为 false，因为是不同对象。数组的项目数和顺序应保持固定。不是深比较，也不会检测某个对象内部被偷偷修改的字段。

// 教学片段：options 每次渲染都是新对象
const options = {topic};
useEffect(() => {
  const subscription = subscribe(options);
  return () => subscription.remove();
}, [options]);

// 如果实际只依赖 topic，可把临时对象放进 effect
useEffect(() => {
  const subscription = subscribe({topic});
  return () => subscription.remove();
}, [topic]);

这里假设 subscribe 是模块外部提供的稳定函数，并返回有 remove 方法的订阅句柄，不是本项目 API 摘录。第一种写法即使 topic 不变，也可能每次提交都重订阅；第二种直接表达真正依赖。不要为躲开重跑删掉依赖：应调整逻辑，使依赖与读取的数据一致。

为什么 Ticker 不需要把 ticks 写进依赖？因为 setup 及其定时回调没有读取外层 ticks，它使用 React 提供 previous 的更新函数。setTicks 的身份稳定，可以省略；加入它也不会因此重建定时器。稳定 ref 对象通常也不需要加入；把 ref.current 放进数组，并不能让 ref 的修改自动触发渲染或 effect。

不是所有逻辑都需要 effect：根据 name 得到 name.trim()，直接在渲染中计算；点击提交表单，在点击回调里提交。不要先在 effect 中计算一个派生值、setState，再多跑一轮渲染。如果 effect 更新了 state，而该更新又持续改变它的依赖，就可能形成循环。

7 · 把闭包知识接回来：旧值与异步竞态

常见错误：定时器一直把数字设为 1。

// 假设首次渲染 count = 0
useEffect(() => {
  const timer = setInterval(() => {
    setCount(count + 1); // 一直读取建立此回调的那轮 count：0
  }, 1000);
  return () => clearInterval(timer);
}, []);

// 对“每次在原数值上加 1”的需求，回调改为：
// setCount(previous => previous + 1);

空数组让这份定时逻辑不会因 count 变化重建；它持有的回调也仍是旧闭包。新一轮渲染创建了新 count，不会改写旧回调所访问的那个变量。这就是 stale closure，通常译作“陈旧闭包”。

函数式更新解决的是“如何基于最新待处理 state 计算下一值”。如果回调还写了 console.log(count) 或读取其他旧 props，它们不会自动变新。若需求确实要求 count 每次变化都重新建立同步，可以声明 [count]，但对定时器会造成每次更新都重置计时间隔，需判断是否符合业务。

另一个问题：先发请求，反而后返回。用户从 A 切到 B，A 的旧请求可能晚于 B 完成。下面是教学 Hook，loadUser 作为参数传入，并假定调用方在无语义变化时保持它的引用稳定：

import {useEffect, useState} from 'react';

type User = {id: string; name: string};

export function useUser(
  userId: string,
  loadUser: (id: string) => Promise<User>,
) {
  const [result, setResult] = useState<{
    id: string; user: User | null; error: string | null;
  } | null>(null);

  useEffect(() => {
    let ignored = false;

    async function run() {
      try {
        const user = await loadUser(userId);
        if (!ignored) setResult({id: userId, user, error: null});
      } catch (error) {
        if (!ignored) {
          setResult({id: userId, user: null, error: String(error)});
        }
      }
    }

    void run();
    return () => { ignored = true; };
  }, [userId, loadUser]);

  // 切换用户时，不把上一个用户的数据当作当前用户展示
  return result?.id === userId ? result : null;
}
  1. A 的 setup 创建 ignoredA=false 并启动请求 A。
  2. 切到 B 并提交，React 清理 A：ignoredA 被改为 true；B 的 setup 则创建自己的 ignoredB=false。
  3. B 返回，检查自己的标记后允许更新；A 以后返回，看到 ignoredA=true，忽略旧结果。

这是闭包共享变量的另一个例子：同一次 setup 里的异步函数和 cleanup 访问同一个标记。该写法忽略过期结果，没有取消底层网络请求；真正取消要看网络 API 是否支持。不要直接写 useEffect(async () => …)，async 函数返回 Promise，而 effect 需要返回清理函数或不返回值。因此把 async 函数定义在 setup 内部，再调用它。

8 · useCallback：缓存的是函数引用，不是执行结果

每次组件执行，普通函数表达式会创建一个新的函数值。即使两次函数体文字相同，(() => 1) === (() => 1) 也为 false。有时候孩子使用 React.memo 比较 props，或者某个 effect 把函数作为依赖，我们希望“输入没变时仍拿到同一个函数引用”。这时才考虑 useCallback。

const onPress = useCallback(() => {
  openDetails(itemId);
}, [itemId]);

这是教学片段，假设 openDetails 是稳定的模块函数。useCallback 本身不会调用传入的箭头函数；第一次返回它，以后依赖没变就返回缓存的旧函数。itemId 改变，则返回这轮传入的新函数，让它读取新 itemId。

渲染这轮传入函数React 返回
itemId=A，首次函数 F1，捕获 AF1
itemId=A，其他 state 更新新函数 F2，仍捕获 A依赖相同，返回 F1
itemId=B新函数 F3，捕获 B依赖变化，返回 F3

因此 useCallback 不会阻止函数表达式被求值或创建函数；它控制的是返回给你的引用是否复用。依赖数组也不是 Kotlin/C++ 意义上的“捕获列表”：JS 闭包已经决定能访问哪些变量，数组只是告诉 React 何时更新缓存。

若改成 []，点击可能一直用首次的 itemId。若 openDetails 来自 props，也要考虑把它放入依赖。不要为了“性能”把所有依赖删掉；也不必给每一个按钮套 useCallback。普通孩子仍可能随父级渲染，useCallback 本身并不阻止组件执行。

9 · useMemo：缓存计算结果；计算仍发生在渲染期间

const visibleItems = useMemo(() => {
  return items.filter(item => item.title.includes(keyword));
}, [items, keyword]);

这里的 visibleItems 是数组。第一次渲染时，React 调用计算函数并缓存返回的数组；items 和 keyword 都没变时，返回旧数组；任一依赖变化时重新计算。它适合有实际成本的纯计算，或需要稳定结果引用的场景。简单的 count * 2 通常直接计算即可。

对比useMemo(() => 结果, deps)useCallback(函数, deps)
拿到什么计算返回的结果函数本身
依赖变化时在渲染中调用计算函数返回这轮提供的函数，不调用它
常见例子过滤后的列表、计算结果传给孩子的点击回调
共同边界依赖按 Object.is 比较；不提供后台线程；缓存是优化手段，业务正确性不能依赖缓存永远存在

概念上，useCallback(fn, deps) 类似 useMemo(() => fn, deps)；这是帮助理解返回值的类比，不是声称 RN 源码直接这么实现。不要在 useMemo 内请求网络、setState 或注册监听；计算可能重跑或被放弃。

10 · 为什么必须在顶层调用？先看状态记录，再看源码

function Profile() {
  const [name, setName] = useState(''); // 第一次状态 Hook 调用
  const [age, setAge] = useState(18);   // 第二次状态 Hook 调用
  const inputRef = useRef(null);       // 接着读取 ref 的记录
  // 其余逻辑和 JSX……
}

React 并不靠 name、age 这些变量名字识别状态。你可以先把它理解为：React 针对组件保留一串记录；下次按相同调用顺序依次取回 name 状态、age 状态、ref 对象。如果某次 if 跳过了第一个 useState，后面就无法按原顺序匹配。

// 错误：是否调用 Hook 随条件改变
if (enabled) {
  useEffect(() => startWork(), []);
}

// 正确结构：每次调用 Hook，在 setup 内判断
// 假设 startWork 是外部稳定函数，并返回 cleanup
useEffect(() => {
  if (!enabled) return;
  return startWork();
}, [enabled]);

React 18 常见 Hook 应在函数组件或自定义 Hook 顶层调用，不能放在条件、循环、普通事件回调中，也不能放在可能提前 return 之后。事件中调用 setState 是允许的；在事件中临时调用 useState 创建状态则不行。这两个动作要分开。

进阶：本地 RN 0.72.10 渲染器如何支撑这个模型

本次实际读取 pikachu/node_modules/react-native/Libraries/Renderer/implementations/ReactNativeRenderer-dev.js。这是本地 RN 自带的开发版渲染器实现，以下是按函数行为整理的说明，不是完整执行器伪装成的几行代码：

  • mountWorkInProgressHook（11010 行）：创建有 memoizedState、queue、next 等字段的 Hook 记录，将第一条接到正在渲染的 Fiber，后续用 next 串起来。
  • mountState（11556 行）：处理初值，保存状态和更新队列，返回状态与 dispatch；updateState 进入更新队列处理，所以不是每次重置初值。
  • mountRef / updateRef（11621 / 11633 行）：首次保存 {current: initialValue}，更新时返回保存的对象。
  • updateEffectImpl（11650 行）：比较依赖，保留旧清理函数，按需要标记 effect；不是在组件函数运行到这里时立即执行 setup。
  • updateCallback / updateMemo（11797 / 11824 行）：依赖相同时分别返回旧函数、旧结果；不同则保存新的值。

“按顺序取记录”是入门模型。实际实现还有 Fiber 的当前树与工作树、更新优先级、队列和重渲染处理，不是一个全局数组保存所有组件状态。这里也不推断宿主带后缀的二进制与该源码逐字一致。

11 · 自定义 Hook：把状态与同步逻辑组合成一个函数

当多个组件都要“保存计数，暴露增加和重置操作”，可以抽成 useCounter。它仍是普通 JS/TS 函数，但内部调用 Hook，因此使用位置要遵守 Hook 规则，名字以 use 开头也让检查工具能识别这种约定。

import {useState} from 'react';
import {Button, Text, View} from 'react-native';

function useCounter(initialValue = 0) {
  const [count, setCount] = useState(initialValue);
  const increment = () => setCount(previous => previous + 1);
  const reset = () => setCount(initialValue);
  return {count, increment, reset};
}

export function TwoCounters() {
  const left = useCounter(0);
  const right = useCounter(10);
  return (
    <View>
      <Text>左边：{left.count}；右边：{right.count}</Text>
      <Button title="左边加 1" onPress={left.increment} />
      <Button title="右边加 1" onPress={right.increment} />
    </View>
  );
}

点左边，左边变成 1，右边仍是 10。复用了函数逻辑，没有自动共用状态。两次 useCounter 中的 useState 对应不同记录，记录归调用它的组件管理，不是 useCounter 函数的静态字段。

如果确实需要共享一份状态，应提升到共同父级，或结合 Context / 外部 store。自定义 Hook 也可以包装共享 store，所以“自定义 Hook 一定独立”同样不准确，要看它内部的数据来源。上例没有用 useCallback，因为这里没有必须稳定回调引用的需求。initialValue 后续变化不会自动重置 count，但当前渲染的 reset 会使用当前 initialValue。

12 · 回到你的项目：按同一套问题读三段真实代码

下面才是项目摘录，保留实际名称；展示时仅调整缩进或标明省略范围。每段都问：谁调用它、捕获了什么、什么时候更新、什么时候清理？

实例 A：头像点击随 jumpUrl 更新。源码：pikachu/pages/VipPin/src/components/NavBar/Avatar.tsx，66 行附近。

const onPress = useCallback(() => {
  if (jumpUrl) {
    void ZRouter.openURL(jumpUrl)
  }

同文件把 onPress 传给点击组件。useCallback 在渲染时返回回调，用户点击时才执行 openURL。jumpUrl 没变可复用引用；变了就返回能读取新地址的回调。改成 [] 会有旧地址风险。void 表示忽略该表达式的返回值，本身既不延迟执行，也不是异常处理。

实例 B：关注回调不直接读取旧 pageData。源码：pikachu/pages/VipPin/src/PinIndex.tsx，115 行附近。

const handleFollowStatusChange = useCallback((isFollowing: boolean) => {
  setPageData(prev => ({
    ...prev,
    info: {
      ...prev.info,
      isFollow: isFollowing,
    },
  }))
}, [])

外层回调由业务事件传入 isFollowing；内层更新函数由 React 提供 prev，并捕获这次事件的 isFollowing。它没有从外层闭包读取 pageData，所以不用把 pageData 加进依赖。setPageData 身份稳定，这就是这里 [] 有依据的原因。更新时创建新 pageData 和新 info，保留其他字段。

如果后来往这个回调里增加对某个 prop 的读取，就需要重新检查依赖，不能照抄空数组。函数式更新只保证 prev 的来源，不会让所有外部变量自动保持最新。

实例 C：声音组件的 useMount 是什么？源码：pikachu/node_modules/@cfe/hooks/dist/useMount.js，19 行附近。省略说明注释后，实现为：

import { useEffect } from 'react';
export function useMount(effect) {
  useEffect(effect, []);
}

useMount 不是 React 内置 Hook，也没有新生命周期机制，只是这里的依赖包对 useEffect 的封装。它传入空数组，所以不要误以为用它后，回调就自动读取最新 props/state。

调用点在 pikachu/pages/VipPin/src/components/Sound/index.tsx 109 行开始：setup 注册 statusListener 和 timeListener；147 行附近返回以下清理函数（只摘录返回部分）：

return () => {
  SoundBridges?.destroy(soundKey.current)
  statusListener?.remove?.()
  timeListener?.remove?.()

两个 listener 变量通过闭包保留，清理时移除那次 setup 创建的监听。soundKey 则是 ref，soundKey.current 在清理执行时才读取；它不是自动冻结的初始字符串。若该值可能变化，通常需要核对创建与销毁是否对应同一个资源。

13 · 进阶选读：另外三个常见 Hook

useReducer：状态更新规则多时，把规则集中起来

useState 适合直接设置或按旧值算新值。如果页面有 loading、success、error 等多种状态转换，可用 reducer 函数集中表达：“旧状态 + action → 新状态”。dispatch 是提交一个动作；reducer 负责纯计算，不负责发请求。

import {useReducer} from 'react';

type Action = {type: 'increment'} | {type: 'reset'};
function reducer(state: number, action: Action): number {
  switch (action.type) {
    case 'increment': return state + 1;
    case 'reset': return 0;
  }
}

function useReducerCounter() {
  const [count, dispatch] = useReducer(reducer, 0);
  return {count, increment: () => dispatch({type: 'increment'})};
}

Android 视角可类比把状态处理收进一个 reducer，但 useReducer 本身不等于完整 MVI 或 Redux，也不会自动成为全局 store。它仍随组件身份保存状态，dispatch 后当前回调里的 count 也不会被原地改写。

useContext：从上层 Provider 读取共享输入

逐层传 props 太繁琐时，上层可以通过 Context.Provider 提供一个值，后代用 useContext 找到最近的对应 Provider读取它。它不会单独替你创建业务状态；常由父级 useState 保存数据，再作为 value 提供。

import {createContext, useContext} from 'react';
import {Text} from 'react-native';

const ThemeContext = createContext('light');

function Caption() {
  const theme = useContext(ThemeContext);
  return <Text>当前主题：{theme}</Text>;
}

export function ContextExample() {
  return (
    <ThemeContext.Provider value="dark">
      <Caption />
    </ThemeContext.Provider>
  );
}

Caption 读到 dark；没有匹配 Provider 时才使用 createContext 的默认值 light。这里采用 React 18 的 Provider 写法。Provider 的 value 变化可以使消费者重新渲染；每次都传新对象需要留意更新范围。它有“由上层提供依赖”的相似性，但不是 Android Context，不提供 Activity、Resources 等平台能力。

useLayoutEffect：确实需要布局阶段同步处理时再使用

useLayoutEffect 与 useEffect 一样有依赖和 cleanup，主要区别是执行阶段：前者在提交的布局 effect 阶段同步运行，常用于需要配合宿主布局测量的处理；普通 useEffect 属于被动 effect。同步执行更容易延长提交过程，因此不要把所有 useEffect 改成它。

RN 的原生测量结果何时可用，还要看具体组件、测量 API 和渲染架构；不能照抄浏览器 DOM 的 getBoundingClientRect，也不能把 useLayoutEffect 当作 Android onLayout 的同名替代。一般先理解 RN 的 onLayout 事件，只有明确时序需求再深入这个 Hook。

需求先考虑理由

自测 1：每次都是 const count，状态怎么增加？

每次组件调用创建新的 count 绑定，它接收 React 该轮返回的状态。React 保存了组件身份对应的状态记录；旧回调仍读取旧一轮的绑定。不是通过重新赋值某个 const 增加状态。

自测 2：useEffect 的函数是在代码执行到这一行时运行吗？

渲染时调用的是 useEffect，向 React 提供 setup 和依赖；setup 在相应提交后的 effect 阶段运行。setup 返回 cleanup，cleanup 到依赖变化或卸载等清理时机才执行。

自测 3：[] 表示函数不捕获外部变量吗？

不表示。捕获由 JS 词法作用域决定；依赖数组控制 effect 重新同步或 memo/callback 缓存更新。删掉依赖不会删掉捕获，可能造成旧值问题。

自测 4：修改 ref.current，为什么控制台变了但页面没变？

修改的是普通对象字段，React 不会因此自动调度渲染。需要展示的值通常放在 state；不要依赖其他更新“顺便刷新”。

自测 5：两处调用 useCounter，是不是共享一个 count？

本节实现中不是，每次调用内部的 useState 对应独立状态记录。自定义 Hook 复用逻辑；只有它显式读取同一 Context/store 等共享来源时，才可能共用数据。

自测 6：useMemo、useCallback 和 useEffect 怎么一句话区分？

useMemo 在渲染时按依赖缓存纯计算结果；useCallback 按依赖缓存函数引用；useEffect 在提交后与外部系统同步，并返回清理逻辑。前两者的缓存是性能手段，后者承担外部同步语义。

12 · map、filter、列表 key 与不可变更新

map 把每个元素转换成一个新结果，组成新数组；filter 留下满足条件的元素。它们不会自动深复制数组里的对象。

const items = [{id: 'a', title: '第一项'}, {id: 'b', title: '第二项'}];
const titles = items.map(item => item.title);    // ['第一项', '第二项']
const kept = items.filter(item => item.id !== 'a'); // 只保留第二项

// JSX 中，小列表可以这样显示；长列表通常用 FlatList 等组件
<View>
  {items.map(item => <Text key={item.id}>{item.title}</Text>)}
</View>

key 让 React 判断更新前后同级条目是否仍是同一个条目。优先使用稳定的业务 ID，不要每次生成随机数，也不要在会重排的列表里轻率地使用数组位置。它不是普通 props；孩子需要 ID 时，要另传 id={item.id}。

// 更新一个条目：创建新数组，变化的条目创建新对象
setItems(previous => previous.map(item =>
  item.id === targetId ? {...item, title: '新标题'} : item
));

// 删除一个条目
setItems(previous => previous.filter(item => item.id !== targetId));

// 添加一个条目
setItems(previous => [...previous, newItem]);

这样的写法保留未变化条目的引用，为变化的数据创建新引用，便于 React 和相关优化判断更新。不是“只要创建新对象就快”；如果每次无意义地创建所有 props 对象，也可能让 memo 的浅比较失效。

13 · RN 样式与 Flexbox：先会排一个横向条目

浏览器常用 CSS 文件和 class；RN 内置 View 常用 JS 样式对象，属性名多为驼峰形式，例如 CSS 的 background-color 对应 backgroundColor。可以用 StyleSheet.create 集中声明样式。

const styles = StyleSheet.create({
  row: {
    flexDirection: 'row',
    alignItems: 'center',
    padding: 16,
  },
  title: {flex: 1, marginRight: 12},
  button: {padding: 8, backgroundColor: '#e4f0e9'},
});

<View style={styles.row}>
  <Text style={styles.title}>订单详情</Text>
  <Pressable style={styles.button} onPress={openDetail}>
    <Text>打开</Text>
  </Pressable>
</View>
  • flexDirection 决定主轴：row 横向，column 纵向。RN 默认 column，区别于网页 Flexbox 常见默认 row。
  • justifyContent 控制主轴上的分配；alignItems 控制交叉轴上的对齐。不能固定背成“一个水平、一个垂直”。
  • padding 是内容与边界之间的内部空间，margin 是与外部相邻布局之间的空间，border 是边框。
  • 这里 title: {flex: 1} 让标题在父布局有可用宽度时使用剩余空间；不是不受父约束地自动铺满屏幕。
  • style={[styles.title, extraStyle]} 可以组合样式，后面的有效同名属性覆盖前面的。

RN 普通尺寸数值按逻辑布局单位使用，不写 '16px'。它不提供完整浏览器 CSS 层叠和选择器机制；StyleSheet.create 也不会创建 DOM 或启动浏览器。排版原理会在后文 Yoga 小节继续解释。

14 · 用一个完整组件，把这些语法串起来

下面是一个完整的教学 TSX 组件文件：输入框、按钮和状态都在本地，不需要网络。它仍需放到已配置的 RN 工程中使用；本文没有把它注册或运行成独立 App。

import {useState} from 'react';
import {Button, Text, TextInput, View} from 'react-native';

type NameCardProps = {
  initialName?: string;
  onSave: (name: string) => void;
};

export default function NameCard({
  initialName = '',
  onSave,
}: NameCardProps) {
  const [name, setName] = useState(initialName);
  const trimmed = name.trim();

  return (
    <View style={{padding: 16}}>
      <Text>昵称：{trimmed || '未填写'}</Text>
      <TextInput
        value={name}
        onChangeText={setName}
        placeholder="请输入昵称"
      />
      <Button
        title="保存"
        disabled={trimmed.length === 0}
        onPress={() => onSave(trimmed)}
      />
    </View>
  );
}
  1. import：从 React 获取状态 Hook，从 RN 获取原生 UI 组件接口。
  2. NameCardProps：声明初始昵称可以不传，保存回调必须传。
  3. 函数参数解构：从 props 取出字段，未传 initialName 时使用空字符串。默认值针对 undefined，不是任意空值。
  4. [name, setName]：从 useState 返回的二元组中，取出当前状态和更新函数。
  5. value={name}：让输入框显示由状态控制的值。
  6. onChangeText={setName}：把更新函数作为回调，输入变化后请求更新状态。
  7. onPress={() => onSave(trimmed)}：点击时才通知父级保存，渲染期间不会调用保存。
  8. 下一次渲染重新计算 trimmed 和 JSX；RN 随后完成必要的原生界面更新。

注意初始值边界：组件已经挂载后，父级改变 initialName，不会让这个 useState 自动重置。你需要根据产品语义决定由父级完全控制输入，还是明确同步、重置。这个例子也没有声称 onSave 返回就意味着远端保存成功。

回头再读项目代码：const {vip_pin_id: pinId} = props 是解构重命名；useState<PageDataType>(…) 是带类型的状态；useCallback(() => …, [store, pinId]) 是按依赖缓存函数引用；<Text>{title}</Text> 是将表达式放进 JSX。先把语法读顺，再跟进每个函数的具体实现。

15 · 自测：能回答这些，就可以继续看 RN 原理

为什么 onPress={save()} 通常不对？

它在渲染时立即调用 save，并把返回值交给 onPress。通常应传 save 本身，或传一个点击时再调用 save 的包装函数。

const 声明的对象能改吗？{...obj} 是深复制吗？

const 限制重新赋值，不禁止对象字段变化。对象展开只复制第一层，嵌套对象仍可能共用引用。

as User 会检查接口数据吗？async 会创建线程吗？

都不会。as 是类型断言，不进行运行时数据校验；async 让函数以 Promise 组织结果，不自动把代码送到后台线程。

组件重新渲染和重新挂载是一回事吗？

不是。重新渲染是重新计算 UI 描述，状态可以继续保留；卸载后重新挂载通常会重新建立局部状态和副作用。身份、位置和 key 等会影响 React 如何保留状态。

为什么 state 变了，老定时器里可能还是旧值？

老定时器仍持有旧渲染创建的回调，读取的是那次渲染的词法作用域。需要根据场景设置 effect 依赖、使用函数式更新，或通过 ref 管理所需的最新值。
