01. 岗位深度 P0

三到五年要从“会用”升级到“能解释取舍、能定位问题、能承担模块结果”。

这一模块具体要掌握哪些内容？（岗位深度）清单

先说结论：三到五年最重要的是能把需求、方案、风险和验证结果讲成一条完整的故事。

我会先确认用户路径、异常路径、数据从哪里来，以及上线有什么限制。然后再决定模块怎么划分、接口怎么定、任务在哪个线程跑。

  • 能说明状态放在哪里，谁可以修改。
  • 能说明异步任务何时启动，页面离开时何时取消。
  • 能用日志、trace、指标或测试结果证明判断。
  • 能说清灰度、开关、回滚和复盘怎么做。

个人结果和职责只说自己能拿出证据的部分，仓库里的代码不能自动证明作者身份。

当前项目怎么用：在这个多业务、多模块 Android 工程里，yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/mvx/MvxViewModel.kt 把状态整理出来，供页面订阅。这里只能看出模块怎样实现，但代码里没有留下谁负责或发布指标，所以是否由你负责要按真实经历说。

三到五年 Android 的回答与初级有什么差别？深度

先说结论：初级更多是把功能写出来，三到五年还要解释为什么这样拆、出了问题怎么查，以及方案有什么代价。

回答时我会先讲业务约束，再讲数据和线程怎么走，最后讲异常、取消和验证。不会只报一个 MVVM 或 MVI 的名词。

比如一个网络页面，我会说明请求从哪里发出、结果在哪里变成页面状态、页面销毁时谁停止订阅。团队约定要说成团队约定，不能说成 Android 唯一标准。

当前项目怎么用：在源码里，API 和业务模块是分开的，例如 yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/api/net/Net.java 作为网络入口、各业务模块通过接口依赖它；可以拿来说明请求从哪里进、模块之间怎么依赖。不过只看这些代码还看不出是谁负责的，是否由你完成要按真实经历说。

如何回答一个没有亲自踩过的故障题？方法

先说结论：没有亲自遇到过的故障，可以按现象、猜测、证据和验证顺序回答，但不能假装自己处理过。

我会先问清楚发生频率、设备版本、操作步骤和影响范围。接着看主线程栈、日志、trace、内存或网络记录，选最能区分猜测的证据。

验证时尽量一次只改一个变量。修复后还要补回归场景，并说清楚哪些结论仍然未知。

当前项目怎么用：可拿 yyyyy-cdoe/Picture/picture/src/test/java/com/zhihu/android/picture/MatrixTest.java 作为一个可以直接运行的测试入口，说明先定位输入和结果再验证假设；代码里没有留下该故障的个人处理记录或线上指标，不要编造。

架构题先讲什么，才能避免空泛？表达

先说结论：架构题先讲业务约束、数据流和依赖方向，再讲使用了什么模式。

我通常按“用户输入—状态变化—副作用—数据源”来讲。这样面试官能听到页面怎样从输入走到结果，而不是只听一串名词。

还要补一句取舍，比如为什么把网络和缓存放在同一个仓库入口，为什么页面只订阅一个状态出口。没有证据的个人设计和收益，不主动把成果说成自己的。

当前项目怎么用：先讲接口与实现的依赖关系：yyyyy-cdoe/Premium/premium-api/src/main/java/com/zhihu/android/interfaces/PremiumApiService.kt 定义 Premium 能力接口，业务实现通过接口接入。这里能看到接口存在和用途，但源码看不出面试者是否设计或负责它。

怎样证明自己有工程 ownership？项目

先说结论：工程责任不是“我写过这个类”，而是对设计、交付、线上表现和后续改进负责。

回答时我会明确自己负责的模块和决定，说明上线前做了哪些验证，线上用什么指标判断结果，出问题如何降级或回滚。

如果只能看到仓库代码，我只把它当作实现证据。个人职责、发布结果和指标要由本人补充可核验材料。

当前项目怎么用：可以用 yyyyy-cdoe/ZRouter/zrouter/src/test/java/com/zhihu/android/app/router/ZRouterTest.java 说明功能与回归测试一起交付；但源码里没有记录作者、上线、监控、回滚或结果，是否由你负责，按真实经历说。

怎样把一段项目经历准备成可连续追问的“问题树”？项目准备

先说结论：项目问题树要从业务目标开始，逐层准备架构、关键链路、异常、验证和复盘问题。

一条主线至少准备一个入口图、一个真正的难点、两个备选方案，以及一次故障或风险。每个数字都要知道来源。

我会把“为什么这样做”“如果流量翻倍怎么办”“页面退出时怎么办”提前写成追问，回答保持在自己实际参与的范围内。

当前项目怎么用：以 yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/PagingDataAdapter.kt 为主线可追问数据输入、异步 diff、加载状态和列表更新；这些能力都能在这个类里直接看到，代码里没有留下个人参与内容和结果记录。

02. Kotlin / Java P0

语言题的核心是类型、安全、对象所有权与 Java 互操作。

这一模块具体要掌握哪些内容？（Kotlin / Java）清单

先说结论：Kotlin/Java 基础要落到空值、可变性、泛型、对象生命周期、Java 互操作和运行时成本。

  • 能区分可空类型、平台类型，以及 ?.、?:、!! 的使用场景。
  • 能说明 val 只是不换引用，data class.copy() 默认只是浅复制。
  • 能解释 out/in、reified、扩展函数、委托、密封类。
  • 能说清 Java 的 length、Kotlin 的 size，以及数组和 MutableList 的增删区别。
  • 能处理 Java 注解、SAM、受检异常和 Kotlin 集合的互操作。

面试时最好用一次 SDK 接入或页面状态建模，说明这些语言差异怎样避免 bug。

当前项目怎么用：仓库存在 Kotlin/Java 混编，例如 yyyyy-cdoe/Premium/premium-api/src/main/java/com/zhihu/android/api/VipPayResult.java 与 yyyyy-cdoe/Premium/premium-api/src/main/java/com/zhihu/android/api/VipAlertType.kt 分别承载 Java 与 Kotlin API；可以拿来讲互操作，但不能说成是自己做的。

val 能保证对象不可变和线程安全吗？Kotlin

先说结论：val 只保证这个变量不能重新指向别的对象，不能保证对象内容不变，也不能单独保证线程安全。

例如 val list = mutableListOf<String>() 仍然可以添加元素。多个线程同时改它，还会遇到竞态。

实际开发里我会优先使用不可变数据，把更新做成新快照，并通过一个明确的状态出口发布。共享可变对象必须配合同步、锁或单线程访问。

当前项目怎么用：yyyyy-cdoe/KnowledgeMarket/sku-manuscript/src/main/java/com/zhihu/android/app/sku/manuscript/vip_manuscript/novel/theme/ZHThemeModule.kt 使用 private val 保存主题流并暴露只读 StateFlow；这说明引用不重新赋值和只读暴露，不等于内部对象或所有并发操作都安全。

Kotlin 空安全为什么仍会出现 NPE？空安全

先说结论：Kotlin 能减少 NPE，但 !!、Java 平台类型、反射和并发变化仍可能让空值检查失效。

Java 方法没有完善的空值注解时，Kotlin 看到的可能是平台类型，编译器无法替你判断。把它直接当非空值用，运行时仍可能崩。

我会在 Java/SDK 边界做一次校验，把结果转换成可信的 Kotlin 模型，业务内部尽量不扩散平台类型，也少用 !!。

当前项目怎么用：Java/Kotlin 混编可以在 yyyyy-cdoe/VipGrowth/growth-api/src/main/java/com/zhihu/android/MonitorHelper.kt 等 API 模块；可以拿来说明平台类型和注解信息需要在入口处校验。代码里没看到专门的 NPE 复现样例，面试时不要说项目已经解决过某个 NPE。

data class.copy() 是深拷贝吗？对象

先说结论：data class.copy() 是浅复制，嵌套对象和可变集合默认仍与原对象共享。

复制外层对象后修改里面的 MutableList，原对象也可能被改到。它适合做不可变状态的局部更新，不等于深拷贝。

需要隔离时，我会把嵌套模型也显式复制，或从模型设计上不暴露可变集合，并用测试确认修改一边不会影响另一边。

当前项目怎么用：yyyyy-cdoe/Picasa/picasa-api/src/main/java/com/zhihu/android/picasa/model/UploaderModel.kt 是 Kotlin 模型承载上传数据；只看这些代码还看不出该模型调用 copy() 或深拷贝实现，因此只能把它作为模型层面的例子，不能把它当成当前项目真的用了这个方案。

协变、逆变在 Android 中有什么实际意义？泛型

先说结论：out 表示只生产某种类型，in 表示只消费某种类型，目的是让泛型接口的读写方向安全。

只读数据源可以用 out T，事件处理器通常可以用 in T。如果一个接口既读又写，就不能随意标成协变或逆变。

Android 里它常用于把数据提供方和事件接收方的职责分开，减少强制类型转换。先看调用方实际读还是写，再决定变型。

当前项目怎么用：yyyyy-cdoe/VipGrowth/growth-api/src/main/java/com/zhihu/android/growth/task/TaskAware.kt 定义任务能力接口，可以看到 API 用接口把生产和消费分开；代码里没看到该接口明确使用 out/in，所以不要把这种泛型写法说成项目现状。

inline、noinline、crossinline 与 reified 分别解决什么？内联

先说结论：inline 允许函数和部分 Lambda 在调用点展开，reified 借此在函数体里拿到具体类型；noinline 和 crossinline 是对 Lambda 行为的限制。

noinline 让某个 Lambda 保持对象形式，方便保存或传递。crossinline 禁止 Lambda 通过非局部返回跳出外层函数。

我会把它们用于小型高阶工具或确实需要类型信息的 API。大函数盲目内联会增大字节码，reified 也不能恢复被擦除的嵌套泛型全部信息。

当前项目怎么用：yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/PagingDataAdapter.kt 使用 Kotlin 高阶 API 封装分页适配能力；代码里没有这四种修饰符的直接实现，从这份代码只能确认有 Kotlin 封装，不能自己补具体字节码收益。

扩展函数为什么不能真正“给类增加方法”？扩展函数

先说结论：扩展函数通常只是一个静态工具函数，不会把真正的方法写进原类，也不会参与运行时多态。

成员方法优先于同名扩展，调用哪个扩展由变量的编译期类型决定。扩展函数还不能直接访问原类的私有成员。

我会用扩展函数放无状态的格式转换和小工具。需要根据子类动态变化的行为，仍然放在成员方法或接口里。

当前项目怎么用：Kotlin 工具和接口可以在 yyyyy-cdoe/VipGrowth/growth-api/src/main/java/com/zhihu/android/growth/util/GrowthABUtils.kt；它是独立工具入口，不改变被扩展类的成员表。代码里没看到该文件对应扩展函数的调用链，所以不能说成是自己设计的。

object、伴生对象与 lazy 的线程安全边界是什么？初始化

先说结论：object 和伴生对象的初始化由 JVM 类初始化保证；lazy 是否安全取决于选择的模式。

lazy 默认同步，只初始化一次。PUBLICATION 可能并发计算多次但只发布一个结果，NONE 不提供线程保证。

这只解决初始化，不代表单例内部的可变字段安全。无状态工具可以长存，页面状态和账号状态不要随手放进全局对象。

当前项目怎么用：yyyyy-cdoe/VipGrowth/growth-api/src/main/java/com/zhihu/android/growth/UserRecordHelper.kt 是可复用的记录辅助类，可以拿来讨论全局辅助对象和页面生命周期的区别；只看这些代码还看不出 object/companion/lazy 的直接用法，面试时不要说项目采用了某种初始化线程策略。

Kotlin 的 ==、=== 与可变 Map key 为什么容易出错？相等性

先说结论：== 比较内容，=== 比较是不是同一个对象；可变 Map key 会破坏哈希查找。

对象放进 HashMap 或 HashSet 后，如果参与 equals/hashCode 的字段被改了，容器可能还留着它，却再也找不到。

缓存 key、列表主键和 Diff 比较字段我会使用稳定的不可变值，并明确业务上什么才算相等。

当前项目怎么用：yyyyy-cdoe/KnowledgeMarket/sku-manuscript/src/main/java/com/zhihu/android/app/sku/manuscript/vip_manuscript/novel/theme/ZHThemeModule.kt 以主题模型作为状态值并通过 Flow 发布；代码里没看到可变 Map key 或 === 的项目示例，具体相等规则还得看模型实现，面试时不要把它说成项目做法。

03. JVM 与并发 P0

理解可见性、原子性、对象可达性和主线程阻塞，比背虚拟机实现更重要。

这一模块具体要掌握哪些内容？（JVM 与并发）清单

先说结论：JVM 并发题要能把对象回收、线程可见性、同步、线程池和主线程排障串起来。

  • 知道栈、堆、GC Root，以及强引用和弱引用怎样影响回收。
  • 能区分可见性、原子性和有序性，理解 volatile、锁和安全发布。
  • 能分析锁竞争、死锁、原子类和复合操作。
  • 能按 CPU 计算、阻塞 I/O、串行写入拆分线程池和队列。
  • 会用 heap dump、分配记录、线程栈和 trace 找证据。

遇到内存上涨或卡死，我会先提出可验证的猜测，再选对应工具，不靠感觉下结论。

当前项目怎么用：这个页面在 yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/discovery/HomePinTabFragment.kt 里用 lifecycleScope 启动后台任务；可用它串联任务与生命周期。代码里没看到统一的 JVM 调度规范，也没有个人性能结果。

volatile 为什么不能替代锁？JMM

先说结论：volatile 主要解决一个变量的可见性和部分有序性，不能把多个读改写步骤变成一个原子操作。

比如 count++ 仍然可能丢更新。一个线程看到最新的标志，也不代表它看到了一组字段的一致快照。

简单状态标志可以考虑 volatile。复合状态则用原子类、锁或固定的单线程执行器，并明确谁负责修改。

当前项目怎么用：业务源码里没有直接使用 volatile 维护复合状态；可引用 yyyyy-cdoe/Audio/audio/src/main/java/com/zhihu/android/player/walkman/player/AudioPlayService.java 的服务状态与 Binder 入口说明“跨线程或跨组件共享状态，要把所有读写放在同一套同步保护里”，面试时不要说 volatile 已解决并发安全。

内存泄漏和内存抖动如何区分？内存

先说结论：内存泄漏是该回收的对象仍被引用，内存抖动是短命对象大量创建和回收。

泄漏通常看 heap dump 的引用链，确认哪个 GC Root 一直抓着 Activity、View 或业务对象。抖动要看分配热点和 GC 频率，再对照帧耗时。

两者可能同时出现，但处理方法不同。不能因为堆占用高就直接说是泄漏。

当前项目怎么用：yyyyy-cdoe/Camera/camera/src/main/java/com/zhihu/android/camera/utils/GestureHelper.java 持有 Handler 并在手势结束时移除延迟消息，能作为“回调引用需释放”的真实例子；代码里没看到 heap dump 或分配曲线，面试时不要把它说成已经发生泄漏或抖动。

线程池为什么不能一个解决所有后台任务？调度

先说结论：线程池要按任务性质和资源上限拆分，CPU、阻塞 I/O 和串行写入不适合无差别共用一个队列。

线程太多会增加上下文切换，队列太长会把延迟藏起来。还要定义并发上限、排队超时、拒绝策略和取消行为。

实际排查时我会看活跃线程数、队列长度和任务等待时间，再决定调大小还是隔离任务。

当前项目怎么用：yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/app/util/NetworkSchedulerTransformer.java 将网络调度作为独立转换器，说明网络任务单独经过调度层；全仓没有统一线程池或拒绝策略配置，所以不要说所有后台任务共用一个池。

ANR 排查先看哪里？排障

先说结论：ANR 先看主线程当时在等待什么，不要只搜索 sleep。

我会先拿 ANR trace 和主线程栈，再看它是否卡在 I/O、锁、同步 IPC、复杂布局或大量计算。日志和复现条件用来确认是不是同一条路径。

修复后要回归冷启动、页面切换和高负载场景，避免只是把等待挪到另一个位置。

当前项目怎么用：yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/app/util/NetworkLifecycleTransformer.java 表明网络链路与生命周期有关；排查 ANR 还需主线程栈、trace 和耗时日志。代码里没有这次问题的前后数据，面试时不要自己补。

共享对象怎样做到安全发布，happens-before 到底解决什么？JMM

先说结论：安全发布要让一个线程的初始化和写入，在另一个线程读取前建立明确的先后关系。

锁释放后再加锁、写入 volatile 后读取、线程启动和结束，都能建立这样的先后保证。它解决的是“看到什么、何时看到”，不自动把复合操作变成原子操作。

我会优先发布不可变快照；有多个字段需要一起保持一致时，用同一把锁或一个固定线程完成更新，避免构造过程中把 this 暴露出去。

synchronized、ReentrantLock 与 CAS/原子类怎么选？锁选型

先说结论：默认先用写法更直接的 synchronized；需要可中断、超时或多个条件时选 ReentrantLock；很短的单变量状态转换才考虑 CAS/原子类。

CAS 不是没有竞争，失败后可能不断重试，还会遇到 ABA 和多字段难以同时保持一致的问题。

我会先缩小共享数据和锁住的范围，再根据竞争情况、等待方式和可取消要求选工具，并用线程转储验证。

当前项目怎么用：业务代码里没看到直接使用这三类同步原语；yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/PagerMediator.kt 这里只能看到分页信号状态存在。代码里没有锁选型和竞争数据记录。

类加载的双亲委派有什么价值，Android 的 ClassLoader 有何实际影响？类加载

先说结论：双亲委派让类加载优先问父加载器，减少核心类重复和类型身份混乱；Android 的 ClassLoader 决定 dex 代码从哪里进入运行时。

常见的 BootClassLoader、PathClassLoader、DexClassLoader 会按不同路径加载类。同名类如果由不同加载器加载，也可能被认为是不同类型。

普通业务不需要破坏这条加载链。插件或热修复题还要说明来源校验、类冲突、系统版本兼容和失败回退。

04. Handler / Looper P0

掌握消息入队、取出、执行，以及消息如何把页面或回调意外留在内存中。

这一模块具体要掌握哪些内容？（Handler / Looper）清单

先说结论：Handler、Looper、MessageQueue 和线程是一套消息投递系统，Handler 负责把任务放到指定 Looper 所在线程。

  • Looper 绑定一个线程并循环取消息，Handler 本身不会创建后台线程。
  • sendMessage 和 post 都是入队，前者带消息数据，后者把 Runnable 放进去。
  • 延迟消息不是新开定时线程，退出页面时要按 Runnable、what 或 token 清理。
  • 主线程 Handler、HandlerThread 和线程池分别适合串行投递、后台串行任务和后台并发。
  • 静态 Handler 只能减少隐式外部引用，不能替代取消任务和清理回调。

面试时能画出“后台完成—投递主线程—页面退出清理”的时序，基本就能说明白。

当前项目怎么用：yyyyy-cdoe/Camera/camera/src/main/java/com/zhihu/android/camera/utils/GestureHelper.java 创建 Handler、发送 LONG_PRESS_START 延迟消息并在结束时移除，可以直接看到消息队列与手势状态结合。

post 后 Runnable 会立刻执行吗？消息队列

先说结论：post 只是把 Runnable 放进目标线程的消息队列，不保证立刻执行。

Looper 要先处理排在它前面的消息，主线程繁忙时，Runnable 可能明显延迟。postDelayed 也只是设置最早执行时间，不是精确闹钟。

我会用它切回主线程或安排轻量工作，不把耗时计算和网络请求直接塞进主线程 Handler。

当前项目怎么用：yyyyy-cdoe/Account/account/src/main/java/com/zhihu/android/app/zombie/ZombieUtil.kt 使用 Handler(Looper.getMainLooper()).postDelayed 调度清理/检测工作，说明 postDelayed 只是入队，实际执行取决于主线程 Looper；所以面试时不要说它会立即执行。

Handler 泄漏的真实引用链是什么？泄漏

先说结论：泄漏链通常是 MessageQueue 持有 Message，Message 或 Runnable 再持有 Activity、View 或包含它们的对象。

页面销毁后，延迟消息仍在队列里，就可能把整棵页面对象树留住。静态 Handler 只解决 Handler 对外部类的隐式引用，Runnable 仍可能抓住页面。

实际开发里我会在合适的生命周期移除消息和回调，长任务支持取消，回调只保留必要的数据，不直接长期持有 UI。

当前项目怎么用：yyyyy-cdoe/Camera/camera/src/main/java/com/zhihu/android/camera/utils/GestureHelper.java 的 Handler 是手势辅助对象成员，且延迟消息可携带 Runnable/目标引用；文件有 removeMessages 清理动作。代码里没有这次问题的前后数据，面试时不要自己补。

Handler 和线程池分别解决什么问题？选型

先说结论：Handler 解决指定 Looper 上的串行投递，线程池解决后台任务的并发执行，它们是两种不同的调度方式。

常见做法是后台线程池完成 I/O 或计算，再用主线程 Handler 更新 UI。需要严格顺序的轻量后台任务可以使用 HandlerThread。

我会根据任务是否需要并发、顺序、取消和生命周期来选，而不是看到“异步”就统一使用一种工具。

当前项目怎么用：yyyyy-cdoe/Audio/audio/src/main/java/com/zhihu/android/player/walkman/Walkman.java 使用主线程 Looper Handler 处理播放器回调；yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/app/util/NetworkSchedulerTransformer.java 负责网络调度。两处源码支持串行消息与后台调度是不同职责。

HandlerThread 适合什么场景？线程

先说结论：HandlerThread 适合少量、需要顺序执行的后台消息任务，不适合大量 CPU 并行计算。

它启动一个带 Looper 的线程，多个消息按队列串行处理。任务不用时要移除消息并退出 Looper，否则线程和回调可能一直存活。

如果任务之间可以并行，或者队列可能长时间堆积，我会改用带上限和取消策略的线程池或协程调度器。

当前项目怎么用：代码里没看到业务模块使用 HandlerThread；yyyyy-cdoe/ZhihuLite/app/third/tbs/java/com/tencent/smtt/sdk/TbsDownloader.java 确实包含第三方 TbsDownloader 的 HandlerThread，但这是 vendor/third 代码，不能说成是自己的业务架构或贡献。

Looper.loop() 为什么不会把主线程“卡死”，队列没消息时发生什么？Looper 原理

先说结论：Looper.loop() 是事件循环，队列没到期消息时会休眠等待，不是在执行空转死循环。

主线程正是靠它接收输入、绘制和生命周期消息。真正卡住通常是某条消息执行太久，或主线程在等锁、I/O、同步 IPC。

我会看主线程栈、trace 和消息耗时定位慢任务，不会尝试结束主 Looper 来解决卡顿。

当前项目怎么用：yyyyy-cdoe/Bootstrap/bootstrap/src/main/java/com/zhihu/android/bootstrap/viewpager/adapter/VerticalFragmentStateAdapter.java 显式使用 Handler(Looper.getMainLooper())，说明主线程消息投递依赖已有 Looper；代码里没看到项目对 MessageQueue.nativePollOnce 的封装，面试时不要自己补队列内部实现。

同步屏障、异步消息与 Choreographer 有什么关系？消息机制

先说结论：同步屏障会暂时挡住普通同步消息，让异步消息先走；Choreographer 用这套调度组织输入、动画和下一次遍历。

它提高的是帧相关回调的调度机会，不会让一个耗时任务本身变快。业务代码不应依赖隐藏接口手动操作屏障。

遇到掉帧，我会用 trace 区分是排队等待，还是回调内容太重。

当前项目怎么用：只看这些代码还看不出业务源码直接操作同步屏障、Message.setAsynchronous 或 Choreographer；yyyyy-cdoe/Bootstrap/bootstrap/src/main/java/com/zhihu/android/bootstrap/viewpager/widget/VerticalViewPager.java 这里只能看到复杂 UI 组件，不能把它当成当前项目真的用了这套方案。

IdleHandler 适合做延迟初始化吗，有什么风险？空闲任务

先说结论：IdleHandler 只适合很轻、可重复、可放弃的收尾工作，不能当成有确定时间的延迟任务。

队列一直繁忙时它可能迟迟不执行；回调一旦太重，又会挡住后续消息和下一帧。

关键初始化我会用有明确依赖和超时的任务安排。使用 IdleHandler 时要控制执行次数，记录耗时，并确保重复执行不会出错。

05. 协程与 Flow P0

重点是结构化并发、取消、异常、背压和 UI 状态建模。

这一模块具体要掌握哪些内容？（协程与 Flow）清单

先说结论：协程题要讲清挂起与线程、作用域、取消、异常、Flow 背压和页面生命周期的关系。

  • suspend 只表示函数可以挂起，不等于自动切后台。
  • 结构化并发让子任务归到父作用域，页面销毁时能一起取消。
  • StateFlow 适合持续状态，事件要按是否允许丢失选择 SharedFlow 或 Channel。
  • flowOn 改上游执行上下文，withContext 是一段代码主动切换上下文。
  • 测试时注入调度器，控制虚拟时间，不用真实等待。

回答最好结合一个搜索、刷新或页面订阅场景，说明取消和异常怎样处理。

suspend 是否意味着后台线程？协程

先说结论：suspend 只说明函数可以暂停后恢复，不说明它会在哪个线程运行。

它可能在当前线程执行，也可能因为调用方的 Dispatcher 切到后台。挂起和阻塞也不同，挂起通常释放线程，阻塞会占住线程。

我会在调用边界明确使用 Dispatchers.IO、Default 或主线程，并确保底层库不会在主线程做阻塞工作。

当前项目怎么用：yyyyy-cdoe/km-attention/attention/src/main/java/com/zhihu/android/attention/viewmodel/SearchViewModel.kt 的 viewModelScope.launch 说明协程由作用域和 dispatcher 决定调度；代码里没看到该文件把 suspend 等同后台线程，面试时不要这样描述项目行为。

为什么要结构化并发？取消

先说结论：结构化并发把子协程放进父作用域，让生命周期、取消和异常有明确归属。

例如在页面作用域启动的请求，页面销毁时应一起取消。子任务结束后父任务再结束，调用方不会收到一个“看起来完成、实际还有后台工作”的结果。

我会用 coroutineScope 表示子任务都成功才继续，用 supervisorScope 表示一个子任务失败不必连带取消其他子任务。

StateFlow 与一次性事件如何区分？状态

先说结论：StateFlow 保存当前状态并向新订阅者重放最新值，一次性事件则要单独考虑重复消费和丢失问题。

导航、Toast 这类事件如果放在 StateFlow 里，旋转或重新订阅可能再次触发。界面状态适合 StateFlow，事件可按需求使用 SharedFlow 或 Channel，并定义是否允许丢失。

我会让 ViewModel 暴露只读流，页面只收集和渲染，不在收集处偷偷修改同一份状态。

当前项目怎么用：yyyyy-cdoe/KnowledgeMarket/sku-manuscript/src/main/java/com/zhihu/android/app/sku/manuscript/vip_manuscript/novel/theme/ZHThemeModule.kt 用 MutableStateFlow 保存当前主题、MutableSharedFlow 发布更新事件并暴露只读流；这是仓库中可直接观察的状态/事件区分。

collectLatest 为什么常用于搜索？Flow

先说结论：collectLatest 会在新值到来时取消上一个收集块，适合只关心最新关键词的搜索。

用户输入“a”后很快输入“ab”，旧请求如果还能取消，就不必继续做完并刷新旧结果。它只取消收集块，底层网络库还要正确响应协程取消。

我通常会配合 debounce、distinctUntilChanged 和可取消的请求，并处理取消异常，不把正常取消显示成错误。

launch、async 与 Supervisor 的异常传播有何不同？协程异常

先说结论：launch 直接启动任务，async 返回稍后取得结果的 Deferred；普通父作用域中子协程失败可能取消兄弟任务，Supervisor 则隔离这种失败。

async 的异常通常在 await 时暴露，launch 的异常会交给作用域处理。不要为了“并行”把所有任务都写成 async。

我会先判断是否真的需要返回值和并行，再选 coroutineScope 或 supervisorScope，并为失败任务补上明确的恢复或展示策略。

当前项目怎么用：yyyyy-cdoe/DevKit/devkit/src/test/java/com/zhihu/android/devkit/SafeCoroutineTest.kt 覆盖 safeAsync 测试入口，可以拿来说明 async 封装需要单独验证异常怎么传出去；代码里没看到完整 launch/async/Supervisor 对照实现，是否由你参与要按真实经历说。

调用 cancel() 后协程为什么可能仍停不下来？协程取消

先说结论：调用 cancel() 只是发出取消信号，协程必须到达可取消的挂起点或主动检查信号才会停。

长时间 CPU 循环、阻塞的 Java 调用和吞掉 CancellationException 都会让取消看起来失效。

我会使用可取消的挂起 API，在循环中检查 isActive，把不可取消的阻塞调用隔离出去，并在 finally 中释放资源。

Flow 在页面不可见时为什么还可能继续运行？Flow 生命周期

先说结论：页面不可见不等于收集自动停止，关键看协程是挂在哪个作用域以及收集方式是否绑定可见生命周期。

如果任务放在 ViewModel 作用域，它会跨过页面的可见和不可见阶段继续运行。使用 Fragment 的 viewLifecycleOwner 或 repeatOnLifecycle，才能让收集跟着 View 的状态启停。

flowOn 与 withContext 为什么不能随意互换？Flow 调度

先说结论：flowOn 改变它上游的执行上下文，withContext 则包住一段明确的代码，两者不能按名字直接互换。

Flow 的收集通常发生在下游上下文，flowOn 适合把数据库查询或转换放到指定调度器。withContext 更适合一个挂起函数内部切换线程。

我会先画清上下游，再确认是否需要保持顺序、背压和取消传播，避免在收集器里随意切线程造成难以追踪的行为。

StateFlow、SharedFlow 与 Channel 应怎样选择？热流

先说结论：StateFlow 用来表示当前值，SharedFlow 用来广播事件，Channel 更像点对点的队列，选择取决于订阅和丢失规则。

页面状态通常要让新订阅者马上拿到最新值，所以用 StateFlow。事件是否需要给多个订阅者、没有订阅者时是否能丢，要提前定清楚。

我会在 ViewModel 内部保留可变实现，对外暴露只读流，并写测试覆盖旋转、重复订阅、取消和缓冲区满的情况。

06. 四大组件、生命周期与进程死亡 P0

生命周期题要区分配置变化、页面销毁、进程被系统回收三种不同问题。

这一模块具体要掌握哪些内容？（组件与生命周期）清单

先说结论：组件题要掌握进程、Activity、Fragment、Service、Provider、Receiver 的启动时机和生命周期，而不是只背回调顺序。

  • Service、WorkManager、AlarmManager 和前台服务各自有后台限制。

旋转屏幕与进程死亡有什么区别？恢复

先说结论：旋转通常是配置变化导致 Activity/View 重建，进程死亡则是整个进程和内存对象都消失，恢复依据完全不同。

ViewModel 能处理进程死亡吗？状态

先说结论：ViewModel 能跨配置变化保存内存状态，但不能独自处理进程死亡。

什么时候持有 Application Context？Context

先说结论：只有确实需要跨页面、跨组件或跨进程长期使用的对象，才适合持有 Application Context。

Application Context 生命周期和进程一致，适合数据库、系统服务和不依赖页面主题的工具。需要显示 Dialog、读取页面主题或操作 View 时，必须使用合适的 Activity Context。

Service 是否等于“后台常驻”？组件

先说结论：Service 不是后台常驻的保证，它仍受系统内存、后台启动限制和进程优先级影响。

持续播放、导航等用户可感知任务通常需要前台服务和通知。可延后的可靠任务更适合 WorkManager，精确时间提醒再考虑 AlarmManager。

先说结论：Receiver 里只做很短的工作；需要在回调结束后继续异步执行时用 goAsync()，需要可靠延后执行则交给 WorkManager。

goAsync() 给你一小段额外时间，但仍有系统期限，不能拿来跑长任务。WorkManager 适合可推迟、需要约束和最终完成的工作。

前台服务、WorkManager 与 AlarmManager 在后台限制下怎样分工？后台任务

先说结论：前台服务适合用户正在感知的持续任务，WorkManager 适合可延后但要最终完成的任务，AlarmManager 适合有时间要求的唤醒。

后台限制会因 Android 版本、应用状态和任务类型变化。不能用普通后台 Service 当作永久保活方案。

我会先确认任务能否延后、是否必须准点、是否需要持续通知，再决定工具，并处理权限、重试、取消和进程被杀后的恢复。

组件放到 android:process 后，单例与 Application 会发生什么？多进程

先说结论：组件放到 android:process 后会进入另一个进程，Application、单例、静态变量和内存缓存都不再共享。

每个进程都会创建自己的 Application 实例，也会各自初始化全局对象。跨进程传数据要经过 Binder 或其他 IPC，不能直接把内存引用传过去。

07. Binder P1

要能讲清跨进程隔离、参数编组、线程与死亡处理。

这一模块具体要掌握哪些内容？（Binder）清单

先说结论：Binder 是 Android 进程间调用的基础，面试要讲清代理、服务端 Stub、Parcel、线程和生命周期。

  • 客户端拿到代理对象，调用被写入 Parcel 后发送到服务端。
  • 服务端 Binder 线程池取出请求并执行，不一定是主线程。
  • 同步调用会等待返回，单向调用则不等待结果。
  • 连接断开时要处理死亡通知和重连，数据量也受事务缓冲区限制。
  • 跨进程接口还要考虑权限、超时、异常和版本兼容。

用 Service、Provider 或 AIDL 的真实调用链来讲，会比只背“内核驱动”更容易复述。

当前项目怎么用：yyyyy-cdoe/Audio/audio/src/main/java/com/zhihu/android/player/walkman/player/AudioPlayService.java 定义 IBinder 字段、onBind 返回值和 AudioBinder 内类，这里能看到 Android 组件绑定接口；代码里没看到跨进程 AIDL 服务，但这是本地 Binder，不能说成跨进程通信。

一次同步 Binder 调用大致发生什么？IPC

先说结论：一次同步 Binder 调用会从客户端代理进入 Parcel，经驱动转到服务端 Stub，再在线程池线程执行并把结果写回。

客户端线程在等待返回期间会被占住，服务端可能同时处理多个请求。参数和返回值必须能写入 Parcel，跨进程不能直接传普通对象引用。

我会把耗时工作放在服务端后台线程，接口返回小结果或异步通知，并为死亡、超时和版本不兼容准备处理。

当前项目怎么用：yyyyy-cdoe/Audio/audio/src/main/java/com/zhihu/android/player/walkman/player/AudioPlayService.java 的 onBind 返回 Binder，可以拿来讲绑定调用入口；代码里没看到代理/Stub/transact 或跨进程调用链，面试时不要说仓库实现了某次同步 IPC。

为什么主线程应避免同步 IPC？卡顿

先说结论：主线程做同步 IPC 会把网络、锁或服务端卡顿直接变成 UI 卡顿，严重时触发 ANR。

同步调用的等待时间受客户端、Binder 驱动、服务端线程和服务端依赖共同影响，客户端无法只靠自己保证快。

我会把调用放到后台，使用异步回调或状态流回传结果，并限制传输数据大小。主线程只做很快、可预期的操作。

当前项目怎么用：yyyyy-cdoe/Account/account/src/main/AndroidManifest.xml 的 provider 独立进程声明可作为判断是否跨进程的背景信息；只看这些代码还看不出调用方主线程同步 IPC 的代码或卡顿 trace，代码里没有这次问题的前后数据，面试时不要自己补。

为什么要处理 Binder 死亡？稳定性

先说结论：Binder 对端进程崩溃或被杀后，原来的代理仍可能存在，但调用已经失效，所以需要处理死亡通知。

通过 linkToDeath 等方式可以得知连接断开。重连时要重新获取代理、恢复必要状态，并避免多个线程同时发起重复连接。

我会把死亡当成正常异常路径，给调用方明确错误或重试结果，不在死亡回调里做很重的工作。

当前项目怎么用：yyyyy-cdoe/Audio/audio/src/main/java/com/zhihu/android/player/walkman/player/AudioPlayService.java 提供服务 Binder 生命周期入口；代码里没看到 linkToDeath/death recipient 实现，这里只能确认有绑定服务，不要说项目已经处理 Binder 死亡。

AIDL、Provider、Intent 如何选？选型

先说结论：AIDL 适合稳定的跨进程方法接口，Provider 适合结构化数据读写，Intent 适合简单的一次性组件交互。

选择时看数据模型、调用频率、是否需要查询语义、权限和生命周期。Intent 不适合塞大列表，Provider 也不是所有业务通信都要用。

我会先定义权限和失败处理，再按数据大小与调用方向选择工具，并为跨版本字段缺失做兼容。

当前项目怎么用：同一个仓库里可以看到 yyyyy-cdoe/Account/account/src/main/java/com/zhihu/android/app/provider/AccountOauthProvider.java Provider、yyyyy-cdoe/ZRouter/zrouter/src/main/java/com/zhihu/android/app/router/RouterUrl.java Intent/Bundle 路由封装和 Binder 服务；代码里没看到 AIDL 文件，所以不要把 AIDL 说成当前项目真的用了这个方案。

为什么大 Bundle 或大列表会触发 TransactionTooLargeException？Binder 事务

先说结论：大 Bundle 或大列表会和其他 Binder 事务共同占用有限的事务缓冲区，超过限制就可能抛出 TransactionTooLargeException。

限制不只看单个字段，还包括整个事务中序列化后的大小和同时发生的事务。把 Bitmap、长文本或大量 Parcelable 塞进 Intent 都很危险。

我会只传 ID、URI 或分页参数，让接收方重新读取数据；同时在低内存和真实跳转链路上测试。

当前项目怎么用：yyyyy-cdoe/ZRouter/zrouter/src/main/java/com/zhihu/android/app/router/RouterUrl.java 提供 putSerializable 等 Bundle 写入 API，是真实的大参数风险入口；代码里没有这次问题的前后数据，面试时不要自己补。

AIDL 方法运行在哪个线程，为什么持锁做同步 IPC 容易死锁？Binder 线程

先说结论：AIDL 方法通常在服务端 Binder 线程池运行，不保证在主线程；持锁期间再做同步 IPC 很容易形成互相等待。

客户端可能持锁等待服务端，服务端又通过回调或另一个 IPC 等待客户端释放同一把锁，最终形成死锁。服务端还可能同时处理多个调用。

我会让 IPC 前先释放业务锁，缩短临界区，用异步回调传结果，并对跨进程接口做超时和并发测试。

当前项目怎么用：yyyyy-cdoe/Audio/audio/src/main/java/com/zhihu/android/player/walkman/player/AudioPlayService.java 只有本地 AudioBinder 方法入口；代码里没看到 AIDL Stub 线程池、锁或同步 IPC，面试时不要补线程归属或死锁案例。

Parcelable 与 Serializable 怎么选？序列化

先说结论：跨进程或 Intent 传输优先选择 Parcelable；Serializable 写法简单但通常更慢、分配更多。

Parcelable 需要显式定义读写顺序，字段变更要考虑版本兼容。Serializable 依赖反射和 Java 序列化，不适合大对象和高频 IPC。

我会只传必要字段或 ID，避免把整个页面模型塞进 Bundle，并用进程边界测试读写顺序和空值。

当前项目怎么用：yyyyy-cdoe/ZRouter/zrouter/src/main/java/com/zhihu/android/app/router/RouterUrl.java 明确提供 putSerializable 写入 Bundle，这里能看到项目有 Serializable 路径；代码里没有 Parcelable 对照和实际传输数据，不能说项目已经完成选型。

08. View 渲染 P0

传统 View 仍是维护混合工程和排查卡顿的基本功。

这一模块具体要掌握哪些内容？（View 渲染）清单

先说结论：View 渲染题要掌握测量、布局、绘制、帧调度、触摸和资源回收，并能联系到实际控件。

  • 测量决定尺寸，布局决定位置，绘制把内容画到 Canvas。
  • MeasureSpec 的模式和尺寸共同限制子 View。
  • 改变内容和改变尺寸要分别考虑 invalidate() 与 requestLayout()。
  • 自定义 View 要避免每帧创建对象、重复计算和主线程 I/O。
  • 掉帧要分清是重组/布局/绘制慢，还是业务线程阻塞了主线程。

回答时我会从一帧开始讲，再落到控件里的具体方法。

当前项目怎么用：yyyyy-cdoe/barrage/barrage/src/main/java/com/zhihu/android/barrage/BarrageView.java 覆盖自定义 View 的 onDraw，yyyyy-cdoe/Bootstrap/bootstrap/src/main/java/com/zhihu/android/bootstrap/consecutive/ConsecutiveScrollerLayout.java 覆盖容器布局与触摸；可以按传统 View 的测量、布局和绘制来讲。

测量、布局、绘制的职责是什么？渲染

先说结论：测量回答“要多大”，布局回答“放在哪里”，绘制回答“画什么”。

父 View 在测量阶段通过 MeasureSpec 给子 View 约束，子 View 根据内容和约束计算 measuredWidth/Height。布局阶段再确定左右上下位置，绘制阶段使用 Canvas。

尺寸依赖内容时要在测量里计算，颜色或进度变化通常只需重绘。不要在 onDraw() 里反过来修改布局。

当前项目怎么用：yyyyy-cdoe/Bootstrap/bootstrap/src/main/java/com/zhihu/android/bootstrap/consecutive/ConsecutiveScrollerLayout.java 实现 onLayout 并管理子项位置，yyyyy-cdoe/barrage/barrage/src/main/java/com/zhihu/android/barrage/BarrageView.java 实现 onDraw；两个真实类分别对应布局与绘制职责。

invalidate() 与 requestLayout() 如何选？View

先说结论：只改变绘制内容时调用 invalidate()，改变尺寸、位置或父布局需求时调用 requestLayout()。

requestLayout() 通常会触发重新测量和布局，成本比单纯重绘更高。反过来，尺寸变了却只 invalidate，界面可能仍用旧尺寸。

我会先判断变化影响的是像素还是布局，并在滚动和动画场景里避免高频触发完整布局。

当前项目怎么用：yyyyy-cdoe/barrage/barrage/src/main/java/com/zhihu/android/barrage/BarrageView.java 是绘制型自定义 View，可以拿来把“只变内容”和“尺寸/位置变更”区分开；代码里没看到该类完整调用 invalidate/requestLayout 的变更链，所以不要说项目已经按这个方式处理。

MeasureSpec 为什么重要？测量

先说结论：MeasureSpec 把父容器给出的模式和上限传给子 View，决定控件能不能按内容或指定尺寸展示。

EXACTLY 表示尺寸被定死，AT_MOST 表示不能超过上限，UNSPECIFIED 表示父容器限制较少。自定义 View 需要结合自己的建议尺寸处理三种情况。

我会在 onMeasure 中同时考虑 padding、最小尺寸和父约束，并用不同布局参数测试 wrap_content、match_parent 和固定尺寸。

当前项目怎么用：yyyyy-cdoe/Bootstrap/bootstrap/src/main/java/com/zhihu/android/bootstrap/consecutive/ConsecutiveScrollerLayout.java 是自定义 ViewGroup 的 onLayout 实现，说明父容器必须先决定子项可用空间；代码里没看到完整 onMeasure 实现，面试时不要补写 MeasureSpec 处理细节。

自定义 View 的 onDraw 如何优化？性能

先说结论：自定义 View 的 onDraw() 要做到少分配、少计算、只画可见内容。

先说结论：不是。重组是重新执行受影响的 Composable 函数，也就是用来描述 UI 的函数；Compose 会尽量跳过没受影响的节点，后面是否重新布局或绘制还要看实际变化。

比如一个计数状态只被标题读取，状态变化时通常只重跑读取它的那段组合代码；布局参数变了可能触发测量和布局，颜色或 Canvas 内容变了才更可能进入绘制。每次重组也不等于一定产生一帧。

实际排查时我会用 Layout Inspector、Compose Tracing 或系统 trace 看重组次数和帧耗时，同时检查是否在 Composable 里创建新对象、做排序或同步 I/O。先找真正耗时的阶段，再决定是拆组件、稳定参数还是把工作移出主线程。

当前项目怎么用：现在这些仓库里没找到真正的 Compose 实现。能直接参考的是 yyyyy-cdoe/BlurView/library/src/main/java/eightbitlab/com/blurview/PreDrawBlurController.java，它处理传统 View 的预绘制模糊；这不能说明项目做过 Compose 重组性能优化。

remember 能保存多久？状态

先说结论：remember 只在当前 Composition（当前页面的 Compose UI 树）还存在时保存值；页面离开这棵 UI 树后就会失效，旋转等配置变化也不一定保留。

同一个 Composable 重新组合时，位置和 key 没变，remember 的值会继续用。需要跨配置变化保存的小型 UI 值可以用 rememberSaveable，需要跨页面或进程恢复的数据仍应放到 ViewModel、数据库或其他持久化层；进程被杀时普通 remember 一定不可靠。

我会按数据寿命来选：输入框临时值用 remember，能放进 Bundle 的筛选条件用 rememberSaveable，列表和请求结果交给 ViewModel/数据层，避免把大对象塞进保存状态。

当前项目怎么用：现在这些仓库里没找到 remember 或 rememberSaveable 的调用。yyyyy-cdoe/BlurView/library/src/main/java/eightbitlab/com/blurview/PreDrawBlurController.java 是 View 绘制控制器，不是 Compose 状态容器，所以不能把它当成 remember 的项目用法。

为什么副作用不能直接写在 Composable 主体？副作用

先说结论：Composable 主体可能被重复执行、跳过或在预览中执行，直接写网络、写数据库、发事件就可能重复触发，所以副作用要交给 Effect API（由 Compose 管理启动、取消和清理时机）。

需要按 key（决定任务何时重启的输入）启动可取消协程时用 LaunchedEffect，订阅或注册监听器并在离开时解除用 DisposableEffect，把已经完成的状态同步到外部对象可考虑 SideEffect。这些 API 的 key 变了会取消旧工作并启动新工作。

常见坑是把每次重组都会变的对象当 key，导致请求不停重启；或者在 LaunchedEffect(Unit) 里捕获旧回调。回调需要用 rememberUpdatedState 读取最新引用，资源则在 onDispose 里清理。

当前项目怎么用：现在这些仓库里没找到 Composable 主体、LaunchedEffect 或 DisposableEffect。yyyyy-cdoe/BlurView/library/src/main/java/eightbitlab/com/blurview/PreDrawBlurController.java 里只有兼容 Compose 的注释，不能说项目真的有这条 Effect 调用链，也不能说明个人做过它。

Lazy 列表为什么需要稳定 key？列表

先说结论：稳定 key 让 Compose 知道一条数据前后还是同一条，插入、删除或排序时才能正确保留对应 item 的滚动位置和局部状态。

不写 key 时，列表通常按位置对应。头部插入一项后，后面的 item 可能被当成换了数据，造成输入框内容、动画或加载状态串到别的行。key 必须在数据生命周期内稳定且唯一，优先用服务端 ID，不要用 index；没有 ID 时先补一个真正稳定的本地 ID。

我还会检查分页重复数据、ID 变化和 placeholder（占位项）。key 稳定不代表 item 参数一定稳定，行内仍要避免传入每次重组都新建的可变对象。

当前项目怎么用：现在这些仓库里没找到 Compose 的 LazyColumn 或 key 用法。列表相关代码是传统 RecyclerView/Adapter；可以看 yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/PagingDataAdapter.kt 这个自定义分页适配器，但不能把它说成 Compose Lazy 列表经验。

Compose Snapshot、稳定性与重组跳过是什么关系？Compose 状态

先说结论：Snapshot 负责让 Compose 观察状态读写，稳定性帮助它判断参数是否能安全复用；当读取的状态没变、参数也满足稳定条件时，某段组合代码才有机会被跳过。

这里的“稳定”不是说对象永远不变，而是 Compose 能可靠知道它的变化，或者能用相等性判断两次输入没有变化。把一个可变集合原地修改后仍传同一个引用，Compose 可能看不到变化；用不可变集合和新对象更新更容易得到可预测结果。

我不会为了跳过重组到处加 @Stable。先确认模型真的满足承诺，再用 Layout Inspector/Compose Tracing 看效果；错误标注稳定性比多跑几次重组更难排查。

当前项目怎么用：现在这些仓库里没找到 Compose Snapshot API 或稳定性标注。yyyyy-cdoe/BlurView/library/src/main/java/eightbitlab/com/blurview/PreDrawBlurController.java 只能说明传统 View 的绘制时机，不能当成 Snapshot 或重组跳过的项目例子。

LaunchedEffect 的 key、旧闭包与资源清理怎样处理？Compose 副作用

先说结论：把“任务应该跟谁的生命周期走”放进 key：key 变化就取消旧协程并启动新协程；需要拿最新回调时，避免旧闭包（把外部变量带进来的函数）一直捕获老值。

例如按 userId 加载详情用 LaunchedEffect(userId)，而不是把每次变化的临时对象直接放进去。回调可以先用 rememberUpdatedState 包起来，让长任务调用最新回调。监听器、播放器、Receiver 之类的资源用 DisposableEffect 注册并在 onDispose 解除。

页面退出、key 变化和异常都要测；如果任务不能跟 Composable 生命周期走，就让 ViewModel 或业务层持有，并提供明确的取消方式。

当前项目怎么用：现在这些仓库里没找到 LaunchedEffect、rememberUpdatedState 或 Compose 资源清理调用。能参考的传统生命周期清理在 yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/mvx/MvxViewModel.kt 的 ViewModel/Flow 边界，但不能把它说成 LaunchedEffect 实现。

状态提升、rememberSaveable 与单向数据流怎样配合？状态管理

先说结论：把可被多个组件使用或需要业务决策的状态提升到共同的上层，子组件只接收值和事件；小范围、纯 UI 的临时值才留在 remember 或 rememberSaveable。

单向数据流，就是“上层给状态，子组件发事件”。例如列表筛选条件由 ViewModel 保存，Composable 传入 filter 和 onFilterChange；文本框正在输入但尚未提交的值可以先由组件保存，提交时再通知上层。这样不会出现两个地方各自改同一个状态。

rememberSaveable 适合 Bundle 能保存的小值，不适合大列表、文件句柄或请求对象。涉及跨页面、网络和数据库时，我会让 ViewModel/数据层成为唯一最终数据来源，再把 UI 临时状态和业务状态分开。

当前项目怎么用：现在这些仓库里没找到 Compose 状态 API。yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/mvx/MvxViewModel.kt 确实有状态 reducer 和 viewModelScope 的架构能力，但它不是 rememberSaveable，也看不出某个 Compose 页面用了这条链路。

Compose 页面掉帧怎样区分重组、布局、绘制与业务阻塞？Compose 性能

先说结论：先用帧时间和 trace 判断卡在哪一段，再分别处理重组过多、测量布局过重、绘制昂贵或主线程业务阻塞，不能看到掉帧就只优化 Compose。

我通常先复现并记录滚动/点击时的帧耗时，再看 Compose Tracing、Layout Inspector、Perfetto 和 Android Studio Profiler：重组阶段看读取范围和参数稳定性，布局阶段看嵌套和反复测量，绘制阶段看大图、阴影和 Canvas，主线程外还要排查同步 I/O、JSON 解析和锁等待。

改动后用同一设备、同一路径回归，比较 p95/p99（95%/99% 的帧都不超过的耗时）或帧时间分布。不要只拿一次顺滑录屏当结论；仓库没有真实 Compose 页面时，也要明确这是通用排查方案。

当前项目怎么用：现在这些仓库里没找到 Compose 页面、Compose tracing 或 Macrobenchmark 配置。yyyyy-cdoe/BlurView/library/src/main/java/eightbitlab/com/blurview/PreDrawBlurController.java 能用来讲传统预绘制控制，但没有 Compose 掉帧分段数据，不能把通用排查方案说成项目结果。

12. Jetpack 架构 P0

架构不是堆 Jetpack 名词，而是状态、数据源、导航和任务的边界清晰。

这一模块具体要掌握哪些内容？（Jetpack 架构）清单

先说结论：Jetpack 架构题重点是生命周期、数据来源和恢复方式怎么配合，不是把 ViewModel、Room、WorkManager、Navigation 的名字背一遍。

  • ViewModel 只保存页面需要的业务状态和事件处理，不持有 Activity、View 等短生命周期对象。
  • Repository 可以理解成数据中转层：它把网络、数据库等来源整理成业务可用的接口；要说清缓存优先级、错误处理和刷新方式。
  • Room 负责本地结构化数据，Flow 负责把变化送到 UI；Paging3/RemoteMediator 要处理刷新、追加、重复页和离线数据。
  • WorkManager 适合可延迟、需要约束且能重试的后台工作；实时任务、精确闹钟和前台交互要选别的工具。
  • Navigation 参数传 ID 或轻量值，跨模块路由要有明确契约；Hilt/Dagger 的作用域要和真实生命周期对齐。

回答时我会把“输入—数据层—ViewModel—UI—退出和恢复”讲成一条链，并说明仓库代码只说明实现，不自动说明个人负责范围。

当前项目怎么用：项目里能直接看到的是 Mavericks/RxJava 架构：yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/mvx/MvxViewModel.kt 将 Flow/Observable 结果通过 reducer 写入状态，yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/mvx/MvxRepository.kt 负责 Repository 的状态更新；现在这些仓库里没找到完整 Jetpack Navigation、Paging3、Hilt 组合落地。

ViewModel 应持有 Activity、View 或 Adapter 吗？分层

先说结论：通常不应该。ViewModel 可能比某个 Activity、Fragment 或 View 活得更久，直接持有它们会泄漏，也会让业务层依赖 UI 细节。

ViewModel 里放可恢复的 UI 状态、调用用例或 Repository；Activity/Fragment 负责把状态渲染出来并转发事件。Adapter 也不建议放进去，列表数据由页面收集后提交，点击通过事件回到页面或 ViewModel。需要 Context 时优先用 applicationContext，但也要先确认确实需要。

例外不是“能不能编译”，而是生命周期是否明确：短暂的纯计算对象可以传入方法，不能把页面引用存成字段。遇到泄漏，我会看 heap 引用链和 ViewModel 清理时机，而不是只凭代码样式下结论。

当前项目怎么用：yyyyy-cdoe/Comment/comment/src/main/java/com/zhihu/android/comment_for_v7/viewmodel/CommentViewModel.kt 的 CommentViewModel 持有 LiveData 与多个 Repository，并将评论结果交给 UI；从这段代码看，没有其持有 Activity、View 或 Adapter，是否由我参与，要以本人经历为准。

Repository 的价值是什么？数据层

先说结论：Repository 把“页面怎么拿数据”与“数据来自网络、数据库还是缓存”分开，让上层不必知道每个数据源的细节。

它不应该只是把 Retrofit 方法改个名字。一个有价值的 Repository 会定义刷新和读取规则、合并错误、处理缓存过期，并给 ViewModel 一个稳定的业务接口。比如页面先展示 Room，再由网络刷新并写回 Room，UI 只订阅数据库变化。

也不是所有项目都必须加一层：只有一个数据源、没有业务规则时可以简单一些。加了 Repository 后要防止它变成巨型类，按业务能力拆开，并为网络失败、空数据和并发刷新写测试。

当前项目怎么用：yyyyy-cdoe/Feed/feed/src/main/java/com/zhihu/android/app/feed/ui2/feed/repo/FeedRepository.kt 的 FeedRepository 同时协调 FeedLocalDataSource、远端数据源、预加载和缓存标记，并将刷新/加载更多映射为统一结果；从这段代码可以直接看出，Repository 不只是 Retrofit 转发层。

WorkManager 适合什么，不能做什么？任务

先说结论：WorkManager 适合“现在不一定执行，但最终要做完”的后台工作，能配网络/充电等约束并在进程重启后继续；它不适合实时循环、毫秒级定时或必须立刻完成的前台交互。

上传日志、同步本地草稿、定期清理这类任务可以用 OneTimeWorkRequest 或周期任务，并设置约束、退避重试和唯一任务名。任务要可幂等，也就是重复执行不会产生重复副作用；返回 Result.retry() 只用于暂时性失败。

精确闹钟、持续播放或导航这类需求要分别考虑 AlarmManager、前台服务等方案。还要注意后台限制、任务最长运行时间、取消和网络变化，不能把 WorkManager 当成通用线程池。

当前项目怎么用：现在这些仓库的 Kotlin/Java 代码里没找到 WorkManager、Worker 或 WorkRequest 的实际调用，所以不能说项目使用它做同步或重试。能直接看到的后台/取消边界是 yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/mvx/MvxRepository.kt 的 CoroutineScope 生命周期，而不是 WorkManager 持久任务。

Navigation 参数为什么不要传大对象？导航

先说结论：导航参数优先传 ID、筛选条件等轻量值，不要把大列表、Bitmap 或复杂可变对象塞进 Bundle；这样更稳，也不容易撞上 Binder（Android 进程间传输机制）的消息大小上限。

目标页面拿到 ID 后从 ViewModel、Repository 或数据库重新取数据。大对象会带来序列化开销、进程死亡后无法恢复、对象引用过期和参数版本难兼容等问题。即使实现了 Parcelable，也只是传输更快，不代表适合跨进程或长期保存。

参数需要校验缺失和非法 ID，Deep Link 也要走同一套入口。页面之间共享的临时状态不要靠全局单例偷传，应该有明确的数据层或 SavedStateHandle。

当前项目怎么用：项目路由通过 Parcelable 的 ZHIntent 传递目标和 Bundle：yyyyy-cdoe/ZRouter/zrouter/src/main/java/com/zhihu/android/app/util/ZHIntent.java；调用方 yyyyy-cdoe/ZRouter/app/src/main/java/com/zhihu/android/app/MainActivity.java 创建并放入 Intent。代码里看不出 Jetpack Navigation 参数实现，所以别把它说成 Jetpack Navigation。

复杂页面采用 MVVM 还是 MVI，怎样避免双状态源与巨型 ViewModel？架构选型

先说结论：我不会先选名词，而是先看页面的状态数量、事件复杂度和团队习惯；MVVM 和 MVI 都能做，关键是页面只从一个地方读取最终状态，且 ViewModel 不包揽所有事情。

MVVM 可以让 ViewModel 暴露多个可观察状态，MVI 常把事件转成一个不可变 UI State。无论哪种写法，都要把网络、数据库和复杂业务拆到用例/Repository，把状态按功能拆成小模型，并为加载、空态、错误、重试写清楚事件路径。

双状态源的典型问题是 Fragment 自己有一份列表、ViewModel 又有一份，回调顺序一变就互相覆盖。解决办法是选一个最终来源，其他地方只发事件；如果页面已经变成巨型 ViewModel，就按子功能拆分，而不是继续增加字段。

当前项目怎么用：更直接的项目里能直接看到的内容是 Mavericks 风格状态而非严格 MVI：yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/mvx/MvxViewModel.kt 提供 setState/Async reducer，yyyyy-cdoe/Comment/comment/src/main/java/com/zhihu/android/comment_for_v7/viewmodel/CommentViewModel.kt 则以功能 Repository 拆分评论操作；这只能说明前面的事实，不能说这是个人架构决策。

网络与 Room 都能返回数据时，谁是 UI 的单一事实源？单一事实源

先说结论：对需要离线展示和持续更新的页面，我通常让 Room 成为 UI 的单一事实源，就是页面只认一个最终数据来源；网络负责拉取并写入 Room，UI 只订阅 Room 的结果。

这样网络返回和本地数据不会各自直接更新列表，刷新、进程恢复和重试都走同一条路径。需要即时反馈的提交动作可以先更新本地状态，再根据服务端结果确认或回滚，但这个临时状态也要有明确字段，不能偷偷维护第二份列表。

如果数据非常短命、无需离线，直接由 Repository 暴露网络结果也可以。关键是把选择理由说清楚，并处理写库失败、网络旧响应、删除后重新出现和页面退出等情况。

当前项目怎么用：yyyyy-cdoe/Feed/feed/src/main/java/com/zhihu/android/app/feed/ui2/feed/repo/FeedRepository.kt 的 UI 数据流明确区分缓存与网络，并在刷新成功后调用本地保存；同时仓库里虽然有 Room 数据库（如 yyyyy-cdoe/KnowledgeMarket/sku-manuscript/src/main/java/com/zhihu/android/app/sku/manuscript/preload/ManuscriptHtmlDatabase.kt），现在没看到这条 Feed 链路直接由 Room 驱动 UI，所以不能把 Room 说成这条链路的唯一数据来源。

Paging3、RemoteMediator 与 Room 怎样形成稳定分页？Paging3

先说结论：常见稳定方案是 PagingSource（负责分页读取数据）读 Room，RemoteMediator（负责协调网络和本地库）负责刷新/追加，Pager 再把结果交给 UI；网络结果先事务写入数据库，再由数据库驱动列表。

刷新时清理或替换旧页并保存新的远端键，追加时根据 RemoteKeys（记录每页对应的远端游标）找到下一页。数据库写入和 key 更新要放在同一事务里，避免数据已经写入但 nextKey 没保存，或者 key 更新了却没有对应数据。重复页、空页、网络失败和末页都要有明确处理。

item 的唯一 ID 交给稳定 key，不能用位置代替。RemoteMediator 解决的是网络与本地分页协作，不会自动解决接口重复、服务端排序变化或业务去重，这些规则仍要在数据层定义。

当前项目怎么用：现在这些仓库里没找到 RemoteMediator 或 Paging3 API；项目里能看到自定义分页适配器 yyyyy-cdoe/DevKit/devkit/src/main/java/com/zhihu/android/devkit/paging/PagingDataAdapter.kt，以及 Feed 的刷新/加载更多协调 yyyyy-cdoe/Feed/feed/src/main/java/com/zhihu/android/app/feed/ui2/feed/repo/FeedRepository.kt，别把它说成 RemoteMediator+Room 实现。

Hilt/Dagger 的作用域为什么会导致泄漏或状态串用？依赖注入

先说结论：依赖的存活时间不能比它持有的对象更长；作用域（依赖实例能活多久）太大可能把 Activity、View 或账号态留住，作用域太小又可能让本该共享的实例不断重建。

例如 Singleton 组件里不能放页面引用，ActivityRetained 适合跨配置变化但不适合保存短页面 View，ViewModelComponent 适合跟 ViewModel 一起活。账号切换时还要清理或重新建立对应容器，避免上一个账号的缓存串到下一个账号。

排查时我会沿依赖图看谁创建、谁持有、何时销毁，再结合 heap dump 验证泄漏。不要只看注解名称；自定义 scope、Provider/Lazy 和多进程也会改变真实生命周期。

当前项目怎么用：现在这些仓库里没找到 Hilt/Dagger 注解或组件图；项目更多通过显式构造和全局单例装配，例如 yyyyy-cdoe/Feed/feed/src/main/java/com/zhihu/android/app/feed/ui2/feed/repo/FeedRepository.kt 中的 object 与数据源字段。所以不能说项目存在 Hilt scope 泄漏或个人 DI 设计。

Navigation 返回栈、Deep Link 与多模块路由怎样避免状态错乱？导航架构

先说结论：每条路由都要定义参数、目标栈和重复打开规则，Deep Link 也要走同一套参数校验；返回时只让栈按明确规则变化，不要在各页面里随意 pop。

常见做法是路由只传轻量 ID，目标模块自己加载数据；需要复用已有页面时明确 launchSingleTop、popUpTo 和是否保存状态。Deep Link 可能在冷启动、登录中断或进程恢复后到达，所以要有登录拦截、缺参处理和回退路径。

多模块之间可以用接口或类型安全路由封装参数，避免直接依赖对方实现。测试至少覆盖连续点击、重复 Deep Link、返回到列表、旋转和进程重建，否则“偶现回错页面”很难复现。

当前项目怎么用：yyyyy-cdoe/ZRouter/zrouter/src/main/java/com/zhihu/android/app/router/ZRouter.java 解析路由并通过 ZHIntent 打开 Fragment/Activity；yyyyy-cdoe/Feed/app/src/main/java/com/zhihu/android/feed/MainActivity.kt 还展示了通过 URI 解析 Feed 入口。这里是自研路由，不是 Jetpack Navigation，项目现在看不出 deep link 的完整恢复策略。

13. 组件化、Gradle、Maven、AAR P1

构建题考依赖边界、产物、可复现性与模块协作，不是背脚本 DSL。

这一模块具体要掌握哪些内容？（组件化与构建）清单

先说结论：组件化和构建题要能说明模块职责、依赖方向、产物交付和构建速度，不是只会改一行 Gradle。

  • 按业务能力或稳定基础能力划分模块，API 与实现分开，避免循环依赖和“大杂烩”公共模块。
  • 理解 api/implementation、AAR/JAR、APK/AAB，以及 variant（构建变体）、POM（依赖元数据）和 Maven 仓库如何接上。
  • 通过版本目录、依赖约束、锁文件和依赖树处理冲突；用构建扫描或 Gradle profile 区分配置、执行、缓存和网络问题。
  • 组件改动要做单模块编译、单测、宿主 App 集成、R8/Release 和二进制兼容检查。
  • 把依赖方向、禁止列表和 CI 门禁写成可执行规则，不靠口头约定。

仓库代码能说明当前工程的模块和配置，但不能自动说明我个人搭建或维护了整套构建系统。

当前项目怎么用：组件化的例子集中在 Account 工程：yyyyy-cdoe/Account/settings.gradle 按开关 include 模块，yyyyy-cdoe/Account/app/build.gradle 在代码项目与 Maven 坐标之间选择依赖，并区分 api/implementation。AAR 发布、构建变体和排除冲突可从这些配置复核；个人具体做了什么，还是要按本人经历说明。

组件化的边界如何划分？模块

先说结论：边界应该围绕业务能力和变更频率划分，让模块有清楚的输入输出；不要按“每个页面一个模块”或“所有工具一个 common”机械切割。

我会先看谁使用、谁负责数据、哪些代码需要独立发布，再把稳定接口放在 API 模块，具体实现留在实现模块。基础组件只能向下依赖，业务模块不能反向引用宿主内部细节；跨模块通信通过接口、路由或事件契约完成。

边界太细会增加构建和维护成本，太粗则改一个功能牵动全仓。用依赖图、改动频率和发布节奏复盘，而不是只看目录名字。

当前项目怎么用：yyyyy-cdoe/Account/settings.gradle 将 account、app、account-api 分成模块，yyyyy-cdoe/Account/account/build.gradle 以 account-api 为 API 入口并配置组件依赖；这是能直接看到的模块边界，代码里看不出团队分工，个人参与要按本人经历说明。

api 与 implementation 的区别为何重要？Gradle

先说结论：api 会把依赖的公开类型暴露给下游，implementation 只在当前模块可见；默认优先用 implementation，确实需要让下游编译到该类型时才用 api。

比如模块 A 的公开方法返回库 B 的类型，A 可能需要用 api；如果 B 只在 A 内部实现网络或日志，就用 implementation。滥用 api 会扩大编译影响面，也让模块边界变得模糊。

改配置后我会看下游模块是否真的引用了该类型、跑依赖树和增量构建验证。不能只凭“现在能编译”判断合理，公开 API 变化还要考虑二进制兼容。

当前项目怎么用：yyyyy-cdoe/Account/account/build.gradle 同时使用 api 暴露 account-api、feed-api 等公共类型，并用 implementation 隐藏 base、net 等实现依赖；yyyyy-cdoe/Account/app/build.gradle 也用 implementation 引入 account 模块，说明下游模块能看到哪些依赖、哪些依赖只留在当前模块内部。

AAR 与 Maven 仓库在交付中各扮演什么角色？发布

先说结论：AAR 是 Android 库的一个交付包，Maven 仓库是存放和按坐标分发这些包及元数据的地方；一个是产物，一个是发布渠道。

AAR 通常包含 class、资源、Manifest 和 ProGuard/R8 规则，适合 Android library；JAR 主要是 JVM class，不能承载完整 Android 资源。发布到 Maven 时还要带 POM、版本、variant 和传递依赖信息，下游才能正确解析。

我会在发布前用一个干净示例工程验证依赖、资源、Manifest、Debug/Release variant 和 R8。只把 AAR 拷贝给别人，容易漏传递依赖和版本信息，也无法稳定回滚。

当前项目怎么用：yyyyy-cdoe/Account/account/build.gradle 声明 group = 'com.zhihu.android.component' 和 archivesBaseName = 'account'，而 yyyyy-cdoe/Account/app/build.gradle 从 Maven 坐标或本地 project 依赖组件；这段代码能说明发布坐标和消费方式，现在这些仓库里没找到本次构建的 AAR/POM 实物。

如何减少构建不稳定和依赖冲突？工程

先说结论：先让版本和依赖来源可追踪，再处理冲突；版本目录、依赖约束、锁定版本、统一仓库和 CI 重复构建是基础。

遇到冲突我会先跑 dependencies 或 dependencyInsight 找出谁引入了不同版本，再决定升级、约束、排除还是替换，而不是随手写一个全局强制版本。插件、Kotlin、AGP、compileSdk 也要按兼容矩阵一起升级。

网络仓库抖动、动态版本、未提交的本地 AAR 都会让结果不稳定。CI 要使用固定输入并保留构建日志；改完还要验证干净构建和常用 variant。

当前项目怎么用：yyyyy-cdoe/Account/app/build.gradle 对 component-api、OkHttp、Okio 等传递依赖做 exclude，并在 debug/release 选择不同 Stetho 实现；yyyyy-cdoe/Account/settings.gradle 通过 local.properties 控制代码依赖。这段配置能看出在处理冲突，但没有 CI 结果，不能说稳定率是多少。

JAR、AAR、APK、AAB 分别是什么，产物怎样流转？构建产物

先说结论：JAR/AAR 是库，APK 是可安装包，AAB 是提交给商店的发布包；通常是库先被 App 编译合并，再由 APK/AAB 打包输出。

JAR 主要装字节码，AAR 还能带 Android 资源和 Manifest。Gradle 先解析依赖和 variant，再编译 class/Kotlin、处理资源、合并 Manifest，最后签名生成 APK；AAB 按设备配置交给商店生成更细的 APK。

排查产物问题时我会分别看依赖树、merged manifest、资源合并、mapping 文件和签名信息。AAB 能交付不代表本地 APK 的 ABI、R8 或渠道配置都没有问题。

当前项目怎么用：yyyyy-cdoe/Account/app/build.gradle 是 application 模块并配置 applicationId、versionCode 和 buildTypes，yyyyy-cdoe/Account/account/build.gradle 是 library 模块并配置 archivesBaseName；这能区分 App 与库的构建角色。现在仓库里没找到 AAB 产物或发布流水线，所以不能说仓库已经产出过 AAB。

implementation 与 api 何时选择，怎样影响编译？依赖边界

先说结论：看依赖类型是否出现在当前模块的公开 API；不出现在公开 API 就用 implementation，需要下游直接编译使用才考虑 api。

api 会把依赖传给下游，公开类型变动可能触发更多模块重编译；implementation 把实现藏起来，通常更有利于增量构建和替换。若只是测试、编译插件或运行时需要，还应分别使用对应 configuration。

我会用一个下游模块验证：删掉 api 后是否仍能编译，公开方法签名是否泄漏了依赖类型，再结合构建时间和兼容性决定，而不是把所有依赖都改成同一类。

当前项目怎么用：在 yyyyy-cdoe/Account/account/build.gradle 中，account-api、feed-api 等出现在 api，base、net 等出现在 implementation；在 yyyyy-cdoe/Account/app/build.gradle 中业务组件多使用 implementation。这段配置支持“公共类型才暴露”的判断，没有编译时间数据，不能说收益是多少。

组件改动如何验证没有破坏主 App？回归

先说结论：至少要验证“组件自己能用”和“主 App 接得上”两层，不能只看库模块单测通过。

我会先跑组件编译、单测和 lint，再用宿主 App 做真实集成：检查 API/资源/Manifest、运行时初始化、不同 variant、混淆后的反射和多 ABI。涉及导航、Service 或 ContentProvider 时，还要走一遍实际启动和退出路径。

CI 可以加一个最小宿主样例或集成测试，发布 AAR 后再用干净工程消费一次。失败时保留 Gradle 日志、merged manifest 和 mapping，方便判断是源码、依赖解析还是打包阶段出问题。

当前项目怎么用：yyyyy-cdoe/Account/app/build.gradle 配置了 JUnit、Robolectric、AndroidX test 与 Espresso，且通过 project/Maven 两路装配组件；yyyyy-cdoe/Account/account/build.gradle 配置库测试依赖。这里只能看到测试入口，没看到这次改动对应的测试报告或主 App 构建结果。

Gradle 构建慢时，怎样区分配置慢、任务执行慢和缓存未命中？构建性能

先说结论：先把构建拆成配置阶段、具体任务执行和缓存/网络，再用 profile 或 Build Scan 看时间，别一上来就盲目开并行。

配置慢通常和脚本计算、插件初始化、动态读取有关；任务慢要看 Kotlin 编译、资源处理、R8 等具体 task；缓存未命中则检查输入是否变了、缓存是否可访问、任务是否支持缓存。用同一命令比较 clean、增量和第二次构建，才能看出差异。

优化时固定 Gradle/AGP/JDK 版本，减少每次配置扫描，启用配置缓存和远程构建缓存前先确认插件兼容。并行和更大内存不是万能药，可能让机器争抢资源甚至更慢。

当前项目怎么用：yyyyy-cdoe/Account/app/build.gradle 的 dexOptions 注释明确区分增量 build 与 clean build 的代价，并设置 Java heap；yyyyy-cdoe/Account/settings.gradle 的动态模块 include 可能影响配置阶段。仓库里没有 profile 或 Build Scan，所以现在没法报出本项目各阶段的耗时。

R8 只在 Release 引发反射、序列化或 JNI 崩溃，怎样定位 keep 规则？R8

先说结论：先用 Release 的 mapping、崩溃堆栈和最小复现确认哪个类或成员被移除/改名，再补最小范围的 keep 规则，不要直接 keep 全包。

反射、JSON 序列化、JNI、动态注册和 Manifest 配置都可能让 R8 看不到真实引用。我会先检查官方或库自带的 consumer-rules，使用 -whyareyoukeeping、seeds、usage 等输出确认收缩结果，再对需要保留的类、构造器、字段或注解写规则。

改完必须用 minifyEnabled 的 Release APK/AAB 走真实路径，并保留 mapping 供线上反混淆。debug 能跑不能证明 R8 配置正确，过宽 keep 也会损失包体和优化效果。

当前项目怎么用：yyyyy-cdoe/Account/app/build.gradle 为 release 指定 proguard 文件但将 minifyEnabled false，所以这段代码看不出该工程发生过 R8 release 崩溃，也看不出已经做过 keep 修复；yyyyy-cdoe/Account/account/build.gradle 的 consumer-proguard-files 只说明库可向消费者传递规则，不能说我做过这次排查。

组件化后怎样用工程约束保证依赖方向，而不是只靠口头约定？模块契约

先说结论：把依赖方向变成可失败的检查：模块图、允许依赖清单和 CI 门禁都要能自动执行。

可以用 Gradle convention plugin（统一构建配置的插件）统一配置，给业务模块和基础模块分类，再用 task（自动执行的构建任务）读取依赖图，发现反向依赖、循环依赖或直接引用实现包就失败。跨模块能力放 API 接口，禁止业务模块依赖宿主实现细节。

规则要有例外申请和迁移路径，否则大家会绕过检查。每次新增模块、升级依赖和发布前跑一遍架构检查，并在代码评审里解释为什么新增依赖，而不是只贴一张静态架构图。

当前项目怎么用：yyyyy-cdoe/Account/settings.gradle 以显式模块列表和代码开关控制参与构建，yyyyy-cdoe/Account/account/build.gradle 通过 api/implementation 与多个 exclude 把边界收好；这能把规则落到配置上。现在这些仓库里没找到自动依赖方向校验规则，所以不能说已有架构 lint。

发布 AAR 时，怎样验证 POM、variant 和二进制兼容？库兼容性

先说结论：发布前要在干净工程里按实际坐标消费 AAR，核对 POM/传递依赖、目标 variant、资源和 API 兼容，不能只看发布任务成功。

我会检查 Maven 元数据里的 group/name/version、依赖范围和 Gradle module metadata，再分别消费 debug/release 或对应 variant。用 API diff 工具比较旧版与新版公开类、方法、字段，确认没有不兼容删除或签名变化。

还要跑资源、Manifest、R8、ProGuard consumer rules 和混淆后的冒烟测试。发布后保留产物校验值和回滚版本；仓库能证明发布配置，不代表能证明个人发布结果。

当前项目怎么用：yyyyy-cdoe/Account/account/build.gradle 提供 library 插件、group 与 archivesBaseName，yyyyy-cdoe/Premium/premium-api/build.gradle 也配置 api 库和坐标；现在这些仓库的代码里没找到 publication/POM 校验任务、variant API 或 ABI 检查报告，没有报告就不能说完整发布验证已经做完。

14. 网络 P0

网络能力要覆盖线程、失败模型、缓存、幂等和可观测性。

这一模块具体要掌握哪些内容？（网络）清单

先说结论：网络题要从请求生命周期讲到失败处理、缓存、安全和监控，不能只背 Retrofit API。

  • 区分 DNS、连接、TLS、请求发送、服务端处理、响应读取和解析各阶段的耗时与错误。
  • 知道超时、重试、取消、幂等、退避和 401 刷新之间的关系，避免重试风暴和重复提交。
  • 理解 OkHttp 连接池/拦截器、Retrofit Converter/CallAdapter，以及 HTTP/1.1、HTTP/2、HTTP/3 对请求的影响。
  • 区分 HTTP 缓存和业务缓存；业务缓存通常还要落到 Room，并定义过期、刷新和离线策略。
  • 记录可定位的请求上下文，但要脱敏；仓库代码能说明拦截器和调用链，不自动说明线上指标或个人贡献。

回答一个问题时，我会先说用户看到的结果，再按阶段拆证据，最后补上取消、重试和离线情况。

当前项目怎么用：yyyyy-cdoe/Feed/feed/src/main/java/com/zhihu/android/app/feed/ui2/feed/repo/FeedRepository.kt 将 FeedService、缓存、预加载、刷新和加载更多串起来；yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/app/util/NetworkUtils.java 提供统一 createService 与 Response 错误处理。SSE 的取消、重试和监控还可以看 yyyyy-cdoe/Net/net/src/main/java/com/zhihu/android/net/sse/SseCallImpl.kt。

网络请求为什么不能只分“成功/失败”？错误模型

先说结论：同样是失败，DNS、超时、TLS、HTTP 4xx/5xx、业务错误和解析错误的处理完全不同；成功也要区分缓存命中、部分数据和业务拒绝。

我会至少保留网络阶段、HTTP code、业务 code、可重试性、是否用户主动取消和请求耗时。比如 401 要重新登录或刷新 Token，429 要尊重服务端节奏，超时可能重试，参数错误则不该重试。

错误模型要能让 UI 给出合适反馈，也要让日志按版本、网络和接口聚合。不要把所有异常转成一个“请求失败”，否则既无法指导用户，也无法判断下一步。

当前项目怎么用：yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/app/util/NetworkUtils.java 区分 HTTP 非成功响应并转换为 RetrofitAPIError/API 错误，yyyyy-cdoe/Comment/comment/src/main/java/com/zhihu/android/comment_for_v7/repository/RootCommentListRepository.kt 又分别处理成功、HTTP code failure 与 Throwable error；这里能看到三条处理路径：成功、HTTP code failure 和 Throwable error。

重试为什么可能造成更大事故？可靠性

先说结论：重试会放大请求量和副作用，服务端已经变慢时更容易形成雪崩；只有确认暂时性失败、操作可安全重复，并且有上限和退避时才重试。

GET 或带幂等键的提交相对容易重试；支付、下单这类操作要靠服务端幂等键防止重复。重试应使用指数退避加抖动，限制次数和总时长，区分用户取消、网络不可用、4xx 和 5xx。

还要避免拦截器、Repository、WorkManager 各自重试一次，叠加后次数会失控。线上需要看重试率、失败率和服务端压力，发布前用断网、超时和快速点击测试。

当前项目怎么用：yyyyy-cdoe/Net/net/src/main/java/com/zhihu/android/net/sse/SseRetryPolicy.kt 明确区分取消、超时、TLS/协议错误和可重试 HTTP 状态，yyyyy-cdoe/Net/net/src/main/java/com/zhihu/android/net/sse/SseCallImpl.kt 设有最大重试次数并延迟重连；这里展示的只是 SSE 的重试，不能直接套到所有业务写请求。

缓存策略应先回答哪几个问题？缓存

先说结论：先回答“数据能旧多久、谁能读、何时刷新、失败怎么办、怎么失效”，再选内存、磁盘、HTTP 或数据库缓存。

我会确认数据是否敏感、是否允许离线、更新由谁触发、缓存 key（缓存键）是否包含账号/参数，以及清理时机。短生命周期的小对象可放内存，HTTP 响应服从 Cache-Control/ETag，业务列表通常需要 Room 作为可查询的数据源。

缓存命中不等于数据正确，账号切换、登出、服务端删除和版本升级都要清理或迁移。缓存策略要配合指标看命中率、过期读取、刷新失败和占用空间。

如何避免重复请求和旧响应覆盖？并发

先说结论：先给同一类请求定义稳定 key，再决定复用、取消还是并发；响应写回前要确认它仍对应当前参数，旧结果不能覆盖新结果。

搜索框可以对输入做 debounce，并取消上一次请求；详情页可按 ID 复用 in-flight（正在执行中的）任务。分页要把页码/游标、筛选条件、账号和缓存策略放进 key，不能只用 URL。写回 UI 前比较请求 token（用来标记当前请求）或当前查询条件。

一个订阅者取消不一定要取消所有消费者的底层请求；共享任务完成、失败和取消时都要从 map 清理。要测快速刷新、重复点击、离页和网络乱序，避免内存中留下永久占位。

Retrofit 与 OkHttp 各负责什么，怎样统一装配？网络栈

先说结论：OkHttp 负责底层 HTTP 客户端、连接、缓存、拦截器和超时；Retrofit 负责把接口声明转换成调用对象，并接入 Converter 和 CallAdapter。

我会在一个装配入口创建共享的 OkHttpClient、认证/日志/性能拦截器、Dispatcher 和缓存，再把它交给 Retrofit。业务 API 只声明路径和参数，不在每个接口里各自 new client，否则连接池、Token 和超时配置会分裂。

文件上传、长连接或特殊域名可以使用独立 client，但要说明为什么不能共享。日志要在 Release 脱敏，取消要一直传到 OkHttp，Converter 解析失败也要进入统一错误模型。

应用拦截器和网络拦截器如何区分？Interceptor

先说结论：应用拦截器围绕一次逻辑请求工作，适合加业务公共头、重试和统一日志；网络拦截器更接近真实网络交互，能看到重定向、重试后的连接细节和响应头。

应用拦截器通常只调用一次，不关心中间重定向；网络拦截器可能被多次调用，也受 HTTPS、连接和缓存路径影响。缓存控制、压缩和网络层调试要放在能看到正确阶段的位置。

不要在两个拦截器里重复刷新 Token 或统计一次请求，容易重复执行。上传大文件、敏感 header 和响应 body 日志都要限量并脱敏，必要时只在 debug 开启。

HTTPS 很慢或证书失败，怎样分段定位？TLS 排障

先说结论：按 DNS、TCP 连接、TLS 握手、请求发送、服务端处理、响应读取逐段测时，先确定慢在哪一段，再处理证书或网络配置。

我会看 OkHttp EventListener、系统抓包/trace 和服务端日志：DNS 慢可能是解析或网络问题，连接慢要看复用和网络切换，TLS 失败要看系统时间、证书链、主机名、代理和证书固定；服务端耗时则不能只改客户端。

证书固定升级时要预留新旧证书，不能把关闭校验当修复。Release 和不同 Android 版本都要测，代理、VPN、弱网和连接复用会改变结果。

大量请求同时收到 401 时，怎样刷新 Token 而不形成刷新风暴？鉴权并发

先说结论：把刷新 Token 变成同一账号下可共享的一次任务，其他请求等待它的结果；刷新成功后只重放仍可安全重放的原请求，失败则统一登出或报错。

关键是并发下只有一个刷新者：先读取当前 Token，收到 401 后加锁，或复用同一时间已经在执行的刷新任务，再确认 Token 没被别的请求更新。刷新请求本身不能再次走同一套 401 重试链，避免递归。

要限制等待时间和重放次数，区分用户主动取消、幂等请求和不可重放请求。账号切换、登出、进程重启时要清理旧任务，日志里不要打印 Token。

当前项目怎么用：现在这些仓库里没找到 401 token 刷新、Authenticator，或者“让并发请求共用一次刷新任务”的处理；yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/app/util/NetworkUtils.java 只提供统一 service/错误转换，yyyyy-cdoe/Account/account/src/main/java/com/zhihu/android/app/passport/login/LoginPolicyService.kt 只是账号登录策略入口，这两个类只能说明有统一 service 和登录入口，不能说明项目已经有并发刷新方案。

HTTP Cache-Control/ETag 与 Room 业务缓存有什么区别？缓存分层

先说结论：HTTP 缓存是客户端与服务端围绕响应新鲜度协商，Room 业务缓存是应用自己保存和组织数据；前者减少网络传输，后者支撑查询、离线和 UI 更新。

Cache-Control、ETag/If-None-Match 由 HTTP 客户端和服务端决定，命中 304 时仍是协议层行为。Room 可以保存列表、时间戳、同步状态和本地修改，让页面在离线时继续展示；它不能代替服务端的版本冲突规则。

两层同时使用时要避免各自维护不同的过期标准。通常由 Repository 决定何时请求网络并写 Room，UI 订阅 Room；敏感数据、账号切换和服务端删除要单独处理。

Retrofit 的动态代理、Converter 与 CallAdapter 分别做什么？Retrofit 原理

先说结论：动态代理把接口方法调用转成 HTTP 请求描述，Converter 负责请求/响应体与对象之间的转换，CallAdapter 负责把底层 Call 适配成协程、Rx 或其他返回类型。

调用接口方法时，Retrofit 读取注解和参数生成 Request；OkHttp 执行后，Converter 把 JSON、文本或字节流解析成业务类型。CallAdapter 决定调用者拿到的是 Call、挂起函数结果还是 Flow/Rx 类型，但它不负责业务重试。

排查解析问题要看原始 HTTP code、body、Converter 注册顺序和泛型信息。不要把网络错误、解析错误和业务错误都塞进 Converter，也不要在多个层重复包一层 Result。

当前项目怎么用：代码里能直接看到的是 yyyyy-cdoe/Net/net-api/src/main/java/com/zhihu/android/app/util/NetworkUtils.java 的 createService 和 Account 的 converter-gson 依赖 yyyyy-cdoe/Account/app/build.gradle；现在这些仓库里没找到自定义 Converter/CallAdapter 或代理实现，不能把框架内部机制说成项目自己实现。

HTTP/1.1、HTTP/2、HTTP/3 的核心差异如何影响 Android 请求？网络协议

先说结论：HTTP/1.1 多条连接分别排队，HTTP/2 在一条 TCP 连接上多路复用，HTTP/3 基于 QUIC/UDP；QUIC 把连接建立和网络切换处理得更适合移动网络；实际收益仍取决于服务端、网络和客户端支持。

HTTP/2 能减少连接数并共享头部，但 TCP 丢包仍可能影响整条连接；HTTP/3 可能改善弱网和切换网络时的恢复，却不等于所有接口都会更快。Android 侧通常由 OkHttp 和系统协商协议，业务代码不应假设一定使用某个版本。

遇到慢请求先看协议协商、连接复用、DNS/TLS 和服务端耗时，再用 EventListener/抓包对比。推送、长连接、代理和证书策略也会影响最终链路。

15. 存储 P0

选型依据是数据结构、容量、查询、恢复、敏感性和跨进程需求。

这一模块具体要掌握哪些内容？（存储）清单

先说结论：存储题要先按数据大小、查询方式、寿命、敏感程度和分享范围选工具，再谈 API 名称。

  • 少量配置用 DataStore 等键值方案，结构化查询和事务用 Room，临时大文件放缓存/文件目录。
  • 区分应用私有目录、缓存目录、MediaStore 和 SAF（系统文件选择器）的权限与清理规则，不能把绝对路径当跨应用接口。

  • Room 要一起设计事务、索引、Flow、Migration、分页和并发写入。

我会把数据寿命和恢复场景讲清楚：进程被杀、卸载、清缓存、换账号和系统备份都可能改变结果。

键值、数据库、文件如何选？选型

先说结论：少量简单配置用键值存储，结构化数据和查询用数据库，大块二进制或导入导出内容用文件；选择看访问方式和寿命，不看个人偏好。

还要考虑多进程、备份、账号隔离、加密、迁移和分享权限。不要用 SharedPreferences 保存大 JSON，也不要把文件内容全塞进数据库却没有容量和清理策略。

数据库事务解决什么问题？Room

先说结论：事务让一组相关写入要么全部成功、要么全部回滚，避免数据只写了一半导致页面看到互相矛盾的结果。

例如同步分页时，数据表和 nextKey 必须一起更新；订单状态和本地操作记录也不能只成功一个。Room 的 @Transaction 或数据库事务可以把这组操作包起来，但事务内部不要做网络请求或长时间计算。

事务不自动解决并发冲突、服务端重复提交和死锁。要根据索引、锁范围和失败重试设计，Flow 观察到的是提交后的结果；迁移也要验证旧数据能否安全转换。

缓存目录的数据能永久保存吗？文件

先说结论：不能。应用的 cache 目录只是可回收的临时空间，系统在存储紧张时可能删除，用户清缓存也会删掉。

可以重新下载、重新生成的数据放 cache；登录凭据、用户草稿和离线必需数据不能只放这里。持久文件放 files 或数据库，并设计版本、容量上限和清理任务。即使 files 比 cache 稳定，也要考虑卸载、备份和账号切换。

读取缓存必须接受文件不存在、损坏和版本过期，失败后回源或提示用户。面试里把“能暂时存在”和“业务必须保留”分开说，边界会更清楚。

敏感信息只做 Base64 是否安全？安全

先说结论：不安全。Base64 只是编码，任何人拿到字符串都能还原，不能提供保密、完整性或防篡改能力。

Token、身份证号和密钥要按风险选择加密存储、Keystore、最小权限和脱敏日志；Keystore 负责保护密钥材料，业务数据仍要设计加密格式、轮换和失效。传输要用 HTTPS，不能因为落盘加密就忽略网络和内存暴露。

还要考虑备份、root/调试环境、登出、账号切换和 Token 过期。不要把真正的密钥硬编码进 APK，混淆只能提高分析成本，不能替代密钥管理。

SP、MMKV、Preferences/Proto DataStore 怎样选，apply/commit 有何边界？键值存储

先说结论：新代码优先按数据类型和一致性需求选 DataStore：简单键值可用 Preferences，强类型配置可用 Proto；MMKV 适合已有场景和特定性能诉求，SP 主要考虑兼容与迁移成本。

apply() 先更新内存并异步落盘，通常不阻塞调用线程，但不能当成“已经持久化”；commit() 同步写盘并返回结果，不能在主线程频繁用。DataStore 通过单一文件写入和 Flow 暴露变化，不要多实例指向同一文件。

MMKV 依赖额外库和进程/备份约束，迁移时要验证损坏恢复与多进程边界。无论选谁，都要定义默认值、版本升级、敏感数据处理和清理规则。

当前项目怎么用：yyyyy-cdoe/meter/app/src/main/java/com/example/meter/data/EarningsPreferences.kt 明确使用 SharedPreferences 接口和 prefs.edit().apply 保存轻量配置，并用 EncryptedSharedPreferences 加密；现在仓库里没找到 MMKV、Preferences DataStore 或 Proto DataStore，所以不能说这些方案已在项目落地。

Room 的事务、Flow、索引与 Migration 如何一起设计？数据库

先说结论：先画数据关系和读写路径，再同时设计事务边界、查询索引、Flow 触发范围和 Migration；四件事互相影响，不能只把表建出来。

事务包住必须一起成功的写入；高频筛选和排序字段建合适索引，避免为了“可能用到”堆很多索引；DAO 返回 Flow 时，表提交后会重新发数据，查询范围要尽量小。Schema 变化用明确 Migration，并用旧版本数据库跑升级测试。

批量写入、分页 key、删除和本地修改要在同一套规则里验证。不要在事务里调用网络，也不要只测新建数据库，真实用户更常从多个历史版本升级。

Keystore 与敏感数据生命周期怎样设计？数据安全

分区存储下，应用私有目录、MediaStore 与 SAF 怎样选择？分区存储

先说结论：应用私有目录适合只有本应用使用的文件，MediaStore 适合要出现在系统媒体库的内容，SAF 适合让用户选择任意文档或目录；先看所有权和分享范围。

私有目录一般不需要存储权限，卸载时会清理；MediaStore 要填好 MIME、相对路径和 pending 状态，写完再发布；SAF 返回的是用户授权的 content:// URI，要保存持久授权并通过 ContentResolver 读写。

先说结论：跨应用传 Content URI 才能通过临时读权限安全地交给对方；绝对路径通常对方没有权限，也不适配分区存储。

离线编辑恢复联网后，怎样避免重复提交、覆盖新数据和“删除后复活”？离线同步

先说结论：本地编辑要记录操作 ID、版本/时间和同步状态，联网后按幂等规则上传并处理冲突；删除也要有可同步的标记，不能只从本地列表直接删掉。

每次修改生成稳定的 mutation ID（一次操作的唯一编号），服务端用它去重；请求带上实体版本或 ETag，版本不一致时进入冲突策略，而不是盲目覆盖。删除可以先写 tombstone（删除标记），同步成功后再清理，避免旧的拉取结果把数据“复活”。

本地队列、实体表和同步状态要用事务更新，成功、可重试失败、永久失败和用户取消要分开。还要测重复点击、乱序响应、跨设备修改、登出换号和进程被杀，确保重试不会再次产生副作用。

冷、温、热启动与 TTID/TTFD 应如何测量？启动

ANR 有哪些常见类型，traces 应怎样读？ANR 排查

泄漏、内存抖动与 OOM 的区别，分别用什么工具？内存诊断

先说结论：泄漏、抖动和 OOM 是不同问题，分别看引用链、分配热点和内存峰值。

原因是：泄漏是本应不可达对象仍存活；抖动是短命对象反复分配回收；OOM 是可用内存/分配限制下无法满足分配。三者可关联但不能互相替代。

Macrobenchmark、Microbenchmark 与 Baseline Profile 分别解决什么？性能回归

后台耗电升高时，怎样区分唤醒、网络、定位与任务调度问题？耗电治理

17. 安全、稳定与测试 P0

这一模块具体要掌握哪些内容？（安全、稳定与测试）清单

LRU 为什么用哈希表加双向链表，Android 内存单位如何估算？算法 / 缓存

注意：只打“进入页面/请求失败”无法定位，高基数、敏感数据和全量日志又会带来成本，所以要做采样、脱敏、聚合和灰度对比。

小例子：图片失败应能看出是连接、缓存、解码还是回写阶段失败，而不是只看到一条“加载失败”。

当前项目怎么用：网络请求上下文可以先看 yyyyy-cdoe/Net/net/src/main/java/com/zhihu/android/net/interceptors/PerfMonitorInterceptor.java 的请求耗时记录，图片成功/异常维度见 yyyyy-cdoe/Net/net/src/main/java/com/zhihu/android/net/interceptors/ImageMonitorInterceptor.java；启动维度见 yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/module/task/T_CrossActivityManagerInit.java。代码里没有看到统一 trace/session ID 与页面 SLO 配置，所以面试时不要说成上下文已全链路贯通。

怎样回答一个做失败或最终回滚的项目？项目复盘

先说结论：失败项目照实讲目标、证据、偏差、止损和复盘动作，不需要硬包装成成功。

回答顺序：说明当时掌握的信息和决策依据，指出哪个信号说明假设不成立，再说谁做了暂停、回滚或降级。不要甩锅，也不要把团队事故说成个人功劳。

小例子：如果上线后长尾耗时超阈值，可以讲先关闭开关、保留旧路径，再补监控和发布门禁；数据和个人职责只按记录来讲。

当前项目怎么用：可以用 WebView 内核回退逻辑作为“失败路径要可用”的代码例子：yyyyy-cdoe/mercury-core/mercury-core/src/main/java/com/zhihu/android/app/mercury/web/WebViewHelper.java 在 X5 不可用时走 fallbackWebViewType。这段代码能说明有降级分支，但没有看到对应的线上复盘材料，面试时不要编造事故经过或个人止损贡献。

客户端与服务端接口怎样做兼容演进？跨团队契约

先说结论：移动端新旧版本会长期共存，接口优先新增可选字段、保留旧语义，并写清默认值、错误码和退场窗口。

原因是：字段改名、类型变化和枚举扩展都可能让旧客户端崩溃或误判，服务端发布成功也不代表所有客户端已经升级。

我的做法：用契约/Schema、Mock、兼容监控和双端联调验证 N/N-1；删除旧能力前看版本覆盖率，并准备服务端兼容窗口和客户端回退路径。

小例子：新增字段时旧客户端按默认值继续工作；未知枚举按“未知”分支处理，而不是直接抛异常。

当前项目怎么用：客户端分页契约在 yyyyy-cdoe/ZIM/zim/src/main/java/com/zhihu/android/zim/emoticon/ui/Paging.kt 中依赖 API 的 ZHObjectList<T>、Paging 和 isEnd 字段；路由兼容样例由 yyyyy-cdoe/ZRouter/zrouter/src/test/java/com/zhihu/android/app/router/RouterUrlTest.java 覆盖多种 URL 形式。代码里没有看到 Schema/Mock/版本退场配置，不能说项目已经有完整的双端契约治理流程。

最长无重复子串为什么适合滑动窗口？算法 / 滑动窗口

先说结论：滑动窗口让窗口始终满足“没有重复字符”，配合字符最近位置表，每个字符最多被处理几次，整体接近 O(n)。

原因是：右指针负责扩大范围；遇到重复时，左指针直接跳到旧字符后面，不必从头重扫。关键是不让左指针倒退。

我的做法：先讲暴力解为什么慢，再说明窗口条件、空串、全重复和字符编码假设，最后给复杂度。

小例子：处理 abca 时窗口先是 abc，再次遇到 a 就跳过旧 a，得到 bca。

当前项目怎么用：项目代码里没有看到“最长无重复子串”或滑动窗口实现；相邻可参考的代码是 yyyyy-cdoe/Picture/picture/src/test/java/com/zhihu/android/picture/PictureMathUtilsTest.kt 对边界输入做单元断言，以及 yyyyy-cdoe/ZIM/zim/src/main/java/com/zhihu/android/zim/emoticon/ui/Paging.kt 用明确的状态条件防止重复加载。面试时说明这是通用算法知识，不要说成项目里的实现。

海量耗时数据如何求 Top K，为什么常用小顶堆？算法 / 堆

先说结论：维护大小为 K 的小顶堆，堆顶是当前候选里最小的值；新数据只有超过堆顶才替换，因此时间是 O(n log K)、空间是 O(K)。

原因是：目标只是保留 K 个候选，不需要把全部 n 条数据排序。小顶堆把最可能被淘汰的元素放在最容易访问的位置。

我的做法：K 接近 n、需要稳定顺序或数据来自多台机器时，再考虑完整排序、QuickSelect 或分片合并；同时定义并列、空输入和 K 越界规则。

小例子：K=3 时先放前三个耗时，后面只有比堆顶更大的值才替换，堆顶始终是当前候选里最小的值。

当前项目怎么用：代码里没有看到 Top K、小顶堆或慢帧 Top-K 统计的项目实现；可以引用的计时代码是 yyyyy-cdoe/Net/net/src/main/java/com/zhihu/android/net/interceptors/PerfMonitorInterceptor.java 对每次网络请求测量耗时，和 yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/util/SimpleTimeLogger.java 的分步计时。Top K 的堆算法作为通用方案讲，面试时不要说代码里已有聚合器。
