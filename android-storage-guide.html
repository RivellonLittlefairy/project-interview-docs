Android 存储，从头学到面试能讲清

从“一个设置、一份草稿、一个音频文件分别放哪里”开始，逐步解释原理和 Kotlin 写法。先学会选，再理解性能、并发和数据安全。

第一次阅读按正文顺序走；只想准备面试，可以先看第 11 节，遇到答不清的问题再回对应章节。SP、MMKV、DataStore、Room 是重点，其余内容用于补全常见使用场景。

1 · 先弄清：内存、磁盘和缓存是什么

假设阅读页需要保存三个东西：是否开启夜间模式、每本书读到了哪一章、下载的音频。它们都叫“保存数据”，但访问方式不同。夜间模式是一个开关，阅读进度是一批记录，音频则是文件。

先理解持久化：把数据写入磁盘，使它在进程结束以后仍然存在。普通变量、单例、ViewModel 里的值在内存中，进程被杀后会丢；SP、DataStore、MMKV、数据库最终都要保存到文件。MMKV 名字里有 Memory，也同样可以持久化。

数据放哪里退出页面进程死亡适合什么
Fragment 的普通字段实例销毁就丢丢失本次页面使用的临时值
ViewModel取决于所属 Owner；能跨配置重建保留丢失页面状态和正在执行的页面任务
SavedStateHandle / savedInstanceState由系统的状态恢复机制管理满足系统恢复条件时可恢复筛选项、内容 ID 等少量恢复信息
本地持久化通常保留已成功持久化的数据保留设置、草稿、历史、下载内容

“缓存”说的是数据用途。内存 Map 可以是缓存，Room 表也可以是缓存。缓存通常可以重新获取，因此可以设置过期时间、容量上限和淘汰规则；用户未发布的草稿则需要更严格的保留策略。

这里还要区分两种操作：杀进程通常不删除应用文件；清除应用数据会删除应用本地数据。卸载通常也会删除应用专属数据，但重新安装时，系统备份恢复可能带回符合备份规则的数据。

2 · 用四个问题选方案

选存储时，先问数据怎样读取，再比较性能。下面这些方案可以在同一个 App 里同时使用。

你要保存什么优先考虑选择的原因
夜间模式、首次启动标记、小型配置新需求优先评估 DataStore；存量 SP 按需维护通过 key 或配置对象读写，不需要查询一批记录
已有 MMKV 基建中的频控、高频小键值MMKV同步 API、mmap 持久化；可以沿用项目封装
草稿、阅读历史、待上传记录Room / SQLite需要按条件查询、排序、局部更新和事务
音频、图片、模型、较大导出文件文件系统直接读写字节，数据库可以只保存路径和元数据
用户相册的图片、用户选择的文档MediaStore / 系统选择器 / SAF需要遵守公共内容的访问和授权规则
  1. 是一两个小值，还是不断增加的一批记录？
  2. 是否要按条件查找、排序、分页或同时修改多条数据？
  3. 丢了能否从服务端重拉，还是会丢掉用户劳动？
  4. 只给本应用使用，还是需要让用户或其他 App 访问？

优先掌握第 3～7 节。文件共享和安全部分理解用途即可；面试前用第 11 节检查能否讲清。

3 · SharedPreferences：小配置怎样读写

SharedPreferences，常简称 SP，是 Android 自带的键值存储。你可以把一个 SP 文件理解成小字典：给定 key，读取相应的 Boolean、Int、Long、String 等值。

val sp = context.getSharedPreferences("reader_settings", Context.MODE_PRIVATE)

// 找不到这个 key 时，返回 false。
val darkMode = sp.getBoolean("dark_mode", false)

// edit() 取得编辑器；只有 put 没有 apply/commit，不会提交。
sp.edit().putBoolean("dark_mode", true).apply()

sp.edit().remove("dark_mode").apply() // 删除一个 key
// sp.edit().clear().apply()          // 清空这个文件的所有 key

reader_settings 是偏好文件名，dark_mode 是文件内的 key。相同应用、同一进程中，以相同文件名获取的 SP 共享对应的内存状态。MODE_PRIVATE 表示普通应用无法直接访问这个私有文件，不表示内容已经加密。

底层发生了什么？

  1. 获取 SP 后，Framework 加载对应的 XML 文件，解析成内存中的键值集合。第一次读取可能需要等待加载完成。
  2. 调用 get 时，通常从这份内存数据里取值。
  3. 编辑器提交时先合并内存变更，再安排或等待磁盘写入；典型实现持久化时会序列化整个键值集合，因此不适合大文件和高频写。

apply 和 commit 的区别

apply()commit()
内存可见性先更新内存也会更新内存
磁盘写入安排异步写入在调用线程等待写入结果
返回值没有成功标记Boolean，表示持久化是否成功
主要风险返回时未必已落盘；生命周期切换可能等待未完成写入直接占用调用线程，主线程使用可能卡顿

apply() 后同进程马上 get，通常已经能读到新值，因为内存先更新了。但马上崩溃或断电，不能据此保证磁盘里也是新值。

“异步写入”也不等于绝不影响 UI。Framework 在 Activity、Service 的部分生命周期切换阶段会等待未完成的 SP 写入，积压的磁盘同步可能造成卡顿甚至 ANR。频繁 apply、大 SP 文件、首次加载等待都应关注。

线程安全，为什么 count + 1 还会错？

// 两个线程都先读到 0，随后各自写入 1，最终得到 1。
val count = sp.getInt("count", 0)
sp.edit().putInt("count", count + 1).apply()

单次调用内部有同步保护，不代表“读取、计算、写入”这几步整体不可分割。需要统一串行执行或给整段操作加同一把锁；进程内锁也只能解决该进程中的竞争。SP 不支持可靠的多进程一致性，MODE_MULTI_PROCESS 也不应作为解决方案。

项目里怎么用？

VipHome 的 PromotionTask 保存推广配置 JSON、版本号、展示次数和错误标记。更新推广版本后会重置展示次数。这适合解释“小型配置和频控为什么可以用 SP”。不过源码分多次 apply 保存这些字段，不能把它描述成一笔跨字段事务。

4 · MMKV：为什么快，mmap 又是什么

MMKV 是腾讯开源的键值存储库。使用上仍是“根据 key 读写值”，常见特点是同步 API、紧凑编码，以及基于 mmap 的文件访问。

// 应用初始化流程中执行。
MMKV.initialize(applicationContext)

// 按业务名称取得实例，不同 ID 可以隔离数据文件。
val settings = MMKV.mmkvWithID("reader_settings")
val success = settings.encode("font_size", 18)
val fontSize = settings.decodeInt("font_size", 16)
settings.removeValueForKey("font_size")

encode 是写入，decodeInt 是按 Int 读取；第二个参数 16 是未找到时的默认值。它和 SP 的使用模型相近，所以已有项目常用它保存配置、展示时间和频控信息。

先把 mmap 理解成“文件在进程里的一个窗口”

普通文件操作需要通过 read/write 等接口传递字节。mmap 则把文件的一段区域映射到进程虚拟地址空间，程序可以通过内存地址访问这段区域。修改映射页后，由操作系统负责相应的文件回写；也可以主动请求同步。

业务：保存 font_size = 18
          ↓
MMKV：把 key 和 value 编码成字节
          ↓
写入文件的 mmap 映射区域
          ↓
操作系统把脏页回写到存储设备

“映射”不等于启动时把整个文件复制进内存。文件页可以按需加载；访问时也可能发生缺页和 I/O。它更不表示写一次内存就绝对完成了磁盘持久化。

MMKV 常见小键值读写快，是 mmap、内存索引、编码方式和增量写入等设计共同作用的结果。SP 的 XML 全量序列化开销较重；MMKV 通常可以追加变更记录，空间不足或需要整理时仍会重写。不能只用“零拷贝”解释全部性能。

它没有自动解决什么？

  • 不能直接做 SQL 的筛选、排序、关联查询。
  • 同步方法仍会占用调用线程；大对象编码、文件整理和 I/O 都可能耗时。
  • 多次 encode 不自动构成一笔业务事务；先 decode 再加一再 encode 也可能丢更新。
  • 默认不等于加密。加密需要明确配置和管理密钥。

确实有多个进程读写时，可以按 MMKV 文档使用 MULTI_PROCESS_MODE，并保证实例 ID、路径和配置一致。它提供进程间同步机制，但多个独立 API 调用仍需单独设计原子性。

项目里怎么用？

ShareBubbleUseCase 把上次展示气泡的日期写入 manuscript_daily_share_bubble_date，下次读取后比较自然日和配置的间隔天数，决定是否再展示。这个例子只需要一个日期字符串，不需要数据库查询。

// 摘自 ShareBubbleUseCase，省略日期计算细节。
fun markBubbleShownToday() {
    val mmkv = MMKV.defaultMMKV()
    mmkv.encode("manuscript_daily_share_bubble_date", getTodayDateString())
}

还要区分“每天一次”和“间隔满 24 小时”：前者比较自然日，后者比较时间差，两者跨午夜时的结果不同。

5 · DataStore：用协程安全地更新设置

Jetpack DataStore 是 Android 官方的配置存储方案。它用协程执行异步读写，通过 Flow 提供数据变化，并提供原子的读改写。官方建议新的小型配置存储需求优先评估它。

先看要解决的问题：若多个协程都要给计数加一，分开读取和保存会互相覆盖；设置改变后，界面还需要收到通知。DataStore 把这两类操作作为 API 的一部分提供出来。

形式读写方式适合什么
Preferences DataStore通过类型化 key 读写设置几个开关、字号、排序方式
类型化 DataStore<T>通过 Serializer 保存整个对象；Proto 是常见选择需要明确数据结构和演进规则的设置对象

Preferences 不要求预先定义完整 schema，但 key 仍有类型，不能随意把同名 Int key 改成 String key。类型化 DataStore 也不局限于 Proto；选择序列化格式时需要明确兼容策略。

从零看一份 Preferences DataStore 示例

import android.content.Context
import androidx.datastore.preferences.core.edit
import androidx.datastore.preferences.core.intPreferencesKey
import androidx.datastore.preferences.preferencesDataStore
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.distinctUntilChanged
import kotlinx.coroutines.flow.map

// 顶层声明一次。相同文件在同一进程中只维护一个 DataStore 实例。
val Context.readerSettings by preferencesDataStore(name = "reader_settings")

class ReaderSettings(context: Context) {
    private val store = context.applicationContext.readerSettings
    private val fontSizeKey = intPreferencesKey("font_size")

    val fontSize: Flow<Int> = store.data
        .map { settings -> settings[fontSizeKey] ?: 16 }
        .distinctUntilChanged()

    suspend fun setFontSize(size: Int) {
        store.edit { settings ->
            settings[fontSizeKey] = size
        }
    }

    suspend fun increaseFontSize() {
        store.edit { settings ->
            val current = settings[fontSizeKey] ?: 16
            settings[fontSizeKey] = current + 1
        }
    }
}

store.data 提供设置快照的 Flow；map 从整份设置里取出字号；distinctUntilChanged 避免其他设置变化时重复通知相同字号。edit 是挂起函数，等待更新完成时可以挂起调用协程，磁盘操作由 DataStore 管理。

increaseFontSize 把读取和写入放在同一次 edit 中。DataStore 会串行处理更新，后一个更新基于前一个更新后的值计算。这解决的是这份 DataStore 数据的原子更新，不能把网络请求和另一个文件也一起回滚。

类型化 DataStore 使用 updateData { old -> new } 表达相同的更新思想。不要先用 data.first() 读取，再在另一段更新里写入旧值加一，否则又把读改写拆开了。

Fragment 怎么接？

// settings 由页面的依赖装配提供。
viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        settings.fontSize.collect { size ->
            binding.content.textSize = size.toFloat()
        }
    }
}

binding.increaseFontButton.setOnClickListener {
    viewLifecycleOwner.lifecycleScope.launch {
        settings.increaseFontSize()
    }
}

这段展示生命周期收集方法。实际复杂页面可以由 ViewModel 读取设置、组合成 UI 状态，再由 Fragment 收集。不要用 runBlocking 把异步读取强行变成主线程等待。

接入时还要注意哪些边界？
  • 同一进程不能为同一个文件创建多个活跃 DataStore 实例。顶层委托、单例和依赖注入都可以用来保证唯一性。
  • 读取可能抛出 I/O 异常，需要明确错误上报、默认值或损坏恢复策略；示例省略了这部分，不能对所有异常一律返回空配置。
  • 从 SP 迁移可使用 SharedPreferencesMigration，要核对旧文件名、key 类型和迁移后的读取路径。
  • 跨进程要使用对应版本的 MultiProcessDataStore 支持；不要混用单进程和多进程实现访问同一文件。
  • DataStore 默认不加密，也不支持数据库式的局部行更新。

本节是官方 API 教学示例。本次核对的项目案例不涉及它；项目中一个自定义类叫 DataStore，也不能仅凭名称判定它是 Jetpack DataStore，要看包名和实际 API。

6 · Room / SQLite：一批记录怎样保存和查询

假设每篇内容都有一份评论草稿。你要根据内容 ID 找到草稿、显示最近编辑的十条、删除已发布的草稿。这时将所有草稿转成一个大 JSON 塞进 SP，会导致每次查询都要读取和解析整个列表，更新时还容易覆盖别的草稿。

数据库把每份草稿保存成一行，按列保存内容、更新时间等字段。SQLite 是 Android 提供的关系数据库；Room 是建立在 SQLite 上的 Jetpack 库，提供实体映射、DAO、SQL 编译期检查、异步访问和版本迁移支持。

Room 概念你可以怎样理解
Entity说明一张表有哪些列，什么字段能唯一定位一行
DAO声明插入、查询、更新、删除的方法
Database组织这些表和 DAO，管理数据库版本和连接入口

用一份草稿示例串起来

import androidx.room.*
import kotlinx.coroutines.flow.Flow

@Entity(tableName = "drafts", primaryKeys = ["userId", "contentId"])
data class Draft(
    val userId: String,
    val contentId: String,
    val text: String,
    val updatedAt: Long
)

@Dao
interface DraftDao {
    // 保存相同用户、相同内容的草稿时更新已有记录。
    // @Upsert 需要 Room 2.5.0+。
    @Upsert
    suspend fun save(draft: Draft)

    @Query("SELECT * FROM drafts WHERE userId = :userId " +
        "ORDER BY updatedAt DESC LIMIT 10")
    fun observeRecent(userId: String): Flow<List<Draft>>

    @Query("DELETE FROM drafts WHERE userId = :userId AND contentId = :contentId")
    suspend fun delete(userId: String, contentId: String)
}

@Database(entities = [Draft::class], version = 1, exportSchema = true)
abstract class DraftDatabase : RoomDatabase() {
    abstract fun draftDao(): DraftDao
}

复合主键 (userId, contentId) 表示：同一用户对同一内容最多保存一份草稿。带上 userId 可以避免不同账号互相覆盖；查询时也必须带上用户条件。

// 由应用级依赖容器创建并复用，避免每次打开页面都构建数据库。
val db = Room.databaseBuilder(
    applicationContext,
    DraftDatabase::class.java,
    "drafts.db"
).build()

// 在协程里调用。Room 的 suspend DAO 管理数据库异步执行。
db.draftDao().save(
    Draft(userId = "u1", contentId = "book_42",
        text = "尚未发布的评论", updatedAt = System.currentTimeMillis())
)

Room 的 Flow 查询在订阅时执行查询，观察到相关表失效后重新查询并发出结果。表变化不保证查询结果一定变化，业务只关心结果差异时可以再做 distinctUntilChanged()。普通同步 DAO 仍需要后台执行；不要为了方便开启 allowMainThreadQueries()。

项目里为什么用 Room 存草稿？

CommentDraft 的复合主键是 (commentType, resourceId)，保存正文、图片链接、回复对象、评分和富文本信息。CommentDraftDao 按类型和资源 ID 查询或删除草稿，插入采用 REPLACE。这正是按记录定位和更新的需求。

上面 Kotlin 示例为教学设计，额外加入了 userId、更新时间和响应式查询，不能当成原项目实现。项目使用 REPLACE 也不等同于普通 UPDATE：SQLite 的 REPLACE 在约束冲突时可能删除旧行再插入，涉及外键和触发器时要特别检查。

7 · 数据库面试追问：事务、索引、迁移

事务：几步修改需要一起成功

比如把草稿从一个业务标识迁移到另一个标识，需要“删除旧记录 + 插入新记录”。若只完成删除就发生错误，草稿会丢失。把两步放进同一个数据库事务，失败时可以回滚。

// 需要 androidx.room.withTransaction。
db.withTransaction {
    db.draftDao().delete(userId, oldContentId)
    db.draftDao().save(newDraft)
}

事务常说 ACID：原子性表示全部成功或全部回滚；一致性表示满足约束和业务不变量；隔离性约束并发操作如何互相影响；持久性表示已提交修改按数据库和存储配置持久保存。事务范围是当前数据库，不能让 HTTP 请求和普通文件写入自动一起回滚。

@Transaction 可以标在 DAO 的组合操作上。一个数据库的单写入操作通常已由 Room 放入事务；显式组合事务主要解决多步操作和一致读取的问题。

索引：用额外空间换少查一些记录

没有合适索引时，查询可能逐行检查整张表。索引维护一份便于检索的有序结构，帮助快速定位。代价是占空间，并在插入、删除、修改时额外维护。

对上节“某个用户的最近十份草稿”，可以评估 (userId, updatedAt) 复合索引：先按用户缩小范围，再按更新时间取记录。复合索引通常遵循左前缀，不能认为它对任意列的独立查询都同样有效。是否命中应查看 EXPLAIN QUERY PLAN。

Migration：升级 App 后，旧数据库怎么办？

用户手机里已有 version 1 的表，新版本代码需要新增标题列。只改 data class 不会自动把旧表变成新表；必须提供迁移路径，或按所用 Room 版本支持的自动迁移规则生成迁移。

// 独立的版本演进示意：新 Entity 也必须新增相应字段和默认值，
// @Database 升到 version = 2，并注册这条迁移。
val migration1To2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE drafts ADD COLUMN title TEXT NOT NULL DEFAULT ''")
    }
}

迁移不只是“能打开库”。还要保留原数据、核对默认值和索引，并测试历史版本到当前版本的升级路径。可使用 MigrationTestHelper 配合导出的 schema 检查。

服务端可重拉的缓存，可以按策略允许缺失迁移时删库重建；草稿、未上传进度等数据则需要可靠迁移。fallbackToDestructiveMigration 会有数据删除风险，不能用它掩盖所有升级问题。

WAL 是什么？需要现在就深挖吗？

WAL 是 Write-Ahead Logging。修改先进入 WAL 文件，之后通过 checkpoint 合并回主数据库文件。它有助于改善读写并发，读者可读取一致快照，但同一时刻仍只有一个写事务。复习到能解释这个作用即可；备份数据库时要注意活跃 WAL 中可能还有尚未合并的已提交数据，不能直接只复制主 db 文件。

8 · 文件目录：内部、外部、缓存怎么区分

音频和图片通常直接写文件。数据库只保存文件路径、下载状态、大小和业务 ID，避免把大块二进制数据塞进键值配置或普通业务表。

位置用途生命周期与权限
filesDir内部应用专属文件无需存储权限；通常保留到主动删除、清数据或卸载
cacheDir内部可重建缓存系统空间紧张时可能清理，读取前要检查
getExternalFilesDir(null)外部应用专属文件Android 4.4+ 访问本应用目录无需存储权限；可能不可用，卸载通常删除
externalCacheDir外部应用缓存可能返回 null；必须允许丢失和重新生成
公共媒体 / 用户文档希望用户独立保存和管理的内容按 MediaStore、选择器或 SAF 的访问规则操作

“外部存储”可能是设备内置的共享存储分区，不一定是可拔 SD 卡。“外部”也不自动等于“其他应用可以随便访问”，现代 Android 对应用专属目录和共享集合有访问限制。

// 教学示例：普通文件 I/O 放在后台执行。
suspend fun saveText(context: Context, text: String) = withContext(Dispatchers.IO) {
    val target = File(context.filesDir, "last_note.txt")
    target.writeText(text, Charsets.UTF_8)
}

简单覆盖写入在中途失败时可能留下不完整文件。重要小文件可使用 AtomicFile 等封装，通过临时文件、成功替换和失败恢复保护旧版本；并发写入仍需要额外协调。下载文件也可以先写临时文件，校验成功后再发布为完成态。

缓存目录不是“写完系统就会替你限制容量”。应用仍要设置容量、TTL、淘汰与清理时机。数据库元数据与实际文件也可能失配，启动恢复或读取时要能处理文件缺失。

9 · 保存相册、选择文件、分享文件是三件事

这几种操作都可能得到 content:// URI，但目的不同。URI 是内容的访问标识，不能保证能转换成真实文件路径。

需求常用方案关键点
把下载的图片保存到公共相册MediaStore向共享媒体集合插入记录，再通过 ContentResolver 写入
让用户选一张图片系统 Photo Picker只获得所选内容的访问能力，通常不必申请整库权限
让用户打开 / 导出文档SAF：OPEN_DOCUMENT / CREATE_DOCUMENT由系统 UI 选择文档或目标位置，通过返回 URI 读写
把自己的缓存图片发给微信FileProvider对指定文件授予临时 URI 权限，文件仍在原目录

MediaStore 的写入流程

  1. Android 10+ 创建图片记录时设置文件名、MIME 类型、相对目录，使用 IS_PENDING=1 标记尚未完成。
  2. 取得 URI，通过 contentResolver.openOutputStream(uri) 写图片。
  3. 成功后改为 IS_PENDING=0，发布给其他应用；失败时删除已插入记录。

Android 10+ 向 MediaStore 新增本应用拥有的图片，通常不需要广泛的存储读取权限。读取其他应用的共享媒体则要结合系统版本、targetSdk 和用户授权：Android 13 起有细分媒体权限，Android 14 还涉及所选照片访问。只选少量内容时优先考虑系统选择器。

SAF 为什么不要求自己找文件路径？

文档可能来自本地、网盘或其他 Provider。业务只需拿 URI 调用 ContentResolver 打开流。需要跨重启长期访问时，核对 OPEN_DOCUMENT 返回的授权 flags，再调用 takePersistableUriPermission。持久授权仍可能因为文档删除、移动或授权撤销而失效。

ACTION_GET_CONTENT 更适合一次性选取并导入；它不应被当成永久文档授权。项目 Picasa/FilePickerFragment 就是选择后将内容复制到自己的 filesDir，后续使用内部副本。

FileProvider 的授权边界

把指定应用文件转换成 content URI，通过 Intent 的 FLAG_GRANT_READ_URI_PERMISSION 等 flag 授权接收方。paths 配置只暴露必要子目录；不要暴露整个根目录。直接对外发送 file URI 在现代 Android 会受到限制。

FileProvider 不会把文件复制到相册。需要“保存到相册”就走 MediaStore，需要“临时分享”就考虑 FileProvider。

10 · 登录态、账号隔离和数据丢失

Token 存进 SP / MMKV 就安全了吗？

私有目录提供操作系统访问隔离，默认的 SP、MMKV、DataStore 和 Room 都不等于密文存储。需要静态加密时，可以用 Android Keystore 生成或保护密钥，再用合适的加密方案保存 Token 密文。

Keystore 主要管理密钥，不是拿来直接存一大段业务 JSON。密钥可能受设备能力、用户认证和系统状态影响；硬件保护是否可用也需要检查，不能默认所有设备相同。

加密还涉及备份：若密文被恢复到另一设备，但原密钥无法恢复，就会解密失败。要按产品规则排除相应备份，或在失败后清理本地凭证并重新登录。也不要把 Token 打到日志里。

切账号时为什么还会看到上一个人的数据？

键值 key、数据库查询和文件路径没有按账号隔离，或者内存缓存仍保存旧状态。可以采用用户级 key / 实例 / 目录，数据库以 userId 作为查询条件或主键的一部分；登出时按数据归属清理。

还要处理旧账号的异步回调：请求发出时记录账号或会话标识，回调时核对，避免切账号后把旧结果写进新账号的数据区。

什么时候保存？

重要变更发生时就及时保存，必要时节流合并。不要等 onDestroy 才保存草稿：系统杀进程不保证调用它，页面的异步保存任务也可能随作用域取消。保存时机、任务作用域和失败提示都需要明确。

进程恢复只保存足够重建页面的信息。例如 Bundle / SavedStateHandle 保存书籍 ID 和筛选项，实际内容再从数据库或网络读取。不要往 Bundle 塞大列表和图片，避免 Binder 事务大小限制带来的异常。

11 · 面试问答：先说结论，再补原因

先把每题第一两句讲顺，再根据追问展开前面的原理。下面的项目示例可以帮助理解实现，是否作为个人经历陈述，以自己实际参与的范围为准。

Android 常用的存储方式有哪些？怎么选？

少量配置用 DataStore，存量项目也常见 SP 和 MMKV；需要查询、排序和事务的记录集合用 Room / SQLite；大文件放文件目录。公共图片通过 MediaStore，用户文档通过 SAF，临时对外分享应用文件可用 FileProvider。选型还要看数据能否丢失、是否跨账号或跨进程。

SP 的 apply 和 commit 有什么区别？

两者都会更新内存。apply 安排异步磁盘写入且不返回写入结果；commit 等待并返回成功与否。apply 返回不保证已落盘，生命周期切换还可能等待积压写入，所以异步不能保证完全不影响主线程。

SP / MMKV 是线程安全的，为什么加一仍会丢？

单个 get 或 put / encode 受到保护，不表示多个调用合起来就是原子操作。两个线程可能都读到旧值，再各自覆盖成相同新值。需要将完整读改写串行化，或采用 DataStore 的 edit、数据库事务内更新等方案。跨进程还要使用相应进程间协调。

MMKV 为什么比 SP 快？

常见小键值场景下，MMKV 结合 mmap、内存索引、紧凑编码和增量写入，减少 SP XML 解析与全量序列化等开销。但缺页、编码、同步与文件整理仍有成本。性能取决于数据量和设备，需要实测，不能认为所有场景都更快。

mmap 是不是把文件全部读进内存？写入就立刻落盘？

它建立文件与进程虚拟地址空间的映射，页可以按需加载。修改映射页后还涉及操作系统回写和同步策略，所以访问像内存，不表示数据只在内存，也不表示写完即获得绝对断电安全。

DataStore 比 SP 改善了什么？能代替 Room 吗？

它提供协程异步读写、Flow 观察和原子读改写，减少手动处理线程与并发覆盖的工作。DataStore 面向小型配置快照；多条记录的条件查询、索引和局部更新仍适合 Room。它也不默认提供加密。

Room 和 SQLite 是什么关系？

SQLite 是底层关系数据库，Room 是上层 Jetpack 库。Room 通过 Entity、DAO 和 Database 显式组织表与访问方法，提供大量 SQL 编译期检查、协程 / Flow 支持及迁移能力。使用 Room 仍需理解主键、索引、SQL 和事务。

事务和锁有什么区别？

锁协调并发访问，事务把一组数据库操作作为整体提交或回滚。数据库内部也会使用锁等机制，但业务给代码加 synchronized，并不能在第二步失败时自动恢复第一步已经写入的数据。需要两者分别对应并发与数据原子性的问题。

数据库升级为什么要 Migration？可以直接删库吗？

新代码的表结构与用户已有数据库可能不同，需要从旧版本迁移。缓存可按策略删库重拉，草稿和未上传进度要保留。必须验证完整迁移路径和原数据，不能只把 version 加一或一律破坏性重建。

索引是不是越多越好？

索引帮助定位记录和部分排序，但占空间，写入时也要维护。应按真实 WHERE 和 ORDER BY 设计复合索引，关注左前缀，再用查询计划验证；小表、低选择性条件也不一定从索引获益。

cacheDir、filesDir、外部存储有什么区别？

cacheDir 放可丢缓存，filesDir 放内部应用专属文件。外部应用专属目录适合相应资源，但要处理不可用和卸载删除；外部不等于 SD 卡或无限制公共访问。用户希望保留的公共图片应通过 MediaStore 管理。

系统杀进程时，怎么防止草稿丢失？

在用户编辑过程中及时持久化，按需要防抖和定期保存，明确异步保存失败及取消策略；页面恢复时从数据库读取。不能依赖 onDestroy，因为杀进程不保证触发。ViewModel 只帮助跨配置重建保留内存状态，不能替代持久化。

FileProvider、MediaStore、SAF 有什么区别？

FileProvider 用于给其他应用受控访问自己的文件；MediaStore 管理共享媒体集合；SAF 让用户选择或创建文档。拿到 content URI 通过 ContentResolver 访问，不要依赖“真实路径”。长期访问还要核对授权类型和失效情况。

12 · 用项目例子串起来，再做一次选型

一份阅读业务可以同时使用多种存储：

  • 字号、夜间模式：小型配置，使用项目统一的键值封装；新需求可评估 DataStore。
  • 气泡展示日期：按一个 key 读取日期，现有 ShareBubbleUseCase 使用 MMKV。
  • 评论草稿：按类型与资源 ID 查询多条记录，Comment 模块使用 Room。
  • 下载音频：文件保存字节，数据库维护下载状态、路径和业务 ID。
  • 分享封面：临时文件通过 FileProvider 授权；保存到相册则写入 MediaStore。

面试口述：我会按数据的访问方式选存储。小型设置用键值存储，需要按条件查找和维护多条记录就用数据库，大文件直接落文件系统。然后区分哪些是能重拉的缓存，哪些是不能随意丢的用户数据，分别设计过期、迁移和恢复策略。还要处理账号隔离、敏感数据和进程死亡后的恢复。
