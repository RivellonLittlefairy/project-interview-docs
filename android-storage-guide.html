Android 存储方案：从 SP、MMKV 到 Room、文件与安全存储

1. 先把 Android 存储分成六层

层次代表方案适合的数据不适合的数据
少量键值SharedPreferences、Preferences DataStore、MMKV开关、频控、时间戳、小型配置大量记录、条件查询、大 JSON
类型化配置对象Proto DataStore有稳定 schema 的设置对象需要分页、关联、局部 SQL 更新的集合
结构化记录SQLite、Room草稿、历史、进度、离线缓存、关系数据图片二进制、大视频、临时渲染文件
应用专属文件filesDir、cacheDir、externalFilesDirJSON、日志、下载物、中间文件、模型希望直接出现在公共相册的媒体
公共内容MediaStore、Storage Access Framework相册媒体、用户选择导入导出的文档只给本应用使用的内部状态
密钥与敏感数据Android Keystore + 加密载体加密密钥、需要静态加密的 Token/配置把大段业务对象直接塞进 Keystore

容易混淆的三个概念：SavedStateHandle/Bundle 是页面状态恢复，不是业务持久化方案；ContentProvider 是跨进程/跨应用的数据访问协议，不是底层存储本身；Glide/Coil 的磁盘缓存是缓存策略，不等于你的业务数据库。

2. 选方案前先问四个问题

  1. 数据是一两个 key，还是会不断增加的记录集合？前者偏键值，后者偏数据库。
  2. 是否需要按条件查询、排序、分页、去重或事务？只要答案是“需要”，Room 通常比把 JSON 塞进 MMKV 更合理。
  3. 数据能不能丢？网络可重拉缓存可以删库恢复；用户草稿、学习进度需要完整 Migration 和备份策略。
  4. 数据属于谁？仅本应用使用放应用专属目录；属于用户相册或文档系统就走 MediaStore/SAF。
一句话判断：根据 key 直接取一个小值，用键值存储；需要从一批记录中查、排、关联，用 Room；数据本身是文件就放文件系统；要进入系统公共集合，用 MediaStore/SAF；敏感数据先解决密钥保护，再决定密文放哪里。

3. SharedPreferences：官方 XML 型键值存储

3.1 它解决什么问题

SharedPreferences 是 Android Framework 提供的轻量键值 API。调用方通过文件名获得一个偏好对象，读写 Boolean、Int、Long、Float、String 和 String Set。实现会维护内存中的键值视图，并把变化持久化到应用私有的偏好文件。

Kotlin · 基础写法
val preferences = context.getSharedPreferences(
    "feature_config",
    Context.MODE_PRIVATE
)

preferences.edit()
    .putBoolean("enabled", true)
    .putLong("last_show_time", System.currentTimeMillis())
    .apply()

3.2 apply() 与 commit()

方法调用返回磁盘写入典型选择
apply()立即更新内存视图并返回随后异步安排持久化绝大多数 UI 配置、频控
commit()等待写入结果，返回 Boolean同步完成极少数必须立即知道落盘结果的后台场景

“apply 是异步的”不能简化成“调用后立刻读取不到”。同进程内存值会先更新；真正需要警惕的是崩溃窗口、主线程同步提交、跨进程一致性和高频整文件改写成本。

3.3 真实案例：VipHome 启动推广缓存

PromotionTask 使用名为 vip_launcher_sp_config 的 SharedPreferences，保存推广 JSON、版本、展示次数、关闭开关和渲染错误标记。这类数据有明确 key、体量小、主要是启动频控，非常符合 SP 的模型。

Kotlin · 根据源码简化
private val sp by lazy {
    BaseApplication.get().getSharedPreferences(
        "vip_launcher_sp_config",
        Context.MODE_PRIVATE
    )
}

private fun putPromotionCache(model: PromotionModel) {
    sp.edit()
        .putString("vip_launcher_promotion", gson.toJson(model))
        .putInt("show_count", 0)
        .apply()
}

实际调用链：空闲启动任务 → 拉取推广配置 → 成功回调 → 比较版本 → JSON 序列化 → SP apply()；展示时再读取缓存和次数进行频控。

证据：yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/promotion/task/PromotionTask.kt:21-31, 40-52, 84-102, 112-125, 128-158

3.4 SP 的边界

  • 不要保存持续增长的列表；你会被迫自己做索引、删除、并发和整体 JSON 重写。
  • 不要把 SharedPreferences 当多进程数据库；当前业务调用使用 MODE_PRIVATE，没有跨进程同步证据。
  • 监听器适合观察少量配置变化，不适合构建复杂响应式数据层。
  • 私有目录不等于加密。root、备份、调试环境或密钥泄漏仍可能暴露明文。

4. MMKV：基于 mmap 的第三方高性能键值存储

4.1 mmap 到底是什么

MMKV 是腾讯开源的第三方方案，不是 Android 官方 API。它通过 mmap 把文件映射到进程虚拟地址空间，调用方读写映射区域，脏页最终由操作系统回写文件。它不是“只存在内存”，也不是“完全没有系统调用”。

普通文件 I/O：业务对象 → 序列化 → write() → 内核缓冲 → 文件

MMKV：业务键值 → 编码 → 修改 mmap 映射页 → 操作系统回写文件

MMKV 适合高频、小型、按 key 访问的数据，但仍不是 SQL 数据库。需要条件查询、排序、事务和关系约束时，mmap 不会自动替你解决数据建模。

4.2 常用 API 速查

Android 侧通常先在 Application 中初始化一次，再按隔离范围选择默认实例或命名实例。encode() 有多种类型重载并返回写入结果；decodeXxx() 在 key 不存在时返回调用方传入的默认值。

用途常用 API说明
初始化MMKV.initialize(context)通常放在应用级初始化流程，只做一次
默认实例MMKV.defaultMMKV()适合不需要单独文件隔离的普通键值
命名实例MMKV.mmkvWithID(id)按业务 ID 使用独立存储文件，方便隔离和清理
多进程实例MMKV.mmkvWithID(id, MMKV.MULTI_PROCESS_MODE)仅确有跨进程访问时使用，会增加同步成本
写基础类型encode(key, value)支持 Boolean、Int、Long、Float、Double、String、ByteArray 等重载
读基础类型decodeBool()、decodeInt()、decodeLong()、decodeString()、decodeBytes()读取时显式传默认值，避免把“无值”误当成有效的 0 或 false
对象与集合encode(key, parcelable)、decodeParcelable()、encode(key, stringSet)、decodeStringSet()Parcelable 结构升级要考虑兼容；复杂或持续增长的数据不要硬塞进键值存储
判断与枚举containsKey()、allKeys()、count()检查 key、枚举 key 和获取键值数量；不要依赖全量枚举实现复杂查询
删除removeValueForKey()、removeValuesForKeys()、clearAll()分别删除一个、多个或当前实例的全部键值
空间与生命周期actualSize()、totalSize()、trim()、clearMemoryCache()、close()查看有效/分配空间、整理文件、释放内存缓存或关闭实例；不要在仍有调用方使用时关闭
刷盘sync()、async()主动同步或异步请求落盘；方法返回不等于存储介质在断电场景下绝对安全

版本快照：Android 模块声明 MMKV 2.0.2，RN 工作区声明 react-native-mmkv 3.2.0。证据：yyyyy-cdoe/VipCommon/version.gradle:335、yyyyy-cdoe/VipCommon/vip_common/build.gradle:102、pikachu/package.json:38。升级版本时应以对应版本 API 为准。

Kotlin · 常用写法
// Application 中初始化一次
MMKV.initialize(applicationContext)

val settings = MMKV.mmkvWithID("feature_settings")

// 写入：encode 根据 value 类型选择重载，返回 Boolean
val success = settings.encode("dark_mode", true)
settings.encode("launch_count", 3)
settings.encode("last_open_time", System.currentTimeMillis())
settings.encode("nickname", "Alice")

// 读取：第二个参数是 key 不存在时的默认值
val darkMode = settings.decodeBool("dark_mode", false)
val launchCount = settings.decodeInt("launch_count", 0)
val lastOpenTime = settings.decodeLong("last_open_time", 0L)
val nickname = settings.decodeString("nickname", "")

if (settings.containsKey("nickname")) {
    settings.removeValueForKey("nickname")
}

初始化边界：工作区源码里有业务类直接调用 MMKV.initialize() 的写法，但更稳妥的工程组织是由应用启动框架统一初始化，业务层只获取实例和读写，避免把全局初始化散落在 Fragment 或 UseCase 中。

4.3 项目源码摘录：默认实例保存展示日期

ShareBubbleUseCase 使用默认 MMKV 保存“上次展示气泡的自然日”。写入和读取都直接使用 String API，适合这种单 key、小体量的频控状态。

Kotlin · ShareBubbleUseCase 源码摘录
companion object {
    const val KEY = "manuscript_daily_share_bubble_date"
}

fun markBubbleShownToday() {
    val mmkv = MMKV.defaultMMKV()
    val today = getTodayDateString()
    mmkv.encode(KEY, today)
}

fun isFirstTimeToday(): Boolean {
    val mmkv = MMKV.defaultMMKV()
    val lastShowDateStr = mmkv.decodeString(KEY, "")

    if (lastShowDateStr.isNullOrEmpty()) {
        return true
    }

    val todayDateStr = getTodayDateString()

    if (lastShowDateStr == todayDateStr) {
        return false
    }

    val lastShowDate = parseDateString(lastShowDateStr) ?: return true
    val todayDate = parseDateString(todayDateStr) ?: return true
    val daysDiff = calculateDaysDifference(lastShowDate, todayDate)
    return daysDiff >= interval
}

4.6 MMKV 的工程代价

  • 引入 Native 库和 ABI 产物，需要关注包体、初始化、崩溃与升级兼容。
  • MULTI_PROCESS_MODE 是明确选择，不代表所有 MMKV 调用天然跨进程。
  • 加密能力是否安全取决于密钥怎样生成、保存和轮换，不能把加密 key 再明文硬编码。
  • 大 JSON 虽然“能存”，但局部更新、TTL 索引和查询仍由业务手写；复杂度上来后应转 Room。

5. Jetpack DataStore：现代化的官方配置存储

DataStore 是 Jetpack 的异步持久化方案，主要分为 Preferences DataStore 和 Proto DataStore。

类型模型优点边界
Preferences DataStore无 schema 的类型化 key-value协程/Flow、串行原子更新、异常流、SP 迁移仍不适合复杂记录查询
Proto DataStoreProtocol Buffers schema编译期类型、默认值、演进规则清晰更新围绕整个配置对象，不是关系数据库
Kotlin · Preferences DataStore 典型写法
val Context.settingsDataStore by preferencesDataStore("settings")
val DARK_MODE = booleanPreferencesKey("dark_mode")

suspend fun setDarkMode(context: Context, enabled: Boolean) {
    context.settingsDataStore.edit { preferences ->
        preferences[DARK_MODE] = enabled
    }
}

val darkMode: Flow<Boolean> = context.settingsDataStore.data
    .map { it[DARK_MODE] ?: false }

5.1 “原子更新”不是数据库事务

edit（Preferences）或 updateData（Proto）会在同一个 DataStore 实例中串行执行 read-modify-write：转换成功就整体替换这一份数据快照，转换抛异常就不提交。它不能把两个 DataStore、一次网络请求和一次文件写入包成共同事务，也没有 SQL 的按行查询与局部更新。

  • 同一进程、同一文件只维护一个 DataStore 实例；通常把 delegate 放在文件顶层。
  • 读取是 Flow，I/O 异常要显式处理；不能用空值静默掩盖所有损坏。
  • Preferences DataStore 没有 schema；key 改名、类型改变和默认值仍然是你的兼容责任。

5.2 从 SharedPreferences 迁移到 DataStore

Jetpack 提供 SharedPreferencesMigration。迁移会在 DataStore 第一次向外提供数据之前执行；迁移成功后再把新写入收敛到 DataStore，避免新旧两份长期双写而产生冲突。

Kotlin · 官方迁移入口（平台知识）
val Context.settingsDataStore by preferencesDataStore(
    name = "settings",
    produceMigrations = { context ->
        listOf(
            SharedPreferencesMigration(
                context = context,
                sharedPreferencesName = "legacy_settings"
            )
        )
    }
)

迁移不是“拷完就算”：要验证旧 key 的类型与默认值、观察迁移失败率，并决定旧文件何时清理。读取 data 时常见的 IOException 与真正的数据损坏不是一回事；需要恢复损坏时，应使用与所选 DataStore 类型匹配的 corruption handler，并明确重置数据的产品后果。

5.3 Proto DataStore 为什么更“类型化”

Proto 的字段号才是持久化兼容契约。新增字段通常可以向前演进；删除字段后应保留编号，不能把旧编号重新用于另一种含义；默认值、枚举演进和未知字段都要遵守 protobuf 规则。它降低了字符串 key 和类型转换错误，但不代表 schema 可以随意修改。

当前工作区的负面证据同样重要：业务源码没有找到 androidx.datastore、preferencesDataStore、DataStore<Preferences>、edit 或 Flow 读取的真实调用。只在 meter 发现 Preferences DataStore 依赖声明，不能写成“项目已经使用”。

6. 重要纠错：Account 的 DataStore 不是 Jetpack DataStore

Account 仓库中有 DataStoreImpl，但名字相同不代表技术相同。源码解析到同包自研抽象类 accounts/data/DataStore.kt，它直接在 filesDir/account/<id>/parcel|json 下读写 token、People 和简化 People 文件，并使用 ReentrantReadWriteLock。

AccountManager
    ├─ 从 SharedPreferences 取得账号 ID
    ├─ DataStoreImpl.readAccount(id)
    │    ├─ ParcelStore：优先读取 Parcel 字节文件
    │    └─ JsonStore：失败时读取 JSON 文件
    └─ 旧 FileDataStoreFactory：新路径失败时兼容兜底

writeAccount 同时写 ParcelStore 和 JsonStore；读取优先 Parcel、失败再回退 JSON。Parcel 版本串变化时会清理旧文件。这个设计解决的是账号文件格式迁移和兼容，不是 Jetpack DataStore 的 Preferences/Proto、Flow 或 updateData。

类型证据：yyyyy-cdoe/Account/account/src/main/java/com/zhihu/android/app/accounts/data/DataStore.kt:20-83
实现证据：.../accounts/data/DataStoreImpl.kt:19-87
业务入口：.../accounts/AccountManager.java:85-116, 219-226, 443-452
延迟补全：.../module/task/T_PeopleDelayInit.kt:15-28

面试表达：“仓库里虽然有 DataStoreImpl，但我核对 import、同包 DataStore 抽象、实际委托类型和文件路径后确认它是自研账号文件存储，不是 Jetpack DataStore。DataStoreImpl 本身是 object，真正实现该抽象的是 ParcelStore 与 JsonStore。判断技术不能只看类名，要看依赖坐标、类型来源和实际 API。”

7. SQLite 与 Room：当数据从‘一个值’变成‘一批记录’

SQLite 是 Android 内置关系数据库。Room 是 Jetpack 提供的上层抽象，通过 Entity、DAO、Database、Migration 把表结构和访问契约显式化，并在编译期检查大量 SQL 问题。

业务 Repository / Manager
        ↓
DAO：查询、插入、更新、事务
        ↓
RoomDatabase：连接、版本、Migration
        ↓
SQLite：表、索引、事务、查询计划、WAL/文件

为什么 Room 不是“更高级的 SP”

  • 复合主键能表达“每个用户、每个业务、每个单元只有一条记录”。
  • 索引能加速按用户、课程、时间等条件查询。
  • 事务保证多步修改要么一起成功，要么一起回滚。
  • Migration 明确数据库版本升级时怎样保留不可丢数据。
  • SQL 可以只读取或更新需要的行，不必反序列化一个巨大 JSON。

7.1 事务到底包住什么

DAO 中的 @Transaction 适合把一组数据库操作放进同一事务；需要跨多个 DAO 时，可以使用 RoomDatabase.withTransaction。事务只能保证这一个数据库中的操作原子提交，不能让网络请求、普通文件写入或另一个数据库一起回滚。读取“主表 + 关联表”时，事务也能保证映射过程看到一致快照。

Kotlin · Room 事务边界（平台知识）
@Transaction
suspend fun moveDraft(oldType: String, oldId: String, newDraft: Draft) {
    delete(oldType, oldId)
    insert(newDraft)
}

db.withTransaction {
    draftDao.delete(oldType, oldId)
    draftDao.insert(newDraft)
}

7.2 索引不是越多越好

索引用额外空间和写入维护成本，换取符合索引顺序的查询更快。复合索引通常遵循左前缀：例如 (userId, type, businessId) 更适合先按 userId、再按 type 过滤的查询，不能自动优化任意列组合。设计时要同时看 WHERE、ORDER BY 与数据分布，并用 EXPLAIN QUERY PLAN 或实际 profiling 验证，而不是给所有“常用列”都建索引。

7.3 Migration 是可测试的升级契约

数据库从历史版本升级到当前版本，必须存在完整迁移路径。对不可丢数据，应导出 schema，并用 MigrationTestHelper 打开旧版本数据库、写入样本、执行升级，再验证表结构、索引和数据。fallbackToDestructiveMigration 只适合明确可从服务端重拉的缓存；重要数据不能把“升级失败就删库”当兜底。

9. 文件存储：数据本身是文件时，不要硬塞数据库

目录/API特点适合场景
filesDir应用内部、卸载删除、系统通常不会主动清理需要长期保留的应用专属文件
cacheDir应用内部、空间紧张时可被清理可重新生成的中间文件和缓存
externalFilesDir外部存储上的应用专属目录，可能不可用较大、可重新获取或有其他保障的应用资源
externalCacheDir外部缓存目录，可能为 null较大、可丢弃缓存

getExternalFilesDir() 与 externalCacheDir 可能因为介质状态返回 null，也可能在运行期间变得不可写；必须检查可用性并准备内部目录回退。现代 Android 访问自己的应用专属外部目录通常不需要广泛存储权限，但“应用专属”不等于内部私有或天然加密，重要且不可重建的数据不能只因空间较大就放外部目录。

复制后业务持有自己的内部副本，不再依赖外部 Provider URI 的长期权限。这不是 ACTION_OPEN_DOCUMENT，源码也没有 takePersistableUriPermission。

9.3 FileProvider 是授权桥梁，不是存储引擎

FileProvider 把应用文件映射成受控 content:// URI，并通过临时 flag 授权外部应用读写。文件仍在原来的目录，FileProvider 不会自动复制文件，也不会让它进入系统相册。

  • paths.xml 只暴露业务真正需要的最小子目录，不要配置根目录或整个外部存储。
  • Provider 通常保持 exported=false、grantUriPermissions=true，并按需求只授予读或写 flag。
  • Android 7.0+ 不应把 file:// 直接发给其他应用；授权结束后，接收方不应继续假设 URI 永久可读。

10.3 内容选择与 SAF：四种常见动作

动作含义持久 URI 权限
ACTION_GET_CONTENT从可提供内容的应用选择并读取一次通常不作为长期授权使用
ACTION_OPEN_DOCUMENT通过系统文档提供器打开文档配合 flag 和 takePersistableUriPermission 可持久化
ACTION_CREATE_DOCUMENT让用户选择位置创建导出文档按返回 URI 写入；是否持久化以实际 flags 为准
ACTION_OPEN_DOCUMENT_TREE让用户授权一个目录树可持久化目录授权，但应申请最小范围

ACTION_GET_CONTENT 更接近一次性内容选择；长期访问用户文档，应优先理解 ACTION_OPEN_DOCUMENT 返回的授权 flags，并把这些 flags 传给 takePersistableUriPermission。拿到 content URI 后不要反推“真实文件路径”，而要通过 ContentResolver 读写。目录树授权同样不是整块磁盘通行证，应限制到用户选择的最小目录。

当前业务源码只找到 ACTION_GET_CONTENT 的真实选择链路，没有找到可靠的 ACTION_OPEN_DOCUMENT、ACTION_CREATE_DOCUMENT、ACTION_OPEN_DOCUMENT_TREE 或持久 URI 授权调用。文档因此只把后三者作为平台知识，不冒充项目实践。

10.4 只选照片时，还要知道 Photo Picker

如果需求只是让用户选一张或几张图片/视频，现代 Android 的 Photo Picker 往往比申请整个媒体库读取权限更符合最小权限原则。它负责“用户选择媒体”；MediaStore 仍负责公共媒体集合，SAF 更偏文档与目录，两者不能互相替代。

11. Android Keystore 与加密存储：先保护密钥

Android Keystore 的核心职责是生成、保存或使用受系统保护的密钥材料。业务通常用这个密钥加密 Token、配置文件或数据库，再把密文放到 SP、文件或数据库。Keystore 不适合直接保存大量业务对象。

Android Keystore：保护主密钥/密钥句柄
        ↓
AES-GCM 等算法：加密业务明文
        ↓
SP / DataStore / MMKV / 文件 / Room：保存密文、IV、版本信息

11.2 敏感数据的常见错误

  • 把 Token 明文放 SP，然后说“因为 MODE_PRIVATE 所以安全”。
  • MMKV 开启加密，却把 cryptKey 硬编码在 APK。
  • 只加密 value，不设计密钥轮换、登出清理和解密失败恢复。
  • 把用户密码长期保存到本地；通常应该保存短期凭证或可撤销 Token。
  • 备份恢复到另一台设备后，密文存在但 Keystore 密钥不可用，没有兜底。

12.1 从 SP/MMKV 迁移时怎么做

  1. 先定义新模型和版本，不要在读取时随意猜旧格式。
  2. 读取新存储；未命中时读取旧存储并校验。
  3. 写入新存储成功后再设置迁移完成标记，必要时保留一个版本周期的回退。
  4. 统计迁移成功、解析失败、回退次数，不要静默吞掉数据损坏。
  5. 确认回滚版本是否还能读取数据；双写时间过长也会引入一致性成本。

13. 面试怎么回答

13.1 40 秒版本

Android 存储要按数据形态选。少量配置用 SharedPreferences、DataStore 或 MMKV；DataStore 是 Jetpack 的异步配置方案，MMKV 是腾讯基于 mmap 的第三方键值方案。需要复合主键、条件查询、排序和事务的记录集合用 Room。大文件放应用专属目录，公共图片通过 MediaStore，用户选择文档通过 SAF。敏感数据不是换成 MMKV 就安全，而是用 Keystore 保护密钥，再把密文放到合适载体。实际项目里我还会根据数据能否重拉决定 Migration 还是允许删库恢复，并按用户隔离、在登出时清理，验证备份恢复后密钥是否仍可用。

13.2 结合项目的两分钟版本

我会先看访问模型，而不是比较谁跑分高。比如 VipHome 的推广 JSON、次数和开关都是少量 key-value，用 SP 很直接；盐言详情预加载要求 Native 写、RN 读同一份高速缓存，代码里使用同一个 MMKV ID 和 pin key，还显式选择多进程模式。评论草稿则是按评论类型和资源 ID 定位的多条记录，还有富文本、图片状态、LIKE 查询和跨 key 事务，所以用 Room。学习进度更不能丢，仓库里明确写了 Migration；表情和 HTML 预加载能从服务端重拉，损坏时可以采用更激进的恢复策略。保存到相册的图片不能只写 cacheDir，要通过 ContentResolver 插入 MediaStore。安全方面，meter 用 MasterKey 和 EncryptedSharedPreferences；我会继续关注密钥失效、备份和登出清理，而不是只说“文件在私有目录”。

13.3 高频追问

SP 的 apply 和 commit 有什么区别？

apply 先更新内存并立即返回，随后安排磁盘持久化；commit 同步等待并返回结果。不要把 apply 简化成“调用后读取不到”，也不要在主线程高频 commit。

MMKV 为什么快？是不是一定比 SP 好？

MMKV 通过 mmap 和紧凑编码缩短常见键值读写路径，但 mmap 本身不是性能保证，结果仍受编码、数据体量、页回写、多进程同步和设备 I/O 影响。它还引入 Native 依赖、初始化、文件恢复和密钥管理成本；复杂查询、事务和记录集合仍应使用数据库。

DataStore 和 Room 怎么选？

DataStore 面向一份配置对象或键值流，原子更新只覆盖单个 DataStore 数据快照；Room 面向记录集合、SQL 查询、索引、数据库事务和迁移。判断点不是数据大小一个维度，而是访问模型。

Room Migration 失败能不能直接删库？

取决于数据价值。服务端可重拉缓存可以明确采用破坏性恢复；用户草稿、学习进度等不可丢状态需要完整 Migration、测试和失败兜底。

FileProvider、MediaStore、SAF 有什么区别？

FileProvider 临时授权外部应用访问一个 app 文件；MediaStore 管理公共媒体集合；SAF 让用户通过系统文档 UI 选择或创建文档。三者都可能返回 content URI，但所有权和生命周期不同。

Account 的 DataStoreImpl 是 Jetpack DataStore 吗？

不是。它解析到同包自研 DataStore 抽象类，直接读写 filesDir 下的 Parcel/JSON 文件，没有 androidx.datastore 依赖或 Flow/updateData API。
