跨端项目面试手册：RN Bundle 与本地 Agent Web 工具

检查范围：pikachu、html-anything，时间为 2026-07-24。
本文以当前 checkout 的源码、构建配置、测试和 CI 为准，README 只作为线索。分析过程只读业务源码；没有提交、推送、安装依赖或执行会改变仓库状态的构建。

0. 先把表达边界说清楚

这两个项目适合证明的不是“会写几个 React 页面”，而是三类可迁移能力：

  1. 能沿着 Native/RN 或 Browser/Node 边界追完整调用链；
  2. 能处理异步任务、流式数据、取消、生命周期和状态一致性；
  3. 能识别“功能可用”和“安全地暴露能力”不是一回事。

但必须区分三层口径：

  • 源码事实：仓库中确实存在的架构、调用链、风险和测试。
  • 可合理主张的工作：只有确实由本人做过的业务接入、问题排查、性能治理或方案取舍，才能使用“我负责”。
  • 不能从源码推出的事实：个人职责、业务指标、线上故障、团队规模和最终收益都需要本人补充，不能由本文代填。

面试中更稳妥的条件式开场是：

【需本人确认】仅当本人确实参与过相关接入时，可表述为：“我主要从 Android 业务侧参与跨端页面的接入和协作。下面我会先讲项目本身的链路，再明确哪些调用点是我实际负责的；底层 PRN 框架或整个 Web 工具不是我个人从零开发的。”

第一部分：pikachu

2. 项目定位

pikachu 是 React Native 0.72.10 的多页面 Bundle 工作区，不是一个具备 android/、ios/、app.json 和 metro.config.js 的独立 RN App。它通过 PRN 工具链生成页面 Bundle，再由原生宿主通过页面名、Deep Link、初始化参数和 Bridge 承载。

源码当前有：

  • 76 个 pages/* 页面目录；
  • 18 个 packages/* 横向共享包；
  • 排除依赖目录后约 1770 个 TS/TSX 文件；
  • entry、entry-lite、entry-zhi 三套入口；
  • React Native、Jotai、Reanimated，以及内部 PRN bridge、UI、utils、bootstrap 等依赖。

根 package.json 声明的工作区是 prn/*、pages/*、packages/* 和 docs。因此合理架构应是：

text
Native App
  ├─ Deep Link / pageName / initProps
  ├─ Native loading、导航栈、编辑器等能力
  │
  ▼
PRN runtime（当前副本缺失 prn/*）
  ├─ @kfe/prn-entry
  ├─ @kfe/prn-bootstrap
  ├─ @kfe/prn-bridges
  ├─ @kfe/prn-utils
  └─ @kfe/prn-ui
  │
  ▼
pages/entry*
  ├─ pages.mjs：页面名 → workspace package
  ├─ getRNPageLoaders.ts：动态构造 loader
  └─ index.tsx：批量注册、检测、启动耗时
  │
  ▼
pages/*
  ├─ AI 生图、内容、搜索、直播等垂直页面
  └─ 通过 Bridge / HTTP / Jotai 与宿主及服务交互
  │
  ▼
packages/*
  └─ shared、preview、biz-components 等横向复用能力

这套结构的价值是：业务页面可以独立拆包和按名称加载，Native 只依赖稳定的页面合同；代价是本地开发、Bundle、Native 联调都依赖完整的 PRN 工作区和宿主环境。

3. 动态页面入口链路

调用顺序不是普通 RN App 的 AppRegistry.registerComponent()，而是 PRN 自己的注册协议：

  1. pages/entry/src/pages.mjs 维护 pageName → workspace package 的映射，开发态还会额外注册示例页面。
  2. pages/entry/src/getRNPageLoaders.ts 遍历映射，通过 new Function('', "return require(...)") 为每个页面构造延迟 loader。
  3. pages/entry/src/index.tsx 最先导入 @kfe/prn-entry，保证拆包前初始化核心组件。
  4. 随后调用 registerAll(getRNPageLoaders()) 批量注册，再调用 registryDetect() 和 logBootTime()。
  5. 原生侧以 moduleName=pikachu&pageName=...&initProps=... 打开具体页面。

这里的关键取舍是“页面映射集中、页面实现分散、加载发生在运行时”。它降低了 Native 对每个 RN 页面实现的感知，但 new Function + require 会降低静态分析透明度，也让页面名、包名和构建产物之间的合同更依赖工具链校验。

面试时可以这样解释：

它不是把所有 RN 页面做成一个大入口，而是先用页面表生成 loader，再统一注册给宿主。Native 只需要知道页面名，RN 内部仍能按 workspace 做垂直拆分。排查“页面打不开”时，可按页面表、loader、注册、Bundle 是否含该 package、Native 传参五层往下查，而不是一上来只看页面组件。

4. AI 生图完整业务链路

4.1 创建任务

pages/GenerateAIImage/src/Entry.tsx 维护描述、角色、场景、风格、特征词和 plugin 状态：

  1. 页面挂载后请求生成配置；
  2. 成功后填充风格和特征词，并通知 Native 隐藏 loading；
  3. 用户点击生成时，把角色、场景、描述、特征词拼成请求参数；
  4. POST /km-indep-home-comm/aigc/images 创建异步任务；
  5. 若接口返回业务拦截消息，则 Toast 后终止；
  6. 否则取得 taskId，通过 Deep Link 打开 GenerateAIImageResult，并把原参数和 taskId 编码进 initProps。

这一段能体现两点：

  • UI 并不等待图片生成完成，只等待“任务创建成功”，长任务被拆到结果页；
  • Deep Link 既是路由，也是跨 Native/RN 的序列化合同，字段兼容性和 URL 长度都需要治理。

4.2 轮询结果

pages/GenerateAIImageResult/src/Entry.tsx 的状态机是：

text
taskId
  → 每 2 秒查询任务
  ├─ FINISHED：保存图片，默认选中第一张，停止轮询
  ├─ FAILED：保存失败文案，停止轮询
  ├─ ILLEGAL：标记违规并停止轮询
  ├─ 超过 60 秒：标记超时
  └─ 请求异常：进入失败状态

并发和生命周期处理：

  • isPollingRef 是同步门禁，防止同一页面重复启动轮询；
  • pollingStartTimeRef 记录开始时间；
  • while 每轮请求后用 setTimeout 等待 2 秒；
  • effect cleanup 调用 stopPolling()，页面卸载后下一轮不会继续发请求；
  • 重新生成取得新 taskId 后更新 id，旧 effect cleanup 停止旧循环，新 effect 启动新任务。

它不是严格的网络取消：已经发出的 GetImageResult() 请求没有 AbortSignal，cleanup 只是阻止后续轮询和后续循环。因此更准确的说法是“停止调度”，不是“取消在途 HTTP”。

4.3 把结果交回下游

结果页按 source 分三条回传路径：

  • comment：按 aiImageAtomKey 写入 app 生命周期 Jotai atom，再通过 popNavigation 销毁相关页面栈；
  • publisher：通过 editor/setAiAlbumImageResult Bridge 把资源 ID 交给 Native 编辑器；
  • 默认编辑器：通过 Deep Link 携带资源 ID 打开下游编辑器。

这说明“选择图片”不是单纯页面内部状态，而是一个跨页面、跨 RN/Native 的业务合同。需要明确：

  • 评论场景需要共享完整图片元数据；
  • Native 发布器只需要图片资源 ID；
  • 默认编辑器继续走路由协议。

5. AI 图库、分页与 Jotai 状态

AIImageSelection 首次加载调用 GetHistoryData({ limit: 20, type: 'image' })，接口类型虽然声明了 offset?: number，实际首次请求没有传 offset。后续翻页不再自行累加 offset，而是直接请求服务端 paging.next。

这是 cursor 分页思路：客户端不解释游标，只保存下一页 URL。优点是服务端可调整分页策略，缺点是这个 URL 也成为服务端与客户端的信任边界。

当前实现的优点：

  • 首次请求有 try/catch，能区分 loading、失败和空数据；
  • 用 Set<string> 保存选择顺序和去重；
  • 评论、发布器和默认编辑器的确认逻辑分支清楚；
  • 最多选择数量由 props 控制，并有默认值。

当前实现的风险：

  • handleEndReached() 只检查 isEnd 和 fetchUrl，没有独立的分页 loading 门禁；
  • 连续触底可能并发请求同一个 paging.next，产生重复追加或乱序覆盖；
  • 翻页请求没有 try/catch，失败不会转换为可见状态；
  • app 生命周期 atom 的实现注释明确要求使用后 removeKey()，但列表组件的卸载清理被整段注释，可能留下场景数据；
  • 页面不可见时通过全局事件恢复评论编辑器，说明 AppState、页面可见性和 Native 导航栈并非同一个生命周期，需要联调验证。

如果重做，优先级应是：

  1. 给分页增加 loadingMoreRef 或请求序号，阻止重复请求和旧响应覆盖；
  2. 给翻页增加错误状态与重试；
  3. 恢复并验证 atom 的场景级清理；
  4. 为轮询和 metadata 请求引入 AbortController；
  5. 将 Deep Link 参数做统一 schema 校验和版本化。

6. 错误处理、稳定性与安全

已有处理

  • 首屏配置请求用 try/catch/finally，无论成功失败都会通知 Native 结束 loading；
  • 创建任务同时处理网络异常和业务拦截消息；
  • 轮询区分成功、普通失败、内容违规、超时和请求异常；
  • 重新生成失败会 Toast；
  • 结果页卸载会停止后续轮询。

仍需改进

  • 结果页的 GetAiPrompt(id) effect 没有 catch，也没有取消或组件存活检查；
  • 轮询超时和失败只有 UI 状态，缺少任务耗时、轮询次数、错误类型等结构化观测；
  • Deep Link 的 initProps、Native Bridge 名称和数据 shape 都是跨团队合同，但当前调用点看不到 schema 版本或运行时校验；
  • 图片 URL、下一页 URL和服务端返回文案进入客户端，需要明确可信域、协议和长度限制。

敏感信息

当前根目录存在 .sentryclirc，有疑似明文 token 风险。本文不复制任何值。正确动作是：

  1. 立即轮换对应凭据；
  2. 从仓库历史中清理；
  3. 改由 CI Secret 或环境变量注入；
  4. 对构建日志做脱敏。

7. 工程质量与当前 checkout 边界

当前 checkout 的事实

  • 不是 Git 工作区；
  • 声明的 prn/* 不存在；
  • .yarn/ 不存在；
  • prnn/ 存在但为空；
  • 没有独立 RN App 所需的 android/、ios/、app.json、metro.config.js；
  • package.json 固定 Yarn 3.6.4，当前环境没有可直接使用的 Yarn 命令；
  • 当前 Node 是 20.12.0，而 joker.yml 使用 Node 16.17.1；
  • 只有 2 个实际测试文件，另有 1 个快照文件；
  • CI 的 unittest 是 echo skipping。

因此不能把“当前副本无法 Bundle”直接归因于业务代码。更准确的结论是：

这是一个不完整 checkout，缺少仓库声明的 PRN workspace 和 Yarn 本地发行文件。应先恢复完整源码和匹配工具链，再判断真实构建错误。

本轮没有运行 Bundle、Jest 或 TypeScript 全量检查。旧审计中的历史构建错误若被引用，必须明确标记为旧快照，不能冒充本轮实测。

测试建议

  • 对 getRNPageLoaders() 做页面表与 workspace package 的一致性测试；
  • 对 AI 任务状态机做 fake timer 测试，覆盖成功、失败、违规、超时、卸载；
  • 对 source 三分支做 Bridge/Atom/Deep Link 合同测试；
  • 对分页做重复触底、乱序响应和失败重试测试；
  • 对 app 生命周期 atom 做卸载清理回归测试；
  • CI 不应继续跳过单测，至少把上述纯逻辑链路纳入门禁。

8. pikachu 的亮点与风险排序

最值得讲的亮点

  1. Native/RN 边界清楚：页面名、Deep Link、Bridge 和 app 级 atom 分别承担路由、能力调用和跨页面状态。
  2. 长任务拆页：创建任务与等待任务分离，结果页能独立处理轮询、超时、重试和回传。
  3. 多消费方回传：评论、Native 发布器、默认编辑器使用不同合同，业务分支完整。
  4. 页面动态注册：多页面 Bundle 通过页面表统一注册，适合大型宿主的模块化接入。

风险优先级

  • P0：凭据风险——.sentryclirc 疑似包含明文敏感值，应轮换并迁移 Secret。
  • P1：checkout 不完整——缺 prn/、.yarn/，不能形成可信构建结论。
  • P1：全局状态残留——atom 是 app 生命周期，但页面清理被注释。
  • P1：分页并发——触底没有 loading 门禁与异常处理。
  • P2：取消不完整——轮询只停止后续调度，metadata 请求没有取消。
  • P2：测试门禁弱——CI 跳过单测，跨端合同缺回归保护。

9. pikachu 可直接复述的话术

30 秒版本

【需本人确认】仅当本人确实阅读过该链路且能承受源码追问时，可表述为：“pikachu 是嵌入原生 App 的多页面 RN Bundle，不是独立 RN App。它通过页面表和 PRN bootstrap 动态注册页面，业务页面再通过 Deep Link、Bridge 和 Jotai 与 Native 协作。我重点看过 AI 生图链路：创建任务拿到 taskId，结果页每 2 秒轮询、60 秒超时，成功后按评论、发布器和默认编辑器三种来源回传。这个项目能体现我对 Native/RN 合同、异步任务和生命周期问题的理解；具体哪些调用点由我负责，我会按真实经历说明。”

2 分钟版本

这个项目的定位是大型原生 App 中的 RN 页面工作区。它把页面按 pages/* 做垂直拆分，把共享能力放在 packages/*，入口通过 pages/entry/src/pages.mjs 维护页面名到 package 的映射，再动态生成 loader 统一注册给 PRN runtime。Native 不需要感知页面内部实现，只通过 pageName、initProps、Bridge 和导航栈跟 RN 交互。

【需本人确认】仅当本人确实掌握该源码链路时，可表述为：“我会用 AI 生图作为主链路。生成页先加载风格和特征词配置，用户组合描述、角色、场景和风格后，客户端只负责创建异步任务。拿到 taskId 后跳转结果页，结果页用 ref 做重复轮询门禁，每 2 秒查一次，最多等 60 秒，并区分成功、失败、内容违规和超时。成功后，评论场景写 Jotai 并回退页面栈，Native 发布器走 Bridge，只传资源 ID，默认编辑器继续走 Deep Link。”

这个方案的优点是长任务和输入页解耦，多种消费方合同也比较清楚。风险是轮询只停止后续调度，没有真正取消在途请求；图库触底分页缺少并发门禁；app 生命周期 atom 要求清理，但调用页的 cleanup 被注释。建议的改进顺序是先补分页和 atom 生命周期，再把轮询、metadata 请求接入 AbortSignal，最后给 Deep Link 和 Bridge 参数加 schema 与合同测试。

另外，当前副本缺少 prn/* 和 .yarn/，因此不能把本地不能 Bundle 直接说成业务代码问题；应先恢复完整 checkout 和匹配工具链。

10. pikachu 常见追问

问：为什么不用 WebView，或者为什么不用全 Native？

答：

这类内容和活动页面变化快、数量多，RN 能共享 TypeScript 组件和业务逻辑，同时保留原生导航、编辑器和宿主能力。代价是跨端合同和运行时依赖更复杂，所以要把 pageName、initProps、Bridge 事件和生命周期当成正式 API 管理，而不能只靠口头约定。

问：轮询为什么用 ref，不只用 state？

答：

state 更新是异步的，闭包里的值也可能滞后。isPollingRef 能在同一个事件循环中立刻阻止重复启动，state 则用于 UI 展示。不过当前实现还没有取消在途请求；改进时可把 taskId 和 AbortSignal 一起作为任务身份管理。

问：分页为什么直接请求 paging.next？

答：

这是服务端 cursor 分页，客户端不需要理解 offset 语义，能减少翻页规则耦合。但客户端仍要做可信域校验、并发门禁、响应顺序保护和错误重试，当前实现后面三项还不完整。

问：Jotai atom 和 Bridge 怎么选？

答：

RN 内部且跨页面需要完整对象时，atom 成本低；需要交给 Native 编辑器时，Bridge 是明确的跨运行时合同；需要打开另一个独立功能时，用 Deep Link。选择依据是状态归属和消费方，不是个人偏好。

问：页面卸载后还会不会请求？

答：

当前轮询 cleanup 会把 ref 置为 false，阻止下一轮，但已经发出的 HTTP 不会被真正中止。GetAiPrompt 也没有取消。因此严格回答是“后续调度会停，在途请求未完全取消”。

问：页面打不开怎么排查？

答：

可依次检查页面是否在 pages/entry/src/pages.mjs、package 是否存在、loader 是否生成、入口是否执行 registerAll、Bundle 是否包含页面、Native 的 moduleName/pageName 是否匹配、initProps 是否能解析，最后再看页面首屏和 Bridge。这样能先定位是构建注册问题、路由合同问题，还是业务组件问题。

第二部分：html-anything

12. 项目定位

html-anything 是一个本地优先的 agentic HTML 编辑器：

  • 浏览器输入 Markdown、表格或原始内容；
  • Next.js API 加载技能模板并调用本机已登录的 coding-agent CLI；
  • CLI stdout 被适配成统一事件；
  • 服务端通过 SSE 把 HTML 增量发回浏览器；
  • Zustand 按 task 存储输出；
  • iframe 用 srcDoc 实时预览，再导出 HTML、图片或平台格式。

这不是普通的“前端调用云端大模型 API”。核心能力依赖 Node child_process.spawn 和本机 CLI 会话，所以安全模型是“单机可信用户 + loopback API”，不能把它当成无认证公网服务。

工作区实际包含三个 package：

text
html-anything/
  ├─ next/   Next.js UI、API、agent adapter、技能、导出
  ├─ e2e/    Playwright 配置、UI 与 Host 安全测试
  └─ cli/    CLI package

README 的 workspace 段落只列 next、e2e，但 pnpm-workspace.yaml 还包含 cli。CI 和 scripts/guard.ts 也主要覆盖 Next 与 e2e，没有为 cli 配置同等的 typecheck/test/build 门禁。

13. Agent 检测与 adapter

13.1 检测

GET /api/agents 调用 detectAgents()：

  1. 读取进程 PATH；
  2. 额外扫描用户工具链目录，如 .local/bin、.bun/bin、Volta、pnpm、npm global，以及 Windows Scoop/AppData 目录；
  3. 对每个 agent 返回是否可用、实际 binary、模型选项和平台信息。

源码的 AGENTS 当前定义 20 个条目，不是 README 某处写的 8 个或某处写的 9 个。并且“被检测到”不等于“可调用”：

  • 6 个 ACP adapter 是 detection-only；
  • pi 的 pi-rpc 也未接通；
  • buildArgv() 遇到这些协议会抛 UnsupportedAgentProtocolError；
  • 其余 13 个有 stdin、argv 或 argv-message 调用路径。

因此面试中应说：

源码登记了 20 种 CLI，但当前构建并非 20 种都能完成转换；ACP 和 pi-rpc 共 7 种只做检测和清晰报错。可用性必须按协议 adapter 判断，不能只看 picker 里有没有名字。

13.2 参数与输出协议

next/src/lib/agents/argv.ts 做两件事：

  • 为不同 CLI 生成参数、模型参数和输入协议；
  • 把多种 JSON-line 或纯文本输出解析为统一的 delta、html、meta、raw。

例如：

  • Claude、Gemini、Copilot、OpenCode 等会启用跳过权限或自动批准参数；
  • Codex 使用 workspace-write sandbox，并允许网络；
  • DeepSeek 类把 prompt 放在 argv；
  • OpenClaw 用 --message，并在进程退出后解析整段 JSON；
  • 其余多数通过 stdin 输入 prompt，再逐行解析 stdout。

adapter 模式的好处是上层 SSE/UI 不关心每个 CLI 的协议；代价是 CLI 版本升级后，参数和输出 JSON shape 可能变化，需要独立兼容测试。

14. 转换与流式预览链路

完整链路如下：

text
用户点击转换
  → useConvert.run(taskId)
  → 为该 task 创建 AbortController
  → POST /api/convert
  → loadSkill(templateId)
  → assemblePrompt() 或 buildEditPrompt()
  → invokeAgent()
  → child_process.spawn(local CLI)
  → stdout parser: delta / html / meta / error / done
  → Next ReadableStream 包装 SSE
  → useConvert 解析 SSE block
  → Zustand appendHtmlFor(taskId)
  → PreviewPane 320ms 防抖
  → iframe srcDoc 渲染

几个关键设计：

  1. task 级状态：Zustand 的 setHtmlFor、appendHtmlFor、setStatusFor 都接受 taskId，多个任务不会共用一份输出。
  2. 增量渲染：每个 delta 追加到 task HTML，并记录字节数、chunk 数和首字节时间。
  3. 预览节流：流式期间 iframe 大约每 320ms 更新一次，避免每个 token 都重新加载 iframe；任务结束时立即提交最后值。
  4. diff-edit：已有 HTML 且内容变化时，把旧内容、旧 HTML 和新内容一起发给服务端，要求 agent 做最小差异编辑，降低 token 和样式漂移。
  5. 容错解析：如果 agent 不按要求流式返回，而把 HTML 放进 Write 工具输入，parser 可发 html 事件覆盖之前的文本。

15. 并发、取消和状态语义

15.1 取消链路是完整亮点

text
用户取消 task
  → client AbortController.abort()
  → fetch signal 中止
  → request.signal abort
  → server AbortController.abort()
  → invokeAgent signal
  → child.kill("SIGTERM")

useConvert 用 Map<taskId, AbortController> 管理控制器：

  • 不同 task 可以并发；
  • 同一 task 再运行时先取消旧请求；
  • 取消后状态回到 idle；
  • finally 只清理仍属于当前 run 的 controller，避免旧请求误删新请求的控制器。

服务端外层 SSE 的 cancel() 会 abort child。需要注意，next/src/lib/agents/invoke.ts 内层 ReadableStream.cancel() 是空实现；当前链路依赖外层 request/SSE 的 AbortSignal 传播，而不是依赖直接 cancel 内层 reader。

15.2 当前有一个状态语义风险

agent 退出时，next/src/lib/agents/invoke.ts 无论 exit code 是否为 0 都发 done 事件；client 的 handleEvent("error") 只写错误日志，handleEvent("done") 也只写退出日志。只要 SSE 正常读到 EOF，useConvert.run() 最后就会：

  • 设置 status = done；
  • 提交 diff-edit baseline。

因此可能出现“日志里有 agent error 或非零 exit，但任务状态仍为 done”。更稳妥的设计是：

  1. client 记录是否收到 error 和最终 exit code；
  2. 非零 exit 或 error 事件把 task 标为 error；
  3. 只有成功且 HTML 通过最小完整性校验时，才提交 baseline；
  4. 区分 cancelled、failed、completed_with_warnings。

16. 安全模型

16.1 Host 校验是最重要的安全亮点

/api/convert 接受 cwd 和 binOverride，并能用高权限参数启动本地 coding agent。这意味着如果恶意网页能通过 DNS rebinding 请求用户本机 API，就可能把“生成 HTML”变成对本机的间接远程代码执行。

项目用 middleware 对全部 /api/* 做 Host allowlist：

  • 默认只允许 127.0.0.1、localhost 和 [::1]；
  • 拒绝空 Host、0.0.0.0 和伪装子域；
  • 可用环境变量显式增加可信 Host；
  • 也提供完全关闭门禁的开关，但源码明确标记为高风险；
  • Playwright 专门覆盖 /api/convert RCE 向量和 deploy token-write 向量。

这是一个很好的面试点：

安全不是只给输入做 escape，而是先识别系统中“高权限能力在哪里”。这里真正危险的是本地 agent spawn、文件写入和带凭据的部署 API，所以 middleware 覆盖整个 /api/*，在请求进入 handler 前挡掉 DNS rebinding。

16.2 iframe 不是 README 所说的强隔离

主预览实际是：

html
<iframe
  srcDoc="{generatedHtml}"
  sandbox="allow-scripts allow-same-origin">
</iframe>

README 声称“isolated origin”“cookies/localStorage quarantined”。这个表述不能直接成立。srcDoc 继承嵌入文档来源语义，再同时授予 allow-scripts 和 allow-same-origin，不应被当成不可信 HTML 的强安全边界；生成脚本可能接触同源父页面能力。README 自己在两处重复了过强描述。

这是当前最高优先级风险。可选改进按隔离强度排序：

  1. 把预览放到独立 origin，通过严格 postMessage 协议通信；
  2. 如果业务允许，移除 allow-same-origin；
  3. 若必须保留第三方脚本能力，至少使用独立域、CSP、权限策略和网络出口限制；
  4. 导出和截图不要依赖能访问宿主状态的 iframe；
  5. 明确把生成 HTML 视为不可信内容，并增加专门安全测试。

Host guard 保护的是“谁能调用本地 API”，iframe 隔离保护的是“生成内容在浏览器里能做什么”，二者不能互相替代。

16.3 技能安装安全

技能安装链路做得比较扎实：

  • 限制压缩包大小和解压后总大小，防 gzip bomb；
  • 解压前遍历 tar header；
  • 拒绝绝对路径、..、symlink、hardlink 和特殊文件；
  • 限制 SKILL.md、示例 HTML/Markdown 的单文件大小；
  • staging 目录与目标目录放在同一文件系统；
  • 使用 rename 原子替换；
  • 替换失败时恢复备份。

这说明“下载一个模板目录”也应按供应链输入处理，而不是直接 tar -xzf 到用户目录。

17. 导出与部署边界

Web 层支持 HTML、图片和多个平台格式导出，相关代码位于 next/src/lib/export/。这部分的通用价值是：

  • 编辑态保存语义内容和生成 HTML；
  • 预览态通过 iframe 呈现；
  • 发布态对 CSS、公式、图片或平台格式做专门适配。

README 的“Vercel 可部署”只能理解为 Web 层或部分无本地依赖能力可部署。核心转换链需要：

  • Node runtime；
  • 本机已安装并已登录的 agent CLI；
  • child_process.spawn；
  • 本机工作目录和权限模型。

因此不能把当前核心链路直接描述成普通远程 Vercel SaaS。若要远程化，需要新增身份认证、租户隔离、任务队列、沙箱执行器、Secret 管理、资源配额和审计。

19. html-anything 的亮点与风险排序

最值得讲的亮点

  1. adapter 统一多 CLI：上层只消费统一事件，不耦合每家 stdout 协议。
  2. 端到端取消：task 级 controller 一直传播到 child SIGTERM。
  3. 流式性能取舍：SSE 增量写状态，iframe 用 320ms 防抖平衡实时性和重载成本。
  4. Host 安全门：威胁模型准确覆盖本地高权限 API 和 DNS rebinding。
  5. 技能供应链防护：tar 预检、大小限制、拒绝链接、原子替换和回滚形成完整闭环。

风险优先级

  • P0：iframe 隔离不足——不可信脚本与 same-origin 同时开放。
  • P0：不能无认证暴露公网——API 能指定 cwd/bin 并启动高权限本地 agent。
  • P1：错误状态语义——error 或非零 exit 仍可能最终显示 done。
  • P1：README 漂移——agent、skill、workspace 和安全声明与源码不一致。
  • P2：CLI package 门禁不足——workspace 有 cli，CI/guard 覆盖不对等。
  • P2：adapter 漂移风险——外部 CLI 参数与输出协议随版本变化。

20. html-anything 可直接复述的话术

30 秒版本

html-anything 是本地优先的 agentic HTML 编辑器。浏览器把内容发给 Next API，服务端加载技能模板并 spawn 用户本机的 coding-agent CLI，再把 stdout 统一解析成 SSE 增量；前端按 task 写入 Zustand，并以 320ms 防抖更新 iframe。它最值得讲的是多 CLI adapter、端到端取消和 Host 防 DNS rebinding。最大的风险是主预览同时开放 scripts 和 same-origin，不能按 README 所说当作强隔离。

2 分钟版本

这个项目不是前端直接调云端模型，而是复用用户本机已经登录的 coding-agent CLI。启动时 /api/agents 扫 PATH 和额外工具链目录；每个 CLI 在 next/src/lib/agents/argv.ts 里有参数和输出 parser。转换时 /api/convert 加载技能、组 prompt，再通过 child_process.spawn 启动 agent。stdout 被统一成 delta、html、meta、error、done 事件，外层包装成 SSE。客户端按 taskId 维护 AbortController 和 Zustand 状态，每个 delta 追加 HTML，预览组件大约每 320ms 更新一次 iframe。

取消链路很完整：客户端 abort fetch，request signal 传到服务端 controller，再传到 agent stream，最后对 child 发 SIGTERM。它还用 Host allowlist 防 DNS rebinding，因为 /api/convert 能用高权限参数启动本机 agent，本质上是高风险本地能力。

当前有两个关键改进点。第一，error 事件或非零 exit 只记日志，SSE 正常结束后 task 仍可能变成 done，应该把进程结果纳入状态机。第二，iframe 用 srcDoc + allow-scripts + allow-same-origin，不能算强隔离；应迁移到独立 origin 或移除 same-origin。另一个工程问题是 README 的 agent、skill 和 workspace 数量已经跟源码漂移。

如果面试官问部署，应明确：Web 层可以部署，但依赖本机 CLI 和 spawn 的核心转换链不是普通 Vercel 远程服务；远程化需要重新设计认证、沙箱、队列、配额和审计。

STAR 版本

只有本人确实参与该项目时才可改成“我负责”：

  • S：需要统一多家本地 CLI 的输入输出协议，并在浏览器里实时预览生成 HTML。
  • T：【需本人确认】仅当本人真实负责对应工作时，填写“我负责【真实 adapter / SSE / 前端状态 / 安全治理范围】”。
  • A：【需本人确认】仅填写本人实际执行且能举证的动作，例如“我把 CLI 差异收敛到 argv/parser adapter；用 SSE 串起子进程和浏览器；按 task 管理并发和取消；针对本地高权限 API 增加 Host 校验；对【真实问题】补充测试”。
  • R：结果指标必须同时注明【指标定义与计算口径】【统计时间范围】【数据来源或看板/日志】【基线与结果值】。例如支持 CLI 数必须区分“可检测”和“可调用”，性能指标必须给出统计样本。没有可核验数据时，只陈述实际覆盖的链路和测试。
  • 复盘：说明仍需解决 iframe 独立 origin、exit code 状态语义和 CLI 门禁。

21. html-anything 常见追问

问：为什么用 SSE，不用 WebSocket？

答：

当前主要是服务端向客户端单向输出增量，用户输入和取消仍可用普通 HTTP/AbortSignal，SSE 更简单，也能被 fetch 的流直接消费。若以后需要双向会话、工具确认或多路实时控制，再考虑 WebSocket。

问：怎么保证多个任务互不干扰？

答：

controller 按 taskId 存在 Map 中，Zustand 的写操作也都带 taskId。同一 task 重跑先取消旧 controller，不同 task 可以并发。finally 还会校验 Map 中仍是当前 controller，避免旧任务结束时删掉新任务的控制器。

问：为什么不能把 detection-only agent 也算“支持”？

答：

检测只证明 binary 存在。真正支持还要有 prompt 传输、stdout parser、取消、退出状态和测试。源码对 ACP 和 pi-rpc 会明确抛 unsupported，所以应分别描述“可检测”和“可调用”。

问：Host allowlist 能解决所有安全问题吗？

答：

不能。它主要防恶意网页通过 DNS rebinding 调本机 API。它不解决已允许 Host 上的身份认证，也不解决生成 HTML 在 iframe 中的脚本权限，更不替代 agent 自身的文件和网络沙箱。

问：allow-scripts allow-same-origin 为什么危险？

答：

对不可信内容同时开放脚本和同源，会让脚本获得远高于纯 sandbox 的能力。这里又使用 srcDoc，不能轻率声称 cookie/localStorage 与宿主完全隔离。最稳妥方案是独立预览域加严格消息协议。

问：进程退出码该怎样映射到 UI？

答：

可把 run 状态建模成 running、cancelled、failed、done、done-with-warning。error 事件和非零 exit 进入 failed；只有 exit 0、没有 error 且 HTML 通过最低完整性校验，才进入 done 并更新 diff baseline。

问：为什么预览要 320ms 防抖？

答：

iframe 的 srcDoc 更新会触发文档重载。每个 token 都更新会浪费 CPU、重复加载资源并造成闪烁；约 3fps 对“看见逐步生成”已经足够，任务结束时再立即提交最终值。这个值仍应通过性能数据调优，而不是当成固定真理。

问：能直接部署到 Vercel 吗？

答：

静态 Web 和部分 API 可以，但核心转换依赖本机 CLI、登录态、文件系统和 child process。普通远程 Vercel 实例没有用户本机环境。若做 SaaS，需要独立的受控执行器，而不是直接把现有本地 API 暴露出去。
