React Native 0.72 原理
给写过一点 RN 业务的 Android 开发者

从 Android 开发经验出发，结合 RN 0.72.10 官方机制和项目源码，理解一段 JS 在哪里执行、React 如何驱动原生界面，以及 JS 与 Android 如何交换调用和事件。重点跟读运行时、渲染架构、原生接入与业务调用链。

学习入口：JS、React 状态或 Hook 还不熟悉，先看独立的React 与前端基础。本文可从第 02～03 节的整体模型开始，再进入 Bridge、Fabric 与项目调用链。

本文的版本基准已核实：pikachu 声明并安装了 React Native 0.72.10；Android 宿主的版本表使用 0.72.10_1。后者带有项目版本后缀，不能假设与官方二进制完全相同。本文用官方原理和 v0.72.10 源码说明框架，用当前仓库说明实际接入；没有运行 APK 验证线上配置。

01 · 先确定版本，不把不同年代的架构混在一起

RN 0.72 发布于 2023 年。该版本的官方发布说明仍将 New Architecture 称为实验性架构；它不是“只要升级到 0.72，所有页面自然都运行 Fabric”。[官方 O1]

核对对象当前证据能够得出的结论
JS 工程pikachu/package.json：react-native: 0.72.10，React 声明 ^18.2.0本文以 RN 0.72.10 为基准
安装与锁定yarn.lock 有 0.72.10 的解析记录；本地 node_modules/react-native/package.json 同为 0.72.10可以直接读对应版本的框架源码；不等于所有其他依赖均可构建
Android 依赖VipAndroid/version.gradle：RN、Hermes 都为 0.72.10_1宿主有自己的依赖发布版本，需保留与上游的差异边界
开关vip_react_entry/gradle.properties：newArchEnabled=false、enableHermes=true该子工程的静态配置如此，不能代替整个 App 最终构建配置和运行时证据
新架构相关代码有 TurboReactPackage、Native…Spec、组件 Codegen 和 Fabric 补丁项目在接入相关能力；这些类的存在不足以证明所有页面都在走新通道
实际 RN 容器实现通过 Maven 依赖的 PlatformRNApi / PlatformRNProvider / prnkit 接入当前未找到其核心实现源码，运行时、Surface 和 Bundle 策略需要进一步验证

还有两个常见的“伪证据”：TurboModuleRegistry 在 0.72.10 中有旧模块回退逻辑；codegenNativeComponent 也存在使用 requireNativeComponent 的兼容路径。API 名称带 Turbo 或 Codegen，不是架构开关。

本地的 pikachu/prn、.yarn 缺失；node_modules/@kfe/prn-bootstrap 等实际上是内容为相对路径的普通小文件，不是可读取的包实现。因此，业务代码里的 createPage、useRNBridge、useMMKVStore 可以定位到调用点，但不能假装已经追到它们的内部。

02 · RN 到底是什么：JS 决定界面，原生系统显示界面

React Native = React 的声明式 UI 模型 + JS 运行时 + 面向原生平台的渲染器 + 原生能力接入机制。

当你写 <View><Text>你好</Text></View>，并不是把 HTML 塞进 WebView，也不是直接把 TSX 编译成 Kotlin。JS 在 JS 引擎里运行，React 计算应该呈现什么；RN 把结果映射为宿主平台的 View 操作，最终由 Android 的 View 绘制系统显示。

JS / TS 业务与状态→React 计算 UI 描述→RN 渲染器→Android 原生 View

对于 Android 开发者，最接近的理解是：你不再每次自己调用 textView.setText()，而是声明“当前状态下，Text 应显示这个值”，由框架计算和执行必要的原生更新。Compose 的状态驱动思路可以帮助理解，但 RN 并不通过 Compose 渲染，二者的运行时和节点体系不同。

概念Android 类比类比的边界
React Component可复用 UI 单元普通函数组件通常不是一个真实 View，也不是一个 Fragment
props构造参数或 UI 输入由父级传入，更新时 React 会重新计算，子级不应直接修改
state驱动 UI 的状态更新通过 React 调度，不是立即修改某个 TextView
JS Runtime另一套语言执行环境不是 ART，JS 对象不直接等于 JVM 对象
Native Module暴露给 JS 的平台服务提供方法和事件，不一定创建 UI
Native Component接入 RN 的自定义 View要提供属性、事件、注册等适配，并非直接 import Java 类
Shadow Node布局和渲染的中间数据不是屏幕上的 View，不直接绘制像素

也不能说“每个 JSX 标签都一一生成原生 View”。函数组件会被展开；布局专用节点可以被压平；嵌套 Text 可能组合为一段原生文本。实际 Android View 层级往往比 React 组件树浅。

03 · React 做什么：从状态快照到最少必要的 UI 更新

如果还不熟悉 Hook，请先读第 11 章 · Hook 详细教程：那里逐步拆解每一轮渲染、状态更新和 effect 清理，本节回到整体渲染过程。

先看一个教学示例，它不是项目源码摘录：

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <Pressable onPress={() => setCount(n => n + 1)}>
      <Text>点击次数：{count}</Text>
    </Pressable>
  );
}
  1. 首次调用 Counter，count 为 0，函数返回描述 UI 的 React Element。
  2. 点击触发 JS 回调，setCount 把更新交给 React。
  3. React 调度下一次渲染，再调用组件函数，新的状态为 1。
  4. React 对比前后结果，定位需要改变的宿主属性或结构。
  5. RN 渲染器让对应原生文本更新，而不是每次把整页 View 全部销毁重建。

JSX、Element、Fiber，分别是什么？

JSX 是编写 UI 的语法，会转换为普通 JS 调用；TypeScript 类型通常在构建时被移除。Element 是“什么组件、什么属性、什么孩子”的描述。Fiber 是 React 用来组织组件状态、更新工作和树关系的内部结构，负责协调更新。Fiber 不等于 Android View，也不等于后文 Fabric 的 C++ Shadow Node。

为什么更新了 state，当前函数里的值却没变？

一次渲染中的变量可以理解为那次渲染的状态快照。setCount(count + 1) 请求更新，不会把正在执行的函数闭包中的 count 重新赋值。连续累加依赖旧状态时，用 setCount(n => n + 1) 更准确。不能承诺每次 setter 都立即独立渲染一遍，React 可以批处理更新。

为什么 Hook 不能写在 if 里？

React 依赖稳定的 Hook 调用顺序，把每次调用对应到正确的状态槽位。条件分支改变调用顺序，状态就可能对应错位。useRef 保存跨渲染的可变引用，但修改 ref.current 不会自动触发 UI 更新；useMemo 缓存计算结果，useCallback 缓存函数引用，都不是“后台线程执行”。

useEffect 不是 onCreate 的直接替代

useEffect 用于提交后的外部同步，比如订阅、定时器和请求。依赖变化时先清理旧 effect，再运行新 effect；卸载时也会清理。组件重新渲染不等于重新挂载，组件挂载也不等于 Android 页面进入可见状态。开发环境的检查行为还可能额外暴露重复副作用。

key 参与 React 对同级元素身份的判断。列表把位置当 key，在插入、删除、重排时容易把输入状态或组件状态对应到错误条目。它不是原生 View 的资源 ID。

04 · 把整条链路分成四层

层主要职责出问题时的典型表现
业务 / React 层props、state、组件、effect、事件回调状态不更新、重复请求、列表反复渲染
运行时 / 调度层Hermes 执行 JS、任务调度、GC、跨语言接口JS 卡顿、长任务、同步调用阻塞
RN 渲染 / 模块层Paper 或 Fabric、Yoga、模块和组件适配组件找不到、属性不生效、通信积压
Android 平台层Activity、View、主线程、图片、网络和系统能力UI 卡顿、生命周期错位、ANR、原生崩溃

一次按钮点击形成一个闭环：原生触摸 → RN 事件系统 → JS 回调 → state 更新 → React 计算 → RN 渲染器 → 原生 View 更新。如果 JS 回调里处理几万条数据，卡点不一定在 Bridge；如果主线程图片处理太重，JS 再快也不能保证画面流畅。

05 · Bundle、Metro 和 Hermes：谁编译，谁执行？

开发输入：TS / TSX / JS + 图片资源
              ↓ 转换语法、解析依赖、打包
构建工具：常规 RN 使用 Metro；项目也可以有自定义打包链
              ↓
产物：JS Bundle；启用对应发布流程时进一步生成 Hermes 字节码
              ↓ 加载到 JS Runtime
Hermes：执行 JS 逻辑、管理 JS 堆与垃圾回收
              ↓
React / RN：计算 UI、访问平台能力

Metro 是打包工具，Hermes 是 JS 引擎，Fabric 是渲染器。三个名字不在同一层，不能互相替代。JSX 被转换为 JS 调用，TS 类型不直接进入 Android；Java/Kotlin 仍由 Android 构建链处理，C++ 仍由 NDK 等工具处理。

Hermes 面向 RN 做了启动和内存方面的优化，典型发布流程可提前把 JS 编译为紧凑字节码，减少设备端启动时的解析与编译成本。Hermes 字节码不是 DEX，也不是把整个 JS 应用变成 ARM 原生机器码。仍然需要 Hermes 执行，仍然可能被大量计算、对象分配和 GC 拖慢。

官方从 RN 0.69 开始将对应 Hermes 与 RN 一起构建、测试和发布；0.70 起默认启用 Hermes。原因之一是共享 JSI 的版本和 ABI 必须匹配。不要随意替换某个 Hermes .so，也不要认为任意版本的字节码都能被另一版引擎读取。[官方 O3]

项目里看到什么？

pikachu/package.json 的构建命令是 prn bundle，开发依赖有 @callstack/repack、webpack 和 @swc/core。因此不能照抄“本项目一定直接运行 Metro”的结论。pikachu/babel.config.js 明确写了 Jest only，不能拿它推断生产打包链。

CLI 实现缺失，现有证据只能确认脚本入口和工具依赖，不能确认每个 Bundle 的实际编译选项、分包策略或是否都已转成 Hermes 字节码。

Fast Refresh 是开发期反馈机制；线上下载 Bundle 是项目发布机制；Codegen 是生成跨语言接口胶水。它们分别解决不同问题。

06 · Android 怎么把一个 RN 页面启动起来？

先看官方 0.72 的典型 Bridge 宿主路径

Activity / 容器
  → ReactNativeHost 提供配置与 ReactInstanceManager
  → 创建或复用 ReactContext、JS Runtime 和模块注册
  → 加载并执行 JS Bundle
  → JS: AppRegistry.registerComponent("PageName", ...)
  → ReactRootView.startReactApplication(..., "PageName", initialProps)
  → 原生在适当时机调用 AppRegistry.runApplication(...)
  → renderApplication → 根据 useFabric 选择渲染器
  → 原生 View 挂入容器

这是把关键依赖关系展开后的教学路径，实际加载、测量和 attach 可能异步推进，Runtime 也可能早已预热。registerComponent 是登记组件工厂，不表示页面已经在屏幕上；runApplication 才是使用根节点和初始属性启动该应用组件。两端组件名必须匹配。

ReactRootView 可以理解为原生与 React 页面相接的根容器。initialProps 是 Android 给根组件的启动输入。rootTag 用来标识相关根节点，不是 Activity ID。JS Runtime、ReactContext、页面 Root 也不是同一个对象；一个 Runtime 是否共享给多个页面由宿主方案决定。

框架源码已核对

ReactRootView.java：startReactApplication、runApplication。
AppRegistry.js：组件注册表与 runApplication。
RendererImplementation.js：useFabric 为真时进入 ReactFabric，否则进入 ReactNative。

再看项目真正可见的启动段

T_VipReactNative.onRun()
  → PlatformRNApi.start(assetsBundles, remoteBundles, ...)

BaseReactView.initialize(activity, bundleName, componentName, initProps)
  → PlatformRNApi.createProvider(...)
BaseReactView.load(minBundleVersion)
  → provider.load(...)
provider 回调 onRNViewAttached(reactRootView)

T_VipReactNative 注册了 pikachu 和 amadeus-rn 的资产 Bundle 与远程 Bundle 名称，还按配置注册调试 Bundle。BaseReactView 是一个真实的 Android FrameLayout，负责创建 Provider、转发生命周期与加载回调，并把 RN 根 View 接进原生布局。

07 · 旧架构 Bridge：把跨语言调用变成可传递的任务

JS 不能直接拿一个 Kotlin 对象像普通 JS 对象一样随便调用。传统 Native Module 通道把调用描述为“哪个模块、哪个方法、哪些参数”，跨语言转换后交给原生执行；结果通过回调、Promise 或事件回到 JS。

JS: NativeModules.Demo.doSomething(params)
  → 生成模块方法代理
  → MessageQueue.enqueueNativeCall(moduleId, methodId, params, ...)
  → 批量队列 / 刷新
  → C++ Bridge 解析调用
  → Native Module 队列
  → Java/Kotlin 模块方法
  → callback / Promise / event 回到 JS

0.72.10 的 MessageQueue 内部保存模块 ID 数组、方法 ID 数组、参数数组和调用编号。批量发送减少了频繁跨边界的次数，但也引入排队、参数转换、回调管理和跨线程调度成本。

“通过 JSON 通信”为什么不够准确？

许多教程把 Bridge 简化为“把调用序列化成 JSON”。正确的直觉是：需要跨边界传递受支持的结构化数据，并承担转换或复制成本。但不能据此声称每次调用必然执行 JSON.stringify，再通过 socket 传一段字符串。同一 App 内可以通过 C++/JNI 和结构化值传递；远程调试又可能采用另一条通道。

项目某个方法接受 JsonNode，只是业务封装的数据形态，也不是底层 Bridge 一定使用文本 JSON 的证据。

Bridge 不等于“完全不可能同步”

传统架构常见调用是异步批处理，但 RN 也有同步原生方法接口，0.72 的 MessageQueue 里存在 callNativeSyncHook。同步调用会阻塞调用方，受数据类型和调试方式约束，不适合用来做耗时 IO。

await 只表示 JS 代码等待 Promise 完成，并不决定原生方法在哪个线程执行，也不自动把 JS 计算搬到后台。跨模块操作要自己定义超时、失败、取消和生命周期规则。

MessageQueue.js：enqueueNativeCall、flushedQueue、callNativeSyncHook。
NativeToJsBridge.cpp：callNativeModules 和调用解析。

08 · Paper 渲染：JS 计算差异，Yoga 布局，主线程更新 View

Paper 是旧渲染器的常用名称。Android 侧可以沿着这一条主线读源码：

React 组件重新计算
  → ReactNativeRenderer 生成宿主更新
  → UIManager.createView / updateView / manageChildren
  → Bridge → Android UIManagerModule / UIImplementation
  → 更新 Java Shadow Node 与对应 Yoga 布局节点
  → Yoga 计算大小、位置
  → UIViewOperationQueue 排队
  → 主线程 NativeViewHierarchyManager
  → ViewManager 创建 / 更新原生 View，应用布局

Yoga 是布局引擎，不是 JS 引擎，也不负责画图。它根据样式和约束算出宽高与坐标。Android 的 Shadow Node 持有 Yoga 节点，Java 层会调用底层 Yoga 实现。Text 等内容还需要平台参与测量，因为文字字形、字体与实际排版依赖系统。

RN 的 Flexbox 和 Android 的 measure/layout 有什么关系？

RN 使用一组 Flexbox 风格的布局规则。你写 flexDirection、padding、width 等，布局阶段先得到几何结果，再在原生层应用 View 的测量和布局。最终依旧受 Android 父容器约束；RN 根容器拿不到可用尺寸，内部写满 flex: 1 也未必能显示。

不要把 RN 样式当成浏览器 CSS：没有完整 CSS 选择器和层叠模型，部分默认值也不同。普通布局数值是逻辑布局单位，Android 侧会映射到实际像素，并非“100 就是 100 个物理像素”。

为什么组件树比 Layout Inspector 里的 View 树大？

React 组件树包含业务包装层；Shadow Tree 只需要布局和渲染相关的信息；真实 Host View Tree 又可能移除仅用于布局的层。Paper 有自己的布局节点优化，Fabric 有自己的 View Flattening。不要用两棵树节点数量不一致直接判断页面缺失。

ReactNativeRenderer-dev.js：宿主 create/update 操作。
UIImplementation.java：dispatchViewUpdates → updateViewHierarchy → calculateRootLayout。
UIViewOperationQueue.java：将属性、布局、创建操作交给原生 View 层执行。

09 · Fabric 渲染：共享 C++ Shadow Tree 与更灵活的提交

Fabric 是新渲染器，不是“另一种 JS 引擎”。核心变化之一，是将 Shadow Tree 和更多渲染逻辑放到跨平台 C++ 层，通过 JSI 与 React 连接，并提供适合并发、优先级和同步场景的基础。[官方 O2]

先分清三棵树

  • React Element / Fiber 一侧：JS 的组件描述、状态和更新工作。
  • React Shadow Tree：C++ 中保存宿主组件的 props、布局、原生 state 等信息。
  • Host View Tree：最终的 Android View 层级，由平台 UI 线程操作。

Render → Commit → Mount

Render
  React 执行组件、协调更新
  经 JSI 创建或克隆 C++ Shadow Node，形成新 Shadow Tree
          ↓
Commit
  计算布局 / 验证并提交树版本，使其成为待挂载状态
          ↓
Mount
  对比新旧树、得到原生变更操作
  在 UI 线程应用 View 创建、属性更新、插入、删除和布局

Shadow Tree 的不可变设计不表示“每次复制全树”。修改一个节点时，可以克隆受影响节点和到根的路径，共享未改变的子树。这样便于维护一致快照，并在多个更新竞争提交时处理版本冲突。

原生组件也可以更新由 C++ 维护的 state，而不必先修改 JS 的 React state。例如某些滚动状态可以从平台侧推进。这是对渲染状态来源的扩展，不代表应用任何数据都能绕过 React 随意改。

Fabric 改善了什么，又没有保证什么？

它减少对旧式串行 Bridge UI 流程的依赖，让共享渲染逻辑、优先级调度、同步测量和某些同步更新场景更容易实现。但 Fabric 不会把普通业务 JS 变成多线程并行程序，也不会自动消除慢组件、重图片和错误的状态设计。

官方线程模型展示了 JS 线程执行、UI 线程高优先级执行、中断和 C++ state 更新等不同路径。因此不能死记“Render 必在 JS 线程、Commit 必在某个固定后台线程”。稳定的边界是：真正操作 Android Host View 必须满足 UI 线程约束。[官方 O4]

UIManagerBinding.cpp：createNode、cloneNode、completeRoot 的 JS/C++ 连接。
ShadowTree.cpp：提交、布局与重试相关逻辑。

项目有自定义 ReactFeatureFlags 与 SurfaceMountingManager 源码，只证明存在适配和补丁，不证明当前每个根节点启用了 Fabric。

10 · JSI、TurboModule、Codegen、Bridgeless 不要混为一谈

名词它负责什么它不等于什么
JSI统一操作 JS Runtime、值、函数和宿主对象的 C++ 接口不是 JS 引擎、不是线程池，也不自动做到零复制
TurboModule新原生模块系统，配合类型规格、绑定和模块管理不负责把 UI 树渲染成 View；同步和异步取决于方法定义与实现
Fabric新渲染器，管理渲染树、布局、挂载等不是 Native Module 的同义词
Codegen从受支持的类型规格生成跨语言接口和绑定代码不是把整个 TSX 业务编译成 Java 或 C++
Hermes执行 JavaScript 的引擎旧架构也可以用 Hermes
Bridgeless不依赖传统 Bridge 实例的运行模式启用 Fabric 不自动等于进入 Bridgeless，尤其不能套用到 0.72

JSI 怎样让 JS 调到 C++？

C++ 可以把一个 HostFunction 暴露给 JS，也可以用 HostObject 表达宿主对象的属性访问。JS 调用该函数时进入绑定的 C++ 实现。它可以直接完成轻量工作，也可以调度异步工作。需要进一步调用 Android Java/Kotlin 时，仍然可能经过 JNI、类型转换与线程切换。

“更直接”不等于“没有成本”。如果 HostFunction 同步处理 50 MB 数据，调用它的线程仍被占住；JS 值和宿主对象仍有生命周期、线程安全和所有权要求。

为什么项目的 TurboModuleRegistry 不能证明新通道已经启用？

官方 v0.72.10 的实现先在非 Bridgeless 模式中查 NativeModules[name]，找到就返回；没有找到时再尝试 global.__turboModuleProxy。这是迁移兼容逻辑。下面是保留关键顺序的源码摘录：

if (global.RN$Bridgeless !== true) {
  const legacyModule = NativeModules[name];
  if (legacyModule != null) {
    return ((legacyModule: $FlowFixMe): T);
  }
}
if (turboModuleProxy != null) {
  const module: ?T = turboModuleProxy(name);
  return module;
}

getEnforcing 的核心区别是模块不存在时抛错，不能把 Enforcing 理解成“强制开启新架构”。这一逻辑已同时核对本地 0.72.10 源码和官方版本文件。[官方 O5]

还有一个反例：旧 Bridge 的 JSIExecutor.cpp 已经通过 JSI 操作 Runtime，并调用 __fbBatchedBridge。因此，“堆栈里出现 JSI”也不能证明没有 Bridge。

TurboModuleRegistry.js：兼容回退顺序。
codegenNativeComponent.js：组件运行时兼容逻辑。
JSIExecutor.cpp：JSI 与旧 Bridge 并存。

11 · RN 的线程：不要只背“JS、UI、Native 三条线程”

“三线程”可以作为旧架构的入门图，但不是整个 App 只有三条线程。Android 还有 RenderThread、图片线程、网络线程、业务线程池；额外 JS Runtime 也可能有自己的执行安排。

执行位置常见工作Android 开发者需要注意
主线程 / UI 线程宿主生命周期、输入分发、真实 View 操作与挂载不要在这里解码大图、做重 IO 或长同步等待
普通 JS Runtime 的 JS 线程组件函数、React 更新、普通事件回调、业务 JS长循环、巨大 JSON 处理和高频 setState 会挤占响应时间
旧架构 Native Modules 队列许多异步原生模块调用、部分 Paper 更新相关工作不是任意线程的保证；模块可能自己切线程，同步方法也不同
其他线程 / Runtime网络、图片、业务 IO；部分动画库的 UI Runtime必须查具体库与调用链，不要把所有回调都算到 JS 主 Runtime

60 Hz 屏幕的一帧约 16.7 ms，120 Hz 约 8.3 ms。JS 侧和 UI 侧都可能错过自己的关键时间窗口：JS 卡住时原生 ScrollView 可能仍然滚动，但依赖 JS 的新内容和交互反馈延迟；UI 线程卡住时，即便 JS 已算完更新，也无法及时挂到屏幕。

优化之前先问：是哪一段慢？组件计算慢、跨边界传递太频繁、原生布局重、图片解码慢和 Bundle 冷启动慢，分别要用不同手段处理。不能一律通过 useMemo 解决。

12 · 项目例子一：JS 调 Android 路由

这是 Native Module 最容易理解的场景：RN 页面点击某段内容，希望宿主 Android 打开一个原生页面。

VipPin 业务中的 ZRouter.openURL(...)
  → @kfe/prn-bridges 导出层【本地实现缺失】
  → 原生侧提供的 ZRouter Spec / 模块契约
  → ReactEntryPackage 注册 RouterModule
  → RouterModule.openURL(...)
  → Handler(Looper.getMainLooper()).post { ... }
  → Android ZRouter.open(...)

这里的缺口是 @kfe/prn-bridges 的实际导出和包装逻辑。可以核实业务调用和原生契约，也可以核实注册和执行，但不能声称缺失那段包装已经逐行读过。

第一步：JS 侧定义契约

// NativeZRouter.ts：摘录
export interface Spec extends TurboModule {
  canOpenURL: (url: string) => boolean
  openURL: (url: string) => void
  back: (count?: number) => void
}
export const ZRouter = TurboModuleRegistry.getEnforcing<Spec>('ZRouter')

类型规格声明了名称、参数和返回值。canOpenURL 的返回值是 Boolean，而 openURL 返回 void。不能因为某个 Kotlin 文件的旧注释写了 .then(...)，就把这个契约说成返回 Promise。

第二步：Android 注册实现

ReactEntryPackage 继承 TurboReactPackage，通过 ReactModuleMap 把 NativeZRouterSpec.NAME 映射到 RouterModule；后者继承生成接口 NativeZRouterSpec。这说明项目采用类型规格和原生模块适配体系，但 ReactModuleMap、完整生成产物以及运行时配置并未在当前源码中全部展开。

第三步：真正操作 UI 前切到 Android 主线程

// RouterModule.kt：openURL 的关键实现
Handler(Looper.getMainLooper()).post {
    val context = ActivityStack.getTopActivity() ?: BaseApplication.get()
    ZRouter.open(context, url, true)
}

方法从 RN 被调用，不意味着它天然处于主线程。这段代码显式把 Android 路由操作投递到主线程。还要看到一个重要的业务边界：openURL 返回，不等于目标 Activity 已经启动或页面已经显示。如果业务需要知道真正完成结果，应增加明确的回执，而不是猜测 void 方法已经做完所有异步操作。

13 · 项目例子二：RN 图片组件怎样变成原生 View？

Native Module 解决“调用一个能力”；Native Component 解决“把一个原生 UI 控件放进 RN 页面”。项目的 ZRNImageViewV2 就属于后者。

ZRNImageViewV2NativeComponent.ts
  → 声明 src / resizeMode / filter 等属性
  → codegenNativeComponent('ZRNImageViewV2')

ReactEntryPackage.createViewManagers()
  → ZRNImageViewManager2
  → createViewInstance() 创建 ZRNImageView
  → setSrc() / setResizeMode() / setFilter()
  → ZRNImageView（继承 ZHDraweeView）
  → Fresco 图片管线与 Android View 绘制

属性更新不是“重新加载一整个 RN 页面”

JS 改变图片的 src，渲染器得到属性差异后，原生适配层把新值交给 ViewManager。项目的 setSrc 最终调用 setRetainImageUri，由 ZRNImageView 使用 Fresco 设置图片数据源。JS 决定显示哪张图，原生图片系统负责获取、解码和显示。

// ZRNImageViewManager2.java：摘录
protected ZRNImageView createViewInstance(ThemedReactContext context) {
    return new ZRNImageView(context);
}

@ReactProp(name = "src")
public void setSrc(ZRNImageView view, String sources) {
    if (sources == null || sources.isEmpty()) {
        view.setImageURI((String) null);
    } else {
        view.setRetainImageUri(sources);
    }
}

上面省略了注解、可见性修饰的非关键细节与其他方法，保留创建和属性更新的实际逻辑。

管理器同时有 @ReactProp 和生成的 ZRNImageViewV2ManagerDelegate / Interface。这种适配可以服务不同架构路径；它不是“组件只要有 Codegen，就不再使用 ViewManager”。原生控件依然要处理属性重置、布局、资源释放、异常 URL 和复用等 Android 问题。

业务 PinIndex.tsx 确实导入了 NativeImage，但该包装来自缺失的 @kfe/prn-rct-components。因此目前不能把这个导入自动等同于 ZRNImageViewV2，也不能据此证明 VipPin 当前一定走这个管理器。

检查一个 RN 自定义 View 的最短路径：JS 组件名 → 原生注册名 → ViewManager → createViewInstance → 属性 setter → 真实 Android View。如果缺的是布局，继续看 Shadow Node / measure；如果缺的是回调，继续查原生事件定义和 JS 订阅。

14 · 项目例子三：Android 收到 MQTT，JS 怎么知道？

这个例子可以接上上一篇 MQTT 原理。网络消息先由 Android 的 MQTT 客户端接收，再通过 RN 的原生事件机制通知 JS。MQTT Broker 到设备的网络传输，与设备内 Android 到 JS 的事件传递，是两段不同的链路。

JS useMqtt.start({ topic, onMessage })
  → ZMqtt.startListening(topic)【JS 导出封装缺失】
  → NativeZMqtt 契约 / MqttModule
  → Android MQTT 客户端 subscribe(QoS 1)

网络消息到达 Android
  → MQTTTopicListener.onMessageArrived(...)
  → reactContext.emitDeviceEvent("MqttMsg_主题", data)
  → NativeEventEmitter 中的匹配监听
  → JS onMessage 回调
  → 如回调更新 state，再进入 React 渲染流程

原生发出的事件里装了什么？

// MqttModule.kt：摘录
reactContext.emitDeviceEvent("MqttMsg_${message.topic}",
    Arguments.createMap().apply {
        putString("topic", message.topic)
        putInt("messageId", message.id)
        putString("response", (message.content as? String)
            ?: JsonUtils.toJsonString(message.content))
    })

这里明确把 topic、messageId 和 response 放入跨语言参数。response 被转成字符串是这个模块自己选择的数据契约，不应该扩大成“所有 RN 通信都必须把内容变成 JSON 字符串”。

JS 监听和清理

useMqtt.ts 用 NativeEventEmitter 监听 MqttMsg_${topic}，保存订阅对象；停止时调用 remove() 和 ZMqtt.stopListening(...)，卸载时通过清理函数收尾。原生 MqttModule 还按 topic 保存计数，协调订阅者数量。

0.72 的 NativeEventEmitter 底层使用全局 RCTDeviceEventEmitter 分发；在 Android 上可以不传原生模块对象，iOS 则有不同的构造约束。不能从 Hook 中某条“是否需要 TurboModule”的旧注释直接推断当前架构。

读这段代码时要留意的边界

  • JS Runtime 未就绪、监听尚未注册、页面已卸载时，事件不自动变成可靠持久队列。
  • 当前 Hook 先调用原生 startListening，再添加 JS listener；若原生可能立刻回放缓存，要审查这个间隙。这里是潜在时序边界，本文未做复现实验。
  • 多次调用 start、切换 topic、旧回调闭包和原生引用计数，都需要按使用方式核对；不能只见到 cleanup 就断言所有情况都安全。
  • MQTT 层 QoS 1 不直接保证 JS 的业务回调执行完毕。需要端到端业务可靠性，应另加持久化、结果确认或状态恢复。

当前能证明该 Hook 和原生适配都存在；限定的业务搜索没有找到这个 Hook 的直接调用点，所以不声称某个在线页面正在使用它。

15 · 触摸、手势和动画：为什么 JS 卡住了，有时还能滚动？

普通 React 交互仍然从 Android 输入开始。对典型 Paper 触摸路径，可沿 ReactRootView、JSTouchDispatcher、EventDispatcher 和 JS 事件处理往下看，最终才到 onPress 等业务回调。JSX 的 onPress 不是直接设置一个业务 Kotlin OnClickListener 那么简单。

连续触摸、滚动事件可能采用合并等策略，避免每一个中间事件都引起独立处理。业务如果依赖每个物理 MOVE 都逐个到达 JS，往往会建立错误的假设。

原生滚动和 JS 响应可以分开。ScrollView 自己有原生滚动能力；JS 被长任务堵住时，它仍可能继续滚动，但 JS 驱动的加载、交互反馈或列表窗口更新可能迟到。

Animated 与 Reanimated

RN 的 Animated 在支持的属性和动画形式上可使用 native driver，把动画描述交给原生，使播放不需要每帧经过 JS。不是所有布局属性都支持，也不能把“用了 Animated”自动等同于已启用 native driver。

项目声明了 react-native-reanimated 3.6.3 与 react-native-gesture-handler 2.14.1。PinIndex.tsx 中实际使用了 useSharedValue 和 useAnimatedStyle。Reanimated 可把特定 worklet 放进 UI Runtime 执行，减少主 JS Runtime 的每帧参与。

但不是整个 React 组件因此迁到 UI Runtime：普通 state、effect 和业务函数仍有各自执行位置；跨 Runtime 回调、捕获的数据、同步调用和原生 UI 压力仍有成本。Reanimated 是库提供的能力，也不能当成 Fabric 已启用的证明。

16 · 混合页面的生命周期：React 挂载不等于页面可见

Android 开发中你会区分 Activity、Fragment 和 Fragment View 的生命周期。混合 RN 页面还要加入 React 组件挂载、RN Root、JS Runtime 和原生业务监听的生命周期。

  • 组件挂载 / 卸载：由 React 树决定，影响 effect 和组件局部状态。
  • 页面显示 / 隐藏：可能由原生导航、BottomSheet、View attach 或自定义容器决定。
  • Runtime 存活：可能跨多个页面共享，不应因一个卡片销毁就盲目销毁全局引擎。
  • 原生资源存活：网络订阅、播放器、View 监听、Activity 引用要按实际所有者释放。

项目已经有自己的“页面生命周期协议”

BaseReactView 通过 Provider 暴露 callJS、addJSEventHandler 和 release。ViewLifecycleEventHandler 注册名为 getPageLifecycleStatus 的 JS 事件，保存回调并根据 View attach / detach 和显式触发发送 show / hide。

这说明方法名虽然像“同步获取状态”，实际是一种持续监听；应该读实现，而不是根据名字猜返回值。View 可见性与页面业务可见性也不总完全一致，复杂嵌套场景要依赖容器约定。

评论仓库是一个混合页面的实例

vip_rn_comment 的 generateReactPageArgs 把 bundleName、componentName 和 launchOptions 放进 Android Bundle；VIP 场景选择 pikachu，另一个宿主分支选择 sylas。VipRNCommentFragment 继承 BaseReactPageFragment，注册 bottomsheet/dragEnable、bottomsheet/close、comment/notify 等处理器。

它把 JS 请求转成原生 BottomSheet 行为，也把评论变化转成 Android 的业务事件。这些 JSEventHandler 是团队封装的端能力接口，不能与 RN 内置的 NativeEventEmitter 直接画等号；当前缺失的 Provider 实现决定它最终怎样传递。

维护这类页面时，先画清楚“谁拥有资源”：Fragment View 销毁要清什么，React 卸载要清什么，共享 Runtime 退出才清什么。常见泄漏来自持有 Activity 的模块、未移除监听、未取消任务，以及 JS/Java/C++ 跨语言引用没有一起断开。

17 · 从你写过的业务入手：缓存、state、列表更新

项目的 VipPin 适合把“会写功能”连接到“理解执行成本”。它读取初始参数，用 MMKV 包装获取预加载数据，再把数据放进 React state，使用多种 Hook 和动画能力构建页面。

// PinIndex.tsx：实际片段，省略周边逻辑
const store = useMMKVStore({id: 'com.zhvip.preload.pin'})
const getStore = useCallback((): PageDataType | null => {
  const data = store.getString(`pin_${pinId}`)
  if (data) {
    return camelizeKeys(safeJSONParse(data) || {}) as PageDataType
  }
  return {}
}, [store, pinId])

const [pageData, setPageData] = useState<PageDataType>(getStore() || {})

这段说明：进入 React 的首屏数据不一定要等网络；它可以先读本地准备的数据。getStore 本身还包含字符串读取、JSON 解析和键名转换，成本要算在实际执行线程上。

一个很容易忽略的 JS 语义

useState(getStore() || {}) 中的 getStore() 是普通函数调用，所以每次组件函数执行都会先计算这个表达式；React 只在首次挂载时使用该初始状态值。它不同于 useState(() => getStore() || {}) 的惰性初始化。

这不是在宣称当前页面已经发生性能故障，也不是建议不看语义就替换代码。惰性初始化同样不负责后续 pinId 改变时的重置，后者需要明确的状态更新策略。这里只是说明：理解 Hook 的执行规则，比到处添加 memo 更有价值。

不要看到 MMKV 就倒推整个新架构

项目直接声明 react-native-mmkv 3.2.0，业务调用却来自 @kfe/prn-utils 的 useMMKVStore。包装实现缺失，不能确认它具体绑定了哪个模块、是否经过项目补丁，以及与最终原生版本的兼容性。它是应该核对的依赖边界，不是启用 Fabric 的证明。

FlatList 为什么也会卡？

FlatList / VirtualizedList 通过窗口化减少同时活跃的条目，不代表它等于 RecyclerView 的全部复用模型，也不保证大列表永不卡。重点检查：稳定业务 key、条目渲染成本、props 引用稳定性、列表窗口参数、图片尺寸与缓存、状态更新范围，以及滚动时是否把大量事件回传 JS。

React.memo 主要在 props 比较满足条件时避免父级带来的重复渲染；组件自身 state 和使用的 context 变化仍可能触发渲染。useCallback 如果缺依赖，会稳定地保存一个读取旧值的闭包。性能优化必须同时保证语义正确。

18 · Bundle 发布和原生版本：为什么改 JS 也可能白屏？

混合 RN App 至少存在两类产物：安装包中的原生能力与引擎，以及被加载的 JS / 字节码 Bundle 和资源。它们需要兼容，不能把“JS 可以独立发版”理解成“JS 可以随意调用尚不存在的原生功能”。

新 Bundle 调用 NativeNewFeature.doWork()
                 ↓
旧 APK 未注册 NativeNewFeature
                 ↓
模块不存在 / 方法缺失 / 参数不兼容
                 ↓
初始化失败、红屏或白屏

项目的 T_VipReactNative 同时给出资产 Bundle 和远程 Bundle 配置；BaseReactView.load(minBundleVersion) 有最低 Bundle 版本参数。这证明项目设计了多种 Bundle 来源和版本约束入口，不能据此证明已实现签名校验、完整灰度、自动回滚、原子切换或某种差分包算法，这些要读 prnkit / 发布平台实现才能确认。

工程上通常需要考虑原生能力版本、JS Bundle 版本、组件注册名、资源可用性、Hermes 字节码兼容性、加载失败兜底，以及 JS 错误对应的准确 source map。source map 必须与实际发布的 Bundle 匹配，否则堆栈还原可能误导排查。

Runtime 预热可减少后续等待，但也占内存并可能竞争启动 CPU；复用 Runtime 可节省资源，却要求控制全局状态、事件监听和页面隔离。本文没有足够证据断言项目实际使用“一个 Bundle 一个 Runtime”或“所有页面共用一个 Runtime”。

现象先查什么下一步证据

怎样确认当前页面实际启用了什么？

  1. 先看宿主最终 Gradle 属性和 BuildConfig，而不是某个独立模块的默认文件。
  2. 读真正创建 Runtime、ReactContext 和根 Surface 的代码，确认根节点走哪条渲染路径。
  3. 在测试构建中记录引擎、RN$Bridgeless、__turboModuleProxy、Fabric 相关标识等诊断信息；这些属于内部诊断线索，不能单独作为稳定业务 API。
  4. 通过原生调用栈或渲染日志确认对应页面；例如只看到 nativeFabricUIManager 存在，仍不足以证明所有根都使用 Fabric。
  5. 核对线上 APK 与本地构建是否同一套二进制和配置，不用本地默认值替代线上结论。

性能比较尽量使用 Release 或接近发布的构建，保留相同设备、数据规模和页面状态。开发工具、日志和调试模式会改变成本。尤其传统 Remote JS Debugging 可能把 JS 执行搬到电脑上的引擎，不能直接用那个性能结果代表设备上的 Hermes。

React Native 不是“能跑起来就只剩前端问题”。你已有的 Android 排查能力仍然有用，只是需要再补上 JS、React 调度和跨语言边界。

20 · 推荐学习顺序，以及面试时怎么讲

按一条链学，不按一堆名词背

  1. 先补前端基础：从React 与前端基础理解模块、类型、JSX、闭包、异步和数据流，能逐句读懂 NameCard 示例。
  2. 再理解 React：用一个计数器解释 state 快照、组件重新执行、effect 清理和 key。
  3. 接着理解宿主：从 Activity / FrameLayout 到 Runtime、Bundle、AppRegistry 和 Root。
  4. 掌握旧架构：能讲出 MessageQueue、模块调用、Yoga 和主线程 View 更新。
  5. 比较新架构：分别解释 JSI、TurboModule、Fabric、Codegen；说明为什么不等于 Bridgeless。
  6. 回到项目：分别跟读 RouterModule、ZRNImageView 和 MQTT 事件三种接入。
  7. 做一次实际诊断：区分 JS 卡顿和 UI 卡顿，记录自己验证到的事实。

一段适合当前经验的回答

我主要做 Android，RN 写过一些业务功能。我的理解是，React 在 JS 引擎中根据 props 和 state 计算 UI，RN 再把结果交给原生渲染系统，最终仍是 Android View。旧架构常见路径通过 Bridge 批量传递 UI 和模块调用，Android 侧用 Shadow Node、Yoga 和 View 操作队列完成布局更新。新架构中 Fabric 把更多渲染逻辑放到 C++ Shadow Tree，JSI 提供 JS 和 C++ 的接口，TurboModule 负责原生模块接入，Codegen 根据类型规格生成绑定。我们当前源码基准是 RN 0.72.10，但不能仅凭代码里使用 TurboModuleRegistry 就认定全量启用了新架构。我结合项目读过 JS 路由到 RouterModule、图片 ViewManager 和原生事件回 JS 的链路；具体个人参与的功能和优化结果，以实际负责内容为准。

追问：RN 为什么不是 WebView？

常规 RN 核心组件由原生宿主 View 显示，没有浏览器 DOM 和完整 CSS 渲染链。应用当然可以嵌入 WebView，但那是一个特定组件，不代表整个 RN 页面都运行在 WebView 中。

追问：React render 是不是等于 Android draw？

不是。React render 是计算下一版组件结果，之后还有协调、提交、布局和挂载。Android View 的 draw 才是宿主绘制阶段的一部分。组件函数调用了很多次，也不表示每次都重建或重绘了全部原生 View。

追问：旧架构也能用 JSI 和 Hermes 吗？

可以。Hermes 是执行引擎，JSI 是 C++ 运行时接口。0.72 的 JSIExecutor 同时使用 JSI 和旧的 BatchedBridge。是否 Bridgeless、是否 Fabric、是否 TurboModule 不能仅看其中一个名字。

追问：Fabric 为什么使用不可变 Shadow Tree？

便于持有一致的树快照，支持线程安全的读取、克隆和提交；更新可以共享未变化子树。它不是简单把整棵树复制一遍，也不是把所有工作都扔到后台线程。

追问：JS 调了原生方法，原生操作就完成了吗？

要看方法契约和实现。项目 RouterModule.openURL 只是把操作 post 到主线程，void 返回不证明页面打开完成；需要实际执行结果就提供明确回执。Promise 同样要看在哪个阶段 resolve。

追问：升级到新架构能解决所有卡顿吗？

不能。它改变通信和渲染基础，但业务计算、列表刷新范围、图片、主线程 IO 和生命周期问题仍然存在。应先用性能数据定位瓶颈，再判断升级或局部优化能解决哪一段。
