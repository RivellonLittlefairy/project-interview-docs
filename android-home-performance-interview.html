首页性能优化：做过哪些尝试，面试怎么说

这篇整理了首页优化里能讲清楚的六件事，后面附源码和提交记录。主要看盐言 Android 首页，也补充了知识市场首页的做法。哪些现在还在用、哪些只在历史分支里，都有说明。源码核对日期：2026-10-13。

01 · 面试先记这六点

面试时可以先说遇到了什么问题，再讲改了哪里、为什么这样改、有没有副作用，最后说怎么验证。下面按项目里的做法来讲；你实际做过的部分，再换成“我做了”。

重点怎么讲代码里做了什么
不需要的就别做启动时先删掉用不上的工作，少做一点，用户就少等一点。以前给 Launcher 加过 isFinishing 判断：启动页已经结束，就跳过它的布局。当前代码里已经没有这层判断。
不着急的晚点做先让首页内容出来，再处理红点、阅读浮层和弹窗。历史分支把这些 Observer 分别延迟 300 / 500 / 800ms 注册。开关关闭时还是立即注册。
复杂卡片提前准备有些卡片创建起来比较慢，就提前准备几个，用的时候直接拿。用 IdleHandler 提前创建 HybridCard；用异步 inflate 准备心理测评和精品课布局；也会提前往池里放 ViewHolder。
相同的东西别反复设置ViewHolder 虽然能复用，每次 bind 还是可能做很多重复工作。图片 URL 没变就不重建 controller；子 View 找到后存起来；圆角没变就不再设置。
滑动时少做重活用户正在滑列表时，尽量少做分页和图片加载，让主线程有时间画下一帧。停止滚动、离末尾不超过 3 项时才加载下一页。Android 10 以下滑动时暂停 Fresco pipeline，停下来再恢复。
加载时间要算对先分清页面真的变快了，还是计时方法变了。用户切走首页就取消这次统计；冷启动广告期间取消计时，广告结束再重新开始。

60～90 秒口述稿

项目里主要做过两类优化：一类是让首页早点出来，另一类是让列表滑起来更顺。启动时，曾经尝试跳过已经结束的启动页布局，也尝试把红点、阅读浮层、弹窗这些不着急的东西晚一点初始化。列表里，有些卡片创建比较慢，就提前准备几个，使用时直接拿；每次绑定数据时，图片没变就不重建 controller，圆角没变就不重新设置，子 View 也不用反复找。用户正在滑列表时，还会少做分页和部分图片加载。加载时间也单独修过：用户已经离开首页，就取消这次统计；广告时间另做处理。具体快了多少，需要拿同样场景、同样计时方法的真机测试和线上数据来比较。

可以按这个顺序记：不需要的别做，不着急的晚做，复杂的提前准备，相同的别重复设置，滑动时少做重活，最后把时间算对。

02 · 查了哪些代码，哪些结论还没确认

主要查了盐言 Android 的 VipHome 和 km_home_base，也查了 KnowledgeMarket/kmarket-home。它们对应的页面和版本不完全一样，所以每种做法都会写清楚来自哪里，不能直接说某个线上版本同时用了全部方案。

仓库 / 当前提交找到了什么需要说明的地方
VipHome · ccbb5206以前尝试跳过无用的启动布局；现在还能看到提前创建布局和修改加载计时的代码。当前已经没有那层 isFinishing 判断。提前创建布局是否执行，还要看开关和执行时机。
km_home_base · 17a8fc74过滤重复刷新、网络优先的缓存、榜单滑动调整，以及 WebView 预加载尝试。当前分支是 feat_time_reward。以前的 vip_km_home 模块已经不在当前源码里。
KnowledgeMarket · 77f150529c异步创建布局、提前准备 Hybrid / ViewHolder、减少重复设置，以及调整滚动时的工作。这些来自知识市场首页，不能据此认定盐言当前线上也用了同一套卡片。

这些结论是在 2026-10-13 根据本地源码和 Git 历史整理的。本次没有真机性能 trace、线上看板、AB 实验结果或完整发版记录。代码能说明项目做过什么；是谁负责、有没有上线、上线后快了多少，还需要你自己的经历和记录来补充。

03 · 启动：少做无用的事，不着急的晚点做

3.1 启动页都结束了，就别再创建它的布局

VipHome / 3fe20c10（2024-03-20，“提交首页启动优化”）给 setContentView 加了 !isFinishing() 判断，也给动画 View 加了空判断。意思很直接：前面的代码如果已经 finish 了这个 Activity，后面就不用再创建它的布局和动画 View，省掉这部分时间。

这个做法现在只适合作为历史尝试来讲。当前 LauncherActivity 还留着原来的注释，但第 208 行 setContentView 外已经没有 isFinishing 判断了。看代码时要把注释和实际执行的逻辑分开。

同一个提交还换了提前创建的布局，并注释掉 ZPatch.preInit() 和 ZPatch.onColdLaunch()。这确实减少了调用，但也可能影响补丁功能。讲这部分时，需要同时说明少做了什么、功能有没有受到影响。

3.2 布局先准备好，首页创建时再拿来用

T_LayoutPreInflate 会提前准备系统栏、主容器和 VIP 首页的布局，结果放在 preInflater 里。之后 MainDelegation.attachBaseContext() 取出它，用它包装 Context。准备布局和使用结果的两端都能找到；这次没有继续查缓存内部，也没有测实际拿到缓存的次数。

postinfl 默认是 true。当前 T_LayoutPreInflate.onRun() 在开关为 false 时直接创建布局；为 true 时，交给 T_LaunchComplete 通过 RulerScheduler.runUrgent 调用。如果执行时顶部已经是 MainActivity，就直接跳过。所以这段代码是否帮上忙，要看它有没有赶在首页创建之前执行。这里用到的调度方式也要单独看，不能统称为 IdleHandler 异步 inflate。

3.3 历史分支试过：红点、浮层和弹窗晚点初始化

km_home_base / ae4358ac（作者日期 2025-10-13，“优化首页启动加载”；提交时间 2025-10-15）改的是历史文件 vip_km_home/.../VipKmHomeFragment.kt。vip_home_tab_improve 开启时，用 root.postDelayed 延迟注册 Observer；关闭时就立即执行。

延迟晚点做什么为什么晚点做
300ms消息红点、TTS 阅读信息、上次阅读进度的 Observer这些回调和浮层处理不用全挤在首页刚初始化的时候。
500ms通用弹窗、发布入口、订阅入口等 Observer先把首页准备好，再处理这些附加功能。
800ms分享恢复跳转、关注红点、协议更新等 Observer把工作再往后分散一些。分享跳转和协议更新能不能等，要按实际业务确认。

本地只有 refs/remotes/realOrigin/bugfix/foldable-kingkong-width 包含这个提交，当前 HEAD 不包含，当前源码里也没有这个模块。它说明有人在历史分支里试过，不能当作当前版本正在用的方案。

面试可能会问：延迟 300ms 就保证首页画完了吗？没有。它只是晚一点排到主线程执行，任务本身还是占主线程。viewLifecycleOwner 能在 View 销毁时移除已经注册的 Observer，但不会替你取消还没执行的 Runnable。因此要检查页面销毁、View 重建、重复注册，以及用户提前点击时会发生什么。要继续改进，可以根据首页真正显示完成的信号来安排任务，同时检查生命周期，并限制每个任务的耗时；这部分是建议，本次没有确认项目已经这样做。

04 · 复杂卡片提前准备，用的时候直接拿

4.1 提前准备 HybridCard 和两种复杂布局

KnowledgeMarket / 47629ee019（2022-10-13，“HybridCard预加载 & 异步加载复杂布局”）做了这件事：ContentMarketHomeFragment.setupViews 调用 HomePreloadUtils.preload，提前准备 1 个 HybridCard，以及心理测评、精品课各 2 个 View。HybridCard 等调用线程的消息队列空闲时再创建，两种 View 用 AsyncLayoutInflater 异步创建，最后都放进软引用缓存。

PsychAssessmentAdapter 和 TopCourseAdapter 创建条目时先取缓存，没有就正常 inflate。HybridCard 也是一样，取不到就现场创建。obtainCached* 取的时候会把这一项从缓存里 remove 掉，所以这里是提前备几个，用完就没了，并不会无限保留或反复借还。

提前加载 URL 还有额外条件：kmarket_home_preload_url 默认 false，开关打开且设备被判定为慢设备时，才通过一次性 IdleHandler 调用 hybridCard.load(url)。绑定卡片时会对比 View tag 里的 URL，相同就不再 load 一遍。

这些缓存 View 还没加入页面，切换日夜主题时不会跟着页面自动更新，所以代码会主动给它们切主题。页面销毁时会调用 release 清空池。软引用可能被 GC 清掉，实际有多少次能拿到缓存还要测。也要检查异步创建完成得太晚、Context 一直被持有、主题切换和额外内存占用的问题。AsyncLayoutInflater 对布局有要求：控件要能在后台构造，不能随意在后台操作 View；遇到不支持的情况，创建工作可能回到主线程。

4.2 提前创建 ViewHolder，放进 RecyclerView 的池里

ContentMarketHomeFragment.tryPreloadViewHolder() 会先看列表数据里有没有对应类型。FCT01C / FCT14A 有数据时，在一次性空闲任务里提前创建；FCT03C / FCT03D 则把池容量设为 10。

源码：yyyyy-cdoe/KnowledgeMarket/kmarket-home/src/main/java/com/zhihu/android/app/market/newhome/ui/fragment/ContentMarketHomeFragment.kt · 1115 至 1131 行。

ContentMarketHomeFragment.kt
    private fun prefetchViewHolder(pair: Pair<Int, Int>) {
        //往 recycledViewPool 里预先创建一个 ViewHolder。
        val createViewHolder = listAdapter.createViewHolder(
            myRecyclerView,
            pair.second
        )
        //绑定一次 ViewHolder
        listAdapter.bindViewHolder(createViewHolder, pair.first)
        //设置进 recycledViewPool 里
        myRecyclerView.recycledViewPool.putRecycledView(
            createViewHolder
        )
    }

    private fun setViewHolderMaxSize(pair: Pair<Int, Int>, maxSize: Int) {
        myRecyclerView.recycledViewPool.setMaxRecycledViews(pair.second, maxSize)
    }

可以这样讲：第一次滑到复杂卡片时，要创建 View、初始化控件，可能一下子做了很多事。提前准备几个，就能把一部分工作挪到前面空闲的时候。之后 RecyclerView 从池里拿 ViewHolder，仍可能重新 bind 数据；省掉创建不代表连绑定都省了。

这里还提前 bind 了一次，所以可能触发图片请求、监听或埋点。要确认卡片还没显示时不会上报曝光。池子变大也会多占内存。另外，这里的 IdleHandler 仍在主线程执行，任务太长一样会卡住界面。

05 · 绑定数据时，相同的东西别反复设置

KnowledgeMarket / 258977d9e4（2023-05-16，“优化首页滑动卡顿”）主要改了每次绑定数据时重复做的事。下面这些改动在当前源码里还能找到：

位置之前后来怎么改
TopListVH.onBindData每次绑定都新建 Fresco controller。记住 lastImageUrl，URL 变化才重建。
TopListVH.adjustItemView反复 findViewById 找标题、副标题、底部文案等。找到子 View 后按位置存起来；alpha 颜色值用 lazy，取过一次就保留。
FCT01CVHTitleView.setData每次 removeAllViews，再逐个 addView。先 getChildAt(index) 拿已有的子 View，缺少才创建；部分 dp 转换结果也存起来。
KmListCommonIconView.setData每次都设置 elevation、背景和图片圆角 hierarchy。固定样式放在 init 设置；圆角、边框宽度和颜色没变，就不再更新。

复用 ViewHolder 后，每次出现或数据更新时还是可能执行 bind。如果这里总在新建对象、查找子 View、改样式、增删 View，主线程仍然很忙，还可能触发重新布局和绘制。所以这次优化又把 bind 里面重复的工作减少了一些。60Hz 下，一帧大约只有 16.7ms；120Hz 下约 8.3ms。平均耗时低也不代表不卡，还要看有没有某一帧特别慢。

少做重复设置时，也要检查显示有没有出错。比如先显示图片 A，再绑定空图片，最后又绑定 A，图片能不能重新显示？复用子 View 后，数据数量变少，多出来的旧 View 会不会还在？主题颜色用 lazy 保存以后，切换日夜模式会不会拿到旧颜色？这些都要验证，不能看到少调用了几个方法就认定没有问题。

06 · 用户滑列表时，少做分页和图片加载

ContentMarketHomeFragment 的 scrollListener 控制了分页请求和图片加载的时机：

列表停下来、离末尾不超过 3 项时，才请求下一页。这样可以少一些“用户还在滑，接口又回来了，主线程还要更新列表”的情况。Android 10 以下还会在滚动时暂停 Fresco pipeline，停止后再恢复。这个暂停有作用范围：它不会让下载、解码、绘制全部自动变成后台任务，也不保证已经开始的工作立刻停下。

这样做也可能让用户更晚拿到下一页，尤其是快速滑到底部的时候。Fresco pipeline 可能被其他页面共用，离开当前页面时要检查有没有恢复。验证时既要看滑动有没有掉帧，也要看用户滑到底后是不是等得更久。

榜单还调过：甩动、吸附和内外层滑动

km_home_base / c48734a4（2025-12-17）先让内层 RecyclerView.fling 返回 false，关掉默认的惯性滑动。56f4b9ce（2025-12-25）又改成把速度限制在 ±3000，再调用 super.fling。同时用 PagerSnapHelper 向左侧吸附，开启内层嵌套滚动，并允许用户滑动榜单 ViewPager2。当前代码还把榜单页的 itemAnimator 设为空。

这组改动主要是在调手感：先试着关掉惯性，后来又恢复惯性并限速，再配合吸附和内外层滑动。列表滑到边界后能不能正确切换，需要真机操作确认。提交叫“滑动优化”，并不直接说明掉帧少了；关掉 fling 也不是所有列表都适合的做法。

07 · 数据提前拿，重复请求少发，缓存看清楚

7.1 数据可以提前请求，页面晚点再显示

KnowledgeMarket / bc620cc61e（2022-11-20）的提交说明是“会员首页 tab 初始化改为页面展现时，接口请求改为预加载”。当前 MarketHomeMultiTabFragment 会先返回一个简单容器，再用 AsyncLayoutInflater 创建真正的布局。需要操作控件的代码通过 onLazyAsyncReady 等布局准备好再执行；事件订阅绑定 viewLifecycleOwner。

prefetchHomeModulesInfoListData() 在空闲任务里调用 ViewModel 发请求，结果放在 prefetchHomeModules。这样数据可以先准备，UI 另选时机显示。要检查提前请求的数据有没有被用到、什么时候作废、登录态和请求参数有没有变化，以及异步回调回来时还是不是原来的 View。

VipHome 里还有 MainDelegateAction → FeedRequestAdvanceInterface 这个提前请求推荐数据的入口。它调用的是 Feed 接口；本次没有确认盐言 HomePinTab 是否用了这个入口，所以这里只作为另一个发现记录下来。

7.2 短时间重复刷新时，跳过一部分请求

场景怎么改为什么这样算
MainActivity onPause，或从底部首页切到其他 Tabcancel YanHomeLoadProcessFirst / YanHomeLoadProcess，并记录中断点。用户已经离开首页，之后等回包的时间就不再算进正常首页加载。取消了多少次也要单独统计，才能看出有没有大量失败或中断。

10 · 常见追问与结果怎么讲

为什么不用全部异步化？

不少 View 操作要在主线程做，异步创建布局也要看控件是否支持。首屏马上要用的东西，不能一直往后拖。可以先判断这件事有没有必要、是不是重复做、首屏要不要马上用，再决定删掉、缓存、放后台计算，还是晚一点执行。

IdleHandler 和 postDelayed 区别是什么？

IdleHandler 是等消息队列空闲时执行；postDelayed 是等延迟到期后再排队。它们都不保证到点立刻执行，也不会自动切到后台线程。放进去的任务要小，页面不用了能取消，准备好的缓存拿不到时也要能正常创建。

缓存多一点是不是更快？

缓存会多占内存，也可能增加 GC，所以要看准备的东西有多少次真的被用到。项目里 Hybrid 只准备 1 个，两种复杂布局各 2 个，部分 Holder 池容量是 10。合适的数量要结合设备和卡片类型来测，也要检查创建耗时和页面销毁后能不能释放。

你怎么确认性能变好了？

本文没有实测结果。实际做的时候，可以用 Perfetto / 主线程 trace 看 inflate、bind、布局和长任务分别花了多久，再重复同样的场景比较。除了首页出现的时间和掉帧，也看滑到底要等多久、最高内存占用和提前准备的缓存有多少次被用到。最后用线上分组数据核对。讲结果时要分清：只是晚点做了，确实少做了，还是仅仅换了统计范围。

用 STAR 讲自己做过的部分

S 可以说首页里卡片类型多，启动和滚动时容易集中创建、重复绑定，加载时间也曾有统计不一致的问题。T 说你实际负责哪一段，比如榜单卡片或启动统计。A 从本文选 2～3 个你做过的改动，讲清楚改前和改后，以及有什么副作用。R 填真实验证结果：哪台设备、哪个包、什么场景、测了多少次、怎么计时、改前和改后分别是多少。没有数值时，就讲实际验证过的行为，不编百分比。

如果只剩两分钟准备，先看第 1 节的口述稿，再选重复绑定、提前准备 ViewHolder、加载计时这三个例子。延迟注册 Observer 那部分来自历史分支；你确实参与过，或者明确是在讨论历史方案时，再拿来讲。
