DevKit 魔改 MVI × Paging3

从框架实现到盐言项目落地：状态如何流动、分页怎样触发、多类型列表如何渲染，以及新页面应该照着哪一套写。

Mavericks 3.0.6 Paging Runtime 3.2.0 Kotlin 1.7.20 Coroutines 1.6.4 盐言 / Knowledge Market

结论先行

DevKit 不是从零实现的 Redux 式 MVI，而是把 Mavericks、Paging3、RecyclerView 多类型列表、ViewHolder 生命周期和轻量注入拼成了一条更适合知乎 Android 组件化业务的开发链。

Mvx

用 MvxState / MvxViewModel / MvxView 包住 Mavericks，并补齐 RxJava、LifecycleViewModel 与列表收集扩展。

Paging3

Pager 缓存流，ResponsePagingSource 统一 Retrofit 响应，PagingFlow 负责分页数据变换。

1 Adapter

SuperAdapter 按数据运行时类型分发不同 ViewHolder，同时承接注入、生命周期与默认加载状态。

对“魔改 MVI”的准确理解：State 是单一 UI 状态源，ViewModel 通过 reducer 更新 State，View 订阅 State；但业务动作通常直接调用 ViewModel 方法，并没有统一的 Intent/Action/Reducer 类型层。因此它是“基于 Mavericks 的轻量 MVI”，不是严格 Redux。
  • 盐言最完整的端到端案例是 HomePinTabFragment + HomePinTabViewModel。
  • 最精炼、最适合作为新页面参考的是 NativeManuscriptAuthorFragment + ManuscriptBillboardViewModel。
  • 盐言当前没有使用 MvxRepository；网络分页逻辑通常直接放在 ViewModel 内部的 PagingSource 中。
  • LiteKnowledgeMarket 的 BasePagingFragment 属于旧分页体系，不应和 DevKit/Paging3 混为一谈。

整体架构

一次列表刷新从 View 发起，穿过 ViewModel 和 PagingSource，最终以新的 PagingData generation 回到 State，再由 SuperAdapter 提交给 AsyncPagingDataDiffer。

View / Fragment调用 refresh()、订阅 State、监听 LoadState。
MvxViewModel持有 Pager；用 setState / setOnEach 更新不可变 State。
Pager包装 AndroidX Pager，并在 viewModelScope 中 cachedIn。
PagingSource把 Refresh / Append / Prepend 映射为 Retrofit 请求和 prev/next key。
PagingData通过 map/filter/combine/mediator 做惰性分页变换。
SuperAdapter按数据 Class 选择 ViewHolder，Differ 驱动 RecyclerView 更新。
状态环路：网络列表数据不落成普通 List 再塞进 State，而是让 State 持有 PagingData<T>。加载进度和错误则走 Adapter 的 CombinedLoadStates，两者是两条并行信号。

魔改 MVI / Mvx

类型基类DevKit 增量盐言用法
MvxStateMavericksState只做语义别名，方便以后加扩展。PinTabState、BillboardState。
MvxViewModel<S>MavericksViewModel<S>委托 LifecycleViewModel；补 RxJava execute、Flow/Rx collectState；清理时发 clear event。ViewModel 直接拥有服务、Pager、PagingSource 和业务方法。
MvxViewMavericksView给 SuperAdapter 增加 State 属性收集：collectFrom / collectFromAsync。Fragment 通常让 invalidate() 保持空实现，列表由属性订阅自动提交。
MvxRepository<S>MavericksRepository<S>独立 StateStore、协程作用域、Rx execute 和生命周期清理。盐言扫描范围内未发现实际使用。

Paging3 封装

Pager：减少配置样板

com.zhihu.android.devkit.paging.Pager 包装 AndroidX Pager，默认 pageSize=15、prefetchDistance=5、关闭 placeholder，并直接在传入的 scope 上 cachedIn。每次工厂创建 PagingSource 时记录为 currentPagingSource，所以业务层可以通过 pager.invalidate() 触发新 generation。

ResponsePagingSource：统一 Retrofit 分页

子类只需实现三类请求、前后 key 和列表解析。基类负责 Retrofit 成功判断、API Error 包装以及把异常转换为 LoadResult.Error。

Paging3 LoadParamsDevKit 回调返回 key典型场景
RefreshonRefresh同时解析 prevKey 与 nextKey首次进入、下拉刷新、invalidate。
AppendonLoadMore只解析 nextKey接近列表底部时预取。
PrependonLoadBefore只解析 prevKey从中间章节打开后向上补数据。

PagingFlow：对 PagingData 内部元素做变换

mapPagingItem、flatmapPagingItem、filterPaging、header/footer/separator 插入和 combinePaging 都保留 PagingData 的惰性加载语义，避免把数据先展开成 List。

PagerMediator：对已展示分页数据做局部更新

它缓存流经的原始 item，以 changed 和 removed 集合记录变更，再用一个 MutableStateFlow 触发 PagingData 重新 map/filter。盐言用它完成删卡和点赞状态更新，不必刷新整个网络列表。

fun deleteItem(id: String) {
    pagerMediator.remove { item ->
        item is PinAllDataV2 && item.data?.businessId.toString() == id
    }
}

fun likeEvent(id: String, isVote: Boolean, likeCount: String) {
    pagerMediator.update(
        predicate = { it is PinAllDataV2 && it.data?.businessId.toString() == id },
        transform = { (it as PinAllDataV2).copy(/* 更新点赞字段 */) }
    )
}

列表、ViewHolder 与加载状态

SuperAdapter 如何支持多类型

每个数据具体 Class 的 hashCode() 被当作 viewType。registerViewHolder 建立数据类型到工厂的映射；绑定时再用 item 的运行时 Class 找工厂。因此一个 PagingData 可以混放榜单、内容卡、Banner、广告、直播间等完全不同的类型。

反射建 Holder

ViewBinding 的静态 inflate 与 Holder 的单参数构造器通过反射调用，并有 inflate Method 缓存。

轻量注入

adapter.inject(instance) 存入 SimpleInstanceContainer；Holder 内通过 by inject() 延迟读取。

Holder 生命周期

Holder 实现 LifecycleAware 后，item attach/detach 会收到独立 LifecycleOwner，适合曝光、动画和订阅。

盐言项目真实用法

案例 A：HomePinTab——完整端到端链路

1. State
PinTabState.data 保存 PagingData<BaseModulesListItemData>。
2. ViewModel
创建 Pager(viewModelScope, prefetchDistance = 5)，工厂每次返回新的内部类 DiscoverTabListDataSource。
3. Source
onRefresh 请求 offset 0；onLoadMore 用 offset + limit；resolveNextKey 在 isEnd 后返回 null；不支持向前翻页。
4. Transform
原始网络模块先映射为 moduleData，过滤允许展示的卡片类型，再绑定 PagerMediator。
5. Reduce
setOnEach { copy(data = it) } 把新的 PagingData 放回 State。
6. View
collectFrom(viewModel, PinTabState::data) 自动 submit；setupWithRecyclerView 接入默认加载状态。
业务特点：这是一个瀑布流、多卡型、动态删改 item 的复杂列表。自定义 DiffUtil 用业务 ID 判断 item，同一 Adapter 注册二十多种 Holder，并向 Holder 注入 ViewModel、父页面接口、曝光上报器和 LifecycleOwner。

案例 B：NativeManuscriptAuthor——双向目录分页

ManuscriptBillboardViewModel 内的 ManuscriptBillboardSource 同时实现 Refresh、Append、Prepend。首次请求可以围绕指定章节拼接前一页数据，让目标章节靠近第二个位置；到达顶部后把 header/author 信息写入首项。

private val pager = Pager(viewModelScope) {

init {

                    isSelected = item.id == initSectionId

            }

        .setOnEach { copy(catalogData = it) }
}

案例 C：NativeManuscriptRecommend——只借 Adapter，不做网络 Paging

该页面使用 SuperAdapter、Holder 注入和 PagingData.from(list)，但网络“加载更多”是 RecyclerView 滚动监听 + Rx 请求 + 手工缓存完成的。它展示了 DevKit 各部分可拆开使用，但不应把它当作 PagingSource 接入范例。

与旧盐言 Paging 的边界

不要混淆：KnowledgeMarket / LiteKnowledgeMarket 中大量 BasePagingFragment<ZHObjectList<...>>、旧 PagingRequestHelper 和 com.zhihu.android.api.model.Paging 是历史分页框架。只有出现 com.zhihu.android.devkit.paging 与 androidx.paging.PagingData/LoadState 的链路，才属于本文的 DevKit + Paging3。

推荐接入模板

1. State + ViewModel + PagingSource

data class StoryListState(
    val data: PagingData<StoryCard> = PagingData.empty()
) : MvxState

class StoryListViewModel(
    initialState: StoryListState
) : MvxViewModel<StoryListState>(initialState) {

    private val service = Net.createService(StoryService::class.java)

    private inner class StorySource :
        ResponsePagingSource<StoryPaging, StoryCard, StoryResponse>() {

        override suspend fun onRefresh(
            params: LoadParams<StoryPaging>
        ): Response<out StoryResponse> =
            service.firstPage(limit = params.loadSize).awaitFirst()

        override suspend fun onLoadMore(
            params: LoadParams.Append<StoryPaging>
        ): Response<out StoryResponse> =
            service.nextPage(params.key.nextUrl).awaitFirst()

        override suspend fun onLoadBefore(
            params: LoadParams.Prepend<StoryPaging>
        ): Response<out StoryResponse> {
            throw NotImplementedError("此列表不支持向前加载")
        }

        override fun resolveValue(result: StoryResponse?) =
            result?.data.orEmpty()

        override fun resolvePreKey(
            curParams: LoadParams<StoryPaging>?,
            result: StoryResponse?,
            firstValue: StoryCard?
        ): StoryPaging? = null

        override fun resolveNextKey(
            curParams: LoadParams<StoryPaging>?,
            result: StoryResponse?,
            lastValue: StoryCard?
        ): StoryPaging? = result?.paging?.takeUnless { it.isEnd }
    }

    private val pager = Pager(viewModelScope) { StorySource() }

    init {
        pager.flow.setOnEach { copy(data = it) }
    }

    fun refresh() = pager.invalidate()
}

2. Fragment + Adapter

class StoryListFragment : BaseFragment(), MvxView {
    private val viewModel: StoryListViewModel by fragmentViewModel()
    private lateinit var adapter: SuperAdapter

    override fun onViewCreated(view: View, state: Bundle?) {
        adapter = SuperAdapter(StoryDiff)
            .registerViewHolder(StoryCardVH::class.java)
            .inject(viewModel)
            .collectFrom(viewModel, StoryListState::data)
            .setupWithRecyclerView(binding.recyclerView)

        adapter.addLoadStateListener { states ->
            binding.refreshLayout.isRefreshing =
                states.refresh is LoadState.Loading

            binding.errorView.isVisible =
                states.refresh is LoadState.Error && adapter.itemCount == 0
        }

        binding.refreshLayout.setOnRefreshListener(viewModel::refresh)
    }

    override fun invalidate() = Unit
}

边界与踩坑

刷新：优先用 pager.invalidate() 还是 adapter.refresh()？

两者都会产生新的 PagingData generation，但当前盐言架构把刷新入口放在 ViewModel，所以成熟案例使用 pager.invalidate()。这样 View 不需要知道 PagingSource。adapter.refresh() 更适合纯 UI 触发且不经过 ViewModel 的页面，但会削弱单向数据流边界。

默认 getRefreshKey() 返回 null

ResponsePagingSource 没有基于 anchorPosition 恢复 key。刷新会回到业务定义的首屏语义；若页面要求保持当前位置，需要子类重写 getRefreshKey 或重新设计 key。

单向列表也必须面对 Prepend 抽象方法

ResponsePagingSource 要求实现 onLoadBefore。单向列表应让 resolvePreKey 永远返回 null，确保 Paging3 不会调用它；实现中可明确抛出“不支持”。ZHObjectPagingSource 已提供默认抛错实现。

异常捕获范围偏宽

ResponsePagingSource.load 捕获 Throwable 并转成 LoadResult.Error。这也可能包含协程取消异常，属于值得留意的实现风险：如果升级框架，建议对 CancellationException 直接重新抛出。

默认 DiffUtil 只用 equals

ObjectItemCallback 的 item 和 content 比较都是 oldItem == newItem。复杂业务必须像 HomePinTab、NativeManuscriptAuthor 一样提供稳定 ID 的自定义 Callback，否则更新动画和局部刷新可能不符合预期。

SuperAdapter 的数据类型必须是具体类

registerViewHolder 主动拒绝 primitive、interface 和 abstract class。viewType 来自具体 Class 的 hashCode，因此注册基类并不能匹配其子类；每个实际数据类都要注册，或使用拦截工厂。

ViewBinding Holder 依赖构造器约定

反射工厂要求 Holder 存在“参数类型恰好为对应 Binding 类”的公开构造器。修改为额外构造参数或抽象 Binding 类型会在运行时失败；额外依赖应通过 adapter.inject 传入。

PagerMediator 依赖 equals/hashCode 稳定

内部 HashMap/HashSet 以原始 item 为 key。优先使用不可变 data class + copy；不要在 item 加入缓存后原地修改参与 equals/hashCode 的字段。

Body 状态需连同 Header 或 Footer 使用

当前 setupWithRecyclerView 只有在 header 或 footer 启用时才创建 ConcatAdapter。若只传 bodyType、同时关闭 header/footer，body Adapter 不会挂载。默认参数启用了 header/footer，所以常规调用不受影响。

初始化由宿主任务保证

VIP 宿主通过 T_DevKitInit 在主线程调用 DevKit.init(app)，进而执行 Mavericks.initialize(DEBUG)。独立 Sample 或新宿主必须补同等初始化；旧 Mvx.initialize 已废弃。
