MVI 在这套工程里，
是怎么落地的

这不是一篇 Mavericks 教程，而是对工作区里约 7,000 个 Kotlin 文件做的一次实证扫描： MVI 的“发动机”是 Airbnb Mavericks 3.0.6，DevKit 只做了一层很薄的 Mvx 封装； 真正把它用起来的只有 6 个 VIP 业务组件，而 DevKit 的打包方式决定了这套能力如何被发布、升级和调试。

01

结论先行

先给五个判断，后面每一节都用代码和构建文件来支撑。

5 个文件

引擎不是自研的

DevKit 的 mvx 包只有 Mvx.kt、MvxState、MvxView、MvxViewModel、MvxRepository 五个文件，底层是 Mavericks 3.0.6。

4 件套

State / View / VM / Repository

再用 Pager + ResponsePagingSource + SuperAdapter 把“列表型 MVI”补齐；这是这套工程最常用的组合。

6 个业务仓

主 App 不写 Mvx

Futureve / VipAndroid 只在 app 层用 api 引入 DevKit；真正写 Mvx 的是稿件、音频、会员主页、关注、首页等 VIP 业务组件。

混合 而非纯血

状态容器 + 命令式 UI

Mavericks 管状态和 Async，列表用 Paging3；但 LiveData、RxBus、Fragment 里直接订阅依然大量存在，不能称为“纯 MVI”。

AAR + 源码

两种消费方式

默认走内网 Maven 的 com.zhihu.android.library:devkit AAR；需要改库时，用 sourcecode.properties 把 AAR 替换成本地工程。

19 个 tag

Athena 负责发布

athena.json 声明版本与发布命令，CI 机器人提交版本号并打 tag；最新是 0.0.19，但各仓版本并不齐。

一句话总结：DevKit 把 Mavericks 包装成公司内的“MVI 标准件”（状态、异步、分页、适配器、初始化、版本锁定、AAR 发布），业务按需取用；这是一次渐进式、工具化的 MVI 落地，而不是全量架构改造。

术语对齐：仓库里把 MVI 写成 Mvx（Mavericks 的缩写），包名 com.zhihu.android.devkit.mvx。本文中的“MVI / Mvx / Mavericks”指同一套东西，不表示自研框架。

03

Mavericks 的“方言”

DevKit 没有重新发明概念，而是给 Mavericks 的每个核心概念起了一个 Mvx 前缀的名字。理解这张映射表，基本就能读懂所有业务页面。

如果对照经典 MVI 的三段式 Intent → Model → View，这套实现其实做了两次“简化”：Intent 退化成 ViewModel 的公开方法（没有 sealed class、没有可枚举的事件类型），Model 就是 MvxState，View 通过 invalidate / onAsync / onEach 消费状态。好处是接入成本低、和现有 Rx/Paging 代码兼容；坏处是事件不可枚举、不可回放，复杂页面很难靠类型系统约束。

为什么这些 ViewModel 都没有写 Factory？

页面统一用 fragmentViewModel() 拿 ViewModel，没有自定义 Factory；State 大多给字段提供默认值，业务参数则在 onViewCreated 里通过普通方法补进去。这只是团队约定，不是框架强制：例如 ManuscriptState 的最后一个字段 adMemberPopupConfig 就没有默认值。

约定比机制更重要：现有代码把“参数注入”放在构造之后（initParams、setMemberToken、setScene），并假设这些 setter 在请求前被调用。好处是页面接入简单；代价是参数与请求的时序靠调用方保证，没有编译期约束，也没有 Factory / SavedStateHandle 的恢复能力。

线程与生命周期

  • MvxViewModel 通过委托实现 LifecycleViewModel，因此可以直接用 bindToLifecycle() 绑定 Rx 订阅，并在 onCleared() 里 sendClearEvent()。
  • 协程侧统一使用 viewModelScope；列表分页在 Pager 内部用传入的 scope 启停。
  • setState 是 Mavericks 的入口，状态更新由 Mavericks 串行化；业务侧通常在主线程或 viewModelScope 中调用。
  • MvxView.invalidate() 是 Mavericks 在状态变化 / 页面启动时回调的“全量重绘”入口；很多页面把它留空，改用更细粒度的 onEach / onAsync。
04

DevKit 的四个扩展点

把 mvx 包拆开看，它真正增加的能力只有四类：类型约束、异步执行、列表收集、长生命周期仓库。下面按“源码 + 用途 + 注意点”逐個说明。

4.1 MvxState：一个空接口

DevKit/devkit/.../mvx/MvxState.kt:1-8
package com.zhihu.android.devkit.mvx

import com.airbnb.mvrx.MavericksState

/** 继承自 MavericksState 方便添加扩展方法 */
interface MvxState : MavericksState

它现在是空的，但有两个作用：一是把所有业务的 State 收敛到同一个类型上（S : MvxState），二是给未来加扩展方法留了口子。真正的约束来自 Mavericks 的 MavericksState。

4.2 MvxViewModel：把 Rx / Flow 塞进 Async

这是使用频率最高的扩展。它做了两件事：把“成功值”收集进 state，以及把 Rx 的 Single / Observable / Completable 包成 Mavericks 的 Async。

API所在行行为适用场景

DevKit/devkit/.../mvx/MvxViewModel.kt:92-121（节选）
fun <T, V> Observable<T>.execute(
    mapper: (T) -> V,
    successMetaData: ((T) -> Any)? = null,
    stateReducer: S.(Async<V>) -> S
): Disposable {
    val blockExecutions = config.onExecute(this@MvxViewModel)
    if (blockExecutions != MavericksBlockExecutions.No) { /* ... */ }

    setState { stateReducer(Loading()) }

    return map<Async<V>> { value ->
        val success = Success(mapper(value))
        success.metadata = successMetaData?.invoke(value)
        success
    }
        .onErrorReturn { e -> Fail(e) }
        .compose(bindToLifecycle())
        .subscribe { asyncData -> setState { stateReducer(asyncData) } }
}

4.4 MvxRepository：给“不是 ViewModel 的状态容器”用

Mavericks 本身有 MavericksRepository（实验 API）。DevKit 把它包成 MvxRepository，并委托 LifecycleViewModel，让它可以绑定生命周期、发送清理事件。

DevKit/devkit/.../mvx/MvxRepository.kt:29-64
@OptIn(ExperimentalMavericksApi::class, InternalMavericksApi::class)
abstract class MvxRepository<S : MvxState>(
    private val config: MavericksRepositoryConfig<S>,
) : MavericksRepository<S>(config),
    LifecycleViewModel by LifecycleViewModel.Delegate() {

    constructor(
        initialState: S,
        coroutineScope: CoroutineScope,
        performCorrectnessValidations: Boolean = DevKit.DEBUG,
    ) : this(
        MavericksRepositoryConfig(
            performCorrectnessValidations = performCorrectnessValidations,
            stateStore = CoroutinesStateStore(
                initialState = initialState,
                scope = coroutineScope,
            ),
            coroutineScope = coroutineScope,
        )
    )

    init {
        coroutineScope.launch { awaitCancellation() }.invokeOnCompletion {
            sendClearEvent()
        }
    }
    // 与 MvxViewModel 基本一致的 Rx execute 扩展 …
}

全仓只有一个实现：音频播放器的 KMPlayer2。它不是页面级 ViewModel，而是一个跨页面单例状态容器，用一个 MultiCoroutineScope 把多个页面的生命周期“挂”在一起。

VipKmAudio/.../util/KMPlayer2.kt:167-221（节选）
data class KmPlayerState(
    val playParams: AudioPlayParams = AudioPlayParams("", "", ""),
    val audioDetail: Async<VipAppAudioDetail> = Uninitialized,
    val playState: PlayState = PlayState(),
    // … 共 10 个字段
) : MvxState

class KMPlayer2 : MvxRepository<KmPlayerState>(
    initialState = KmPlayerState(),
    coroutineScope = MultiCoroutineScope(),
) {
    companion object {
        private var instance: KMPlayer2? = null

        @Synchronized
        fun get(scope: CoroutineScope): KMPlayer2 {
            val current = instance
            if (current != null && current.coroutineScope.isActive) {
                current.attachScope(scope)
                return current
            }
            // 创建新实例、attachScope、在 scope 结束时释放播放器与缓存
        }
    }
}

MultiCoroutineScope 的机制是：给每个外部 scope 起一个 awaitCancellation() 的 Job，所有 Job 都结束（页面都退出）后取消自身；MvxRepository 在 init 里也挂了一个 awaitCancellation()，于是 scope 结束会触发 sendClearEvent()，KMPlayer2 再清理单例、播放器和缓存。

代价：MvxRepository 使用了 Mavericks 的 ExperimentalMavericksApi 与 InternalMavericksApi，并依赖 MavericksBlockExecutions 等内部符号。Mavericks 升级时需要重点回归这一块——这是整套封装里最“贴底层”的地方。

4.6 顺带补齐的“列表基础设施”

这套 MVI 的主战场是列表，因此 DevKit 里的 paging 包和 mvx 包是配套使用的。读懂下面几个类，基本就能读懂业务页面的数据链路：

类 / 扩展作用典型组合
Pager包装 Paging3 的 Pager，接收 viewModelScope 与 prefetchDistance。Pager(viewModelScope) { Source() }
ResponsePagingSource把 Retrofit Response 分页响应对齐成 PagingSource，暴露 resolveNextKey / resolvePreKey / resolveValue。列表型 ViewModel 的 inner class DataSource
PagerMediator对分页数据做局部增删改，避免整页刷新。bindMediator(pagerMediator) + remove/update
filterPaging / mapPagingItem / insertPagingSeparators对 Flow<PagingData> 做过滤、映射、插入分隔项。pager.flow.filterPaging {...}.setOnEach { copy(data = it) }
viewScope绑定到 View attach/detach 的协程作用域，detach 时自动取消。binding.rv.viewScope.launch { ... }
SafeCoroutine / MultiCoroutineScope异常安全的协程启动；后者用于多页面共享的长生命周期仓库。播放器、跨页面状态

这也解释了一个现象：业务代码里 MvxViewModel 常常和 Pager 一起出现，而单纯的 MvxView 反而不多。MVI 在这里更像是“列表状态管理”的代名词。

05

业务里的四种用法

把 46 个业务文件按“状态参与程度”分类，能看到四种非常不同的写法。它们不是四个框架，而是同一套 API 的四种使用深度。

用法 A：Async 单请求 —— 最标准的“状态驱动”

代表是会员主页。State 里放一个 Async<ProfileInfo>，ViewModel 用 execute 发请求，Fragment 用 onEach 处理 Uninitialized / Success / Fail（Loading 走 else 分支），用 onAsync 处理成功后的渲染。

07

好在哪，坑在哪

这套 MVI 不是“教科书式”的：它没有 Intent、没有 reducer 目录、没有依赖注入，甚至没有 Factory。但它解决了 VIP 业务最痛的两个问题：异步状态的表达和分页列表的复用。

做得好的地方

  • 用 Async 统一了 Loading / Success / Fail，页面不再各自发明加载态。
  • Pager + ResponsePagingSource + SuperAdapter 把分页样板代码压到很低。
  • MvxRepository 让播放器这类跨页面状态有了合法容器，不必塞进单例工具类。
  • DevKit 统一了 Mavericks 版本、初始化和 AAR 发布，业务不用各自接 Mavericks。
  • collectFrom / collectFromAsync 把“状态 → 列表”变成一行链式调用。
  • 源码依赖机制让“改库 + 调业务”可以在同一个 IDE 工程里完成。

明显的坑

  • 没有 Intent / Event 建模，事件就是公开方法；页面一复杂，VM 的方法会膨胀。
  • State 里塞 PagingData、可变集合、派生属性，状态不可比较、不好测试。
  • Fragment 直接 subscribe 绕过了 VM，出现“双数据源”。
  • MvxView 被当成 marker 用，invalidate() 空实现，MVI 名存实亡。
  • 参数靠 initParams / setter 注入，时序没有编译期保障，也没有 SavedState 恢复。
  • MvxRepository 依赖 Mavericks 内部 API，升级风险高。

典型症状与后果

症状直接后果建议
State 里放 PagingData 与可变 ArrayList 状态无法做相等比较，DiffUtil / 测试 / 回放都困难；容易在原地修改。 State 只放不可变数据；列表用 PagingData 没问题，但不要混入可变集合。
Fragment 里直接 service.xxx().subscribe { binding... } UI 与网络强耦合，状态不可追踪；页面重建后可能重复请求。 请求收回到 VM，结果写 Async；Fragment 只观察。
在 PagingSource 的 onRefresh 里 setState 数据源承担了状态容器职责；重试、预加载、缓存命中时行为难预测。 把 header / 附属状态放到 VM 的方法里，由 pager.flow 的结果驱动。
一个页面同时用 onEach 和 onAsync 订阅同一个 Async 成功回调触发两次；loading / success / fail 的渲染顺序依赖注册顺序。 明确分工：onEach 只做状态渲染，onAsync 只做一次性副作用。
MvxView + LiveData VM Mavericks 的状态机制完全没参与，invalidate() 没有意义。 要么迁到 MvxState，要么不要实现 MvxView，避免误导。
同一份代码在 VipManuscript 与 KnowledgeMarket 各维护一份 修 bug 只修一边，行为漂移；依赖版本也不同。 抽出共享模块，或明确“知识市场是旧版、只维护安全修复”。

如果只做一件事：先把 Fragment 里的网络订阅收回到 ViewModel，用 Async + execute 表达。收益最大，改动最小，也不会动到现有 Mvx 基础设施。

8.3 为什么依赖全是 api？

因为 DevKit 的公开签名里直接出现了 Mavericks / Paging / SugarAdapter 的类型：

  • MvxViewModel<S> : MavericksViewModel<S> —— 业务必须能看见 MavericksViewModel、Async、setState。
  • MvxView.collectFrom(... PagingData ...) —— 业务必须能看见 PagingData、DeliveryMode。
  • SuperAdapter、registerViewHolder、DefaultLoadState —— 业务直接使用。

如果改成 implementation，这些类型不会出现在消费方的编译类路径上，业务代码会直接编译失败。所以 api 不是“懒”，而是这套封装把 Mavericks 当成了公共 API 的一部分。

代价是依赖穿透：任何引入 DevKit 的模块，都会自动获得 Mavericks、Paging、SugarAdapter、ZUI、net、basemodel、logback 等一整串依赖。好处是接入快；坏处是版本冲突面大，最终只能靠宿主的 lock 文件兜底。

8.8 源码依赖：不改 Maven，也能改 DevKit

DevKit 的 settings.gradle 只 include 两个模块，但它 apply 了一个 250 行的 gradle/sourcecode.gradle。这个脚本是知乎组件化体系里的“源码替换器”：

DevKit/settings.gradle:17-19
include ':app', ':devkit'
// 这里决定了可以源码引用
apply from: 'gradle/sourcecode.gradle'

它支持三种配置来源：

  1. local.properties：<组件名>.source=true + <组件名>.dir=路径；配合 gradle.ext.allComponents 或自动扫描。
  2. sourcecode.properties：一行一条，格式是 group:artifact=路径|模块名；模块名可省略，默认取路径最后一段。
  3. 组件化工程：声明 <组件名>.source=true 与 <组件名>.dir=...（脚本会从 local.properties 或 Gradle 属性读取目录），自动把 component 加入源码依赖。
DevKit/gradle/sourcecode.gradle:176-245（节选）
def sourceConfFile = new File('sourcecode.properties')
if (sourceConfFile.exists()) {
    sourceConfFile.eachLine { line ->
        def kv = line.split("=")
        if (kv?.length == 2 && kv[0].trim() && kv[1].trim()) {
            sourceConf.add(new SourceModule(line))
        }
    }
}

def sourceCode = {
    sourceConf.forEach { module ->
        include ":${module.name}"
        project(":${module.name}").projectDir = new File(module.path)
    }
    gradle.allprojects { prj ->
        configurations.all { config ->
            config.dependencies.whenObjectAdded { Dependency object ->
                def sm = sourceConf.find { object.group + ":" + object.name == it.classPath }
                if (sm) project.dependencies.add(config.name, project(":${sm.name}"))
            }
            resolutionStrategy {
                dependencySubstitution {
                    sourceConf.forEach { sm ->
                        substitute module(sm.classPath) with project(":${sm.name}")
                    }
                }
            }
        }
    }
}

sourceCode()

对 DevKit 来说，这个脚本有两个用途：

  • DevKit 自己可以用它源码依赖别的组件（例如调试某个下游库），而不必等 Maven。
  • 宿主/业务仓可以在自己的 sourcecode.properties 里写一行，把 com.zhihu.android.library:devkit 替换成 ../DevKit/devkit，这样改 DevKit 代码能立刻在主工程生效，不需要 uploadLocalRepo。
使用示例（按仓库现有约定整理，不是仓库原文件）

  • README.md 只有一行标题，CHANGELOG.md 只有一句“记录版本修改记录”，没有任何 Mvx 用法或升级说明。
  • 示例 App 没有 Mvx 页面，库的核心能力没有可执行样例。

版本与发布治理

如果要让这套东西从“若干业务仓各自用”变成“可长期维护的基础设施”，优先级最高的不是加功能，而是收敛版本和补齐文档。下面是一份可以直接照着做的清单。

9.1 先统一版本

  • 把所有 versions.devkit 对齐到最新稳定版（当前是 0.0.19），至少让 VipManuscript / VipKmAudio 这两个重度用户先升级。
  • 删除 VipReader 里的硬编码 0.0.9，改为 ${versions.devkit}。
  • 发版前扫描并禁止 TEMP_ 版本进入正式渠道（仓库已有类似的依赖检查机制，可复用）。
  • 在 DevKit 里维护一张“版本 → 变更 → 消费方最低版本”的表，替代空白的 CHANGELOG。

9.2 再收敛依赖

  • Mavericks 必须保持 api（公开签名需要）；但 zui、logback、net、basemodel 可以评估改成 implementation，减少穿透。
  • 如果短期不能改，至少在 DevKit 的 README 里列出“引入 DevKit 会带入哪些传递依赖”，让业务有预期。
  • 把 lock_third_versions.gradle 与宿主的 lock 文件做一次比对，确认 AndroidX / Kotlin 版本没有分叉。
  • 升级 Mavericks 时，优先验证 MvxRepository（内部 API）和 execute 的 blockExecutions 行为。

9.3 最后补使用约束

  • 在 README 写清“宿主必须初始化”：T_DevKitInit 或 DevKit.init(app)，否则 DevKit.DEBUG 与 Mavericks 的调试配置不会生效。
  • 给 MvxView 加注释：它只增加 SuperAdapter 扩展，不强制你使用 State；不要为了“看起来像 MVI”而实现它。
  • 给 MvxRepository 标注“实验性 / 仅长生命周期状态容器”，避免被当成普通 Repository 滥用。
  • 补一个最小 Mvx 示例（State + VM + Fragment + Pager），放在示例 App 里，作为可执行文档。
  • 为 MvxViewModel.execute 的 Loading → Success/Fail 顺序、错误映射写单元测试。

一个务实的顺序：先统一到 0.0.19（一周内可完成）→ 补 README/CHANGELOG/示例（两周）→ 再谈 api 收敛与 Mavericks 升级（一个版本周期）。不要反过来先重构 API，否则会同时得罪所有消费方。

class DemoViewModel(initialState: DemoState) :
    MvxViewModel<DemoState>(initialState) {

    private var businessId: String = ""
    private val service = Net.createService(DemoService::class.java)

    private val pager = Pager(viewModelScope) { DemoSource() }

    init {
        pager.flow
            .filterPaging { it.isVisible }
            .setOnEach { copy(list = it) }
    }

    fun initParams(businessId: String) {
        this.businessId = businessId
    }

    fun loadDetail() {
        service.getDetail(businessId)
            .compose(NetworkUtils.simplifyRequest(bindToLifecycle()))
            .execute { copy(detail = it) }
    }

    fun refresh() {
        pager.invalidate()
    }

    inner class DemoSource :
        ResponsePagingSource<DemoPaging, DemoItem, DemoResponse>() {
        override suspend fun onRefresh(params: LoadParams<DemoPaging>): Response<out DemoResponse> =
            service.getList(businessId, null).awaitFirst()

        override suspend fun onLoadMore(params: LoadParams.Append<DemoPaging>): Response<out DemoResponse> =
            service.getList(businessId, params.key.next).awaitFirst()

        override fun resolveValue(result: DemoResponse?): List<DemoItem> = result?.data ?: emptyList()
        override fun resolveNextKey(curParams: LoadParams<DemoPaging>?, result: DemoResponse?, lastValue: DemoItem?): DemoPaging? =
            result?.paging?.takeIf { !it.isEnd }
        override fun resolvePreKey(curParams: LoadParams<DemoPaging>?, result: DemoResponse?, firstValue: DemoItem?): DemoPaging? = null
    }
}

面试速答

如果要在 5 分钟内讲清这套 MVI，记住下面 8 个问答就够了。

这套 MVI 的“引擎”是什么？DevKit 做了什么？

引擎是 Airbnb Mavericks 3.0.6。DevKit 的 mvx 包只做薄封装：用 MvxState 约束类型，用 MvxViewModel 补 Rx 的 execute 与 Flow / Rx 的 collectState，用 MvxView 补 SuperAdapter.collectFrom，用 MvxRepository 支持长生命周期状态容器；再通过 api 依赖把 Mavericks 暴露给业务，并统一初始化与 AAR 发布。

Async 有哪几种状态？execute 做了什么？

Uninitialized、Loading、Success、Fail。DevKit 的 execute 先 setState { reducer(Loading()) }，再把成功值 map 成 Success（可带 metadata），错误 onErrorReturn { Fail(it) }，最后 bindToLifecycle() 订阅。它和 Mavericks 原生 execute 的语义对齐（Loading → Success/Fail），只是把 Rx 入口补在了 DevKit 里。

为什么 ViewModel 都没有写 Factory？初始 State 哪来的？

现有 State 大多带默认值（并非全部，ManuscriptState 就有字段没默认值），页面用 fragmentViewModel() 直接创建 ViewModel，不写 Factory。业务参数不在构造函数里传，而是在 onViewCreated 里通过 initParams / setMemberToken / setScene 事后注入。这样接入简单，但参数时序没有编译期保障，也没有 SavedState 恢复。

MvxView 和 MavericksView 是什么关系？invalidate() 什么时候调用？

MvxView 继承 MavericksView，只额外提供 SuperAdapter.collectFrom / collectFromAsync 两个成员扩展；invalidate() 仍由 Mavericks 在状态变化 / 页面启动时回调。很多页面留空 invalidate()，改用 onAsync / onEach 做细粒度更新。注意：实现 MvxView 不等于用了 MVI，PinTabFragment 就是反例。

MvxRepository 和 MvxViewModel 有什么区别？为什么播放器要用它？

MvxRepository 继承 MavericksRepository，不是 ViewModel，不随页面销毁；它接受外部 CoroutineScope，适合做跨页面的“单一事实源”。音频播放器 KMPlayer2 是单例，用 MultiCoroutineScope 把多个页面 scope 挂在一起，所有页面退出后才释放播放器和缓存；页面级 VipAudioPlayViewModel 再把仓库状态投影成自己的 State。

DevKit 是怎么打包发布的？AAR 里有什么？

devkit 模块应用 com.zhihu.android.library + Kotlin 插件，设置 resourcePrefix 'devkit'、consumerProguardFiles、ViewBinding，依赖全部用 api；archivesBaseName = 'devkit'、group = 'com.zhihu.android.library'。发布由 Athena 2.0 读取 athena.json，执行 ./gradlew :devkit:uploadArchives，推到内网 Maven；AAR 里是 5 个 Mvx 文件、23 个 Paging 文件（含扩展）、协程/RxBus/工具类、6 个加载态布局和 consumer rules，清单为空。

源码依赖是怎么把 AAR 换成本地工程的？

宿主在 sourcecode.properties 写 com.zhihu.android.library:devkit=../../DevKit/devkit|devkit（或在 local.properties 写 devkit.source=true + devkit.dir=...）。sourcecode.gradle 把目标模块 include 进来，再用 dependencySubstitution 把 Maven 坐标替换成 project(":devkit")；同时监听依赖添加，手动补一次 project 依赖。限制是：指定模块构建时可能不生效，且脚本会改写 .idea/vcs.xml。

为什么 debugMode 只在 dev 开？这和 Robust 有什么关系？

DevKit.DEBUG = ComponentBuildConfig.FLAVOR() == "dev"，然后 Mavericks.initialize(DEBUG)。Git 历史里有一条明确记录：mvx validate 和 robust 有冲突，选择 dev 关闭 robust，启用 mvx validate；随后又提交“Mavericks 只在 dev 时启用 debugMode”。可以这样理解：Mavericks 的校验主要在开发期提供价值，线上关掉可以减少校验开销，也避免与热修复 / AOP 链路互相干扰。代价是线上没有 Mavericks 的状态正确性校验，只能靠测试兜底。
