生命周期与进程死亡：从 Activity、Fragment 到 View 和状态恢复

页面退到后台、Fragment 拆掉 View、整个进程被杀，后续要做的处理各不相同。这篇文章结合项目代码，解释什么时候停任务、释放引用，以及怎样恢复页面。P1 优先掌握，P2 用于追问，最后附 24 道面试题。源码快照：2026-09-21。

01 · P1：Activity、Fragment 和 View 各自什么时候结束

生命周期描述的是：一个对象创建后，什么时候可用、什么时候暂停使用、什么时候结束，框架会通过哪些回调通知你。进程被杀则会让整个进程里的 Java/Kotlin 对象、线程和单例一起消失，不会先挨个调用它们的清理方法。

对象它管理什么容易混淆的地方
Application / 进程当前进程中的应用环境Application 不是永久存活；多进程有各自实例
Activity一个页面宿主及其 Window退到后台不等于销毁；重建不等于进程死亡
Fragment页面中的逻辑组件实例还在，旧 View 可以已经销毁
Fragment 的 View这次创建出来的界面树用 viewLifecycleOwner 管理界面订阅
普通 View / ViewHolder具体控件或列表条目detach、不可见、回收、对象释放是不同事件
ViewModel所属页面或组件的界面状态配置变化时可以保留，进程死亡后要重新创建
Service / Receiver / Provider任务入口、事件入口、数据入口不因叫组件就拥有 Activity 那套回调

先看 P1，弄清旋转、返回、退后台、列表复用和状态恢复时会发生什么。P2 用来准备进一步的追问。文中的项目代码有些写法也存在限制，会在对应位置说明；有这段源码，不等于它就是推荐写法，也不能证明个人贡献。

02 · P1：Activity 什么时候创建、停止和销毁？

代码 / 执行顺序
首次打开：onCreate → onStart → onResume
暂时失去前台交互：onPause
完全不可见：onPause → onStop
从 stopped 回来：onRestart → onStart → onResume
正常 finish：通常 onPause → onStop → onDestroy
默认配置重建：旧实例结束 → 新实例 onCreate → onStart → onResume
后台进程被杀：旧实例不保证收到 onDestroy；恢复时创建新实例

onCreate 里做当前 Activity 的初始化，并读取恢复状态。onStart 表示页面开始可见，onResume 表示进入 resumed 状态。onPause 要尽快返回，别在里面做大数据库事务或耗时上传。页面不再可见时，可以在 onStop 释放只在显示期间需要的资源。正常销毁时，onDestroy 会做最后清理；重要数据不能等到这里才保存，因为进程被杀时它未必会调用。

场景通常发生什么应该记住
按 Homepause → stop，实例可能保留下次回来可能没有 onCreate
普通不透明 B 覆盖 AA pause；B create/start/resume；A stop不要把所有回调跨页面顺序背成适用于所有窗口的定律
透明 / 半透明页面覆盖A 可能只 pause，仍可见Dialog 本身也不必然触发 Activity pause
旋转屏幕默认重建 Activity 和 View配置声明、设备和窗口模式会影响是否重建
返回结束页面正常结束该 Activity任务根 Activity 的返回行为有版本差异，Android 12+ 某些场景退到后台
系统回收后台进程内存中的对象全部丢失通常没有销毁回调可供补救

多窗口下，页面可见时不一定处于 resumed 状态；Android 10+ 还支持多个 Activity 同时 resumed。因此，onResume 不代表自己是唯一在前台的页面。相机等独占资源，还要结合 top-resumed 状态和资源本身的使用规则处理。

03 · P1：项目清空 outState，会影响什么？

项目原码：yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/ui/activity/MainActivity.java，第 242至249 行。

代码 / 执行顺序
    protected void onSaveInstanceState(Bundle outState) {
        try {
            super.onSaveInstanceState(outState);
        } catch (IllegalStateException ignore) {

        }
        outState.clear();
    }

这里先调用 super，再执行 outState.clear()。Bundle 中当时已经写入的数据会被清空，包括上层实现保存的内容，这会影响标准的 View / Fragment 状态恢复。LauncherActivity 第 307至310 行也这样处理。为什么当时要清空，需要查历史记录，单看这段代码看不出来。

系统以后可能重建页面时，onSaveInstanceState 用来保存条目 ID、筛选条件、滚动位置等少量临时状态。用户明确 finish 页面时，通常不需要留下这份重建数据；进程突然被杀，也不能等着它再调用一次。所以，重要数据仍然要及时写进持久化存储。

Android 9+ 且 target 为 P+ 时，onSaveInstanceState 在 onStop 之后调用；老版本的顺序有所不同，不要记成固定在 onPause 和 onStop 之间。恢复时，通常在 onCreate(savedInstanceState) 读取，也可以在 onRestoreInstanceState 处理。后者在有恢复状态时调用，位于 onStart 之后。

如果准备修改这段代码，先查清 outState.clear 的调用位置和当时解决的问题，再决定怎么改。本文只解释它现在的行为，没有修改业务源码。

04 · P1：Fragment 活着，为什么 View 已经没了？

Fragment 对象负责页面逻辑，onCreateView 返回的 View 则负责显示界面。两者可以有不同的寿命：Fragment 留在返回栈里时，它的 View 可能已经销毁；返回这个页面后，同一个 Fragment 再创建一棵新的 View 树。是否发生这种情况，要看具体事务和生命周期限制，并非每次切页面都会销毁 View。

代码 / 执行顺序
Fragment：onAttach → onCreate → onCreateView → onViewCreated → onStart → onResume
View 被拆掉：onPause → onStop → onDestroyView
若 Fragment 仍保留：稍后 onCreateView → onViewCreated → onStart → onResume
Fragment 最终移除：onDestroy → onDetach

需要跟着 Fragment 实例保留的状态，可以放在 Fragment / ViewModel。binding、Adapter 引用、监听和界面数据订阅如果只服务于这一次创建的 View，就要在这轮 View 销毁时清理。用了 ViewBinding，也仍然需要自己清空相关字段。

项目原码：yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/audio/CommonAudioPageFragment.kt，第 163至175 行。

代码 / 执行顺序
    override fun onPause() {
        super.onPause()
        kmViewModel.uploadLastRead()
    }

    override fun onDestroyView() {
        super.onDestroyView()
        layoutBinding.homeRecyclerView.removeOnScrollListener(scrollListener)
    }

    override fun onDestroy() {
        super.onDestroy()
        registerPrerenderOrNot(false)

这段代码在 onDestroyView 移除列表滚动监听，在 onDestroy 取消另一个注册关系。也就是说，有的资源跟着 View 结束，有的跟着 Fragment 结束。不过，移除了这个监听，不代表旧 View 的所有引用都没了；还要检查 binding、Adapter 和其他回调字段。

比如 Fragment 还在返回栈里，它的 binding 字段又引用着旧 View，旧 View 还引用着 Context，这一整串对象就可能都留在内存中。GC 能回收已经不可达的循环引用，但这里 Fragment 仍然可达，所以不能指望 GC 自动把旧 View 清掉。

05 · P1：观察数据到底绑定 Activity、Fragment 还是 View？

项目原码：yyyyy-cdoe/VipCommon/vip_common/src/main/java/com/zhihu/android/vip_common/fragment/SubscriptDialogFragment.kt，第 64至67 行。

代码 / 执行顺序
        vm.subscribed.observe(this.viewLifecycleOwner){ subscript ->
            changeSubscriptStatus(subscript)
        }
        return rootView.root

这里把 LiveData 观察者交给 viewLifecycleOwner 管理。旧 View 销毁时，LiveData 会移除观察者；新 View 创建后，再重新注册。通常只有 owner 达到 STARTED，观察者才会收到更新。如果写 observe(this)，观察者会跟着 Fragment，而 Fragment 可能经历好几轮 View 创建和销毁，旧界面的回调就可能一直留着。原码在 onCreateView 中注册，并返回非空 root，这不一定非法；教学示例放在 onViewCreated，更容易看清它属于哪一轮 View。

写法停止可见后销毁后
LiveData.observe(viewLifecycleOwner)低于 STARTED 不交付界面更新View owner DESTROYED 后移除观察者
viewLifecycleOwner.lifecycleScope.launch普通协程不会只因 STOPPED 自动取消View owner 销毁时取消
repeatOnLifecycle(STARTED)低于 STARTED 取消内部块；重新进入则重启外层随 owner 销毁结束
viewModelScope不由某个 View 的 stop 控制ViewModel 被清除时取消

07 · P1：View 的 attach、布局、可见和销毁不是一回事

阶段 / API含义不要推导成
构造 / inflate创建对象、读取属性已经有最终宽高
onAttachedToWindow连接到窗口用户必然能看见或对象只会 attach 一次
onMeasure / onLayout / onDraw尺寸协商、放置、绘制一次生命周期只调用一次
onVisibilityChanged / onWindowVisibilityChanged自身/祖先可见性或窗口可见性变化像素未被遮挡、曝光比例满足业务条件
onDetachedFromWindow从窗口脱离对象一定死亡或以后不能复用

View 没有通用的 onDestroy 回调。removeView 之后可以再 addView，列表条目滚出屏幕后也可能回来。因此，attach 时开始的监听和动画，要在 detach 时清理，并且下次 attach 还能重新启动。需要根据尺寸初始化时，可以考虑 onSizeChanged。View.post 只是在安排任务，不能仅凭它就认定这轮布局已经结束。

08 · P1：可反复 attach / detach 的 View 示例

代码 / 执行顺序
class TickView(context: android.content.Context) : android.view.View(context) {
    private val handler = android.os.Handler(android.os.Looper.getMainLooper())
    private var attached = false
    private val tick = object : Runnable {
        override fun run() {
            if (!attached || windowVisibility != VISIBLE) return
            invalidate()
            handler.postDelayed(this, 1000L)
        }
    }

    private fun updateTick() {
        handler.removeCallbacks(tick) // 防止重复安排
        if (attached && windowVisibility == VISIBLE) handler.post(tick)
    }

    override fun onAttachedToWindow() {
        super.onAttachedToWindow()
        attached = true
        updateTick()
    }

    override fun onWindowVisibilityChanged(visibility: Int) {
        super.onWindowVisibilityChanged(visibility)
        updateTick()
    }

    override fun onDetachedFromWindow() {
        attached = false
        handler.removeCallbacks(tick)
        super.onDetachedFromWindow()
    }
}

这个示例在窗口可见时定时刷新，相关字段都在主线程访问。detach 后移除任务，下次 attach 再启动。它没有实现列表曝光统计：View 是否被祖先隐藏、是否在屏幕外、被遮住多少，都要另行判断。每秒 postDelayed 也不能当作精确计时，播放进度仍应根据实际时间或播放器状态计算。

09 · P2：View 自己管理 Lifecycle，复用时怎么办？

项目原码：yyyyy-cdoe/VipCommon/vip_common/src/main/java/com/zhihu/android/vip_common/view/lifecycle/LifecycleFrameLayout.kt，第 32至50 行。

代码 / 执行顺序
    override fun onAttachedToWindow() {
        super.onAttachedToWindow()
        mRegistry.currentState = Lifecycle.State.CREATED
    }

    override fun onDetachedFromWindow() {
        super.onDetachedFromWindow()
        mRegistry.currentState = Lifecycle.State.DESTROYED
    }

    override fun onWindowVisibilityChanged(visibility: Int) {
        super.onWindowVisibilityChanged(visibility)
        if (visibility == VISIBLE) {
            mRegistry.handleLifecycleEvent(Lifecycle.Event.ON_START)
            mRegistry.handleLifecycleEvent(Lifecycle.Event.ON_RESUME)
        } else if (visibility == GONE || visibility == INVISIBLE) {
            mRegistry.handleLifecycleEvent(Lifecycle.Event.ON_PAUSE)
            mRegistry.handleLifecycleEvent(Lifecycle.Event.ON_STOP)
        }

LifecycleFrameLayout 自己规定了这套对应关系：attach 时设为 CREATED，detach 时设为 DESTROYED，窗口可见时发出 START/RESUME。这不是 Android 给所有 View 自动提供的行为。在相关模块中找到了这个类，但尚未确认具体哪个业务实例用了它。

DESTROYED 表示这次生命周期已经结束，同一个 LifecycleRegistry 不应再拿来当作重新开始的生命周期。之前移除的观察者、取消的 scope，也不会因为 View 又 attach 就自动恢复；某些 Lifecycle 版本还会对非法状态变化报错。如果 View 要复用，可以为每次 attach 设计新的 owner，或者在 detach 时只清理这段时间用到的资源，把真正结束生命周期的时机另行定义。

还要检查初始状态，以及窗口可见回调实际按什么顺序发生，不能假定它们恰好符合自己写的状态机。通过 ViewTreeLifecycleOwner 找到的 owner，常常属于宿主 Activity 或 Fragment View；它的生命周期也不会随着每个列表条目的 attach / detach 一起变化。

RecyclerView 事件业务应该处理
onBindViewHolder重置旧数据相关样式、绑定新 item ID；取消旧图片/任务，防止串位
onViewAttachedToWindow恢复该条目附着期间需要的资源
onViewDetachedFromWindow暂停附着期间的动画/监听；不假设马上 recycle

14 · P1：进程死亡后，什么东西真的还在？

进程被系统回收后，堆里的对象、static、Kotlin object、Application 字段、ViewModel 和线程都没了。但系统可能还保留着任务记录和之前保存的状态，磁盘数据也可能还在。用户回到原任务时，系统启动新进程、创建新组件，再把能用的保存状态传回来。

项目原码：yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/util/pagerecover/ActivitySavedStateRecorder.java，第 24至24 行。

代码 / 执行顺序

cachePageDescription 是 static 字段，只存在于当前进程内存。第 35至42 行在 Fragment resumed 后 post 更新它，第 53至56 行在 paused 时清空它。即使类名叫 ActivitySavedStateRecorder，这个字段也不能单独用来恢复被杀进程的页面。没有找到把 recorder 注册到 Application 的调用，因此尚未确认线上是否启用了它。

Application.onCreate 在当前进程初始化时调用，不会每打开一个页面就再来一次。多进程应用中，各进程有自己的 Application 和单例。真机上进程被杀时，也不能指望 Application.onTerminate 先被调用。冷启动初始化要能独立完成，不能依赖上一次进程留下的全局对象。

19 · 常见面试题与参考答案

P1 · 1. onPause 和 onStop 有什么区别？

onPause 表示离开 resumed 阶段，界面可能仍可见；onStop 表示 Activity 不再可见。资源应按是否需要可见/交互来选择停止时机，onPause 保持轻量。

P1 · 2. onDestroy 一定调用吗？

不保证。正常 finish 或配置重建通常调用；系统直接终止进程时没有逐一销毁回调的保证。重要数据应在产生变更时持久化。

P1 · 3. 旋转和进程死亡有什么区别？

默认旋转重建 Activity/View，进程通常还在，正确 scope 的 ViewModel 可以保留；进程死亡会让内存对象全部丢失。两者都可能走带 saved state 的新 onCreate，不能只靠 Bundle 是否非空区分。

P1 · 4. onSaveInstanceState 和持久化存储怎么选？

前者保存系统重建需要的小量临时 UI 信息，不保证所有退出场景；重要草稿、离线记录和跨任务数据需要数据库/文件等可靠写入。

P1 · 5. ViewModel 为什么能跨旋转？

配置重建时，框架保留了这个页面的 ViewModelStore，新 Activity 因此能拿到原来的 ViewModel。它不是靠 static 保存的；其他不相关的新页面也不会自动拿到同一个 ViewModel。

P1 · 6. ViewModel 能跨进程死亡吗？

不能，原来的 ViewModel 已经随进程消失。新的 ViewModel 可以从 SavedStateHandle 和持久化存储里读取数据，恢复需要的状态。原 viewModelScope 中的任务不会复活，进程死亡前也不保证调用 onCleared。

P1 · 7. Fragment 的 onDestroyView 与 onDestroy 有什么区别？

前者结束本轮 View，后者结束 Fragment 实例。返回栈中的 Fragment 可跨多轮 View，所以 binding 和渲染订阅应按 View 生命周期清理。

P1 · 8. 为什么用 viewLifecycleOwner？

旧 View 销毁时，它的观察者也该结束。用 viewLifecycleOwner，就能避免 Fragment 还在、旧界面的观察者却一直留下来的情况。项目中的 SubscriptDialogFragment 就用它观察 LiveData。

P1 · 9. lifecycleScope.launch 在 onStop 会自动停吗？

不会。普通 launch 会随对应 owner 销毁而取消，页面只是 onStop 时不会自动停。只想在页面可见时收集数据，可以用 repeatOnLifecycle；不过页面再次可见时，里面的代码也会重新执行。

P1 · 10. detach 是否表示 View 被销毁？

不是。View 可以再次 attach 或留在 RecyclerView 缓存。清理附着资源后，还要支持重新建立，不应默认把一次 detach 当永久结束。

P1 · 11. 项目 lazy Disposable 有什么风险？

RewardCenterProgressIconView 在 detach 时 dispose 了点击订阅，但之后访问 lazy 字段，拿到的还是已经取消的对象。如果同一个 View 还要使用，就需要重新订阅。这是代码中看到的风险，尚未复现线上故障。

P1 · 12. RecyclerView detach 和 recycle 一样吗？

不一样。detach 是离开窗口，可能暂存后直接回来；recycle 是结束当前绑定并准备复用。项目 RN 容器 recycle 仅日志，真正销毁 Fragment 的路径需继续追到宿主。

P1 · 13. 异步回包为什么会串到另一条列表数据？

ViewHolder 已绑定新 item，旧请求回调仍持有它。应取消或替换旧请求，并按稳定 item ID 校验归属，不能只用旧 position。

P2 · 14. 给 View 实现 LifecycleOwner 的难点？

要先规定每个状态代表什么、回调按什么顺序发生，以及何时算彻底结束。同一个 registry 到 DESTROYED 后，不能直接当成新生命周期继续用。窗口可见也不一定代表条目真的达到了业务要求的曝光条件。

P1 · 15. 恢复刷新动画意味着恢复请求吗？

不意味着。View SavedState 只能恢复序列化字段；需要让 ViewModel/Repository 重新确认数据或安排任务，避免只有转圈没有请求。

P2 · 16. 自定义 View 状态保存要做什么？

继承合适 SavedState，保存/恢复 superState 与自身字段，正确 Parcel 化；确保稳定 ID、父层级和宿主参与保存，读取时做类型兼容。

P1 · 17. 项目 outState.clear 会怎样？

会清空该时刻 Bundle 里的条目，破坏默认恢复所需信息。不能再默认完整恢复，也不能在未查历史原因前贸然修改。

P1 · 18. Application 单例能否恢复页面？

仅能保存当前进程内存状态。进程死亡后 static、object 和 Application 都重新创建；多进程也不共享这份实例。

P1 · 19. Service 是后台线程吗？

不是，常规生命周期回调在进程主线程执行。耗时任务要自行调度；Service 的存活规则与线程执行位置是两个问题。

P2 · 20. START_STICKY 可以保证永远运行吗？

不能。START_STICKY 只是要求系统在服务被杀后尝试重建，重建时可能收到 null intent，而且仍受系统条件限制。前台服务也可能被杀。

P2 · 21. 广播里启动 Thread 然后返回安全吗？

不能靠它保证任务完成，回调结束后进程的重要性会变化。短时异步用 goAsync 并 finish，持久可重试任务交给合适调度系统。

P2 · 22. ContentProvider 一定晚于 Application.onCreate 吗？

通常更早：进程启动安装 Provider 时会初始化，随后才调用 Application.onCreate。Provider 不应依赖仅在该 onCreate 中完成的初始化。

P1 · 23. 如何真正测进程死亡恢复？

后台后 am kill 并确认 PID 消失，从最近任务返回，核对新 PID、恢复字段和请求。旋转或不保留活动不能覆盖单例丢失问题，force-stop 语义也不同。

P1 · 24. 面试中怎样串起一个项目案例？

可以讲 RN 评论容器：bind 时换数据，attach 时注册事件并添加 Fragment，detach 时清订阅，recycle 这里只打印日志；Activity 销毁时才走移除 Fragment 的路径。还要说明允许状态丢失的事务对恢复有什么影响，进程重建也需要另外检查。个人贡献只讲自己实际做过的部分。
