生命周期与进程死亡：从 Activity、Fragment 到 View 和状态恢复

先确定对象与资源的归属，再判断该暂停、释放还是保存。P1 优先掌握，P2 用于追问；最后附 24 道面试题。源码快照：2026-09-21。

01 · P1：先分清谁的生命周期

生命周期就是：一个对象从创建、可用、暂停使用到结束，框架会在什么时机通知你。进程死亡是更外层的事件：整个进程里的 Java/Kotlin 对象、线程、单例一起消失，不会逐个通知对象完成清理。

对象它管理什么最容易混淆的边界
Application / 进程当前进程中的应用环境Application 不是永久存活；多进程有各自实例
Activity一个页面宿主及其 Window退到后台不等于销毁；重建不等于进程死亡
Fragment页面中的逻辑组件实例还在，旧 View 可以已经销毁
Fragment 的 View本轮创建出来的界面树用 viewLifecycleOwner 管理界面订阅
普通 View / ViewHolder具体控件或列表条目detach、不可见、回收、对象释放是不同事件
ViewModel某个 owner 的界面状态跨配置重建，不跨进程死亡
Service / Receiver / Provider任务入口、事件入口、数据入口不因叫组件就拥有 Activity 那套回调

阅读建议：先读 P1，能解释旋转、返回、后台、列表复用和状态恢复；P2 用于框架和场景追问。源码来自当前工作区快照，不代表这些代码都是最佳实践，也不据此推断个人贡献。

02 · P1：Activity 什么时候创建、停止和销毁？

代码 / 执行顺序
首次打开：onCreate → onStart → onResume
暂时失去前台交互：onPause
完全不可见：onPause → onStop
从 stopped 回来：onRestart → onStart → onResume
正常 finish：通常 onPause → onStop → onDestroy
默认配置重建：旧实例结束 → 新实例 onCreate → onStart → onResume
后台进程被杀：旧实例不保证收到 onDestroy；恢复时创建新实例

onCreate 负责当前实例的一次性初始化和恢复入口；onStart 表示可见阶段开始；onResume 表示进入 resumed 状态。onPause 要轻量，不能把数据库大事务或耗时上传都塞进去。onStop 可以释放只在可见期间需要的资源；onDestroy 负责正常销毁路径的最后清理，但不能充当可靠的数据保存时机。

场景通常发生什么应该记住
按 Homepause → stop，实例可能保留下次回来可能没有 onCreate
普通不透明 B 覆盖 AA pause；B create/start/resume；A stop不要把所有回调跨页面顺序背成适用于所有窗口的定律
透明 / 半透明页面覆盖A 可能只 pause，仍可见Dialog 本身也不必然触发 Activity pause
旋转屏幕默认重建 Activity 和 View配置声明、设备和窗口模式会影响是否重建
返回结束页面正常结束该 Activity任务根 Activity 的返回行为有版本差异，Android 12+ 某些场景退到后台
系统回收后台进程内存中的对象全部丢失通常没有销毁回调可供补救

多窗口追问：可见不等于 resumed；Android 10+ 支持多个 Activity 同时 resumed。独占资源还可能需要关注 top-resumed 状态及具体资源仲裁，不能只凭 onResume 认定自己唯一处于前台。

03 · P1：项目的 onSaveInstanceState 为什么值得警惕？

项目原码：yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/ui/activity/MainActivity.java，第 242—249 行。

代码 / 执行顺序
    protected void onSaveInstanceState(Bundle outState) {
        try {
            super.onSaveInstanceState(outState);
        } catch (IllegalStateException ignore) {

        }
        outState.clear();
    }

代码先调用 super，然后执行 outState.clear()。这会清空当时 Bundle 中已写入的条目，包括上层实现已保存的内容。不能再默认认为这个页面能完整沿用标准的 View / Fragment 状态恢复。LauncherActivity 第 307—310 行也有同类处理。源码本身不能证明这样做的历史原因。

onSaveInstanceState 用于系统随后可能重建页面时保存小量临时状态，例如条目 ID、筛选条件、滚动位置。它不是每次退出都保证调用的持久化接口：用户明确 finish 时通常不需要保存供重建的数据；进程突然终止也不能指望临终再执行它。

Android 9+ 且 target 为 P+ 时，保存回调位于 onStop 之后；老版本的顺序有差异。因此不要依赖“必定在 onPause 与 onStop 之间”。恢复通常在 onCreate(savedInstanceState) 中读取，也可在 onRestoreInstanceState 中处理；后者在有恢复状态时、onStart 之后调用。

工程上的判断：先查清 outState.clear 的调用链和历史问题，再决定如何调整。这篇文档只分析现有行为，不修改业务源码。

04 · P1：Fragment 活着，为什么 View 已经没了？

Fragment 是负责逻辑和状态的对象，onCreateView 返回的 View 是另一批对象。FragmentManager 的返回栈可以保留 Fragment 实例，却销毁它的 View；返回时，同一个 Fragment 再创建新 View。具体是否销毁取决于事务和生命周期限制，不能把所有页面切换都看成这一种情况。

代码 / 执行顺序
Fragment：onAttach → onCreate → onCreateView → onViewCreated → onStart → onResume
View 被拆掉：onPause → onStop → onDestroyView
若 Fragment 仍保留：稍后 onCreateView → onViewCreated → onStart → onResume
Fragment 最终移除：onDestroy → onDetach

因此：与 Fragment 实例绑定的状态放在 Fragment / ViewModel；与本轮界面绑定的 binding、Adapter 引用、监听和渲染订阅，需要跟随 View 的销毁处理。ViewBinding 并不会自动把字段清空。

项目原码：yyyyy-cdoe/km_home_base/km_home_base/src/main/java/com/zhihu/android/feature/km_home_base/audio/CommonAudioPageFragment.kt，第 163—175 行。

代码 / 执行顺序
    override fun onPause() {
        super.onPause()
        kmViewModel.uploadLastRead()
    }

    override fun onDestroyView() {
        super.onDestroyView()
        layoutBinding.homeRecyclerView.removeOnScrollListener(scrollListener)
    }

    override fun onDestroy() {
        super.onDestroy()
        registerPrerenderOrNot(false)

项目把列表滚动监听的移除放在 onDestroyView，把另一个注册关系的取消放在 onDestroy，体现了不同资源的归属。仅凭这一段不能证明所有 View 引用都已释放；仍需检查 binding、Adapter、回调等字段是否继续引用旧界面。

常见泄漏链：返回栈 → Fragment → binding → 已离开界面的 View → Context。GC 会处理不可达的循环引用，但只要 Fragment 仍可达，这条链就可能保住整棵旧 View 树。

05 · P1：观察数据到底绑定 Activity、Fragment 还是 View？

项目原码：yyyyy-cdoe/VipCommon/vip_common/src/main/java/com/zhihu/android/vip_common/fragment/SubscriptDialogFragment.kt，第 64—67 行。

代码 / 执行顺序

            changeSubscriptStatus(subscript)
        }

这个观察者用 viewLifecycleOwner：旧 View 销毁时，LiveData 移除对应观察者；新 View 建好后再注册。LiveData 通常在 owner 达到 STARTED 时才向它交付更新。若改为 observe(this)，Fragment 的寿命可能覆盖多轮 View，旧的界面回调就可能留得过久。原文件在 onCreateView 中注册并返回非空 root；不要直接断言这种位置必然非法，教学代码通常放在 onViewCreated 更清楚。

写法停止可见后销毁后
LiveData.observe(viewLifecycleOwner)低于 STARTED 不交付界面更新View owner DESTROYED 后移除观察者
viewLifecycleOwner.lifecycleScope.launch普通协程不会只因 STOPPED 自动取消View owner 销毁时取消
repeatOnLifecycle(STARTED)低于 STARTED 取消内部块；重新进入则重启外层随 owner 销毁结束
viewModelScope不由某个 View 的 stop 控制ViewModel 被清除时取消

07 · P1：View 的 attach、布局、可见和销毁不是一回事

阶段 / API含义不要推导成
构造 / inflate创建对象、读取属性已经有最终宽高
onAttachedToWindow连接到窗口用户必然能看见或对象只会 attach 一次
onMeasure / onLayout / onDraw尺寸协商、放置、绘制一次生命周期只调用一次
onVisibilityChanged / onWindowVisibilityChanged自身/祖先可见性或窗口可见性变化像素未被遮挡、曝光比例满足业务条件
onDetachedFromWindow从窗口脱离对象一定死亡或以后不能复用

View 没有一个等价于 Activity.onDestroy 的通用回调。removeView 后可以重新 addView，列表条目也可能离屏后回来。attach 时开始的监听和动画，要在 detach 清理，并保证下一次 attach 可以重新创建。尺寸相关初始化可考虑 onSizeChanged；View.post 只是安排任务，不能笼统保证它代表“本轮布局已完成”。

08 · P1：可反复 attach / detach 的 View 示例

代码 / 执行顺序
class TickView(context: android.content.Context) : android.view.View(context) {
    private val handler = android.os.Handler(android.os.Looper.getMainLooper())
    private var attached = false
    private val tick = object : Runnable {
        override fun run() {
            if (!attached || windowVisibility != VISIBLE) return
            invalidate()
            handler.postDelayed(this, 1000L)
        }
    }

    private fun updateTick() {
        handler.removeCallbacks(tick) // 防止重复安排
        if (attached && windowVisibility == VISIBLE) handler.post(tick)
    }

    override fun onAttachedToWindow() {
        super.onAttachedToWindow()
        attached = true
        updateTick()
    }

    override fun onWindowVisibilityChanged(visibility: Int) {
        super.onWindowVisibilityChanged(visibility)
        updateTick()
    }

    override fun onDetachedFromWindow() {
        attached = false
        handler.removeCallbacks(tick)
        super.onDetachedFromWindow()
    }
}

示例只演示窗口可见期间的轻量定时刷新，主线程访问这些字段。detach 移除任务，下次 attach 可以再次启动。它没有实现列表曝光统计：祖先隐藏、屏幕外位置、遮挡比例还要另行判断。每秒 postDelayed 也不是精确计时器；播放进度等应根据真实时间或播放器状态计算。

09 · P2：给 View 实现 LifecycleOwner 就万事大吉了吗？

项目原码：yyyyy-cdoe/VipCommon/vip_common/src/main/java/com/zhihu/android/vip_common/view/lifecycle/LifecycleFrameLayout.kt，第 32—50 行。

代码 / 执行顺序
    override fun onAttachedToWindow() {
        super.onAttachedToWindow()
        mRegistry.currentState = Lifecycle.State.CREATED
    }

    override fun onDetachedFromWindow() {
        super.onDetachedFromWindow()
        mRegistry.currentState = Lifecycle.State.DESTROYED
    }

    override fun onWindowVisibilityChanged(visibility: Int) {
        super.onWindowVisibilityChanged(visibility)
        if (visibility == VISIBLE) {
            mRegistry.handleLifecycleEvent(Lifecycle.Event.ON_START)
            mRegistry.handleLifecycleEvent(Lifecycle.Event.ON_RESUME)
        } else if (visibility == GONE || visibility == INVISIBLE) {
            mRegistry.handleLifecycleEvent(Lifecycle.Event.ON_PAUSE)
            mRegistry.handleLifecycleEvent(Lifecycle.Event.ON_STOP)
        }

这是项目自定义的生命周期映射，不是 Android 自动给所有 View 提供的标准行为。本次在相关模块检索中找到类定义，未确认具体业务实例的接入。它把 attach 映射为 CREATED，把 detach 映射为 DESTROYED，把窗口可见映射为 START/RESUME。

要审视终态：同一个 LifecycleRegistry 在 DESTROYED 后不应作为可复活的生命周期继续使用；已经移除的观察者、取消的 scope 也不会因为 View 重新 attach 自动复活。不同 Lifecycle 版本还可能对非法迁移报错。若支持复用，需要设计每次附着的 owner，或在 detach 时只结束附着资源，并明确真正终止的时机。

还要检查回调先后顺序和初始状态：窗口可见回调不保证天然按你手写的状态机发生。若使用 ViewTreeLifecycleOwner，拿到的常是宿主 Activity / Fragment View 的 owner，其寿命也不等于每个列表条目的附着寿命。

RecyclerView 事件业务应该处理
onBindViewHolder重置旧数据相关样式、绑定新 item ID；取消旧图片/任务，防止串位
onViewAttachedToWindow恢复该条目附着期间需要的资源

SavedState 继承 BaseSavedState，另外保存 mRefreshing 并实现 Parcel 读写（同文件第 217—253 行）。恢复的是“正在刷新”的界面标记，并没有保存原来那条线程、协程或网络连接。恢复后应让真实数据状态决定转圈、重试还是显示结果，避免一直转圈。

View 层级自动恢复通常要求可保存的 View、有稳定且合适的 ID、父层级参与保存，以及 Activity 保存结果没有被破坏。动态创建 View 时，每次随便生成不同 ID 可能匹配不上旧状态。文本控件等已有自己的状态保存规则，自定义字段则需自行保存。

原码直接强转 SavedState，教学实现更稳妥的做法是先判断类型：若不是自定义 SavedState，就交给 super.onRestoreInstanceState(state)；如果是，先恢复 superState 再恢复自身字段。不要把 Activity、View、Bitmap 大对象或整份列表塞进 Bundle，IPC 事务大小有限，可能触发 TransactionTooLargeException。

14 · P1：进程死亡后，什么东西真的还在？

进程被系统回收后，堆内存、static、Kotlin object、Application 字段、ViewModel 和线程都没有了。系统可能仍持有任务记录和先前提交的 saved state，磁盘数据也可能还在。用户返回原任务时，系统启动新进程并新建组件，再把可用的保存状态交回来。

项目原码：yyyyy-cdoe/VipHome/home/src/main/java/com/zhihu/android/app/util/pagerecover/ActivitySavedStateRecorder.java，第 24—24 行。

代码 / 执行顺序
    public static PageDescription cachePageDescription = null;

这个工具类名里虽然有 SavedState，但 cachePageDescription 是 static 内存字段；第 35—42 行在 Fragment resumed 后 post 更新，第 53—56 行在 paused 时清空。它可以描述当前进程里的页面，不能单独作为进程死亡恢复机制。本次未定位到将这个 recorder 注册到 Application 的调用，不断言线上已启用。

Application.onCreate 是当前进程初始化入口，不是“用户每次打开页面”。多进程应用各有各的 Application 和单例；Android 不会在真机进程被杀前保证调用 Application.onTerminate。初始化应能在冷启动时独立完成，不依赖上一次进程的全局对象。

四大组件的入口也可能拉起进程，不一定先经过主 Activity。ContentProvider 通常在 Application.onCreate 之前初始化，所以全局配置放置位置和启动顺序需要核对。onTrimMemory 等是有条件的内存提示，也不能当必达的最后保存通知。

17 · P1：怎样验证旋转、View 重建和进程死亡？

先在测试设备与可恢复账号上操作。记录 PID、Activity/Fragment/View 的实例 identityHashCode、回调名称和恢复字段。只看“页面又出现了”无法分辨旧对象复用还是新建。

测试操作与预期验证目标
配置重建旋转或调用 recreate；记录实例变化Activity/View 变新，合适 scope 的 ViewModel 保留；控件状态正确
Fragment View 重建进入会销毁旧 View 并入返回栈的事务，再返回View owner 变新，旧监听没有重复回调
列表复用滚出、滚回、快速切换数据集不重复订阅，不串图片，点击仍有效
后台进程死亡Home 到后台，确认可杀后 am kill；PID 消失；从最近任务回到页面新 PID，新 ViewModel，依靠保存状态/持久数据恢复
正常结束与冷启动finish 或明确退出后重新打开不错误地恢复本该结束的临时会话

am kill 只杀可安全终止的后台进程；如果仍有前台服务等，可能没有杀掉，必须验证 PID。“不保留活动”主要验证 Activity 销毁，不等于进程死亡，单例可能还活着。force-stop、清数据和从最近任务划走各有不同语义，不能作为系统后台回收的完全等价实验。强停还会影响组件启动/任务调度；本篇没有对设备执行这些命令。

19 · 常见面试题与参考答案

P1 · 1. onPause 和 onStop 有什么区别？

onPause 表示离开 resumed 阶段，界面可能仍可见；onStop 表示 Activity 不再可见。资源应按是否需要可见/交互来选择停止时机，onPause 保持轻量。

P1 · 2. onDestroy 一定调用吗？

不保证。正常 finish 或配置重建通常调用；系统直接终止进程时没有逐一销毁回调的保证。重要数据应在产生变更时持久化。

P1 · 3. 旋转和进程死亡有什么区别？

默认旋转重建 Activity/View，进程通常还在，正确 scope 的 ViewModel 可以保留；进程死亡会让内存对象全部丢失。两者都可能走带 saved state 的新 onCreate，不能只靠 Bundle 是否非空区分。

P1 · 4. onSaveInstanceState 和持久化存储怎么选？

前者保存系统重建需要的小量临时 UI 信息，不保证所有退出场景；重要草稿、离线记录和跨任务数据需要数据库/文件等可靠写入。

P1 · 5. ViewModel 为什么能跨旋转？

因为 ViewModelStore 随逻辑 owner 在配置重建中保留，新 Activity 取得原 store 的 ViewModel。不是因为 ViewModel 是 static，也不意味着任意新页面都共享它。

P1 · 6. ViewModel 能跨进程死亡吗？

旧对象不能。新对象可通过 SavedStateHandle 和持久化层恢复所需信息；viewModelScope 中原任务不能复活，onCleared 也不是进程死亡必达通知。

P1 · 7. Fragment 的 onDestroyView 与 onDestroy 有什么区别？

前者结束本轮 View，后者结束 Fragment 实例。返回栈中的 Fragment 可跨多轮 View，所以 binding 和渲染订阅应按 View 生命周期清理。

P1 · 8. 为什么用 viewLifecycleOwner？

让旧界面观察者在该 View 销毁时结束，避免 Fragment 尚存导致观察者跨多轮 View。项目 SubscriptDialogFragment 就如此观察 LiveData。

P1 · 9. lifecycleScope.launch 在 onStop 会自动停吗？

普通 launch 不会，只会随对应 owner 销毁而取消。需要可见期间收集，使用 repeatOnLifecycle 等显式策略；它重启块的行为也要考虑。

P1 · 10. detach 是否表示 View 被销毁？

不是。View 可以再次 attach 或留在 RecyclerView 缓存。清理附着资源后，还要支持重新建立，不应默认把一次 detach 当永久结束。

P1 · 11. 项目 lazy Disposable 有什么风险？

RewardCenterProgressIconView detach 后 dispose 点击订阅，lazy 后续仍返回同一个已取消对象。同实例复用时需要重建订阅；源码显示风险，但不据此声称线上已复现。

P1 · 12. RecyclerView detach 和 recycle 一样吗？

不一样。detach 是离开窗口，可能暂存后直接回来；recycle 是结束当前绑定并准备复用。项目 RN 容器 recycle 仅日志，真正销毁 Fragment 的路径需继续追到宿主。

P1 · 13. 异步回包为什么会串到另一条列表数据？

ViewHolder 已绑定新 item，旧请求回调仍持有它。应取消或替换旧请求，并按稳定 item ID 校验归属，不能只用旧 position。

P2 · 14. 给 View 实现 LifecycleOwner 的难点？

要定义状态含义、回调顺序和永久终态；同一个 DESTROYED registry 不能当可重复使用的 owner。窗口可见也不等于业务曝光。

P1 · 15. 恢复刷新动画意味着恢复请求吗？

不意味着。View SavedState 只能恢复序列化字段；需要让 ViewModel/Repository 重新确认数据或安排任务，避免只有转圈没有请求。

P2 · 16. 自定义 View 状态保存要做什么？

继承合适 SavedState，保存/恢复 superState 与自身字段，正确 Parcel 化；确保稳定 ID、父层级和宿主参与保存，读取时做类型兼容。

P1 · 17. 项目 outState.clear 会怎样？

会清空该时刻 Bundle 里的条目，破坏默认恢复所需信息。不能再默认完整恢复，也不能在未查历史原因前贸然修改。

P1 · 18. Application 单例能否恢复页面？

仅能保存当前进程内存状态。进程死亡后 static、object 和 Application 都重新创建；多进程也不共享这份实例。

P1 · 19. Service 是后台线程吗？

不是，常规生命周期回调在进程主线程执行。耗时任务要自行调度；Service 的存活规则与线程执行位置是两个问题。

P2 · 20. START_STICKY 可以保证永远运行吗？

不能。它表达被终止后尝试重建的策略，可能收到 null intent，且受系统限制。前台服务同样不是永生进程。

P2 · 21. 广播里启动 Thread 然后返回安全吗？

不能靠它保证任务完成，回调结束后进程的重要性会变化。短时异步用 goAsync 并 finish，持久可重试任务交给合适调度系统。

P2 · 22. ContentProvider 一定晚于 Application.onCreate 吗？

通常更早：进程启动安装 Provider 时会初始化，随后才调用 Application.onCreate。Provider 不应依赖仅在该 onCreate 中完成的初始化。

P1 · 23. 如何真正测进程死亡恢复？

后台后 am kill 并确认 PID 消失，从最近任务返回，核对新 PID、恢复字段和请求。旋转或不保留活动不能覆盖单例丢失问题，force-stop 语义也不同。

P1 · 24. 面试中怎样串起一个项目案例？

可讲 RN 评论容器：bind 数据、attach 注册事件/添加 Fragment、detach 清订阅、recycle 只日志、Activity 销毁走 Fragment 移除。再说明 state-loss 事务和进程恢复仍要另审，个人贡献只说自己实际做过的部分。

源码静态分析和教学示例不等于完整工程构建或真机验证；涉及系统恢复、窗口与列表复用的行为，应按第 17 节在目标版本测试。
