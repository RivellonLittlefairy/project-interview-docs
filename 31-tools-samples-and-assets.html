1. Purrfolio：本地资产追踪与固定收益桌面应用

定位、技术栈与关键结构

  • 路径：yyyyy-cdoe/Purrfolio；WinUI 3 本地桌面 App，目标是资产总览、永久组合偏离、固定收益 XIRR、派息日历、复利预测和截图 OCR 导入。
  • 技术栈：C#、.NET 8、WinUI 3、CommunityToolkit.Mvvm、依赖注入、EF Core + SQLite、Win2D、xUnit；Purrfolio.sln 为构建入口。
  • 分层边界：
    • src/Purrfolio.App：Views、ViewModels、系统通知和 OCR 客户端；
    • src/Purrfolio.Core：领域模型、仓储接口和纯计算；
    • src/Purrfolio.Infrastructure：EF Core AppDbContext 与 SqliteInvestmentRepository；
    • tests/Purrfolio.Core.Tests：领域算法测试。
  • Purrfolio.App.csproj 启用 WinUI、Native AOT 和 trimming；App.xaml.cs 负责 DI、数据库路径、页面/ViewModel/服务注册和启动时建库。

核心链路与关键实现

资产首页链路

  1. AssetViewModel.LoadAsync() 通过 IInvestmentRepository.StreamInvestmentsAsync() 异步读取 SQLite；
  2. SqliteInvestmentRepository 使用 IDbContextFactory、AsNoTracking() 和 IAsyncEnumerable 流式返回记录；
  3. ViewModel 聚合市值后调用 PermanentPortfolioAnalyzer.Analyze()，按股票/黄金/国债/现金各 25% 目标计算偏离，超过 5% 预警；
  4. CompoundProjectionCalculator.ProjectToTarget() 用月化收益率迭代目标达成月份；
  5. 结果写入 ObservableCollection 和 observable properties，页面再绘制 donut、净值和文字状态。

固定收益链路

  1. FixedIncomeViewModel.LoadAsync() 筛选国债记录；
  2. BuildLotCashFlows() 生成买入负现金流、历史票息与当前/到期终值；
  3. XirrCalculator.Calculate() 先用 Newton-Raphson，导数过小、越界或不收敛时用二分法兜底；
  4. 结果按组合、单券、批次三个层级展示；
  5. CouponCalendarGenerator.GenerateUpcomingEvents() 生成未来派息和到期事件，WindowsNotificationService 推送前几条提醒。

OCR 导入链路

  1. OcrImportViewModel.AnalyzeAsync() 收集图片、endpoint、model 和 API key；
  2. MinimaxOcrService.AnalyzeScreenshotAsync() 把图片编码后提交给外部模型，要求返回 JSON；
  3. 服务兼容多种响应外壳，ParseCandidates() 归一化字段；
  4. ViewModel 先生成可编辑草稿，再逐条校验资产类型、日期、数量、价格、票息、频率和到期日；
  5. 用户复核勾选后才调用仓储写入 SQLite。

测试、工程化、亮点与风险

  • 2026-07-24 实测：dotnet test tests/Purrfolio.Core.Tests/Purrfolio.Core.Tests.csproj 通过 9/9。覆盖 XIRR 已知值/同号异常、永久组合偏离、复利边界、派息与到期事件。
  • 测试运行出现 NuGet 漏洞数据源不可达警告，但包还原、编译和测试成功；这不是测试失败，却说明离线/受限网络下漏洞审计不可用。
  • 亮点：纯领域计算与 UI/SQLite 解耦；XIRR 有迭代失败兜底；OCR 不是直接入库，而是“模型抽取—人工复核—字段校验—持久化”。
  • 风险与改进：
    • EnsureCreatedAsync() 适合原型，不适合长期 schema 演进，应改 EF migrations；
    • OCR 会把投资截图发送到第三方，必须增加脱敏说明、显式同意、域名白名单、超时/大小限制和可删除审计；
    • 外部接口失败时把原始响应拼进异常，可能把服务端敏感信息带到 UI/日志；
    • API key 来自环境变量或页面输入，但没有安全存储与日志脱敏策略；
    • 派息日期从交易日机械递推，不等同真实债券付息规则；应存下一付息日、起息日与日计数约定；
    • 首页“沪深 300 年化 8%、CPI 年化 2%”是离线示意线，不是真实基准数据，必须明确标注；
    • XIRR 对多根现金流只返回一个根，没有歧义检测；UI、仓储、OCR 和迁移缺少集成测试。

面试价值、边界与可复述回答

最适合讲的是“把金融领域规则做成可测试 core，再由 WinUI/SQLite/系统通知组合”。不要说“做了专业投顾系统”；它当前仍是本地资产工具，估值、行情、税费、真实付息规则和合规都没有完整覆盖。

追问

  • 问：为什么 Newton 后还要二分？
    答：Newton 收敛快，但依赖初值和导数；遇到导数接近零或越过 -1 边界会失败。二分慢一些，但在找到异号区间后更稳定。
  • 问：为什么仓储返回 IAsyncEnumerable？
    答：它让 UI 可以边读边聚合并支持取消，也避免把读取方式暴露给 Core；但小数据量下收益有限，仍要用性能数据证明是否值得。
  • 问：如果重做 OCR 会改什么？
    答：加入本地预处理、上传前脱敏与用户确认，限制 endpoint，API key 进入系统凭据库，原始响应不进用户错误信息，并为解析和批量事务补 contract tests。

2. mcp-financial-calculator：金融计算 MCP 服务

定位、技术栈与结构

  • 路径：yyyyy-cdoe/mcp-financial-calculator；Node.js ESM 的 stdio MCP server。
  • 技术栈：@modelcontextprotocol/sdk、Zod、Node 内置 test runner；package.json 提供 npm start 和 npm test。
  • src/index.js 创建 McpServer，读取包版本，调用 registerAllTools()，再连接 StdioServerTransport。
  • src/tools/ 把工具按 basic、cashflow、TVM、metrics 分组；src/schemas.js 统一输入边界；src/lib/finance.js 承载纯算法；src/lib/result.js 统一文本 JSON 响应。
  • 共注册 17 个工具：4 个基础算术、5 个现金流、5 个货币时间价值、3 个指标工具。

核心链路与算法

  1. MCP client 通过 stdio 发起 tool call；
  2. SDK 根据工具注册信息和 Zod schema 校验输入，例如 rate 必须大于 -1、日期必须是严格 YYYY-MM-DD、现金流至少两项；
  3. handler 调用 calcXirr()、calcRate() 等纯函数；
  4. IRR/XIRR/RATE 先执行 Newton 迭代；失败后从接近 -1 的有限下界向正区间扩张，再做二分；
  5. handler 用 numberResult() 或 jsonResult() 返回 JSON 字符串；IRR 类同时提供小数和百分比。

金融约定需要主动说明：

  • XNPV/XIRR 使用 Actual/365；
  • 正数代表流入，负数代表流出；
  • TVM 使用 Excel 风格的正负号约定；
  • payback period 在跨零的期间内做线性插值；
  • 数值结果允许浮点误差。

测试、工程化、亮点与风险

  • 2026-07-24 实测 npm test：21/21 通过，总耗时约 0.19 秒。
  • 测试覆盖已知 NPV/MIRR/CAGR、PV/FV 互逆、IRR/XIRR 残差、RATE 方程残差、无根报错、严格日期和 schema 边界。
  • 亮点：协议层、schema、工具注册与纯算法分离；无数据库和网络副作用，适合作为确定性工具；测试不只比常量，还验证“求出的 rate 代回方程后残差接近零”。
  • 风险与改进：
    • 非常规现金流可能存在多个 IRR；当前返回一个根，没有扫描和歧义提示；
    • day-count convention 只有 Actual/365，没有 30/360、Actual/Actual 等选项；
    • 只有算法/schema 测试，没有真正走 MCP transport 的注册、调用、错误响应 contract test；
    • 所有能力集中在单个 finance.js，继续扩展后应按 cashflow/TVM/metrics 拆分；
    • stdio 本身缩小了网络攻击面，但 host 进程仍需限制可执行路径、依赖来源和日志内容；
    • 财务结果没有精度/舍入策略与“非投资建议”语义，不能直接当生产金融决策系统。

面试价值、边界与可复述回答

30 秒条件式模板（需本人确认）

若本人确认项目归属，并能提供对应 commit/PR 或演示，可回答：“该服务基于 Node.js MCP SDK，包含 17 个工具，并把协议注册、Zod 输入校验和纯算法分层。本人实际负责【需填写的模块与边界】。IRR、XIRR 和 RATE 使用 Newton 加二分兜底，测试还会把结果代回 NPV 方程检查残差。2026-07-24 本地核验的 21 个测试全部通过；该数字来自 npm test，仅代表当前 checkout。项目效果为【真实指标；统计时间；计算口径；数据来源】，若无法补齐则回答‘暂无可核验量化结果’。后续计划是 MCP contract test、多 IRR 检测和日计数约定。”

追问

  • 问：为什么不用普通 REST？
    答：场景是给 Agent/LLM 作为本地确定性工具，MCP 已定义工具发现、schema 和调用协议；stdio 又不需要额外开放端口。若跨机器、多租户或需要审计，再考虑 HTTP transport 和鉴权。
  • 问：为什么 schema 校验不够，还要算法内校验？
    答：schema 只保证类型和基础范围；“现金流必须同时有正负值”“方程必须存在可括区间”属于领域与数值约束，必须由算法层守住。
  • 问：怎么处理多 IRR？
    答：对更宽利率范围分段扫描符号变化，输出所有候选根或明确提示歧义，并推荐 MIRR；不能悄悄返回一个看似精确的值。

3. meter：工资实时计量 Android 原型

定位、技术栈与关键文件

  • 路径：yyyyy-cdoe/meter；单 app 模块、Kotlin + XML/ViewBinding，包名仍为 com.example.meter，更像个人原型而非正式产品。
  • 技术栈：AGP 8.7.2、Kotlin 2.0、Java 17、Retrofit/Gson、Coroutines、EncryptedSharedPreferences、App Widget、Notification、Canvas 自绘；minSdk 32。
  • MainActivity 同时负责表单、权限、动画、趋势图、保存、通知和 widget 刷新；
  • EarningsCalculator 是纯计算；
  • HolidayRepository 管 API、24 小时 SharedPreferences 缓存和工作日 fallback；
  • EarningsWidgetProvider 管 RemoteViews 与定时更新；
  • EarningsTrendView 自绘日/月累计曲线。

核心链路

  1. 用户录入月薪、上下班和午休时间；
  2. EarningsPreferences.saveSettings() 加密保存；
  3. HolidayRepository 优先读缓存，未命中时同步路径先按周一至周五 fallback，异步预取再请求节假日服务；
  4. EarningsCalculator.calculateTodayEarnings() 用月薪/本月工作日/每日有效分钟计算当前累计收入；
  5. Activity、notification 和 widget 各自读取配置与工作日并重复计算；
  6. EarningsTrendView 根据日内时间或当月工作日绘制曲线。

测试、工程化、亮点与风险

  • 本仓只有 Android Studio 默认的 2 + 2 = 4 单测与包名仪器测试，没有覆盖 EarningsCalculator、节假日缓存、widget 或通知。
  • 2026-07-24 尝试运行 gradlew testDebugUnitTest --offline，wrapper 仍下载 Gradle 8.9，60 秒后超时，没有进入测试执行；未继续做长时间构建。
  • 亮点：一个小 App 串起了加密偏好、网络缓存、通知、widget、自绘 View 和纯计算，产品闭环清楚。
  • 高优先级风险：
    • MainActivity 和 EarningsPreferences 把工资及作息写入 debug 日志；加密存储不能抵消日志泄露；
    • EarningsWidgetProvider 使用 GlobalScope，生命周期、异常和取消不可控；
    • 试图用 AlarmManager.setInexactRepeating() 每 10 秒刷新，既不精确也不符合移动端电量策略；系统通常会强制拉长；
    • receiver exported=true 且接收自定义 action，没有权限保护，外部应用可触发刷新；
    • 声明了开机权限却没有清晰的开机恢复 receiver 链路；

10. 8J52SRPW6X_Matchfile：签名同步仓首先是安全治理问题

  • 这是 Ruby/Fastlane Match 配置仓，不是 Android 业务仓；README 的两条主命令分别以 --readonly 同步 development 与 appstore 签名材料。

当前风险与整改顺序

  • 仓内存在 API-key 结构的 JSON 凭据文件，Matchfile 又直接引用它；无论该值是否仍有效，都应按泄露处理。
  • README 强调“无需验证码直接执行”不是安全优势，而是非交互凭据已具备访问能力，更需要最小权限、审计和轮换。

  • Fastlane 版本较旧，需要在隔离分支验证升级，并检查 Ruby/Bundler 与 Apple API 兼容性。
  • 测试/工程化方面只有 CI job 和人工同步命令，未检出安全回归或 dry-run 测试；应增加受控测试 App、证书到期预警、权限审计和不暴露 secret 的 pipeline smoke test。

整改优先级：

  1. 立即吊销/轮换仓内凭据，检查 CI、Apple 后台和签名仓访问日志；
  2. 从 Git 历史清除敏感文件，并启用 secret scanning/pre-receive 阻断；
  3. 凭据迁入受保护 CI secret 或专用 secret manager，只给所需 App/只读权限；
  4. runner 使用临时 keychain、限制 protected branch/tag、禁用 fork pipeline 读取 secret；
  5. 证书/profile 到期、撤销和人员离职形成台账与演练；
