01 · 阅读顺序：先懂请求，再读封装

Android 网络面试通常会从“HTTPS 请求怎么发出去”问起，再追到 OkHttp、Retrofit、线程、缓存和异常处理。会用接口不难，难的是说清楚：请求慢在哪里、失败后该不该重试、页面退出后谁取消请求，以及封装替业务处理了什么。

本文分成两部分。第 2 至 13 节讲网络基础，第 14 节开始读 Net 和 VipNet 的代码。第一次先看 P1；HTTP/2、QUIC、SSE 和实现细节标为 P2/P3，可以第二轮再看。最后有排障顺序和面试问答，不用一次背完整篇。

第一部分 · 面试常问的网络基础

02 · P1：点一下按钮，一次 HTTPS 请求经历什么？

假设用户在详情页点“订阅”。业务知道的是作者 ID 和接口方法，网络层要把这些信息变成能发送的数据，再把服务端响应变回 Kotlin/Java 对象。先沿着一次没有命中缓存、也没有现成连接可用的普通 HTTPS 请求走一遍。

真实请求不一定每次走全套。DNS 可能命中缓存，连接池可能有可复用连接，HTTP 缓存也可能直接返回内容。因此，看不到本次 DNS 或 TLS 事件，不一定是埋点漏了。排查耗时要先判断走了哪条路径。

URL 中，scheme 指协议，host 指主机名，port 指端口，path 和 query 指服务资源与参数。URL 的 fragment（# 后面的部分）通常由客户端处理，不会作为 HTTP 请求目标发给服务器。HTTP 是应用层协议；TCP/UDP 负责传输；TLS 为通信提供加密、完整性保护和身份验证。

03 · P1：DNS、HTTPDNS 和“有网却请求失败”

DNS 解决“这个域名对应哪些 IP”。它可能返回多个 IPv4/IPv6 地址，客户端按策略尝试连接。解析成功只说明拿到了地址，不代表 TCP 能连上，更不代表 HTTPS 证书有效或接口业务可用。

方式 / 现象怎么理解Android 开发要关注什么
系统 DNS通常交给系统配置的解析链路缓存、网络切换、解析超时、运营商环境，以及 IPv4/IPv6 可达性
HTTPDNS通过 HTTP/HTTPS 向特定解析服务查询地址接入方式、TTL、回退策略；厂商 HTTPDNS 不一定就是标准 DoH
DoHDNS over HTTPS，有标准协议定义解析通信受 HTTPS 保护，但仍要处理解析服务本身的可用性
连上 Wi-Fi 但接口失败Wi-Fi 连接只是本地链路状态可能有认证页、DNS 失败、出口被阻断或服务端故障
UnknownHostException没有成功获得可用的主机解析结果检查域名、解析事件、网络切换与 DNS 回退，不能直接归为“服务器挂了”

DNS 缓存会受 TTL 和实现策略影响。网络从 Wi-Fi 切到移动网络后，旧地址或旧连接可能不再合适；清缓存也不是所有问题的通用修复。项目如何选择自定义 DNS、未初始化时怎么回退，后面会读 DnsWrapper。

如果自定义 DNS 返回 IP，通常仍应保留原 URL 域名，让 HTTP Host、TLS SNI 和证书主机名校验按正确的域名工作。把 URL 直接改成 IP、只手动补一个 Host 头，往往不足以保证 TLS 能正确校验。

04 · P1：TCP 为什么要握手、确认和重传？

TCP 为应用提供可靠、有序的字节流。它通过序号、确认和重传处理丢包、乱序等问题，但“对端 TCP 已收到字节”不等于“服务端已经完成了订阅、支付等业务”。这两个层次的成功，要分别判断。

TCP 三次握手（简化，不含 TCP Fast Open 等扩展）
客户端                         服务端
  SYN，seq = x  ───────────────→
                 ←───────────  SYN + ACK，seq = y，ack = x + 1
  ACK，ack = y + 1 ────────────→
  双方建立连接，随后传输应用数据

握手让双方交换初始序号，并确认双方都具备发送、接收能力。第三次确认也有助于避免服务端把过期的连接请求直接当成可用连接。面试别只背“三次保证可靠”，要说明确认的是什么。

机制解决什么容易答错的点
序号与 ACK知道哪些字节已经收到、哪些还需要补发ACK 不表示业务事务成功
重传数据或确认丢失后再次发送重传会增加延迟，TCP 也不保证永远能送达
流量控制接收方用窗口告诉发送方还能接多少关注接收方能力
拥塞控制根据网络拥塞情况控制发送速度关注网络承载能力；不是同一个窗口问题
字节流应用读到连续字节一次 write 不保证对应一次 read，需要应用层分帧

“粘包、半包”通常是在说字节流没有保留业务消息边界。HTTP/1.1 用消息格式、Content-Length、chunked 等规则识别消息体结束；HTTP/2 用帧；业务不应自己按一次 socket read 就解析一个 JSON。

TCP 关闭两个方向的数据流通常需要 FIN 和 ACK，常说“四次挥手”，但实际报文可能合并。主动关闭方通常经历 TIME_WAIT，让迟到的旧报文有时间消失，也能在必要时再次确认对方重发的 FIN。不要把关闭过程、Keep-Alive 和业务退出页面混成一个概念。

05 · P1：HTTPS 到底保护了什么？

HTTPS 是在安全传输之上使用 HTTP。常见 TLS 握手会协商协议参数，验证证书与主机名，完成密钥协商，再用对称加密保护后续通信。不同 TLS 版本、恢复会话与是否已有连接，会影响具体消息和耗时。

要点面试时怎么讲
证书校验校验证书链、有效期、信任关系和目标主机名；证书可信不代表所有业务返回都可信
非对称与对称密码握手中的认证、密钥协商会使用非对称密码机制；大量应用数据通常用对称加密
TLS 1.3完整握手通常需要 1 RTT；TCP 建连等耗时要另算。恢复会话也不等于每次都能零等待
0-RTT某些恢复场景允许提前发送数据，但存在重放风险，不能直接用于不能重复执行的写操作
抓包HTTPS 正常情况下不会给中间人明文；调试代理需要客户端信任相应证书，并受证书固定等策略影响

TLS 1.3 不能简单讲成“客户端生成一个 AES 密钥，用服务器公钥加密发过去”。这不符合现代握手的通用流程。理解到“验证对方身份、协商密钥、保护数据”后，再按指定 TLS 版本展开。

遇到证书错误，应检查证书链、域名、设备时间和代理环境。把 TrustManager 改成全部信任、关闭主机名校验，会失去重要安全保障，不能当作正常修复。项目里的签名、请求体加密属于额外业务协议，它们不会自动替代 HTTPS。

06 · P1：HTTP 方法、状态码、请求头与业务结果

HTTP 请求由方法、目标地址、请求头和可选请求体组成。Retrofit 注解只是让你用接口声明这些内容，最终仍要落成 HTTP。

项目中会遇到的写法对应含义
@GET + @Query查询参数进入 URL；参数需编码，敏感内容不应因为放在 query 就被当作安全
@POST + @Body发送请求体；最终 JSON 等格式由 Converter 决定
@Path替换路径中的变量，和查询参数不同
@Header / @Headers设置 HTTP 请求头；需区分业务发送给服务端的头和客户端内部控制头
@Url动态指定 URL；要考虑地址来源、凭证是否误带到其他主机
Content-Type / Accept前者说明当前内容的类型，后者表达希望接收什么类型
Content-Encoding / Accept-Encoding前者说明采用何种压缩编码，后者说明客户端支持何种编码

GET 按语义用于读取，POST 常用于提交或创建，PUT/DELETE 按协议语义通常具有幂等性。幂等的意思是重复执行同一个操作，期望对服务器状态产生相同效果，不要求每次状态码或响应内容完全相同。具体服务端如果没有遵守语义，客户端不能只凭方法名放心重试。

状态常见含义客户端要做什么
200 / 201 / 204成功、创建成功、成功但没有响应体204 不能强求返回一个非空 JSON 对象
301 / 302 / 307 / 308重定向；不同状态对保留方法/请求体的规则不同关注新地址、凭证与签名；不是普通业务重试
304条件请求表明已有表示仍有效使用缓存内容；它不是完整新响应体
400 / 401 / 403 / 404请求问题、认证问题、拒绝访问、资源不存在分清用户提示、登录处理和参数问题
408 / 429请求超时、请求过多考虑是否可重试，并尊重 Retry-After 与退避
500 / 502 / 503 / 504服务端、网关或上游故障结合幂等性、次数和总时间决定重试

还要区分三层结果：网络有没有拿到响应；HTTP 是否成功；响应里的业务字段是否成功。例如 HTTP 200 返回了 isSuccess=false，网络和 HTTP 都成功了，订阅业务却没有成功。后面 SubscriptDialogViewModel 正好有这个判断。

07 · P2：HTTP/1.1、HTTP/2、HTTP/3 和连接复用

协议主要特点仍然要考虑的问题
HTTP/1.1支持持久连接，客户端通常通过多个连接并行请求同一连接上的响应顺序约束，以及连接数带来的成本
HTTP/2二进制帧、多个 stream 复用连接、HPACK 头部压缩TCP 丢包可能让同一连接上的多个 stream 都等待补包
HTTP/3使用 QUIC，运行在 UDP 之上，采用 QPACKUDP 可达性、握手/恢复策略、实现版本、回退和拥塞控制

HTTP/2 可以让多个请求的帧交错传输，减少 HTTP/1.1 层面的队头等待，但共享的 TCP 字节流仍要有序交付。HTTP/3 的 QUIC 把可靠传输组织到独立 stream，减少了丢包对无关 stream 的这种阻塞；连接仍然共享带宽和拥塞控制，不能理解成“某个流永远不会影响其他流”。

HTTP Keep-Alive 表示可以复用连接，TCP keepalive 是传输层探测空闲连接的机制，WebSocket ping/pong 或业务心跳又是另一层。保持连接可以省建连成本，但不保证 NAT、代理或服务器永远不关闭它。

OkHttpClient 通常应该复用，以复用连接池和调度资源。用现有 client.newBuilder() 派生 Client，和每次 new 一个全新 Client 含义不同；具体哪些资源共享，要查对应版本。项目对 Dispatcher 的共享是显式写出来的，后面可以直接用源码证明。

仓库里的 QUIC / H2 名称体现其策略分类，不足以证明当前请求实际协商成了标准 HTTP/3 或 HTTP/2。需要结合底层库版本、协议协商和运行指标确认。

08 · P1：HTTP 缓存、业务缓存和预请求有什么区别？

HTTP 缓存按协议决定响应能不能存、什么时候还算新、过期后如何验证。业务缓存可能直接保存解析后的列表、数据库记录。预请求则是提前发起一次可能马上用到的请求，它未必使用 HTTP 缓存。

机制 / 头行为容易混淆的点
Cache-Control: max-age在计算出的新鲜期内，可以直接使用符合条件的缓存不是客户端随便指定一个永久缓存时间
Cache-Control: no-cache使用前需要向服务器验证可以存；不等于完全禁止缓存
Cache-Control: no-store不应存储这次请求/响应的缓存内容和 no-cache 不同
ETag / If-None-Match拿之前的验证标识发条件请求304 表示可继续使用缓存内容，不是又下载了一份 body
Last-Modified / If-Modified-Since用修改时间验证精度与适用场景有所限制
Vary告诉缓存哪些请求头会影响响应表示只按 URL 存一份，可能返回错误语言或编码版本
业务缓存 / 预请求按业务条件复用数据或提前请求结果账号、地区、筛选参数等都可能影响是否还能复用

缓存命中仍有几种情况：直接使用新鲜缓存、发请求验证后复用旧内容、完全走网络。观察性能时要区分，否则把 304 当成“请求失败”，或把预请求当成“网络库自带缓存”，都会得出错误结论。

这两个仓库声明了 netcache 依赖，也有业务 Decorator 接口，但仅凭依赖不能说所有 API 都配置了标准磁盘 HTTP Cache。VipAppDecorator 的首页预请求有实际代码，后面单独分析。

09 · P1：Cookie、Token、签名和加密分别做什么？

名词解决的问题常见误区
Cookie服务端通过 Set-Cookie 提供状态，客户端按域、路径、Secure、过期等规则发送App 的 OkHttp CookieJar 不会天然和 WebView CookieManager 同步
Token业务授权凭据，常通过 Authorization 等约定携带Token 可能过期；有凭据不表示对所有资源都有权限
请求签名按约定证明特定请求内容未被篡改或来自持有凭据的一方防重放还需要时间、随机数、服务端校验等机制，不是加一个签名头就完成
请求体加密按业务协议变换请求体内容Base64 只是编码；不能当成加密
HTTPS保护传输过程，并认证通信对端不能替业务判断权限，也不能替本地日志自动脱敏

Token 过期后的刷新是常见追问：多个请求同时 401，不能各自无限刷新。一般要协调成一次刷新，其余请求等待结果；重试前再次确认凭据是否已经更新，失败则结束登录态处理。请求体是否能重新发送、重试次数和幂等性也要考虑。这是设计建议，本篇不会在没找到实现时说 Net 已经自动完成了这一套。

Cookie 或账号切换尤其容易出错：内存清掉了，磁盘里是否还有；旧请求回来会不会把旧账号数据写回；不同用户的缓存是否隔离。日志里完整打印 Cookie、Token 或请求体，也可能泄漏敏感信息。

10 · P1：超时、重试、取消与幂等

超时主要约束什么不能直接等同于
connectTimeout建立连接的等待限制，细节依传输实现整次请求最长耗时
readTimeout等待读取数据的超时限制，细节依协议/实现只要总耗时超过这个值就失败
writeTimeout写出数据时的等待限制服务器处理业务的时间
callTimeout / 总截止时间如果对应实现支持，可限制整次调用的总时间预算任意旧版本或定制库必然具有同样 API

一个请求可能依次排队、解析域名、建连、重定向、重试、读 body。只设几个局部超时，不代表总耗时就是其中最大值。业务最好另外想清楚：用户愿意等多久，超过这个时间展示什么，后台是否还允许继续。

重试前要回答：错误是否暂时、操作能否重复、请求体能否再发、已经试了几次、还剩多少时间。退避可以逐次增加间隔，并加随机抖动，避免大量客户端同一时刻再次压向服务器。不同层都重试时，次数还可能相乘。

最典型的危险是“请求超时，但服务器其实已经成功”。比如提交订阅、订单或支付，客户端没收到响应就重发，服务端可能执行两次。需要通过幂等键、业务流水号、状态查询等方式与服务端配合。TCP 可靠、HTTP 失败、业务是否成功，必须分开判断。

取消请求表示客户端不再继续这次工作，不能撤回服务器已执行的操作。Rx dispose、协程取消是否传到网络 Call，取决于适配器和调用方式；页面旧结果是否仍会更新 UI，也要检查回调和状态归属。

11 · P1：Retrofit、OkHttp、RxJava 各负责哪一段？

层负责什么不会自动包办什么
Retrofit解析接口注解和参数，构造调用；通过 Converter 和 CallAdapter 转换数据与返回类型不是自己实现 TCP/TLS 的网络栈
OkHttp执行 HTTP 调用，处理连接、拦截器、协议、缓存等业务成功判断、UI 生命周期不是它天然知道的
Converter对象与请求/响应数据之间转换，例如 Jackson 读写 JSON不会因为叫转换器就自动切主线程
CallAdapter把调用适配成 Call、Observable 等使用方式返回 Observable 不等于一定已发请求，也不等于回调在主线程
RxJava / 协程组合异步工作、调度、传递结果和取消不能让服务端已经执行的业务回滚
项目 Net 封装统一创建、公共策略、监控与业务扩展入口还要检查每个入口覆盖哪些返回类型、哪些 Client

Retrofit 的接口通常通过动态代理实现。调用接口方法时，框架根据方法注解和参数准备 HTTP 调用；第一次可能要解析方法元数据，之后复用缓存。Converter 处理“数据长什么样”，CallAdapter 处理“业务用什么方式拿结果”。项目还在 Retrofit 外面包了一层动态代理，不要把这两层当成同一层。

标准 OkHttp 的 execute 在调用线程同步执行，enqueue 交给异步调度，回调通常也不会自动来到主线程。项目使用了定制库，还增加了 callbackExecutor，实际回调线程需要继续往下看。普通 Android UI 更新仍要安排到主线程。

12 · P1：拦截器为什么按相反顺序处理响应？

拦截器拿到请求后，可以修改请求，再调用 chain.proceed 把它交给后面。proceed 返回时，后面的拦截器和网络处理已经把响应交回来了，这时当前拦截器还可以修改响应。

拦截器调用顺序示意，不是可直接运行的实现
请求：业务 → A 的前半段 → B 的前半段 → 网络
响应：业务 ← A 的后半段 ← B 的后半段 ← 网络

A.intercept:
  准备请求
  response = chain.proceed(request)  // 进入 B，等待它返回
  处理 response
  return response
拦截器适合放什么调用特点
应用拦截器公共参数、业务响应处理、统一日志、业务缓存等看到逻辑调用；可以直接返回响应，不一定真的访问网络
网络拦截器关注实际网络交换，例如网络层签名、网络细节统计缓存直接命中时不一定调用；重定向等可能带来多次网络交换

理解标准 OkHttp 时，可以先记这条常见链：应用拦截器 → 重试与重定向 → Bridge → Cache → Connect → 网络拦截器 → CallServer。请求出去时正向走，响应回来时逐层返回。类名和具体执行细节会随版本变化；项目的双网络栈和回调扩展，还得查自维护底层库，不能直接拿官方某一版代码当线上实况。

ResponseBody 是一次性流。拦截器里调用 string()/bytes() 读完后，下游不能再当作没读过；要么限制读取方式，要么重新构造 body。不要为了打印日志把大文件全部读进内存。一个应用拦截器如果再次 proceed，还应处理上一次响应体的关闭和重复请求风险。

13 · P2：轮询、SSE、WebSocket 怎么选？

方式通信特点适合 / 代价
轮询客户端隔一段时间问一次实现直观；请求频率、延迟、电量和流量要权衡
SSE服务端通过持续 HTTP 响应发送事件，常用 text/event-stream文本流、状态推送；要处理事件边界、心跳、断线重连与取消
WebSocket建立后支持双向消息通信需要双方频繁主动发送；仍要处理心跳、鉴权与重连
MQTT发布订阅协议，另有会话与 QoS 机制适合相应消息场景；不能仅凭“长连接”就与 SSE 等同

长连接不会免除生命周期管理。页面离开后，要明确连接属于页面、账号还是整个进程；登录切换、网络切换、退后台与进程死亡都要处理。SSE 的 Last-Event-ID 可以把最后见到的事件 ID 告诉服务端，但能否补发、如何去重，需要服务端配合。第 26 节会看 Net 中的 SSE 实现；VipNet 当前目录没有这套代码。

17 · P2：为什么项目还要在 Retrofit 外包一层代理？

项目原码：yyyyy-cdoe/VipNet/net/src/main/java/com/zhihu/android/net/common/NetProviderImpl.java，第 74 至 100 行。

NetProviderImpl.java
    public <T> T createService(@NonNull Class<T> service) {
        T serviceImpl = (T) SERVICE_MAP.get(service);
        if (serviceImpl == null) {
            serviceImpl = createWrapperService(sRetrofit, service);
            SERVICE_MAP.put(service, serviceImpl);
        }
        return serviceImpl;
    }

    @SuppressWarnings("unchecked")
    @VisibleForTesting
    private <T> T createWrapperService(Retrofit retrofit, Class<T> service) {
        return (T) Proxy.newProxyInstance(service.getClassLoader(), new Class<?>[]{service}, new InvocationHandler() {
            @Override
            public Object invoke(Object proxy, Method method, @Nullable Object[] args) throws Throwable {
                if (method.getReturnType() == Observable.class) {
                    // 如果方法返回值是 Observable 的话，则包一层再返回
                    return Observable
                            .defer(() -> {
                                final T service = getRetrofitService();
                                final Observable ob = ((Observable) getRetrofitMethod(service, method).invoke(service, args));
                                // 如果是 Async 模式的话，无需 subscribeOn
                                return sAsync ? ob : ob.subscribeOn(Schedulers.io());
                            })
                            .subscribeOn(Schedulers.io());
                }

SERVICE_MAP 用接口 Class 作 key，保存创建出来的 Service。缓存减少反复创建的成本，不过这里 get、创建、put 不是一个原子操作；并发首次调用时可能创建不止一个代理，不能把 ConcurrentHashMap 直接解释成“创建过程绝对只执行一次”。

外层 Proxy 在调用方法时检查返回值是否恰好是 Observable.class。符合条件才使用 Observable.defer：先返回一个可订阅对象，等订阅发生，再取得 Retrofit Service、反射调用对应方法。这样可以把实际 Service 创建和方法调用推迟到订阅阶段。getRetrofitService 内还有 volatile 与同步检查，实现自身的懒加载。

这个分支并没有自动覆盖 Flowable、Single、Call 或 suspend。它们怎么执行，要看其他适配器或入口。defer 也不等于共享一次请求；多个订阅通常可能分别触发请求，业务需要共享时还得设计共享和缓存策略。

包装层外面已经 subscribeOn(IO)。sAsync 为 false 时，内部 Observable 还会加 subscribeOn(IO)，使同步适配的调用避开主线程；sAsync 为 true 时用异步适配器。但最终网络回调和业务 UI 回调在哪里执行，还要继续看 Client 的 callbackExecutor 与 observeOn。

20 · P1：Client 是按什么顺序装起来的？

OkHttpFamilyProviderImpl.java
    private OkHttpClient.Builder inflateBuilder(Context context,
                                                       OkHttpClient.Builder builder,
                                                       ClientType type,
                                                       List<BuilderDecorator> decorators) {
        // 0. 首先添加统一的度量管理
        composeGlobalMetrics(builder);
        // 1. 添加 应用 interceptors
        composeAppInterceptors(type, builder);
        // 2. 处理 外部（业务） SPI 注册的 decorators
        composeDecorators(decorators, type, builder);
        // 3. 添加 网络库内部的应用 interceptors
        internalAppInterceptors(type, builder);
        // 4. 给特定的 client 使能 doh
        if (NetworkPrefs.isHttpDNSOn(context) &&
                (type == ClientType.API || type == ClientType.IMAGE || type == ClientType.WEB)) {
            builder.dns(initDns());
        }
        // 5. 添加网络 interceptors
        composeNetInterceptors(type, builder);
        // 6. 添加 quic 配置
        composeNetQuicConfig(type, builder);
        // 7. 支持动态配置 connectTimeout，readTimeout，writeTimeout，pingInterval
        composeNetBuildConfig(type, builder);
        // 8. 添加 dispatcher 监控功能
        getDispatcher().setDispatcherListener(DispatcherMonitor.getInstance());
        // 9. 检查 Interceptors，去掉同一个 client 下重复的 Interceptor
        checkInterceptors(builder, type);
        // 10. ClientType API 支持设置最大并发数
        if(type == ClientType.API) {
            getDispatcher().setMaxRequestsPerHost(NetOkHttpConfig.getMaxRequestsPerHost());
        }
        // 11. 添加统一 net 线程池 dispatcher
        return builder.dispatcher(getDispatcher());
    }

inflateBuilder 是这个仓库值得重点读的方法。它把零散能力集中装进 Builder：事件监控、应用拦截器、外部业务 Decorator、内部解压等处理、自定义 DNS、网络拦截器、QUIC 配置、超时和 Dispatcher。最后还会按拦截器的 Class 去重，保留先遇到的实例。

SimplifyRequestTransformer.java
    @Override
    public ObservableSource<T> apply(Observable<Response<T>> upstream) {
        if (mLifecycleTransformer != null) {
            upstream = upstream.compose(mLifecycleTransformer);
        }
        if (mSwitchThread) {
            upstream = upstream.subscribeOn(Schedulers.io()).observeOn(AndroidSchedulers.mainThread());
        }
        return upstream
                .flatMap(response -> {
                    if (response.isSuccessful()) {
                        T t = response.body();
                        if (t == null) {
                            return Observable.error(new IllegalArgumentException("解析出为 null"));
                        } else {
                            return Observable.just(t);
                        }
                    } else {
                        return Observable.error(new RetrofitAPIError(response));
                    }
                });
    }

按执行顺序读：传了 LifecycleTransformer 就 compose；mSwitchThread 为 true 就把订阅安排到 IO、结果切到主线程；随后判断 HTTP 是否成功，成功取 body，非成功生成 RetrofitAPIError。成功但 body 为 null，也会变成错误。

输入结果这个 Observable 分支会怎样
2xx + 非空 body把 Response<T> 拆成 T，业务成功回调收到对象
2xx + null body发送 IllegalArgumentException；204 等无 body 接口不能直接套用这种预期
非 2xx发送 RetrofitAPIError，把 Response 留在异常对象中
HTTP 200 + isSuccess=false仍会输出这个业务对象；内部业务字段要由业务继续判断
网络连接或 JSON 解析异常沿错误链传播；不等同所有错误都叫 HTTP 失败

默认 simplifyRequest() 没有 LifecycleTransformer，所以不会自动绑定页面生命周期。getScheduler 只负责线程；throwAPIError 只在 HTTP 不成功时抛错，仍保留 Response。不同工具做的事不同，别看到 compose 就认为已经把线程、取消、业务错误全部处理完了。

这个分支的 flatMap 位于 observeOn(main) 之后，因此拆 body 和成功判断发生在主线程；这不表示 JSON 是在这里才解析。后续如果继续在主线程做大列表转换，一样会卡。退出页面时还需要处理 Disposable 或使用正确的生命周期变换器。

29 · 常见面试题与参考答案

P1 · 1. 一次 HTTPS 请求从点击到显示，怎么讲？

先组织方法、地址、头和 body，经过请求调度；没有可用缓存/连接时，做 DNS、建连和 TLS；发送请求后接收响应，解压和解析，检查 HTTP 与业务结果，再切到合适线程更新 UI。复用和缓存会跳过部分步骤。

P1 · 2. TCP 可靠为什么还要业务幂等？

TCP 只保证连接中的字节传输语义，不能告诉客户端服务端业务是否已提交。服务端成功后响应丢了，客户端重试可能重复执行业务，需要幂等键或状态查询。

P1 · 3. TCP 粘包怎么解决？

TCP 是字节流，没有一次 write 对应一次 read 的保证。协议需要长度、分隔符或帧等规则；HTTP 已有自己的消息边界，业务不要把一次读取当作完整 JSON。

P1 · 4. HTTPS 用对称还是非对称加密？

握手认证和密钥协商涉及非对称密码机制，大量应用数据用对称加密保护。要按 TLS 版本讲细节，不能把 TLS 1.3 背成老式 RSA 密钥传输。

P2 · 5. HTTP/2 已经多路复用，为什么还会队头阻塞？

多个 stream 共享一条 TCP 字节流，丢失的字节未补齐时可能影响其他 stream 的交付。HTTP/3 的 QUIC 减少这类跨 stream 等待，但仍共享拥塞和带宽资源。

P1 · 6. no-cache 和 no-store 有什么区别？

no-cache 允许存，但使用前要验证；no-store 表示不应存。ETag 验证后收到 304 时，继续使用缓存中的内容。

P1 · 7. HTTP 200 就代表请求成功了吗？

代表 HTTP 层成功，还要检查业务结果。项目 simplifyRequest 拆出 SuccessResult 后，SubscriptDialogViewModel 继续判断 isSuccess。

P1 · 8. 网络超时该不该直接重试？

先分错误类型、幂等性和请求体能否重发，再限制次数与总时间，必要时退避。超时可能发生在服务端已完成操作之后，不能盲目重发写请求。

P1 · 9. Retrofit 和 OkHttp 的关系？

Retrofit 把接口声明适配成 HTTP 调用，通过 Converter 转换数据、CallAdapter 提供不同返回形式；OkHttp 执行 HTTP 与连接等工作。项目 Net 在它们上面统一策略。

P1 · 10. Net 为什么分 net-api 和 net？

业务依赖稳定入口和接口；实现、Client 组装与拦截器放在 net。Net 通过 InstanceProvider 找到 NetProviderImpl，而不是每个页面自己创建 Retrofit。

P2 · 11. Net.createService 返回的就直接是 Retrofit 代理吗？

这里先返回项目自己的 Proxy。Observable 方法通过 defer 延迟取得和调用 Retrofit Service，所以存在两层代理。返回类型检查只覆盖恰好是 Observable 的分支。

P2 · 12. ConcurrentHashMap 缓存 Service，就一定只创建一次吗？

不一定。这里先 get、再创建、再 put，多个线程可能同时 miss。Map 的单次操作安全，不等于这组连续操作是原子的。

P1 · 13. simplifyRequest 是不是自动取消请求？

无参调用没有传 LifecycleTransformer。它默认切线程、检查 HTTP、拆 body；取消要靠正确的生命周期参数或 Disposable 等管理。项目示例不能仅凭方法名认定已清理。

P1 · 14. simplifyRequest 对 204 会怎样？

其 Observable 分支要求成功 body 非空，null 会变成 IllegalArgumentException。因此无 body 接口要选择合适返回类型和处理方式，不能无条件套模板。

P1 · 15. subscribeOn 和 observeOn 在这里分别做什么？

前者安排订阅相关工作的线程，后者改变其后结果处理的线程。Net 的外层代理有 subscribeOn(IO)，simplifyRequest 默认再 observeOn(main)；定制 Client 还配置了网络响应 callbackExecutor。

P1 · 16. 多个 OkHttpFamily Client 的队列互相独立吗？

这里明确使用同一个 getDispatcher()。API 设置 maxRequestsPerHost 时改的也是共享调度器，不能简单说只有 API 受影响。是否共享连接池则还要结合 Client 的派生路径和底层实现。

P1 · 17. 应用拦截器和网络拦截器怎么选？

逻辑请求的公共处理、业务响应和自定义缓存通常放应用层；实际网络交换相关工作放网络层。缓存直接命中时，网络拦截器不一定执行；重定向可能带来多次执行。

P1 · 18. 为什么 Brotli 要在业务拦截器之后添加？

请求正向进入，响应反向返回。Brotli 加在后面，响应就先解压再到读取 body 的业务拦截器，避免业务先消费压缩流。

P1 · 19. 拦截器读了 body.string，后面还读得到吗？

ResponseBody 是一次性流，不能直接再读。项目账号处理和 VIP 预请求会重建 body；同时要防止为日志或缓存把大响应全部读进内存。

P1 · 20. BuilderDecorator 解决什么问题？

让账号、监控、VIP 业务按 Client 类型补配置，减少网络库对具体业务的依赖。但这里还要经过模块发现与白名单，写类并不等于生效。

P2 · 21. 自定义 DNS 失败就一定会自动回退吗？

DnsWrapper 只明确保证未设置 impl 时用 Dns.SYSTEM。impl 已设置后抛异常是否继续回退，要看 impl 的实现；不能把这个包装器讲成所有失败都自动回退。

P2 · 22. 仓库有 QUIC，能说请求都用了 HTTP/3 吗？

不能。还要满足 SO、DNS、开关、健康状态和采样策略，底层协议版本也要确认。运行时协商和监控才说明这次请求实际走了什么。

P2 · 23. Net 与 VipNet 的主要区别怎么回答？

当前快照普通请求 Provider 一致，依赖版本和部分实现不同；Net 额外有动态域名与 SSE 等代码。宿主构建条件还能选择另一版 net，最终包要查依赖解析。

P2 · 24. CookieJar 保存 Cookie 就一定写磁盘了吗？

不一定。这里 add 只改内存，持久化有单独方法和调用点。removeAll 也不能直接当作已清文件；还要核对对外 Store 和实际 Client 使用的实例。

P2 · 25. SSE 断开后怎么恢复？

重新建立流，按条件带 Last-Event-ID，服务端决定能否补发。客户端要处理去重、重试限制与取消。Net 还会取消已安排的重连，避免退出后继续连接。

P1 · 26. 首页预请求和 HTTP 缓存一样吗？

不一样。VipAppDecorator 保存一次提前请求的响应字节，再匹配业务请求复用；它还可能等待 CountDownLatch。标准 HTTP Cache 按缓存头、新鲜度和验证规则运行。

P1 · 27. 请求慢，先改超时和线程池吗？

先分解排队、DNS、连接、TLS、服务端等待、body 读取、解析和 UI 耗时。EventListener 和业务 trace 提供证据，确定瓶颈后再调参数。

P1 · 28. 怎么用项目讲一段完整网络封装经验？

从 VipFollowService 的注解和返回类型讲起，沿 Net 门面、Provider 代理、Retrofit、OkHttpFamily、Decorator、响应转换一路到 isSuccess 和 LiveData。说明自己实际参与的部分，再讲线程、取消与业务错误的限制。
